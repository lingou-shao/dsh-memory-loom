## 三、各场景覆盖什么

- **work**：两条并行会话分别推进一个代码调试任务和一张表格任务，对照「原记忆块每轮全量注入」与「索引 + 按需展开」的 token 账，并交叉验证两套检索路径谁能答上「怎么确认的」。
- **limit**：把对话推到整合阈值之上、单条 1.2 万字、40 条事实挤占，验证切段与驻留稳定；20 次 rebuild 结果逐字一致（防人格漂移的硬指标）。
- **merged**：索引层三个工具的全部分支，包括 `T` 拒绝挂载、同名折叠、promote、遗忘级联（search 返回 `#F2` → forget → expand 拒绝 → gc → 钩子消失）。
- **l0cap**：默认整条落库、显式上限截断带标记、脱敏先于截断、体积 1.14x。
- **diary**（v0.2.9）：日记导出到数据库旁的 `diary/` 目录（一天一个 md、按人分组、带时间、25 篇不丢一行）、`mirror=false` 不建目录、`memory_profile` 给出目录入口与真实总数；事件行尾的语气标注（偏冲 / 愉快 / 中性不标 / `toneHint:false` 全关）；老库多出 `weight`/`mood` 列时读写不受影响。
- **cost / probe-***：数字证据，详见 `docs/design.md` §11.4 与 §9.7。

## 九、v0.2.12：热加载漏挂了一半

真机时间戳先推翻了「装完要重启」：宿主主进程 19:58:15 启动，20:05:09 装插件，20:05:11 `loom.db` 就被建出来了——建库的是那个六分钟前启动的进程。DSH 是**即时重组**，不是「下次启动才装配」。

顺着这条往下查，发现 `apply()` 有一半内容在热加载时是哑的：

| 注入内容 | 注册方式 | 依赖 `agent/created` | 热加载时 |
| --- | --- | --- | --- |
| 记忆使用约定 / 索引约定 | 全局 `systemPrompt.section` | 否 | ✓ |
| 9 个 `memory_*` 工具 | `ctx.tools.register` | 否 | ✓ |
| 人设卡 | `agent.ctx.systemPrompt.section` | **是** | ✗ |
| 钩子索引块 | `agent.ctx.systemPrompt.context` | **是** | ✗ |
| 记忆块 | `agent.ctx.systemPrompt.context` | **是** | ✗ |

原因很直接：热加载时当前会话的 agent 早就创建好了，`agent/created` 不会再来一次。而装机时最容易确认的两样（工具、全局协议块）恰好都不依赖它，所以表面上「一切正常」。

`probe-hotload.mjs` 用 fake ctx 构造「agent 先存在、插件后 `apply`」的场景固定差异：

```
修复前  protocol ✓  index-protocol ✓  persona ✗  hooks ✗  memory ✗  工具 ✓
修复后  protocol ✓  index-protocol ✓  persona ✓  hooks ✓  memory ✓  工具 ✓
新会话（装完之后才创建）：修复前后都 ✓ —— 所以这个缺陷只影响「装之前就开着的那个会话」
```

修法三条，都只影响中途装载这条路径：

1. `apply()` 末尾遍历宿主 `agents` 服务的 `list()`，对每个 live agent 调 `attachAgent`（函数自带幂等保护）。
2. `turn-stopping` 里补一次 `attachAgent`，用于宿主不暴露 `agents` 服务的场合。
3. 新增 `ctx.effect("memory-loom:agents")`，卸载/重组时撤掉全部按会话的 section，避免反复重组叠同名块。

回归：selftest 30 项、work 18 / merged 24 / limit 17 / l0cap 15 / diary 17 全过，`probe-config` / `probe-ceiling` / `probe-recall` / `probe-audit`(×3) / `probe-hotload` 退出码全 0。正常启动路径行为未变。

## 十、v0.2.13：宿主不兜底 prompt 块，一条坏库会让每轮都失败

来自装了这个插件的 DSH 自己的代码审查：它指出 `recallFor()` 外面没有 try/catch，怀疑宿主不兜底。顺着查下去，结论比它说的更糟一点。

读本机 `D:/dsh/resources/app.asar` 里的实际实现（不是文档）：

- `dsh-system-prompt` 的 `assemble()` 与 `resolveContext()` 都是 `section.text(context)` 裸调用，整个模块没有 try/catch。
- `required: true` 只参与「运行期上下文被抑制时是否保留」的过滤，**不参与异常处理**。
- `dsh-agent-loop` 的 `preStep()` 直接 await `assemble()`；`turn()` 外层 catch 把异常折成 `turn/end: { reason: { kind: "error" } }` 再 rethrow；driver 的 `while (await this.turn())` 外面有 `catch (_error) {}`。

所以进程不倒，但**每一轮都失败**，直到库恢复。三块按会话的 prompt（persona / hooks / memory）都会抛，前两块此前没人注意。

`loom-e2e/probe-prompt-guard.mjs` 固定这条（关闭引擎 = 库不可用）：

```
修复前  persona ✗  hooks ✗  memory ✗   （3/3 抛错，exit 1）
修复后  persona ✓  hooks ✓  memory ✓   （3/3 返回空串，exit 0）
```

修法是 `guardPrompt(label, fn)`：失败返回 `""`，同一 label 60 秒内只告警一次。空块会被宿主过滤（`renderPrompt` / `renderContextSections` 都 `filter(text.length > 0)`），不会留下空标题。

回归：selftest 30 项、work 18 / merged 24 / limit 17 / l0cap 15 / diary 17 全过，`probe-hotload` / `probe-prompt-guard` / `probe-config` / `probe-ceiling` / `probe-recall` 退出码全 0。

## 十一、v0.2.14：让降级说话，并给模型一个自检入口

v0.2.13 的降级是安静的：库坏了，模型照样自信地回答，用户看不出区别。这一版补两条——一条给人（状态行），一条给模型（`memory_doctor`）。

**状态行**：三块 prompt 的失败计数进同一份 per-session 注册表；连续失败 3 次后，由 `memory` 块（唯一每轮必被求值、且最后求值的块）输出一句 `【记忆状态】…`，列出所有失败块、要求"如实说明、不要凭印象编造"，并指向 `memory_doctor`。任一 label 成功即清零。前两次失败保持静默，避免单次抖动刷屏。降级期间每轮多约 90 token，且追加在 `budgetTokens` 之外。

**memory_doctor（第 10 个工具）**：只读体检 8 项——库连接、库文件大小与 mtime、WAL、`journal_mode`/`synchronous`、`quick_check`、六张表行数、最近一次 `recall` 时间、prompt 三块连续失败。每项独立 try/catch；不用 `actorOf()`（它会读库）；时间格式化在 `timezoneOf()` 抛错时退回本机时区。报告分 ✓/✗/·，只有 ✗ 计入"发现 N 处问题"。

断库实测（把 `ctx.effect` 全撤，等效库被删/损坏）：

```
✗ 库连接  database is not open
✓ 库文件  280.0 KB · 修改于 2026/10/31 22:56:04
· WAL  不存在（没有未落盘的写入，或库被正常关闭）
✗ prompt 块  memory 连续 3 次（database is not open）
· 日记目录  …\diary

结论：发现 2 处问题。
下一步：库连不上：先确认没有第二个 DSH 实例占着它，再重启 DSH。不要删库；库本身也许是好的：把上面 prompt 块的错误原文发给维护者。
```

## 十三、v0.2.15：三个「以为有、其实没有」

对照一篇外部记忆架构文章（四层 / 四不变量）自查，再加上写探针时撞见的真缺陷。三处共同点是：文档写着有、代码在跑、产物是空的，而且不报错。

**1. 长期偏好根本召回不到（最严重）**

`compileMatch()` 把用户这句话的每个 CJK bigram 用空格连起来交给 FTS5，而空格在 FTS5 里是隐式 AND。实测：

```
偏好：我不吃香菜，点外卖一定要备注
"香菜"             → 命中
"我不吃香菜"       → 命中
"记得我不吃香菜吗" → 不命中（7 个 bigram 只中 4 个）
"今天天气不错"     → 不命中
```

不命中时 `subjective` 为空 → `blocks` 为空 → 记忆块返回空串。**那一轮模型看到的记忆是空的**，不是少一点。facts / events 有 `pinnedFacts()` 和 `recentFacts(8)` 兜底，偏好一条兜底都没有，所以只有它彻底消失。

修法：`recentPreferences()` + `retrieval.residentPreferences`（默认 3）让最近几条每轮常驻；偏好命中改用 `compileLooseMatch()`（OR 连接）。设 0 回到旧行为。

**2. 主观层的 cap 是块内配额，却拿去比全局 used**

`appendSection` 判断 `used + blockUsed + cost > cap`，`used` 全局累加；但主观层传的 cap 是 `target × 0.25`（=500）。事实区超过 500 token 后，印象和日记整块消失，配置里仍写着启用。

`probe-diary-budget.mjs` 实测（20 条长事实，`maxItems: 40`）：

```
修复前  印象 ✗  日记 ✗  偏好 ✓
修复后  印象 ✓  日记 ✓  偏好 ✓
```

偏好幸存是因为它走 `pushWhole(..., hard)`，用绝对上限。修法：cap 改传绝对位置，并给日记留 `diaryShare`（默认 0.4）保底。

**3. 快照靠用户自觉**

`loom.db` 单文件明文无副本，README 把备份写成用户责任。现在默认每 24 小时 `VACUUM INTO` 一份、保留 7 份、放在库同级 `backups/`，空库不拍。产物自包含，不需要另拷 `-wal`。同盘快照挡不住硬盘故障，文档写明异地备份仍是用户责任。

## 十四、v0.2.16：事件块认不出自己

问题不是「缺项目维度」，是「块认不出自己」。同一个人在两段对话里推进同一个项目，插件记成两块互不相干的事件；换个会话之后模型接不上。看起来像缺 `project_id`，实际缺的是块的可辨识与可枚举。

**1. 实测：四块里三块认不出**

本机真实库（`~/.dsh/memory/loom.db`，4 块 / 1 会话 / 4 条事实）：

```
财务·那么，装了这个插件，需不需要考虑上下文崩…     30 字 · 规则兜底
用户想让AI主动追问                                114 字 模型生成
技术·插件我更新了，你去更新一下                    13 字 规则兜底
技术·也就是说，已经撞上了？                        30 字 规则兜底
```

模型路径那一块标题摘要都能用；三块规则兜底是「领域·原句」，摘要就是原句。前缀在同一批块上完全一样，还带错——那段讲插件与上下文预算的对话被判成 `财务`。

**2. 标题取第一句，不取最长句**

第一版取「最长句」，`scenario-merged` 立刻抓到：搜「辞职」期望命中 E1，实际只中 `D1`。E1 第一句含「辞职」，最长句是「她问我在怕什么…」——标题换掉之后关键词从钩子上消失了。改为「第一个 ≥6 字、去掉语气词开头的句子」，语气词表 `那么/但是/不过/所以/然后/对了/其实/也就是说/嗯/啊/诶/哎/哦`，同时剥掉残留的 `用户：`。上限 24 → 32 字符。

模型路径：提示词「标题 ≤12 字」改成「≤16 字」，加一条要求带对象名（项目 / 工具 / 作品 / 人名 / 地点），空标题不再退化成领域名。

**3. 摘要兜底与清单去重**

摘要从「最长两句」改成「首句 + 最长句」。规则路径下标题就是摘要第一句，`标题 —— 摘要` 会说两遍同一句；清单渲染比较公共前缀，超过 12 字只印标题。

**4. 新增第 12 个工具 `memory_episodes`**

只列举不归并：按时间倒序列块（时间 / 类型 / `E` 编号 / 关联事实数 / 标题 / 摘要），支持 `query` 与 `days` 过滤，`limit` 默认 20。跨会话可见。归并留给模型——「这两块是不是同一个项目」是判断，插件做只会做错且无法解释。也不指望 `memory_search` 兼任：FTS 的 match 是二字组隐式 AND，「这个项目我都干过什么」没有关键词可用。

**探针**

新增 `probe-episodes`（18 项，全部通过）：空库不抛错、时间倒序、无领域前缀、两块各带自己的对象名（`loom` / `Blender`）、标题不被摘要重复、`query` 命中相关且排除无关、`days` 过滤、`limit`、跨会话合并、只读不改记忆块。`probe-hotload` 工具数断言改为 12，并加一条「`memory_episodes` 已注册」。

**回归**

selftest 30 项全过；`probe-*` 17 个脚本与 `scenario-*` 六个场景全部 exit 0。中途 `scenario-merged` 的「search 能命中冷区钩子」失败过一次，正是第 2 条描述的退化，改成取第一句后恢复。

**当时未覆盖（下一节补上了第一条）**

- 模型路径下标题是否真的带对象名：前面的探针都跑在规则模式（无 `llm`）上，只能固定提示词与兜底行为。
- 块粒度：当时只写了「可能偏碎」，没有实测。

## 十五、补验：模型路径与块粒度

发布前把 §14 留下的两条未覆盖补上。两条都不改插件代码，只补测试。

**1. 模型路径：假 llm 服务**

此前所有探针都不提供 `llm`，跑的是规则兜底。v0.2.16 改的却是模型提示词（标题 ≤16 字、要求写具体对象）——「提示词写好了」和「模型照做」之间隔着一整条调用链，一行都没被执行过。

`harness.mjs` 加了一个可选的 `llm` 参数（不传时行为与之前完全一致）和一个 `mockLlm(reply)` 工厂：它实现 `listProviders` / `listModels` / `stream` 三个成员，`stream` 推一个 text-delta 再推 `finish(stop)`，正是 `createLlmBridge` 消费的形状。假服务只在探针进程里存在。

`probe-model-title.mjs`（16 项，全部通过）：

| 断言 | 结果 |
| --- | --- |
| 模型路径被调用（不是静默退回规则） | ✓ 1 次抽取 + 1 次冲突判定 |
| 抽取提示词含「具体对象」 | ✓ |
| 抽取提示词含「≤16 字」 | ✓ |
| 模型给的标题被采用 | ✓ `星轨渲染器·glTF 材质丢失` |
| 标题不超 32 字 | ✓ |
| 模型给的摘要被采用 | ✓ 含「相对路径」，不是原句截断 |
| 模型给的事实落库 | ✓ `memory_search` 命中 `· fact ·` |
| 块可按对象名检索 | ✓ `query=星轨` 命中 |
| 记忆块里出现该标题 | ✓ 下一轮就能读到 |
| 空标题退化成句子标题 | ✓ `loom 的 memory_episodes 现在能按天过滤了…`，不是裸领域名 |
| 空标题的块仍可按原文检索 | ✓ |
| 非 JSON 回复退回规则 | ✓ 块仍在，标题含 `Blender` |
| 非 JSON 时对话不中断 | ✓ |
| 模型流抛错时对话不中断 | ✓ 记忆块照常渲染 |

| 模型流抛错时不写脏事实 | ✓ 假事实文本没落库 |

假服务不等于真模型：它能证明插件把请求发对了、把回包用对了、回包坏了会降级；不能证明真模型一定按提示词写标题。后者是提示词工程问题，只能在真机会话里回看。

**2. 块粒度：先分清是配置还是行为**

第一次测出来是「每轮一块」，6 轮 6 块。查下来不是 `drift`，是探针把 `consolidation.triggerTokens` 设成了 1：`completeTurn()` 的判定是 `tokenCount >= triggerTokens`，设 1 就是每轮整合一次，每次整合只看到 1 轮，自然一块一轮。默认是 20000。

按真实节奏重测（每轮约 17 token，`triggerTokens=80` 让五轮凑成一次整合）：

```
五轮同一项目连续推进（材质缓存）→ 3 块
  E1  我在给星轨渲染器加一个材质缓存…（前 3 轮）
  E2  缓存键用文件路径加修改时间应该够（第 4 轮）
  E3  先只缓存颜色贴图，法线贴图以后再说（第 5 轮）
单条消息里混三个话题（缓存 / 配色 / 下雨）→ 1 块
两条消息同一话题 → 各 1 块（同样是 triggerTokens 造成的）
```

结论：同一次整合里，前 3 轮被合并，第 4 轮「缓存键」和第 5 轮「只缓存颜色贴图」各成一块——段内 `drift`（`microTopicJaccard=0.3`）确实在切，切点停在「同一件事的不同侧面」。单条消息内部不切，混三个话题也是一块。

对这个需求（让 AI 或用户按块归拢项目）来说，碎不是缺陷：块越小，标题越具体，越容易认领。代价是清单更长、prompt 里「我们一起经历过」更早被同项目的碎片占满。本次不改阈值，理由是改大之后同一块会混进多个话题，标题又变回含糊——那正是 v0.2.16 要修的问题。真要调，`segmentation.microTopicJaccard` 是唯一的旋钮。

## 十六、v0.2.17：一半重合被 AND 判死

外部一份测评的结论是「没有一家打赢最朴素的 qwen 向量检索加重排」。这个结论在检索这一项上成立，但成因比「词法打不过语义」更具体、也更蠢：

`compileMatch` 把用户这句话切成中日韩二字组，空格连接后交给 FTS5——那是**隐式 AND**。「你还记得我不吃香菜这件事吗」切出 11 个二字组，记忆原文命中 4 个就够人读懂整句，但 FTS 要求 11 个全部出现，判定不命中，那条记忆整条消失，**不报错**。0.2.15 修过偏好层的同类问题（加常驻 + OR），事实与事件一直没动。

**改法：第二遍 OR，三个约束同时成立。**

| 约束 | 配置 | 默认 | 不做会怎样 |
| --- | --- | --- | --- |
| 只在严格命中太少时跑 | `relaxBelow` | 3 | 长句 OR 命中全库，事实区被噪声填满 |
| 放宽命中按分数打折 | `relaxPenalty` | 0.55 | 勉强沾边的记忆排到严格命中前面 |
| 共享太少就丢 | `relaxMinOverlap` | 0.25 | 一个高频二字组就能拖进整库 |

分数上保证不反超：两者共用 `normalize(raw, topRaw)`，严格命中最高 1.0，放宽命中最高 0.55。

`memory_search` 走的是 `Engine.searchFor()` 而不是 `recall()`，此前同样严格 AND——于是「用户问你还记得吗 → 模型主动去查 → 查回没有找到相关记忆」。现在两处共用一个收集器。

事件层更保守：`strictEvents === 0` 才放宽，且排在「最近 3 条」兜底之前。

**探针 `probe-recall-relax`（12 项，全部通过）**

其中三对是 A/B 对照，因为「放宽生效」与「本来就能通」在结果上长得一模一样：

| 对照 | 打开 | 关闭 |
| --- | --- | --- |
| 用自己的话问能否找回 | ✓ 命中 | ✓ 找不到 |
| 守卫调高到 0.9 | ✓ 找不到 | — |
| prompt 路径记忆块含该事实 | ✓ 出现 | ✓ 不出现 |

守卫的实测反例：

```
查询  你还记得我不吃香菜这件事吗    11 个二字组
保留  我不吃香菜，闻到味道就反胃    4/11 = 36%
丢弃  买菜时香菜便宜，不吃也行      2/11 = 18%
```

**一次假绿，值得记下来。** 记忆块那一对第一版是假通过的：记忆块对最近 8 条事实本来就有兜底，目标事实还在里面，开不开放宽都会出现；而整合又会从用户那句话里抽出新事实，永远排最前。改成「单独两个实例 + 关掉整合 + 先写九条填充把目标挤出最近 8 条」之后才是真对照。

**边界**：这不是向量召回。修的是「字面有一半重合但被 AND 判死」；字面完全不重合的近义表达（「香菜」对「芫荽」、换语言、口语改写）仍然找不到。零依赖离线这条没破。

## 十七、v0.2.18：别名救不回「零重合」，但能把它变成「有重合」

0.2.17 修的是「字面有一半重合、被 AND 判死」。剩下的是零重合：

```
存下  用户辞职后一直没跟家里说，怕父母担心
用户  我没敢告诉爸妈                     ← 0 个共同二字组
```

**改法：让模型在写的时候想词。** 整合时多要一个 `aliases` 字段（每条事实 2–3 个口语说法），混进已有的 `tokens` 列；查询端一个字不改。

这支探针要回答的不是「有没有改善」，而是三个更容易被搞错的问题：

1. 改善是别名带来的，还是放宽那一遍本来就有的？
2. 别名会不会让换了话题的对话把旧记忆拖进来？
3. 模型乱写别名时挡不挡得住？

**三臂对照，同一份语料**（6 条记忆 + 24 条干扰项把冷启动窗口挤出去）：

| 问法 | A 无别名 | B 别名+放宽 | C 别名+仅严格 |
| --- | --- | --- | --- |
| 别名原文（短问） | 1/6 | 6/6 | 6/6 |
| 换说法（别名覆盖） | 0/6 | 6/6 | 0/6 |
| 第四种说法（没覆盖） | 0/6 | 0/6 | 0/6 |

C 臂是这次测试里最值钱的一格：**只加别名、不改守卫 = 换说法 0/6**。别名单独存在时几乎不起作用，因为严格匹配要求这句话的每个二字组都出现，三个短别名盖不住一句人话；而放宽那一步的守卫看的是 `containment(query, text)`，纯别名命中在它眼里是 0% 重合，被丢掉。把守卫改成 `containment(query, text + aliases)` 之后，同一批题 6/6。

**换话题不渗漏。** 8 个无关问题（含两个刻意带泛词的：「最近有点累，想休息几天」「这个项目什么时候能结束」）在三条臂下都是 0 条旧记忆漏进块里，块大小一致。块里那 8 条是 `recentFacts(8)` 冷启动兜底——没有命中时塞最近 8 条事实，与话题无关。这件事在 0.2.18 之前就是这样，不是别名引入的。

**脏别名要挡。** 模型被要求给说法时，会混进泛词（「工作」）和整句。`cleanAliases` 只收 2–3 个、单个 ≤6 汉字、不在泛词表、不是纯数字、不含密钥、不重复。端到端验证：带 `['工作','这是一句明显超过六个字的长句子','香菜','香菜']` 写入后，`memory_search('工作…')` 不命中、`memory_search('香菜')` 命中。

**一次差点假绿，记下来。** `probe-alias-prompt` 第一次全绿，但提示词里其实没有 `aliases`——假 `llm` 不看提示词，照样返回别名，数据是绿的、链路是断的。根因是 `toEngineConfig()` 这份显式字段白名单漏了 `aliasCount`，传到引擎是 `undefined`，函数默认参数补 0，提示词悄悄回到旧版。现在两侧都钉住：断言提示词里出现 `aliases`，再断言 `aliasCount: 0` 时提示词干净**且**别名不生效。

**天花板没有变。** 没人教过的第四种说法 6 条全漏（0/6）。别名把「零重合」变成「有重合」，不是语义检索；老库也不会自动回填，`memory_doctor` 会报 `检索别名 N/M 条带别名`。

## 十九、v0.2.20：时间是一个区间，改时间是一次提问

### 19.1 解析放在固定日历上测（`probe-due` 第 1–2 组）

时间解析不能靠「现在」来测，否则结论每天都不一样。探针把基准钉在 **2026-11-02 周一 10:00（Asia/Shanghai）**——这一天恰好是「下周一」最容易算错的日子（在周一问下周一，是七天以后，不是今天）。

| 说法 | 存成 | 精度 |
|---|---|---|
| 下周一 / 下周三 | 11-09 / 11-11 单日 | `day` |
| 下周 | 11-09~11-15 | `week` |
| 这周 | 11-02~11-08 | `week` |
| 11月9日 / 2026-11-09 / 十二月二十号 | 单日 | `day` |
| 明天 / 三天后 | 11-03 / 11-05 | `day` |
| 三天内 | 11-02~11-05 | `fuzzy` |
| 过几天 | 11-04~11-12 | `fuzzy` |
| 下个月 / 月底 | 12-01~12-31 / 11-02~11-30 | `month` |
| 过段时间 / 以后 / 改天 / 早晚 | **不记** | — |

「十二月二十号」这条是后来补的：第一版只认阿拉伯数字，而中文把日期说出来时用的是「十二月二十号」，模型原样照抄就解析不了。

### 19.2 写进库里的形状（第 3 组）

```
- [11-09~11-15 · 截止] 用户打算下周去换个热水器
- [约 11-04~11-12 · 截止] 用户打算过几天把简历改完
```

断言三件事：「下周」是区间不带「约」；「过几天」带「约」；后者没有被压成单日。

### 19.3 改时间先问（第 4–5 组）

| 断言 | 结果 |
|---|---|
| 第二次说「下周一」→ 块里出现「时间待确认」 | 通过 |
| 待确认行写出原记录，并带 `memory_settle(id=…)` | 通过 |
| 新时间落在旧范围里 → 措辞是「说细到」 | 通过 |
| 原区间在被问期间仍然是原区间（没被静默改掉） | 通过 |
| `accept: true` → 区间收窄成单日，待确认消失 | 通过 |
| 新时间在旧范围之外 → 措辞是「改到」 | 通过 |
| `accept: false` → 保留原时间，**下次不再问** | 通过 |

最后一条是这次唯一想错过的设计点。第一版把 `accept=false` 写成 no-op，结果同一个问题每轮都会再问一次——那不是在问，是在磨。

### 19.4 原来没期限、后来给了（第 6 组）

`reconcileDue` 有四种结果，只有一种不需要问：库里本来没有期限，这次给了。那不算覆盖，算补充，直接落。探针把这条也钉住了，顺带验证 `memory_settle` 在没有待确认时明说「没有待确认的时间」，而不是假装成功。

### 19.5 一个真 bug：日期被算了两次，用的还是两个时区

加入区间之后，单日渲染成了两天（`[11-09~11-10]`）。查下去发现两个时间路径：

- 写入：`parseDue(text, now, this.config.timezone)`，而 `config.timezone` 默认是 `""` → 回落 UTC
- 渲染：`renderMemoryBlock(result, config, this.timezoneOf(sessionId))`，而会话已经有本机时区 → 上海

过去 `expires_at` 只显示一个日期，8 小时偏移吞在「日界」里看不出来；区间一来，起止分别落在两天，错误立刻可见。

修法是让两条路走同一个函数：`timezoneOf()` 在会话没有记录时回落到部署时区，写入侧也改用 `timezoneOf(sessionId)`。这个 bug 从有 `expires_at` 那天就在，只是没有任何断言看得见它——记在这里，是因为「加了一个新维度，旧的不一致才现形」这种情况会反复发生。

### 19.6 没做的

- **「又说一遍」不等于「确认」。** 用户把新时间再说一遍时，走的是整合路径，会再生成一次同样的待确认，而不是自动落实。文本上区分不了「重申」和「确认」，猜错的代价是记错日期，所以宁可在待确认上停一轮。
- **`tonight` / 「今晚八点」只精确到天。** 区间是以天为单位的，带钟点的说法取当天。
- **跨时区旅行不切日界。** 会话时区记录在建立时，人在别的时区继续聊，日期仍按原时区算。要修得先有「当前时区」这个信号，宿主没给。
- **计划没有「已完成」。** 一个显式的 `done_at` 需要一次新的工具设计，留到下一版。

## 二十、v0.2.21：认成了另一个日子，比不认贵得多

### 20.1 先量，再改（第 1 组扩到 32 种说法）

基准仍然是 **2026-11-02 周一 10:00（Asia/Shanghai）**。把用户随口会说的说法一次性钉上去，先看现状：

| 说法 | 改前 | 改后 |
|---|---|---|
| `下下周五交初稿` | 11-13（**早一周**） | 11-20 |
| `下下周开评审会` | 11-09~11-15（下一周） | 11-16~11-22 |
| `下个月五号交房租` | 12-01~12-31（**整月**） | 12-05 |
| `下个月5号` | 12-01~12-31 | 12-05 |

「早一周」和「塌成整月」是这一版真正的原因：两者都不是漏，是**答了一个别的**。漏掉的东西在块里是「未定期限」，人一眼能看出来要补；错的日子和正确的一模一样地通顺。

### 20.2 过去的日子：断言「不记」，而不是「记成过去的期限」（第 2b 组）

| 句子 | 结果 |
|---|---|
| `昨天我把车卖了` | 不记 |
| `前天聊的那个事` | 不记 |
| `上周五签的合同` | 不记 |
| `上周末加了两天班` | 不记 |
| `10月15号就交过了` | 不记 |
| `9月1号入职的` | 不记 |

`10月15号` 这一条在改之前不是「不记」，是 **2027-10-15**：绝对日期落在过去时会被推到明年，为的是让「12 月说 1 月 5 号」成立。这两种情形的区别在于往回差了多久，不在于是不是过去。现在只有往回差大半年才推，近处的过去留给出口守卫丢掉。

守卫写在 `parseDue` 的出口而不是各分支里，是因为分支会越来越多，而「窗口已经关上」只有一个判据。

### 20.3 习惯不是期限（第 2c 组）

| 句子 | 结果 |
|---|---|
| `我每周一都要汇报` | 不记 |
| `我每天七点起床` | 不记 |
| `每月5号交房租` | 不记 |

这三条原本会被裸星期几和月内指定日接住，各变成一个固定日期，然后每周重新逾期一次。判据是 `每 + 天/日/周/星期/礼拜/月/年`，写在识别层之外——它是策略，不是能力。

### 20.4 一个顺手拆掉的定时炸弹

无模型兜底路径里的 `hasTemporal()` 是第二份手写关键词表。这一版给「认不认」和「认成什么」接上同一条来源之后，`parseDue` 新认的 `下个月五号` / `周天` / `下周末` 不必再手工同步一次。上一版 `toEngineConfig()` 漏字段导致的「探针全绿但链路是断的」，和这个是同一类问题：**同一份知识写在两个地方，改一处忘一处，测试还看不出来。**

### 20.5 回归

- `probe-due`：50 → **95 项断言**（新增 19 条正向说法 + 6 条过去 + 3 条习惯 + 精度逐条校验）
- 其余 29 个探针 / 场景 + `npm test`（30 项）：全绿，无断言变化
- `parseDue` 的签名与返回形状未变，无迁移、无新列、无配置项

### 20.6 没做的

- **不解析钟点。**「今晚八点」仍落在当天 23:59。带时刻需要另一个字段，而现在没有东西会用它。
- **并列日期只取一个。**「周一到周五」取周五，「周一、周五」取周一。区间只有一条，表达不了「每隔一天」或「一段范围里的全部日子」。
- **「下周三以后」丢掉「以后」。** 老窄缝，这一版没碰。
- **跨时区不切日界，也不打算切。** 时区在会话建立时定一次，之后不改。悄悄跟随系统时区，改对时用户察觉不到，改错时（VPN、容器、笔记本被同步成 UTC）是一个静默移位的日期——和 20.1 那类错一样无法从界面分辨。

| 再一轮（1 分钟） | 不问 | 不问 |

第三行就是这一版的全部理由。上一版把「问过一次」当成了「已经有答案」，于是问句丢了就等于问题结了。

### 22.2 `AND nudged_at IS NULL` 让第二次永远写不进去

`markPlanNudged` 原来是：

```sql
UPDATE facts SET nudged_at = ? WHERE id = ? AND nudged_at IS NULL
```

在「只问一次」的世界里这是对的——`nudged_at` 是状态位，盖一次就够。改成时间锚之后它变成了硬伤：**第二次问句即使被渲染出来，时间锚也刷新不了**，于是间隔永远从第一次算起，下一次判断仍然立刻满足。表现是「每轮都问」，而那正是这一版想避免的另一头。

断言 `nudged_at 被刷新` 抓的就是这一处：两次询问的时间戳必须不同，第二次必须更晚。只断「出现过问句」的话，这个 bug 会在「不再问」和「一直问」之间来回摆，两种都能通过一半。

### 22.3 排序会饿死老计划（第 2d 组）

三条逾期计划，`maxPlans=3` → 逾期名额 `ceil(3/2) = 2`。其中最早那条十天前已经问过：

| 轮次 | 排到哪两条 | 问句数 |
|---|---|---|
| 第一轮 | 体检 (#3)、看房 (#2) | 2（两条从没问过） |
| 第二轮 | 交材料 (#1)、体检 (#3) | 1（只有十天前那条到点） |
| 第三轮 | 体检 (#3)、看房 (#2) | 0（三条都刚问过） |

原来按 `expires_at DESC` 排，第一轮拿到的同样是最新那两条——差别在第二轮：老的那条永远排第三，永远进不了前两名的名额，而占着名额的两条又不满足重问条件。**名额被「排到了但不问」的行占死**，这就是饿死。

改成 `ORDER BY COALESCE(nudged_at, 0) ASC, expires_at ASC` 之后，第二轮第一条就轮到十天前那条。

### 22.4 `planNudgeDays=0` 要能退回去（第 2c 组）

| 配置 | 过期当轮 | 三十天后 |
|---|---|---|
| 默认（2 天） | 问 | 问 |
| `0` | 问 | 不问，仍在计划区 |

把间隔退化成「只问一次」而不是「每轮都问」，是因为 `0` 最容易被误读成「没有间隔 = 每一轮」。这类边界值宁可选择更保守的那个语义，并且在 README 里写清。

### 22.5 没结果就一直留在计划区（第 2b 组）

三次询问之后那条计划仍然在块里：

```
- [11-01 · 已到期，还没有下文] 用户打算明天去交材料
```

没有第七天、没有第十四天、没有「过期太久自动归档」。退出计划区只有一条路：`memory_resolve` 给出结果。这和 22.1 是同一件事的两面——**沉默既不是办成，也不是没办成，它只是还没有答案。**

### 22.6 回归

- `probe-plan-outcome`：28 → **43 项断言**（新增 2b 重问 9 项、2c 关重问 3 项、2d 轮转 3 项）
- 其余 24 个探针 + 6 个场景 + `selftest` 30 项：全绿
- 无迁移、无新列；新增可选配置 `retrieval.planNudgeDays`（默认 2，`0` 只问一次）
- 文案变更一处：`已到期，之后没再提` → `已到期，还没有下文`；doctor 的 `N 条已问过` → `N 条问过没结果`

### 22.7 没做的

- **间隔不递增。** 被无视越久问得越稀的退避，在这条线上是错的假设：问不到更可能是因为每次都撞上别的事。
- **问的次数不设上限。** 出口只有 `resolved_at`。
- **沉默不判失败。** 没有任何「问了 N 次就当没办成」的路径。
- **中断仍会白问一次。** `nudged_at` 在 `recall()` 里盖，被中断的那一轮消耗掉了这次询问，现在只是晚两天，不再是永久。

## 二十三、发布前的一次一致性检查（v0.2.23）

### 23.1 起因

七版改动叠在一起，`lib/index.js` 从 v0.2.16 的体量涨到 8199 行，而这七版各自只被自己的探针覆盖过。**探针证明的是「我想到的那个场景能跑」，不是「七版之间没有互相踩」。** 所以这次不看 diff，按「一条数据从写到读要走哪几步」重走一遍。

### 23.2 升级路径：真的把库降级成 v1

最贵的 bug 会在这里：`migrate()` 用 `ensureColumn` 补五列，但如果某一列的 DDL 与 `CREATE TABLE` 里的定义不一致（多了/少了 `NOT NULL DEFAULT`），老库升级后行为会和新库不同，而这个差异只有老用户遇得到。

造老库的办法不是手写一份「v1 schema」——那样测的是我记忆里的 v1，不是真的 v1。**做法是反向的**：先用当前代码建库、写入数据，然后

```sql
ALTER TABLE facts DROP COLUMN aliases;   -- 以及 due_from / nudged_at / resolved_at / outcome
ALTER TABLE events DROP COLUMN aliases;
PRAGMA user_version = 1;
```

再让当前代码打开它。走的就是真 `ensureColumn` 那条 ALTER TABLE 路径。`probe-upgrade.mjs` 42 项断言，四组：

| 组 | 断言 |
|---|---|
| 迁移 | 五列 + `events.aliases` 都补回、`user_version` 1→4、事实与事件条数不变、文本一字不改 |
| 老数据可用 | 老的猫、老的偏好仍在块里；老计划（有 `expires_at`、三个新列为空）第一次就进「已到期，还没有下文」 |
| 升级后新写入 | 别名落库且进了 FTS 的 `tokens`、新计划仍算出区间、收尾写的事实没有期限 |
| 幂等 | 二次打开不重复 ALTER、版本号不往回写 |

顺带发现 `probe-upgrade` 第一版里「事件一条没丢」是 `0 → 0`：空表上的相等不证明任何事。改成先手工插一条事件再降级——这是同一天里第二次差点放过假绿。

### 23.3 查出的两个一致性问题

**同一行两个问句。** 一条计划如果既有改期提案（`pendingDue`）又过了期，`planLine` 会把两段说明都拼上去：

```
- [10-27~11-01 · 已到期，还没有下文] 用户打算下周去交材料（时间待确认：改到 11-09~11-15，
  原记 10-27~11-01；memory_settle(id=1)）（过了期限还没有下文——这轮问一句「后来成了吗」，
  按他的回答调 memory_resolve(id=1, done=true/false)）
```

两个工具、同一条计划、没有先后。模型大概率先问「后来成了吗」——而用户上一句说的是「改到下周了」，这句问话在时间上是错的。

改法：有 `pendingDue` 时不问「成了吗」。判据在 `planItem` 里，`nudge` 多一个 `pending === null`。理由不是「两个问句不好看」，是**用户刚给出新时间，这件事显然还没结束，问「成了吗」问错了问题**。

**已收尾的计划还能被改期。** `settle()` 只检查有没有提案，不检查有没有结果：

```
resolve(id=1, done=true)    → resolved_at 有值、outcome=done
settle(id=1, accept=true)   → expires_at 改成未来、expired_at 清成 NULL
                            → 计划区看不见（resolved_at 非空）
                            → 事实区也看不见（kind=plan 一律不进）
```

一行活在数据库里、在任何视图里都不存在的记录。现在 `settle()` 先看 `resolved_at`，有值就返回 `reason: "resolved"`，工具回「已经有结果了（办成），不用再确认时间；要重新做就记成一条新计划」。

同一处还漏了一件事：收尾时没清 `pendingDue`，于是 `memory_doctor` 的「N 条时间待确认」会把一条**已经有结果**的计划一直算成欠账。现在 `resolve()` 顺手删掉那条例。

### 23.4 一个 `undefined` 造成的静默失效

改 23.3 第一条时，第一版写的是：

```js
const pending = fact.evidence?.["pendingDue"];
...
nudge: overdue && pending === null && (...)
```

没有提案的行里，这个值是 `undefined`——**`undefined === null` 是 false**，于是所有计划都被读成「有提案」，`nudge` 恒为 false，一条都不会问。

可怕的地方在于它不报错：块照样渲染、行照样带着日期、「已到期，还没有下文」六个字照样在，只是那句问话没有了。如果只测「有提案时不问」，这个 bug 会完全隐身。

现在先归一化再判断：

```js
const raw = fact.evidence?.["pendingDue"];
const pending = raw !== null && typeof raw === "object" && typeof raw["to"] === "number" ? { ... } : null;
```

判断和渲染字段因此用同一个值。探针里补了反向断言：「没有提案的计划照常问」。

### 23.5 检查过、没有问题的

不是每一条都要改，下面这些是逐条看过、确认承担得住的：

| 检查项 | 结论 |
|---|---|
| 五个新列的 `ensureColumn` DDL 与 `CREATE TABLE` 是否一致 | 一致（`aliases TEXT NOT NULL DEFAULT ''`，其余三个 INTEGER / 一个 TEXT） |
| `ttl` 的 `CHECK (ttl IN ('none','absolute','relative'))` 与 `parseDue` 返回的 `kind` | `kind` 只有 `absolute` / `relative`，不越界 |
| `insertFact` 的 26 个占位符与参数顺序 | 数过，对齐（`access_count` 与 `expired_at` 是字面量） |
| 已收尾的计划会不会以事实身份重现 | 渲染层 `item.meta["kind"] === "plan"` 一律跳过，不会 |
| 矛盾扫描会不会把「计划 → 已办成」标成互相矛盾 | `scanContradictions` 要求 `a.kind === b.kind`，plan 与 fact 不配对 |
| 别名里的 FTS 语法字符（`"` `OR` `NOT` `(` `*` `-`） | 进的是 `tokens` 列的分词结果，查询端另有转义；实测不抛错 |
| `timezoneOf("")` 在 `resolve()` 里的返回值 | 回落到实例时区，不会变成 UTC |
| 空白 / 超长文本、不存在的 id | 分别返回「内容太短」「没有找到」，不抛 |
| `memory_settle(accept=false)` 是否清提案 | 清（v0.2.20 修过，这次回归仍绿） |

### 23.6 这次没有覆盖到的

- **没有真模型。** 提示词是否被遵守（别名怎么写、时间短语是否原样抄、`memory_resolve` 会不会被正确调用）一次都没验过，全部是规则模式与假 llm。
- **没有长周期。** 衰减、备份轮转、`l0` 清理、钩子冷区都只在探针的秒级时间轴上跑过，几个月后的堆积没看过。
- **没有并发。** 单进程单会话；两个进程同时写同一个 `loom.db`（WAL 下应该没事）没测。
- **没有真实宿主。** `tick` 的定时器、prompt 块在真实对话里被求值几次、中断一轮后的行为，都还是推断。

## 二十四、v0.2.24：插件能不能说清自己在跑哪一版

这一版没有功能改动，全部内容是一个问题：**当磁盘上的包和进程里的代码不是同一份时，谁能看出来。**

### 24.1 起因

2026-11-02 真机升级（0.2.16 → 0.2.23），`dsh plugin add` 13.9 秒跑完、磁盘确认换了包，但装完一问，三条指标全是旧的：工具 9 个、`memory_doctor` 报 `unknown tool`、`user_version` 还是 1。三条同时成立只可能是 0.2.12。

当时的困境不是「不知道坏了」，而是**没有任何一个地方能直接回答「现在跑的是哪一版」**——只能靠数工具反向推断，而工具数又随版本变化（9 / 12 / 14），推起来既慢又容易错。

### 24.2 现在盯什么（`probe-version.mjs`，12 项）

| 组 | 断言 | 抓的是什么 |
|---|---|---|
| 1 | 医生第一行是版本行、含运行版本、含库 schema、新库不出现「上次由」 | 这一行必须恒在，且不说没有的事 |
| 1 | 运行版本等于 `package.json` 的版本 | 常量漂移会被抓（CI 里 `check-docs` 另有一道） |
| 1 | 关键工具按名字都在 | 不用数总数，避免「加工具 → 探针误红」 |
| 2 | `meta` 里真有 `runtime.version`，新库没有 `previousVersion` | 不是只在内存里算一次 |
| 3 | 把库里版本改成 `0.2.12` 再启动 → 医生说「库上次由 0.2.12 打开」 | 升级这件事被记住了 |
| 3 | 同一轮里运行版本仍报当前版本 | 两个字段不打架：谁在跑 vs 库上次被谁打开 |
| 3 | `runtime.version` 刷新、旧值进 `previousVersion` | 覆盖顺序对，不是把新旧搅在一起 |
| 4 | 同版本再启动一次，`previousVersion` 不变 | 正常重启不该伪造一次「升级」 |

第 4 组是这次新写的判据。没有它，一个「每次启动都覆盖 previousVersion」的实现也能通过前 11 项，而那个实现会让医生永远说「库上次由某个版本打开」，等于把「这次升级真的发生过」变成噪声。

### 24.3 边界：它证明的不是宿主行为

`probe-version.mjs` 是**直接改库里 `meta`** 来模拟升级的。它验证的是「换版本之后能不能说出来」，**不是**「宿主在升级后会不会重新组合插件」——后者只在真机上发生过一次，探针无能为力。

所以这一版的结论要分开说：

- 「医生能报出运行版本、能在升级后说出上次的版本」——有探针，可复跑
- 「同名 bundle 升级不触发重组」——三条真机证据 + 机制推断，没有第二次观测

### 24.4 顺带修掉两处写死的工具数

`probe-hotload` 原本断言 `surface.tools.size === 13`，v0.2.23 加了第 14 个工具之后它就一直红着，而它当时还没进 CI（进 CI 是 0.2.23 发布后补的），所以没人看见。改成 `>= 14`。

`probe-version` 初稿也写了 `=== 14`，同一个坑。改成按名字查四个关键工具（`memory_doctor` / `memory_resolve` / `memory_settle` / `memory_search`）——它要证明的是「工具挂上了」，不是「正好 14 个」。

结论：**断言里不写会随版本变的常数**。工具数、版本号、行数都属于这一类；能按名字查就按名字查，必须写数字时写成下界。

## 二十五、v0.2.25：把「到日子我会问」提前说出来

新增 `probe-demo.mjs`（25 项）、`probe-plans.mjs` 第 6、7 组（15 项），并顺带把 `probe-due.mjs` 的时间漂移修掉了（见 25.4）。这一节只记新探针在守什么，以及它守不住什么。

### 25.1 三件事，五组断言

| 组 | 守什么 | 为什么值得一条断言 |
| --- | --- | --- |
| 1 | 三幕都在；到期那行不重复写同一句话；演示前后真实库 `facts` 计数不变 | 重复写会读成两件事；会写用户记忆的演示比没有演示更糟 |
| 2 | 连跑两次输出同构、每次从 `#1` 开始 | 演示库若没隔离，第二次会带上第一次的痕迹，而人眼看不出来 |
| 3 | 医生「下一步」带日期、说清「之后第一次对话就会问」、只报一行；收尾后整行消失 | 这一行是「等待可验证」的全部来源，报错了比没有更误导 |
| 4 | `planNudgeDays=0` 时不再提「每 N 天再问」 | 文案里写死数字，配置一改就对不上 |
| 5 | 没日期的计划渲染成「未定期限」，且**不写**「到期后我会问一句」 | 没有日子的承诺，写「到期后」就是撒谎 |

第 3 组里有一处是刻意不写成常数的：**间隔天数不断言具体值**，只断言「配成 0 时那句话消失」。断言里写 `每 2 天` 会在有人改默认值时假红一次，而那时该改的是配置不是探针。

### 25.2 演示证明的是「同一套代码」，不是「同一段文案」

`memory_demo` 里没有一行渲染代码是演示专用的：`writeFact` 解析日期、`recall` 挑行、`renderMemoryBlock` 拼行、`resolve` 收尾。探针因此能直接断言演示输出里的那行字——它和真实块里的那行同源。

反过来说，如果有人以后为了「演示好看」在这里另写一套格式化，第 1 组的正则仍会通过（字面一样），但两边会从那一刻起开始漂移。这条约束没法用断言守住，只能写在注释里：**演示的价值是「你看到的就是以后会出现的」，一旦复制一份渲染，这个价值立刻归零。**

### 25.3 演示不碰真库，这一条是硬断言

`probe-demo.mjs` 在演示前后各读一次真实 `loom.db` 的 `facts` / 计划计数，要求完全不变。实现上演示用的是独立 `:memory:` 实例 + 可拨的假时钟（`MemoryEngine` 的 `now` 选项），收尾 `close()`。

值得记的是：这条断言**不依赖实现细节**。哪怕以后把演示改成别的形态，只要它还写用户记忆库，这条就会红。

### 25.4 顺带修掉 `probe-due` 的时间漂移

`probe-due` 有 2 项断言会自己变红：`harness` 把虚拟时钟起点设在「真实时间 − 3 天」，而「截止 / 已到期」是按真实 now 判的。首轮不跳这 3 天，就被锚到三天前，「下周一」落到昨天——探针红在什么都没改的那天。

三处首轮 `turn` 改成 `gapMs: 3 * DAY`，把起点拨到当下。这类探针放进 CI 会每隔几天自己红一次，然后被当成回归去查；比起漏测，这种「假红」对 CI 的伤害更大。

### 25.5 提前做完的计划：从行上抓 id，再收掉

这一组（`probe-plans.mjs` 第 6 组，11 项）的起因是一条真实记录，不是设想的场景：计划写的是「11-13 发推广文」，用户 11-02 晚上就发了。计划区只在过期后才给催问指令，在那之前模型拿不到收尾的理由——**更关键的是拿不到 id**：未到期的计划行里没有编号。

所以断言的第一条不是「能不能收」，而是「那一行有没有给出编号，且给的是不是它自己的」：

```js
const datedId = Number(dated.match(/memory_resolve\(id=(\d+)/u)?.[1] ?? Number.NaN);
```

**从行上正则抓，不写死 `1`。** 写死数字会在这个库里多加一条计划、或写入顺序变化时假红；而假红比漏测更伤 CI——它会训练人忽略红色。抓到的 id 再回喂给 `memory_resolve`，等于顺带验证了「行上写的编号」和「工具收的那个编号」是同一个东西，这一条写死数字是测不出来的。

四件被锁住的事：

| 断言 | 守的是什么 |
| --- | --- |
| 未到期 / 未定期限的行都给出 `memory_resolve(id=N, outcome=done\|cancelled)` | 两条路径都要有入口；未定期限的计划一样会提前完成 |
| 未定期限的行**不带**「到期后」 | 没有日子还写「到期后」是撒谎 |
| 收尾后那一行不在块里，且留下一条「已办成」的事实 | 用户的原话：提前完成了，就不该再待在计划里 |
| 另一条计划没被连坐、重复收尾被挡下 | 收错一条真计划的代价，是它在块里静默消失 |

另外在 `probe-demo.mjs` 加了两条：第一幕那行要能看到提前收尾入口（演示与真实渲染同源，这一条顺带证明演示没漂移）；已到期那行**不叠加**这句（那一行本来就有催问指令）。

顺带改掉的一处矛盾：没日期的计划原来渲染成 `[未定期限 · 截止]`。这个不是查出来的，是加完文案后跑一次渲染、两行并排看出来的。已改成整格省掉，读作 `[未定期限] 我打算戒烟`。

第 7 组补的是第 6 组自己漏掉的一格：判据一开始写成「还没到期」，于是「已过期、刚问过、再问间隔没到」的行两头不靠——`nudge` 为假所以没有 `planAsk`，又不是「还没到期」所以没有收尾入口，整行**没有任何编号**。而用户最可能正是在那个窗口里补一句「去了啊」。

造这一格要直接改库里两个时间戳（`expires_at`、`nudged_at`），自然等到它要两天。有一个坑记在这里：**只把 `expires_at` 拨到过去，会渲染出 `11-13~11-03` 这种反区间**——真实数据里不会出现那样的样本，用它去锁断言，锁住的是伪造本身。`due_from` 必须一起往前挪。


### 25.6 计划的第三种结局：取消

这一节加在 25.5 之后，因为 25.5 的入口只给了「办成了」一条路，而提前结束的计划里有一半是**不做了**。工具参数从 `done` 布尔换成 `outcome` 三选一（`done` / `missed` / `cancelled`），`probe-plan-outcome.mjs` 现在 71 项断言。第二十一、二十二章里那几行 `done=true` 是它们当时的样子，从这一版起读作 `outcome=…`。

新增四组：

| 组 | 守什么 | 为什么不能只靠上一组 |
| --- | --- | --- |
| 3 补 | 第二次调用的回话报**库里那个**结局，不是这次传的 | 照着入参复述会让模型以为结局被改了，接着把它当成「没去」用 |
| 5 补 | 枚举之外的值在进引擎前就被挡下 | schema 挡一次，引擎层再挡一次（`reason: "bad-outcome"`），不默默记成 `missed` |
| 4b | 未到期的行给 `done\|cancelled` 两个值；取消写出「已取消」而不是「没办成」；计划标成 `cancelled`；计划区不再出现它；医生算成「已有结果」；搜索结果带「（已取消）」 | 「取消」和「没做成」是两件事，一个是决定、一个是结果 |
| 4c | 过期之后仍然可以记成取消 | 「到日子了」不等于「必须给个成败」 |
| 4d | 已收尾的计划在维护跑过之后`expired_at` 仍为空，同轮里没结果的计划照旧被打上 | 只断言前者，测的可能只是「维护没跑」 |

4d 要有办法跑维护。维护是 60 秒的定时器，探针等不起，所以 `harness.mjs` 加了 `createLoomWithTimers()`：拦下 `setInterval`，把回调留下来手动跑一次。跑的是宿主在第三分钟会跑的同一段代码，不是替身——用它锁「已收尾的不该被判过期」，断言和实现之间没有中间层。

这一格发现的问题比取消本身更值得记：**一条计划被取消之后，它当初那个日期还是会到。** 维护按 `expires_at <= now` 扫，于是给已收尾的计划也打上 `expired_at`；`scoreFact` 的 `expiryFactor` 按天把它从检索里减半，最后 `factsDueForPurge` 会删掉这条唯一记录——而 `resolve()` 刻意不改写计划，正是为了留下那句原话。修法是 `expireDueFacts` 多一个 `resolved_at IS NULL`。

还有一个洞是在写断言时才看出来的：`memory_search` 里那条计划原来不带任何标记。块里靠「计划区不含已收尾」避免误读，搜索结果没有分区，于是搜「看房」会读到「用户打算周五去看房」，像还没去。命中项现在带 `planEnd`，渲染成「用户打算周五去看房（已取消）」。

### 28.1 现场：一份真文件，不是构造的

`probe-intake` 不画接口，造的是真实文件：

### 28.3 写探针时踩到的三个坑

1. **重复的指令会重复进库。** 第一次跑第 5 组失败：事实数没变，但回话说「导入了 1 条」。原因是 `instruction` 进的是 `preferences` 表，而重复判定只查了 `facts`——同一句「以后都用 pnpm」每导一次就多一行常驻要求，而 `事实` 那条线一动不动。补 `store.preferenceTexts()` 一并比对。
2. **读 SQLite 用了 `ORDER BY ... DESC`。** 同一句话在文件里出现两次（一次 200 天前、一次 2 天前）时，DESC 让新的先被接受、旧的被当成重复丢掉，于是「保留了原始日期」这条断言拿到了 2 天前。导入是**重放历史**，顺序应该是 ASC。
3. **假模型的请求形状不是插件内部的形状。** `mockLlm` 收到的是真实 `llm.stream` 的请求（`messages[0].content[0].text`），不是 `{ prompt }`。第一次拿到 `undefined`、回了空清单，「补了 0 条」看起来像代码没跑——实际是探针自己写错了。

三个坑里只有第一个是产品 bug，另外两个是「断言写对了、但写错了地方」：第 2 个差点被当成通过（数字变了但没到失败阈值以外），第 3 个会把一个正常功能报成坏的。记在这里是因为下一个探针还会遇到同样的三件事。

### 28.4 只有「指向自己的旧库」才会暴露的三种错

打包前的一遍自审里，把本插件自己的库复制一份拖进去当外来文件试了一次。预览说「读出来 12 条」，其中 8 条是从 `l0` 里捞的对话原话、5 条是 `persona_zones` 里的默认设定。这不是边界情况——用户换机器、找回旧文件、或者只是想试试「导入」按钮，都会撞上。

- **对话表被当成记忆。** 表有 `text` 列、有行、不是 `_fts`，所有旧判据都放行了。修法不认名字认结构：有 `role` / `speaker` / `direction` 列的表一律不读。
- **设定表被当成记忆。** `persona_zones` / `narrative` / `diary` / `loom_docs` 都是「关于记忆系统」的表。加一张表名黑名单，顺带把自己前缀 `loom_*` 也算进去。
- **一个坏表连坐整份文件。** 改成逐表 `try`，并把 `ORDER BY rowid` 失败退到无排序（`WITHOUT ROWID` 的表就靠这一条才读得出来）。

顺带修的两处：提示词里的「问三次」原来只按轮号计数，出现**新的一份**文件时不会重新问（次数已经花完了）——现在同时记一个 `路径:字节:mtime` 签名；不带参数的 `memory_import` 改成强制重扫，而不是沿用最多六小时前的结果。

## 二十九、v0.2.27：那一行日期是「他哪天说的」

这一版只改一件事，起因是一个反问：「相对日期不归一化，这个不是有个绝对日期嘛。」

对，有。每条记忆前面都带 `[08-05]`，`probe-due` 一直在断言它没变。但它锚的是**说话那天**，不是**事情那天**。把一条事实的时间拨到 90 天前，同一个场景立刻分成两种性质：

```
- [08-05 · 事实] 用户前天把明信片寄出去了，收件人是他在成都的姐姐
- [08-05 · 事实] 用户明天要去医院复查心脏，挂的是上午的号
```

第一行是精度问题：被问「什么时候寄的」，读者要做一次减法。第二行是**错**：那个「明天」早在三个月前就过完了，而句子还在用未来时。一个照着字面回答的助手会把用户指到一个已经过去的日期，而且语气很确定。

### 29.1 现场：把时间拨回去，而不是构造字符串

探针不手写「渲染结果应该长什么样」，它是真的写库、真的把 `created_at` 往前拨 90 天、真的再开一次插件读记忆块：

```js
raw.exec(`UPDATE facts SET created_at = created_at - ${90 * DAY}, updated_at = updated_at - ${90 * DAY}`);
```

这样测到的就是生产里那条路径：整合写入 → 时间流逝 → 下一轮召回 → 渲染。拨 `expires_at`/`due_from` 是另一件事（`probe-plan-outcome` 那里拨的是它们），这里只动 `created_at`，因为被质疑的正是「行首那个日期锚的是谁」。

### 29.2 十七项，六组

| 组 | 守什么 |
| --- | --- |
| 1 | 五个该补的词各自补对：前天 −2、昨天 −1、大后天 +3、明天 +1、上周三 −7（跨周，按 ISO 周一起算） |
| 2 | 六个不该补的都不补：先天和后天、后天免疫、明天出版社、前阵子、上个月、手写过 `（11-04）` 的不重复补 |
| 3 | 库里一条都没被改写，原句「用户前天把明信片寄出去了」逐字比对 |
| 4 | `memory_search` 的命中行也补，且日期与行首一致 |
| 5 | 计划行：有期限的不补（行首已是答案），没有期限的照补 |
| 6 | 「今天」不补——行首就是那天 |

第 2 组比第 1 组重要。补错日期是往记忆里写一句假话，而且带着一个看起来很权威的括号；用户不会去核对一个括号，只会某天发现助手坚持认为他在 8 月 7 日要出门。

### 29.3 三个坑

1. **「上周三」我第一次算成了 −5。** 直觉是「上周」等于七天前，手上就写了 5。正确的是 −7：08-05 是周三，上周三就是 07-29。探针当场报 `补注 07-29，应为 07-31`，才回去把 `-5` 改成 `-7`——**期望值写错时断言会「通过得很可疑」**，这次幸亏它算得比代码还准。
2. **「先天和后天都重要」被补成了日程。** 第一版只看了「后天」后面紧跟的词，而这里是「后天都重要」——「都」不在词表里。加 `before` 判据看前四个字有没有「先天」，成对出现时一定是那个意思。
3. **计划行补出了两个相同的日期。** `[11-11 · 截止] 用户打算下周三（11-11）去体检`。`probe-due`、`probe-plans`、`probe-demo` 同时红。三个一起红说明它们测的是同一件事（计划行长什么样），而不是三件不相干的事——所以修法不是改三个断言，是改规则：`dueTo === null` 才补。

顺带发现一个小问题，没有修：`memory_write` 之后同一轮里读记忆块，读到的是缓存（第 5、6 组必须 `turn()` 一次才看得到新写的那条）。实际流程里记忆块是每轮开头渲染的，模型写完不会立刻回头读，所以影响面为零；记在这里是因为下一个探针还会撞上。

### 29.4 回归

全套 39 个脚本（33 个探针 + 6 个场景）+ `selftest` 30 项全绿。`probe-relative` 17 项，`probe-intake` 61 项，`probe-plans` 31 项（有一条断言的文本多了个可选括号，已放宽）。

## 三十、v0.2.28：规矩也得有门

### 30.1 现场：三条路同时断

先取证，再改代码。写四条 `instruction`（第四条是「我不吃香菜」，刚好落在常驻上限 `residentPreferences: 3` 之外），然后连问三种问法：

```
[我有什么忌口]      块里有香菜? false    search: 没有找到相关记忆。
[点外卖注意什么]    块里有香菜? false    search: 没有找到相关记忆。
[我有什么规矩]      块里有香菜? false    search: 没有找到相关记忆。
```

块里也没有（问法和规矩不共享二字组），搜索没有（`searchFor()` 只 `collect` 了 `facts` 和 `events`），于是那一行在表里、在四张表之外谁也够不着。同一个脚本顺手确认了撞号：四条偏好拿到了 `#1…#4`，紧接着写一条事实也拿到 `#1`。

### 30.2 二十四项，七组

`probe-search-preference.mjs`：

| 组 | 断言 | 卡住的是什么 |
| --- | --- | --- |
| 1 | 常驻之外的规矩能被搜到；编号是 `#P` 不是 `#F`；偏好行不打 `domain` 列 | 门开了，门牌号对了 |
| 2 | `memory_expand("P1")` 取回原文 | 拿到编号能查证，不是死胡同 |
| 3 | 同号样本就位 → 退休偏好 → 事实 `#F1` 仍在 → 退休后 expand 拒绝 → 块里也没有 | 一次操作三处同时生效，且不连坐另一张表 |
| 4 | 事实仍可用 `id` 删除，回话带原文 | 老路没被改坏 |
| 5 | 不存在的编号给「没有忘记」；`permanent` 真删且回话带原文；删完 expand 说「没有偏好」而不是「已被移出」 | 两种消失要能分辨 |
| 6 | 主人跨身份查不到对方规矩；同门里对方的事实查得到；朋友自己搜得到、也收得回自己的规矩；主人收不回别人的 | 整类不外借，且不是整条路断了；收回权也只归本人 |
| 7 | `ref="99"` 当事实号；`ref="F1"` 与 `id=1` 等价；`id="P1"` 被宿主拦下；两个都不给时说人话 | 填错字段不该让整轮白跑，也不该静默删错 |

第 6 组要一个真的 `friend` 身份。harness 里每个会话都映射到 master（`identityForSession`），也没有工具能造第二个身份，所以这组先用第二个 SQLite 连接塞一条 `identities` 和一条 `sessions`，再正常开机——`s2` 起来就是货真价实的朋友，跨身份分支才真的被走到。两句断言必须成对（事实查得到 / 规矩查不到），否则一个写坏的 SQL 也能让测试通过。这组后来又加了两条：主人调 `memory_forget(ref="P1")` 必须被拒，朋友自己调必须成功——因为收回的回话会点名被收回的那句话，给主人开例外等于从后门把刚才关上的门开回来。

### 30.3 四个坑

1. **`memory_identity` 的 claim 会让主人自己掉级。** 第一版想用「朋友自报 → 主人approve」造第二个身份，结果 `claim` 把 master 那个身份改成了 `pending_review`，紧接着 `approve` 抛 `只有主人可以做这个操作`。根因是 harness 里所有会话共享一个 master 身份——这不是被测代码的 bug，是脚手架造不出第二个身份。所以改成直接写库。
2. **`refAlive("P3")` 会掉进「当它是事实」的兜底。** `parseRef` 加了 `p` 之后，`refAlive` 里「不是 doc 也不是 event → 查 facts」这一支会把 `P3` 拿去 `facts` 表里找第 3 行。它不会报错，只会用一个不相干的事实回答「这条规矩还在吗」。`body()` 也一样，所以两处都先加了偏好分支。
3. **`memory_forget` 的 `id` 曾是必填。** 加 `ref` 之后必须把 `id` 的 `required` 去掉，否则只传 `ref` 的调用在参数校验层就被拒了——报错还长得像「参数不合法」，很容易被当成模型填错。去掉之后补一句「没给编号」的兜底，让「两个都没传」有人话。
4. **`id` 的类型声明本身也是一道门。** 第一版探针写 `memory_forget({ id: "P1" })`，想证明「规矩号填进 id 也能落地」，结果在 `defineTool` 那层就抛 `invalid arguments: "id" must be an integer`——参数校验发生在 `run` 之前，`String(args.id)` 那段根本没被执行。所以工具里那段字符串兜底只在不过校验的宿主上有用；对着校验过的宿主，正确的说法是「宿主会拒绝，模型下一轮改用 ref」。探针改成断言这件事本身（拒绝而不是静默删错），因为「宿主拒绝」也是一个正确结局，而它比我们的兜底更早生效。

### 30.4 回归

全套 40 个脚本（34 个探针 + 6 个场景）+ `selftest` 30 项全绿。新增 `probe-search-preference` 24 项；`probe-collision` 29 项（工具数仍是 16，`memory_forget` 多一个参数不改变工具数）；`probe-preference-resident` 3 组未受影响（常驻路径没动）。

### 30.5 补上之后才出现的洞：作废的规矩能被导入复活

`active` 这一列在 0.2.28 之前没有写者，所以 `normalizeIntakeRows` 从来不需要看它——搬进来的每一行都是有效的。补上收回之后，同一份文件里就可能同时有「还在生效」和「已经作废」两种规矩，最典型的两条路是：把 `memory_export` 的产物拖回来、或从另一台机器找回旧文件。前者甚至更隐蔽——`exportData` 原来只导 `id/text/created_at`，正好把「这条还算不算数」丢掉了。

改法是三处各加一小步：

1. `exportData` 带上 `active`——原来只导 `id/text/created_at`，正好把「这条还算不算数」丢掉了；
2. `normalizeIntakeRows` 跳过写着 `active: 0` 的记录，并在预览里报「已收回的 N 条」。只认显式标记，形状认不出来的按有效处理；
3. `preferenceTexts()`（导入去重的那份名单）不再过滤 `active = 1`。这是第二条路：源文件根本不可能知道用户后来改主意了，所以「没标状态但本地已经收回」的情况只能靠去重拦。要让一条已经收回的规矩重新生效，正确的动作是用户再说一次（`memory_write`），不是导入一个旧文件。

`probe-intake` 第 7 组因此多了 9 项（61 → 70）：先写一条规矩再收回，然后分别用「没标状态的文件」和「标了 `active: 0` 的文件」试两次——预览各只认一条、原因都说得出来、落库各只落一条，事后搜「周报」「汇报」都搜不到。

## 三十一、v0.2.29：给抽取加一个校验位

### 31.1 现场：evidence 里没有一个字段关于出处

先看已经存下来的东西。一条抽取出来的事实，`evidence` 里只有两个键：

```json
{"ttlPhrase":null,"duePrecision":null}
```

两个都是关于**时间**的。关于「这句话从哪来」——一个字都没有。所以模型编出一条「用户对芒果过敏」，插件既不能证实也不能证伪，它会进库、能搜到、读起来通顺，然后一直待在那里。

这不是检索问题，也不是渲染问题。是写入路径上**从来没有过一个校验位**。

### 31.2 二十三项，七组

`probe-extract-quote.mjs`：

| 组 | 断言 | 卡住的是什么 |
| --- | --- | --- |
| 1 | 提示词要 quote、要逐字复制、点名主语改写、允许省略号、写不出就删、JSON 模板里有这个字段 | 口径写在字符串里，改了代码没改口径时模型不会知道 |
| 2 | 逐字摘抄 → `true`；摘抄原文留在 `evidence` 里；只差标点也算 `true` | 对得上要能看出来 |
| 3 | 编造的摘抄 → `false`；主语被改写的摘抄 → `false`；**两条事实都还在库里** | 只记不拦，且两种 false 都要出现 |
| 4 | 没给 quote 不写这个键；短到没法判的也不写；两条都照常进库 | `null` 不是 `false` |
| 5 | 省略号两段都在 → `true`；有一段不在 → `false` | 跨句事实也能给摘抄 |
| 6 | 全对时 `· 引用核对`；有错时 `✗` 并带条数；没有可校验的行时这行不出现 | 医生要能报，也不能在冷库里多一行 |
| 7 | 有错时 ✗ 且点名那条；`memory_forget` 之后这一行整个消失 | 它自己给的建议得真的管用 |

第 3 组是这一版最重要的两组之一（另一组是第 4 组）：它同时要求「标出来」和「不拦」。只断前者，实现会倾向于拦截；只断后者，实现会倾向于什么都不做。

### 31.3 四个坑

1. **模板字符串里多写了一个反斜杠。** 输出模板那段是模板字符串，我按 JSON 的直觉写成 `"quote\":""`，虽然 `\"` 在反引号里求值后仍是 `"`、结果碰巧正确，但下一个改这里的人会以为那是必需的转义，然后在别处照抄出错。改回 `"quote":""`。

2. **`maxTokens: 900` 会在真实使用中截断。** 这是改完代码才想到的：每条事实多一个 ≤30 字的摘抄，8 条就多 240 tokens 左右，而 900 本来是刚好够 8 条事实的。截断的 JSON 解析不出来，`extractWithModel` 返回 `undefined`，整段掉到规则路径——**失败是无声的，掉的是记忆不是错误码**。提到 1200。探针测不出这一条，因为它用的是固定回复；只能靠算。

3. **第一版探针里有一个 `check('标点不同不影响判定', true)`。** 那是我写的时候留的占位，永远通过、永远占一个 ok。它比没有断言更糟：一个永远绿的项会让人以为那一格被守住了。改成真的跑一次——同一段对话里放两条事实，一条摘抄逐字、一条把逗号换成空格，两条都要 `true`。
4. **医生那条查询漏了 `status IN ('active','disputed')`。** 这一版唯一的真 bug，而且是「仔细检查一遍」时才发现的：软删除只把状态改成 `pending_delete`，行还在表里。于是这行报出 ✗、点名那条编造的事实、建议 `memory_forget`，用户照做之后——✗ 原地不动。**一条照着做也没有用的建议，比没有建议更坏**：它教用户跳过医生的输出。补上 `live` 判据，并加第 7 组：删之前 ✗ 在并点名，删之后整行消失。教训是：凡是「建议某个动作」的汇报，都得测一遍做完那个动作之后它自己是否消失。

### 31.4 回归

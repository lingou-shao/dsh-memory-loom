## 1. 设计目标与不变量

1. **记忆必须可解释**：每条事实都能回答「从哪轮对话来、什么时候、为什么权重变了」。所以有 `audit`、`traces`、`sourceIds`、`evidence`，而不是一个不透明向量。
2. **记忆不能比对话更响**：当前对话永远优先（Q66）。过时的记忆要显式标注、降权，仍可被用户纠正。
3. **没有模型也要能活**：规则模式下 L0 照常积累、事实照常抽取、检索照常工作。模型只是让抽取更准、判断更细。
4. **数据属于人**：按人隔离；能查、能导、能删；删有冷静期也有立即彻底删除；路人默认更强保护。
5. **时间只在写入时解释一次**：「明天」在写下的那一刻换算成绝对日期（Q10/Q52），之后不跟着当前时间漂移。

## 2. 三层架构（Q47–Q50）

```
┌──────────────────────────────────────────────┐
│ dsh 宿主                                      │
│  session/event · agent/created · turn-stopping│
│  systemPrompt.section/context · ctx.tools     │
└───────────────┬──────────────────────────────┘
                │  只在这五个接缝上耦合
┌───────────────▼──────────────────────────────┐
│ src/index.ts 适配层                           │
│  · 事件 → engine 调用                         │
│  · 人设卡 / 记忆块 → prompt 位置              │
│  · 定时器 → maintain / consolidate            │
│  · 不包含任何记忆策略                         │
└───────────────┬──────────────────────────────┘
                │  纯 TypeScript 接口
┌───────────────▼──────────────────────────────┐
│ src/engine 内核                               │
│  store · decay · segment · consolidate ·      │
│  retrieval · render · persona · roles         │
│  只依赖 node:sqlite 与 Intl                   │
└──────────────────────────────────────────────┘
```

内核不认识 dsh 类型：`LlmComplete` 是一个 `(request) => Promise<{text}>` 的函数签名，时钟是注入的 `() => number`。因此内核可以换宿主（Q47 的「SDK 为内核」），也可以在测试里完全脱离 harness 运行。

**耦合边界（Q50）**：

| 接缝 | 用途 | 是否阻塞 |
|---|---|---|
| `session/event` → `user/message`, `assistant/message` | 同步写 L0 | 写一次 SQLite，毫秒级 |
| `session/event` → `request/context` | 记路由，供整合调用复用 | 否 |
| `session/event` → `compaction/start` | WAL checkpoint | 否 |
| `agent/created` | 注册人设 section 与记忆 context | 否 |
| `agent/turn-stopping` | 收尾计数，必要时启动后台整合 | 否（整合不 await） |
| `ctx.tools.register` | 六个工具 | 否 |

存储 schema、检索算法、prompt 文本都不与宿主共享；宿主升级只需保证这五个接缝。

## 3. 数据模型

单文件 SQLite（WAL）。所有表都带 `identity_id`，除人设与元数据外均按人隔离。

| 表 | 层 | 作用 |
|---|---|---|
| `l0` | L0 | 原始对话：`session_id, turn, role, text, created_at, consolidated, purge_at` |
| `facts` (+ `facts_fts`) | L1 | 原子事实：`kind, domain, tags, salience, base, stability, stability_max, confidence, ttl, expires_at, expired_at, pinned, status, isolated, from_visitor, source_ids, evidence, weight` |
| `events` (+ `events_fts`) | L2 | 事件：`title, summary, domain, started_at, ended_at, turn_from/to, l0_from/to, salience, valence, arousal, status` |
| `event_facts` | — | 事件 ↔ 事实 |
| `narrative` | L3 | 自我叙事的历史版本 + 证据计数 |
| `impressions` | 主观 | 每个用户一份印象 + 观察次数 + 置信度 |
| `diary` | 主观 | 按用户隔离，每天上限 3 条。**只存 `entry / day_key / created_at`**（v0.2.9 删掉了 `weight` 与 `mood` 两个空转列）；同时导出为数据库旁边 `diary/YYYY-MM-DD.md` 的只读镜像 |
| `preferences` (+ FTS) | 主观/隔离 | 指令性文本，只在相关 query 上检索 |
| `persona_zones` / `persona_overlays` / `persona_history` | 人设 | 全局面板 + 每人覆盖层 + 变更历史 |
| `identities` / `sessions` / `identity_claims` | 角色 | 主人/朋友/路人、会话绑定、认领审核 |
| `memory_edges` | 图 | `SUPERSEDES` / `CONTRADICTS` |
| `audit` / `traces` / `usage_daily` / `jobs` / `meta` | 运维 | 审计、召回轨迹（14 天）、每日模型调用预算、死信与元数据 |

索引按访问路径建：`facts(identity_id, status, updated_at)`、`l0(consolidated, identity_id, id)`、`events(identity_id, ended_at)`、`l0(purge_at)`。

## 4. 算法

### 4.1 中文检索（Q53 的替代）

SQLite 的 `unicode61` 把一串汉字当一个 token，中文整句只能整句匹配。这里不加词典、不下载模型，改用 **CJK 二元分词**：

```
「我喜欢猫」 → 我喜 喜欢 欢猫
```

写入时用同一套分词生成 FTS5 索引，查询时同样展开成大写的引号短语（`"喜欢" "欢猫"`），隐式 AND。好处是离线、无密钥、子串可召回；代价是语义相近但用词不同的句子会漏——这是明确接受的取舍（见 README「已知边界」）。

`estimateTokens` 与分词共用字符分类：CJK 约 0.65 token/字，拉丁约 1/4 字符。

### 4.2 衰减与融合（Q23/Q56）

```
strength = base · (1 + t/S)^(−d)          base ∈ [0.55, 1]，与 salience 耦合
S_new    = S · (1 + boost·S^(−0.2))      被检索到时；S ≤ S_initial × 50
expiry   = 0.5^(daysSinceExpiry/45)      下限 0.02
score    = (sim·strength + emotion + layerPenalty) × expiry × conflict × weight
```

- `sim` 是「原始 BM25 分数 ÷ 该路 Top-1」，逐路归一化后再融合（Q32）。
- 情绪项对事实带 0.5 权重、对事件与主观层带 1.0（Q56 的用户修正）。
- `layerPenalty` 让同等相似度下事实优先于事件、事件优先于主观层。
- 软失效不删除，只乘 `expiry`；`floor = 0.02` 保证永远不是零分。

### 4.3 事件切分（Q4–Q8）

1. 一级：时间间隔 > 30 分钟硬切；主题域变化且话题 Jaccard < 0.12 硬切；情绪显著度 ≥ 0.70 且比上一轮跳 ≥ 0.25 软切。
2. 二级：间隔 ≥ 2 轮后，微观话题 Jaccard < 0.30 漂移、或更小的情绪尖峰（≥0.55，跳 ≥0.15）细切。
3. 绝对切：任何一段达到 `2N` 轮强制换段。
4. `N` 是最近 K=20 个事件段长的中位数，下限 5；总轮数 < M=100 或样本 < 3 时进入「样本不足」状态，用下限。
5. 段数超过 `N` 时，按「话题连贯 0.6 + 情绪弧连续 0.4」合并最像的相邻两段，不让模型自由裁量（Q6）。

### 4.4 整合（Q2/Q24/Q54）

`completeTurn` 记一次轮次与 token；累计 ≥ `triggerTokens` 时后台启动整合。后台循环还会处理空闲 ≥ 5 分钟的会话。

一次整合：

1. 取未整合的 L0，按 turn 聚成单元，切段。
2. 每段 **一次调用**：抽事实（≤8 条）、标题、摘要、情绪、印象、日记。
3. **第二次调用**：对每条候选与 Top-5 相邻记忆做「duplicate / update / contradicts / unrelated + salience + ttl」判断。
4. 写入：重复 → 提升旧条目 S；更新 → 改写文本并提升 S；矛盾 → 新建并 `SUPERSEDES` 旧条目；用户显式纠错（「不对」「记错了」…）→ 旧条目标 `disputed`、权重 0.3（Q34）。
5. 指令性文本（`looksInstructional`）不进常规事实，写进 `preferences` 隔离区（Q44）。
6. `id` 保持不变（Q24）；TTL 相对短语在此刻换成绝对时间（Q10）。

模型不可用、超时、JSON 解析失败 → 规则抽取 + 规则判断，并把失败送进死信（`jobs`），按 `retries` 重试、按 `dlqItems`/`dlqDays` 报告溢出（Q38）。**规则模式不计入 `degraded`**：只有「配置了模型但没答上来」才算降级。

### 4.5 渲染与预算（Q29/Q33/Q65）

- 软目标 2000 token，硬上限 3000；条目上限 20。
- 事实层拿 `1 − 0.25` 的预算，主观层独立 25%。
- 顺序：事实 → 事件 → 印象 → 日记 → 自我叙事 → 长期偏好 → 原文片段。主观层最后，紧挨对话。事件行尾从 v0.2.9 起附带语气标注（Q64，`retrieval.toneHint`）。
- 事实是表格行（`- ⚠[10-20 · 事实] …`），主观层是自然语言（Q33 的混合格式）。
- 硬上限之外再用 `clip` 兜底，防止单条超长文本撑破。
- 协议 section 与两个内容贡献都设 `interpolate: false`。

### 4.6 权限（Q15–Q21）

人设写权限按**来源**判定，不按区作者的偏好：

| 来源 | 允许 |
|---|---|
| `master`（工具调用） | 任何未锁定区；锁定区需 `confirmUnlock`；可写自己的覆盖层 |
| `ai`（整合过程） | 只写 `editableBy: 'ai' \| 'both'` 且未锁定的区，且必须带 L0 证据 |

锁定单向：锁定无摩擦，解锁必须二次确认。每次修改都进 `persona_history` 与 `audit`。

角色：主人一人；朋友由认领 + 主人审核产生；其余为路人。路人 3 次互动转「暂时朋友」，5 天不聊回落（Q19）；路人 L0 保留 48 小时，事实保留但权重降到 ≤0.4（Q20）。主人跨用户查询只走 L1/L2，且只返回 `evidence.public === true` 的路人事实（Q21）。

表里的 `○` 项，以及 `◐` 项里尚未补齐的部分，不在这张表里展开，统一汇总在 **§13 未解决问题清单**（含原因、代价、若要做的切入点）。

## 6. 三个冲突的处理

**冲突 A：L0 保留期限（Q28 vs Q59）** — 用户决定不清理。实现上 L0 只有三种删除路径：路人 48 小时、删除冷静期到期、用户显式 `permanent`。没有任何「按时间分层清理」的代码。因此 L0 是系统内的唯一完整副本，备份责任按 Q59 在用户侧。

**冲突 B：Q66 裁决机制** — 已询问并确认「规则 + 检测」：协议里写死「当前对话永远优先」；检索时做一次确定性冲突检测（词面重叠 + 否定/数字不一致），命中标「可能已过时」并乘 0.85。没有额外模型调用。

**冲突 C：Q12「检索纯读」** — 确认为离线异步：`recall` 只读，把命中的事实 id 交给 `onAccess` 缓冲；`maintain()` 每个维护周期批量写回稳定性与访问计数。

## 7. 与原始方案的偏差

### 7.1 不实现的部分

| 项 | 原因 | 若要做 |
|---|---|---|
| 相册（Q22） | 需要图像相似度与二进制存储，和当前"纯文本 SQLite"边界冲突 | 独立表 + 独立通道，不改现有 schema |
| 主观层动态配额（Q30/Q31） | 需要跨轮命中率状态机 | 在 sessions 表加 `recall_misses` |
| 对话历史去重（Q45） | 历史归宿主，插件看不到完整的请求拼装 | 依赖 `systemPrompt` 的装配上下文 |
| embedding（Q53） | 引入密钥、网络、模型版本管理 | 把 `retrieval` 的 similarity 换成向量，其余不变 |
| 评估集（Q39） | 没有真实对话语料 | 先积累 trace，再建离线评测【仍开放，§13.3】 |

### 7.2 实现方式不同

- **Q28 的 L1 软上界**：没有「活跃集/归档区」两张表，用 `weight` + `status` + 索引承担同样的效果。硬删只发生在用户请求。
- **Q2 的 48 小时兜底**：5 分钟空闲触发严格更早，因此没有单独的 48h 任务。

  原设计里 48h 兜底负责一种情况：会话一直有活动、累计 token 始终没到 `triggerTokens`，于是迟迟不整合，最多拖 48 小时。替代它的是 `sessionsDue()` 的第二个条件：`last_active_at <= now - idleMinutes * 60000`（`idleMinutes` 默认 5）。判定条件是

  ```
  EXISTS(未整合的 l0) AND (token_count >= triggerTokens OR 空闲 >= 5 分钟)
  ```

  即：**只要还有一条没整合的消息，会话停 5 分钟就到期**，跟累计了多少 token 无关。所以「拖到 48 小时」这个窗口在正常运行时不会出现——最坏延迟是 5 分钟 + 一个 tick 周期（`maintenanceIntervalSeconds` 默认 60 秒），即便宿主从不发消息也一样，因为 tick 是独立定时器。

  两个机制本来共用同一个 tick（`dueSessions()` → `consolidate()`），所以 48h 兜底能覆盖的场景 5 分钟空闲触发都覆盖，且严格更早；而进程关闭时两者都不跑，替换没有引入新的漏点。真正需要担心的不是时间窗，而是 `dailyLlmCalls` 用尽后整合被推迟到次日配额重置——这一点两种触发方式同样受制，已在 `report.degraded` 里体现。
- **Q38 的重试**：失败会写 `jobs` 死信并计数，但不会自动重跑同一段（下一轮整合会重新处理未标记的 L0）。这是有意的：自动重跑在模型侧故障时只会放大成本。
- **Q63 的日记权重**：→ **已定稿（v0.2.9）**，最终决定不加权。叙事证据仍然等于事件条数；日记不去争这个系数，改为每天导出一个 Markdown 文件到数据库旁的 `diary/` 目录，让人能直接读到它。理由与实现见 §13.1。

## 9. 钩子索引层（v0.2.0 新增）

### 9.1 问题

记忆块是渲染出来的摘要：`retrieval.maxItems=20`、事件最多 4 段，超限静默丢弃（`SECTION.more` 从未被引用）。长对话的完整叙事——用户当时的犹豫、助手当时的分析——在库里（`l0`），在 prompt 里却只有一个标题和一个摘要，且**没有任何读取入口**。

> 【v0.2.0 已解决】「没有读取入口」这一半由 §9.3 的钩子索引修掉：正文可按编号取回，且 `memory_search` 有一条不受钩子数限制的 FTS5 通道。
> 未解决的只剩前半句：**记忆块自身仍然超限即丢弃**，`SECTION.more` 这句「还有 {n} 条更早的记忆」至今没被渲染过——它是死常量，不是兜底。见 §13.5。

### 9.2 关键观察

正文存储与"打包"动作在 0.1.x 已经免费完成：`recordMessage` 每轮同步写 `l0`，事件落库时 `events.l0_from/l0_to` 就是指向正文范围的指针。缺的不是架构，是一个读者。所以索引层的全部成本是读取逻辑 + 三张自建表，零模型调用。

### 9.3 机制

- **自建三张表**：`loom_docs`（整理版正文）、`loom_links`（钩子→整理版）、`loom_hooks`（驻留快照）。启动时 `CREATE TABLE IF NOT EXISTS`，老库直接可用，卸载插件后自建表留在库里不碍事。
- **驻留快照**：候选（事件 + 显著度过滤后的事实 + 整理版 + `T` 尾巴）打分排序，受 `index.hooksBudgetTokens` 与 `index.maxHooks` 双重约束，低于 `index.minHookScore` 不占位，同名近重复折叠。落盘后渲染只读快照，轮次间逐字一致——防人格漂移是显式设计目标（Q：注入内容每轮重排是漂移根因，见 §5 讨论）。
- **淘汰而非压缩**：被挤出的钩子进冷区 `index.coldDays`；正文永不被压缩或删除。
- **`T` 尾巴**：`consolidated = 0` 的未整理区间没有事件，若不兜住，最近最多 20000 token 的对话对索引隐形。它是滚动窗口，因此 `memory_pack` 拒绝挂载 `T`，改生成独立 `D`。
- **取回**：`memory_expand` 顺 `events.l0_from/l0_to` / `facts.source_ids` / `loom_links` 取正文，超出 `index.expandBudgetTokens` 自动分页并给续读指令。
- **遗忘级联**：`refAlive` 在取回前校验挂钩存活性；重建时删除不再有候选的钩子行（erase/forget 后不留死钩）；`memory_index gc` 显式清理孤儿整理版，不自动删。
- **身份**：索引与引擎共用 `identityOf`（未知会话回落 master），与人设/记忆块行为一致。

### 9.4 与伴生插件方案的取舍

0.2.0 之前曾以独立伴生插件（`dsh-memory-loom-index`）实现，打开同一个 WAL 库。合并进主插件后：`apply` 恢复同步（消除了 async 装载路径）、工具直接复用 `textTool` 工厂、`identityOf` 语义与引擎一致、少一个连接与一份配置。**独立包已废弃。**

### 9.5 测试

- `test/selftest.mjs`：30 项（v0.2.9 起；此前 29 项），用从 bundle 提取的上游真实 schema 建库。
- 端到端（仓库外脚手架）：真实 bundle + 真实 `defineTool`/`Config`，79 项断言——工作类 15、极限类 17、工具闭环 22、单元 29（部分重叠计数）。测试中发现并修复：未整合尾巴隐形（→`T`）、近重复挤占预算（→同名折叠）、`T` 挂固定正文变死链（→拒绝挂载）、erase 后死钩滞留（→重建清理）。

### 9.6 上限在哪（v0.2.3 记录，暂未调整）

分三层看，只有第二层是真正会撞到的墙：

| 层 | 上限 | 现实约束 |
|---|---|---|
| 编号空间 | `E`/`F`/`D` 取自 SQLite `INTEGER PRIMARY KEY AUTOINCREMENT`，2⁶³−1；`parseRef` 走 `Number()`，可用到 2⁵³−1 ≈ 9.0×10¹⁵ | 按每天 100 条事件算，够用 2.4×10¹¹ 年。不是瓶颈 |
| 驻留钩子 | `index.maxHooks` 16 条 + `index.hooksBudgetTokens` 300 双约束，先到先停 | 实测满员约 59 token/轮，单条 label 被 `clip` 到 16–22 字 |
| 候选池 | 事件 `LIMIT 300`、事实 `LIMIT 150`（`pinned` 或 `salience ≥ 0.55`）、整理版 `LIMIT 60` | **最紧的一层**：合计 511 条封顶 |

候选池是硬截断，不是分页：一旦某个事件落到第 301 条以外，`rebuild` 根本不查它，`loom_hooks` 里也就没有行，`memory_index search` 同样搜不到。模型没有理由去 `memory_expand` 一个看不见的编号。【v0.2.3 的原始判断，v0.2.4 已修正——见下一段】

**但这不是永久失明。** 系统里还有第二条通道：`memory_search` 走 `events_fts` / 事实的 FTS5，不经过候选池，返回 `#E12` 这样的编号，随后 `memory_expand` 走 `body()` 按 id 精确查询，同样不依赖 `loom_hooks`。实测（400 事件库，候选池 300）：

```
E1 不在索引里（候选池外）          ✓ 符合预期
FTS5 仍能命中 E1                  ✓
memory_expand("E1") 读出 93 字正文  ✓
```

所以候选池之外的东西「不会被自然想起，但能被关键词搜到」。真正的盲区是**记不清关键词**：常驻钩子是唯一的"无提示回忆"入口，它只有 16 条。

### 9.7 上限的实测代价（v0.2.4）

| 项 | 数字 |
|---|---|
| 取回成本 vs 钩子数 | 0.040 ms（16 条）/ 0.037 ms（64 条）——**完全解耦** |
| 索引块每轮 | 16 条 124 token；24 条 175；32 条 224；64 条 422；128 条 818 |
| `rebuild`，候选池封顶 300 | 恒定约 118 ms（100/300/1000/3000 事件下都一样） |
| `rebuild`，去掉 events 上限 | 300 事件 121 ms；1000 事件 390 ms；**3000 事件 1248 ms** |

两条由此固定下来的判断：

1. **不扩 `maxHooks`。** 它是唯一会让"每一轮"变贵的东西。16→32 多 100 token/轮（100 轮 +10k，占 200k 的 5%，不显著但也换不来明确收益）；16→64 多 298 token/轮（+15%，开始显著）。而第 17 条以后的候选本来就是按分数排下来的次优项，扩了主要是稀释注意力、扩大漂移面。
2. **不扩候选池。** `rebuild` 是同步调用，1.25 秒会直接卡住事件循环；而候选池扩到 3000 条，能进 prompt 的还是 16 条，收益被上限吃掉。300 这个封顶的正面作用是让 `rebuild` 成本与库龄脱钩——这正是它该做的事。

剩下真正值得做的小改动只有一个：`memory_search` 原本返回 `(#1234)`，而 `memory_expand` 要 `E1234` / `F1234`，两个 id 空间独立自增、同号会撞。v0.2.4 已改为直接返回 `#E12` / `#F7`，取回入口不再需要猜前缀。

同名折叠也会进一步压低实际驻留数：41 段事件里 31 段标题近似的情况，折叠后只剩少数几条占位。这既是防挤占的手段，也意味着「16」是上限而非配额。

仍留在桌面上的方向（未实施）：

1. **分层驻留**：固定 8 条常驻（人设、长期事实）+ 8 条按当前话题从候选池临时补位。常驻部分逐字稳定，临时部分随轮次变化——这是唯一能在不增加每轮成本的前提下提高覆盖的办法，但会动摇「驻留集逐字一致」这条不变量，需要重新设计验证。
2. **`memory_index search` 升级**：现在是 `label LIKE '%q%'`，换 FTS5 可复用同一套 CJK 二元分词并按相关性排序，成本只在调用那一次，不进每轮。
3. **label 结构化**：现在是 `clip(title, 16)`，把时间、参与者、话题拆成字段，同一条 label 的信息密度更高，折叠的误伤也减少。

原先列在这里的「候选池改分页查询」已被 9.7 的实测否掉：收益被 16 条上限吃掉，代价是 `rebuild` 1.25 秒的同步阻塞。

## 10. L0 存储策略（v0.2.1）

### 10.1 原先的问题

捕获层写死 `clip(redactSecrets(text), 8000)`。超过 8000 字的部分被静默丢弃：不报错、不标记、不可配置。贴一段长日志或一个大文件，索引层再准也取不回被扔掉的尾巴——而用户并不知道它被扔了。

实测还发现这笔「节省」并不划算：脱敏在截断之前执行，正则是流式的，8k 与 512k 输入的处理耗时都在 70–86 ms 区间。**截断省下的不是 CPU，只是磁盘，代价是数据。**

> 【v0.2.1 已修复】默认改为整条落库，`l0.maxCharsPerMessage` 只在显式配置时生效，截断会写明原因。见 §10.2。

### 10.2 现在的行为

- `l0.maxCharsPerMessage`，默认 `0` = 整条落库。
- 设了上限时，`storeText` 在脱敏之后截断，并把 `…[已截断：原消息 N 字，仅保留前 M 字。要留存全文请调大 l0.maxCharsPerMessage，或分段发送]` 拼在正文末尾。理由：静默截断会让模型把半截报错当完整报错推理，比直接丢更危险。
- 脱敏先于截断，所以密钥不会因为落在截断点之后而逃过检测。

### 10.3 顺手去掉的浪费

`l0.tokens` 从来没有读取方：`l0From` 不映射它，FTS 虚表只建在 `facts` / `events` / `preferences` 上。但每条 L0 都存一份分词串，体积是正文的 1.6 倍，还要多跑一次全文分词。现在超过 8000 字的行写空串（`l0TokensOf`），短行保持原样。

放开上限后的体积实测：10 条 1.2 万字消息，库 400 KB，约为正文 UTF-8 体积的 1.14 倍。

### 10.4 踩到的坑

`toEngineConfig` 是白名单式转换，新增的配置组必须显式加进去，否则 `engine.config.l0` 是 `undefined`，`recordMessage` 抛 `TypeError`，再被事件层 `catch` 吞掉——**L0 一行都不写，也没有任何日志**。`recordMessage` 里改为 `this.config.l0?.maxCharsPerMessage ?? 0`，让引擎脱离完整 config 单独构造时也退回安全默认值（不截断）。

## 11. 分页切片的估算修正与预算标定（v0.2.2 / v0.2.3）

### 11.1 问题

`sliceByTokens` 用固定 `budget / 0.65` 猜一页能装多少字符。0.65 是中文的 token/字 换算率（最坏情况），而收缩循环只会往下调、不会往上补。于是英文日志与代码（约 0.26 token/字）每页只用到预算的 **38%**：2600 token 的预算，实际只返回 4000 字、约 1000 token。

后果落在最需要它的地方——工作类对话（贴报错、贴代码）的正文页数凭空翻倍，`memory_expand` 的往返次数也跟着翻倍。【v0.2.2 已修复，见 §11.2】

### 11.2 改法

先取正文前 2000 字采样，算出**这段文本自己**的 token/字 比率（下限 0.25），再用它推算一页的字符数；收缩循环保留，兜住采样偏差与混合文本。

### 11.3 效果（5 万字正文，v0.2.2 时的 2600 预算）

| 正文 | 修复前 | 修复后 |
|---|---|---|
| 英文日志（12500 token） | 14 页，每页仅 1000 token | **5 页，每页 2600 token** |
| 中文叙事（29845 token） | 14 页 | **12 页** |

中文场景变化小（本来就在 0.65 附近），说明修正只吃掉了浪费，没有改变中文的既有行为。

### 11.4 单页预算定为 4000（v0.2.3）

`expandBudgetTokens` 的默认值从 2600 提到 4000。四档实测（5 万字正文，累积输入含分页重发）：

| 正文 | 2600 | 4000 | 8000 | 12000 |
|---|---|---|---|---|
| 中文叙事 29845 token | 12 页 / 189.6k | **8 页 / 128.3k** | 4 页 / 71.8k | 3 页 / 53.8k |
| 英文日志 12500 token | 5 页 / 37.3k | **4 页 / 26.5k** | 2 页 / 17.1k | 2 页 / 13.1k |

取 4000 的理由：相对 2600 往返减三分之一、总消耗降到 68%；再往上边际收益递减（8000 只再减一半页数，12000 对英文已无差别），但单页占用的上下文翻倍，正在使用的材料更容易被挤出去。剩下的大头是分页重发的平方成本，改预算只能缓解，根治得靠「按需定位」而不是整篇顺序读——留作扩展点。

### 11.5 顺带确认的成本结构

`memory_expand` 的本地开销（SQL + 切片 + 估算）实测 4–18 ms，可忽略。真正的成本是往返次数：每页都是一次完整的模型请求，且第 k 页要把前 k−1 页重新发一遍，所以计费总量随页数**平方**增长。这让"少一页"比"小一页"值钱得多。

## 12. 逐行审计发现的问题（v0.2.7）

这一版没有新功能，只有"文档承诺了、代码没做到"的修补。三类问题值得单独记下来，因为它们都不是靠读代码能一眼看出的，是靠探针跑出来的。

**§12.1–§12.3 三条都已修复**（0.2.7 内）；§12.4 把「修了的」和「明确不修的」分开了，不修的进 §13.5。

### 12.1 `consolidation.enabled` 是个摆设

schema 里有 `enabled: z.boolean().default(true)`，README 配置表也写着「是否启用自动整合」，但 `grep "\.enabled" lib/index.js` 在修复前**零命中**——整份代码没有一处读它。原因很典型：`toEngineConfig()` 把 `l0` / `decay` / `emotion` / `retrieval` 用 `{...spread}` 整体转发，而 `consolidation` 是**逐字段列举**的；新增字段时漏写，对象展开不会报错，运行时也只会表现为"配置没生效"。

这和 v0.2.1 那次 `l0` 白名单漏转发是同一类错误，只是那次漏的是整组、这次漏的是组内一个字段。

修法：`toEngineConfig` 补 `enabled`，`tick()` 里只跳过整合那一段（`maintain()`、索引重建、`T` 尾巴都不受影响），`apply()` 时打一条 info 日志说明已关闭。实测：`enabled=false` 后事件数从 3 降到 0。

**结论**：凡是"逐字段列举"的转发，都要有一个探针把所有叶子键比对一遍，不能靠 review。

### 12.2 分页会劈开代理对

`sliceByTokens` 用 `text.slice(0, take)` 按 UTF-16 码元切，而 `estimateTokens` 是按**码点**遍历的（`for...of`）。两者混用时，`take` 落在代理对中间就会切出半个 emoji：返回给模型的是 `�`，下一页从一个孤立的低代理开始，同样坏。

中文场景下几乎不会暴露——汉字都在 BMP 内，一个码元一个字符。但只要正文里有 emoji（聊天记录里非常常见），每页边界都可能坏一个字符。

修法：新增 `safeCut()`，切点落在高代理之后时退一格；初始 `take` 与收缩循环都过这个函数。实测（31 个汉字 + 200 个 emoji，budget 13）：修复前 10 页里 8 页以孤立高代理结尾，修复后 0 页。

### 12.3 `memory_pack` 能挂到不存在的编号

`pack()` 只做 `parseRef` 语法解析，不校验编号是否真的存在。传 `ref="E9999"` 会建一条指向 `E9999` 的 `loom_links` 行，回执说「已挂到 E9999」；之后 `memory_expand("E9999")` 走的是"链接存在但源已死"分支，返回「E9999 已被删除」。对模型来说这是个成功回执加一个"被删了"的结论——它会以为自己存住了，实际这份正文永远取不回来。

修法：`pack()` 先用 `refAlive()` 校验，不存在就不建链接，返回 `missingRef`，工具回执如实说明「索引里没有 E9999（编号记错了），所以没有挂上去；正文仍然可用 memory_expand(ref="D{id}") 取回」。正文本身照存不误——它还会作为独立的 `D` 候选进索引，所以信息不丢，只是不挂在错的地方。

### 12.4 顺带修的与没修的

修了的：`sliceByTokens` 负 offset 的 `done` 计算（导出的 API，工具层自己夹紧了所以一直没暴露）；`memory_expand` 工具描述里写死的「4000 token」改成按配置生成；`migrate()` 两个分支完全相同（死代码），合并成一条且只向前打版本号。

**为别人的电脑**加的容错：`PRAGMA journal_mode = WAL` 需要共享内存支持，网络盘、部分 FUSE 挂载、某些企业漫游家目录会拒绝。原来这一抛就发生在 `apply()` 里，整个 profile 起不来。现在捕获后降级到 `DELETE` 日志模式——慢一点，但记忆不丢。

没修的，明确留作已知边界：`body()` 的 `refAlive` 与链接查询不带 `identity_id` 过滤（`events.id` / `facts.id` 全局自增，跨身份撞号时可能读到别人的存活状态，但不返回别人的正文）；`memory_pack` 反复覆盖同一编号时旧 `loom_docs` 会变成无链接孤儿，靠 `memory_index gc` 或候选项 `LIMIT 60` 自然淘汰；`render()` 的 token 统计按行求和，比实际拼接后少算换行符的 0.25 token/个（实测满员 188/300，余量足够）。

### 13.1 Q63：日记没有计入叙事证据

> **→ 已定稿（v0.2.9）：不加权。** 日记不按 0.3 计入叙事证据，也不参与任何排序或配额竞争。理由不是「加了会坏」，而是「加了没用」：0.3 是拍出来的系数，而它只挪动叙事重写的时点，不改变叙事内容（见下面「一个容易误会的点」）。评审时真正的问题其实是「那用户怎么看到日记」，这一点用**导出**解决，而不是用权重：每天一个 `diary/YYYY-MM-DD.md`，落在数据库所在目录下的相对路径（`diary.mirrorDir`，默认 `diary/`），`memory_profile` 打印该目录作为入口，`diary.mirror: false` 可关。同时删掉了 `diary.weight`（写的是 `emotion.salience`，下游无人读）与 `mood`（永远写空串）两个空转列——老库里这两列会留着，因为有默认值，插入不再写它们，读写都正常，无需迁移。实现见 `lib/index.js` 的 `diaryMirrorRoot` / `renderDiaryDay` / `MemoryEngine.syncDiary`，验证见 `loom-e2e/scenario-diary.mjs`（17 项）。

**决策原意**：自我叙事的重写由一个「证据量」触发，阈值 `consolidation.narrativeEvidence = 12`。原决策里证据是加权的——一个事件算 1，一条日记算 0.3。理由是日记属于助手自己的感受，是轻量素材，比一段被观察到的事件弱。

**现状**（`//#region src/engine/consolidate.ts` 里的 `narrativeEvidence`）：

```js
function narrativeEvidence(store) {
  const row = store.db.prepare("SELECT COUNT(*) AS n FROM events").get();
  return typeof row.n === "number" ? row.n : 0;
}
```

只数 `events`，日记一条都不算。触发条件在同一个 region 里（`consolidate`）：

```js
extraction.fromModel
  && evidence >= narrativeEvidence
  && (current === void 0 || evidence - current.evidenceCount >= narrativeEvidence)
```

三个门槛缺一不可：证据够 12、距上一版又攒够 12、且这次抽取来自模型（规则模式永不重写叙事）。

**一个容易误会的点**：证据只决定「什么时候写」，不决定「写什么」。`reviseNarrative()` 的 prompt 里只有「top-12 事实 + 关系印象 + 上一版叙事」，事件与日记都不进 prompt。所以就算把日记按 0.3 计入，叙事正文也不会因此多出日记内容——差别纯粹是**触发时点提前**。

**量级**：`diaryPerDay` 上限 3；若事件与日记大致 1:1，加权后证据涨速 +30%，叙事从「每 12 个事件一版」变成「约每 9.2 个事件 + 3.7 条日记一版」。每次重写 = 1 次模型调用，且只在 `extraction.fromModel` 时发生。

**为什么不修**：0.3 是拍出来的系数，没有数据支撑；而它只挪动触发点。真实语料出现前，改了也无法判断是变好还是变坏——属于「改动无成本、验证无手段」。

**真要改**是两行，但有个前提要一起处理：`narrative.evidence_count` 声明为 `INTEGER`。SQLite 是动态类型，9.3 会原样存进去（只有能无损转整数的 REAL 才被转），所以**技术上不阻塞**；但字段语义会从「条数」变成「加权分」，`index.d.ts` 与本节的措辞要同步改，否则下一个人会把它当整数用。

### 13.2 Q64：语气分离注入做了，离线评估没做

> **→ 已收口（v0.2.9）：范围缩小为「读记忆时看得见当时的语气」。** 用户的实际要求只有一条——AI 读记忆时要能注意到当时说话是什么口气，不是什么重要问题。所以既不做「语气分离注入」这条独立通道，也不做离线评估，改为：用整合时**已经存下的** `valence`/`arousal`，折成一句短标注附在事件行尾（`（语气偏冲）` / `（语气愉快）` / `（语气急切）` / `（语气低落）`），只在情绪不中性时出现；记忆块和 `memory_search` 都带，`retrieval.toneHint: false` 可关。实测两条情绪事件让记忆块从 59 → 65 token（每条约 +3），中性事件 0 成本，不额外调模型、不影响排序。下面「已做的部分」里人设卡独立 section 按 Q65 保留——它解决的是「不跟事实抢预算」，与语气无关；那一段原本被当成 Q64 的成果，其实归 Q65。验证见 `loom-e2e/scenario-diary.mjs`。

**已做的部分（分离注入）**：人设卡是独立 `section`，`order: 10`，`interpolate: false`，排在协议（930）与记忆块（900）之前，内容是 `identity / voice / values / boundaries / relationship` 五区拼成的常量块。分离的意义在于：语气要求如果混进记忆块，每轮都要跟事实抢 2000 token 预算，而且随召回结果变化——那正是漂移的来源。

**没做的部分（离线评估）**：原本要有一组离线指标，回答两个问题——分离注入是否真的让语气更稳？记忆注入有没有反过来污染语气？三层原因：

1. **没有语料。** 与 Q39 同一个卡点，只能拿自造场景代替。
2. **需要 judge。** 要么人评，要么模型评；模型评与「离线、无密钥」的定位直接冲突，判定本身也不稳定。
3. **边界不在插件里。** 插件只能决定「往 prompt 里放什么」；「模型有没有照做」是模型属性。端到端 A/B 必须在宿主侧跑，插件内无法闭环。

**现在的证据强度**：能证明「东西放进去了、位置对、轮次间逐字稳定」（selftest 与 e2e 断言了 order 10/895/900/930、`interpolate: false`、驻留快照跨轮逐字相同）；**不能**证明「语气变好了」。所以 README 里不存在任何关于语气质量的量化声称——这是有意留白，不是漏写。

**附带发现**：`defaultZones()` 只提供中文预设。`locale: 'en'` 时记忆块标题是英文，人设卡仍是中文。可修，见 §13.5。

### 13.3 Q39：评估集与指标

没有真实对话语料，当前用 `loom-e2e/` 里的自建场景与探针替代（清单见 `loom-e2e/REPORT.md`）。要分清它衡量的是什么：**它衡量机制正确性（指针没断、分页无损、注入位置对、删除会级联），不衡量记忆质量**（该记的记了没、该忘的忘没、注入是多了还是少了）。

至少缺四个指标：召回命中率、误注入率、冲突误判率、每轮注入 token 的边际收益。前三个都需要带标注的真实对话，第三个还要人工判定「这句话到底推翻了哪条旧事实」。

| 缺陷 | 影响 | 为什么不修 |

| 候选池 511 条硬顶 | 更早的事不会被「自然想起」，但仍可 `memory_search` 命中 | 见 §9.7：扩池会带来 1.25 秒同步阻塞，收益被 16 条上限吃掉 |

## 14. 宿主装配与生命周期（v0.2.12 实测）

### 14.1 原假设是错的

设计时默认「插件在宿主启动时组合进上下文」，于是 README 写了「装完重启 DSH，不重启不会出现」。这句话**从未被验证**，只是照着「重启才生效」的常识写的，然后被反复抄进后续版本。

### 14.2 实测：DSH 是即时重组

真机上的一次安装（`dsh plugin --profile desktop add ...tgz`）留下了三行时间戳：

| 事实 | 时刻 |
| --- | --- |
| 宿主主进程启动 | 19:58:15 |
| `dsh plugin add` 返回，profile 的 `package.json` 被 pnpm 改写 | 20:05:09 |
| `loom.db` 被创建（`apply()` 执行） | 20:05:11 |

所有宿主主进程的 `StartTime` 至今仍是 19:58:15，会话 id 也没变。所以建库的是那个六分钟前就启动的进程。

机制是**即时重组（live reconcile）**：pnpm 装完 → 把包名追加进 profile 的 `dsh.profile.bundles` → 读包内 `cordis.patch.yml` → 激活该层并调用 `apply()` → 把新的工具 schema 推给正在运行的会话（表现为一条 `### Updated Tool Schemas` 注入）。全程不需要重启，也不需要新开会话。

> **边界（2026-11-02 补，见 §27）：这一段只对「首次安装」成立。**
>
> 上面的时间线是往一个**还没有这个插件**的 profile 里装，宿主看到 `bundles` 列表多了一项，于是重组。**同名的 bundle 原地升级不会触发重组**——列表长短没变，`apply()` 不会被再调一次，旧模块还在进程里。实测装到 0.2.23、实际跑的是 0.2.12：工具 9 个、`memory_doctor` unknown、`user_version` 仍是 1。
>
> 所以「全程不需要重启」这句话的主语是「安装」，不是「升级」。升级必须重启宿主进程。

结论：**插件不是「开机装配的部件」，而是「可以中途插进来的层」**。这改变了 `apply()` 的契约。

### 14.3 由此暴露的缺口：按会话的三块会漏挂

插件向 prompt 注入的内容分两类：

| 内容 | 注册方式 | 依赖 `agent/created` |
| --- | --- | --- |
| 记忆使用约定、索引约定 | `ctx.systemPrompt.section`（全局） | 否 |
| 人设卡 | `agent.ctx.systemPrompt.section` | **是** |
| 钩子索引块 | `agent.ctx.systemPrompt.context` | **是** |
| 记忆块 | `agent.ctx.systemPrompt.context` | **是** |

热加载时当前会话的 agent **早就存在**，`agent/created` 不会再来一次，于是后三块一块都挂不上。而装机时最容易确认的两样——9 个工具、两个全局协议块——恰好都不依赖这个事件，所以看上去「一切正常」。

后果不是崩溃，而是**静默降级**：工具能调，但当前会话的系统提示里没有记忆块，模型得先主动想起去搜才知道有记忆。

用 `loom-e2e/probe-hotload.mjs` 固定这个差异（构造一个 fake ctx，agent 先存在、插件后 `apply`）：

```
修复前  protocol ✓  index-protocol ✓  persona ✗  hooks ✗  memory ✗  工具 ✓
修复后  protocol ✓  index-protocol ✓  persona ✓  hooks ✓  memory ✓  工具 ✓
```

### 14.4 修法与它对设计的约束

三处改动，全部只影响「中途装载」这一条路径：

1. `apply()` 末尾从宿主的 `agents` 服务（`ctx.get("agents", false)` → `AgentRegistry.list()`）取出当前所有 live agent，逐个 `attachAgent`。`attachAgent` 自带幂等保护（`agentDisposers.has(sessionId)` 直接返回），重复调用安全。
2. `turn-stopping` 里补一次 `attachAgent`，用于宿主不暴露 `agents` 服务（或 `list()` 不可用）的情况——下一轮生效，好过永远不生效。
3. 新增 `ctx.effect("memory-loom:agents")`：卸载（含热重组）时撤销全部按会话的 section。缺了这条，反复重组会在同一个 agent 上叠同名 section。

由此得到两条以后必须遵守的约束：

- **`apply()` 必须可重入。** 任何「只在启动时跑一次」的假设，在热加载下都会漏掉当前会话。目前 `apply()` 里的初始化动作（建目录、`CREATE TABLE IF NOT EXISTS`、`ensureMaster`、`seedPersona`、`syncDiary`）全部幂等，所以重复 `apply` 只会在同一路径上多跑一遍，不会破坏数据。
- **按会话申请的资源必须能在「会话已存在」之后补挂，并且必须在 fiber 销毁时撤销。** 只挂事件、不查存量，是这类插件最容易漏的一环。

### 14.5 没变的部分

整合（写事件、写日记）仍然要等单会话 2 万 token 或空闲 5 分钟才触发。热加载只负责挂载工具与 prompt 块，不负责「立刻开始记忆」。装完立刻问「你记得什么」得到空答案，是预期行为，不是故障。

## 15. prompt 块求值失败的处理（v0.2.13）

### 15.1 宿主不兜底

`@deepseek-ai/dsh-system-prompt` 的 `assemble()` 是这么取文本的（本机 `app.asar` 实际实现）：

```js
sections: sectionDefinitions.map((section) => ({
  name: section.name,
  text: typeof section.text === "function" ? section.text(context) : section.text,
})),
contexts: [...contextByName.values()].map((entry) => resolveContext(entry, context)),
```

`resolveContext()` 同样是 `entry.text(context)` 裸调用。整个模块没有 try/catch。

`required: true` 的语义被误解过：它**只**决定「运行期上下文被抑制时是否保留」，与异常无关（`refreshContext()` 与 `assemble()` 里都只做 `entry.required === true` 的过滤判断）。

异常向上传播的路径：

```
preStep()            await this.loopCtx.systemPrompt.assemble(...)
turn() 外层 catch    turnEnds = { kind: "error", ... }; this.throwError(error)
driver kick()        while (await this.turn()) 包在 try/catch(_error) 里 → 进程不倒，但本轮 error
下一次组装            同一处再抛一次
```

结论：**不是崩溃，是每一轮都失败**，直到库恢复。这对「鱼」是致命的——用户看到的是每发一句就报错。

### 15.2 会抛的三块

| 块 | 注册 | 失败面 |
| --- | --- | --- |
| `memory-loom:persona` | `systemPrompt.section` | `engine.personaFor()` 读库 |
| `memory-loom:hooks` | `systemPrompt.context` | 每轮 `prepare()` + 可能 `rebuild()` + `render()` |
| `memory-loom:memory` | `systemPrompt.context` | `engine.recallFor()` 读库并渲染 |

三块共用同一个连接，所以「库不可用」这一种原因就会同时打穿三块。

### 15.3 修法：降级为空块

```js
const guardPrompt = (label, fn) => () => {
  try { return fn(); } catch (error) {
    // 同一 label 60 秒内只告警一次，避免每步刷日志
    return "";
  }
};
```

返回 `""` 而不是一个占位文案，是因为宿主两侧都会过滤空串：

- `renderPrompt()` → `filter((text) => text.length > 0)`
- `renderContextSections()` → `filter((section) => section.text.length > 0)`

所以空块既不会留下空标题，也不会在上下文里多出分隔符。代价是这一轮真的没有记忆；收益是对话继续。

### 15.4 固定它的探针

`loom-e2e/probe-prompt-guard.mjs`：正常时三块都不抛；`ctx.effect` 全部撤销（引擎关闭，等效于库被删/损坏）后三块都必须返回空串。

```
修复前  persona ✗  hooks ✗  memory ✗   （3/3 抛错）
修复后  persona ✓  hooks ✓  memory ✓   （3/3 降级为空块）
```

`required: true` 保持不变——它管的是上下文抑制，不是异常。

## 16. 失忆要让人看见：状态行与 memory_doctor（v0.2.14）

### 16.1 v0.2.13 留下的洞

降级成空串解决了"每轮都失败"，但制造了更难发现的状态：模型的记忆块没了，回答的自信程度一点没变。design.md §14.3 把这种现象叫**静默降级**——工具都在、协议块都在，鱼看起来正常，其实失忆了。所以降级必须能被感知，否则等于把故障从"吵"改成"哑"。

### 16.2 为什么由记忆块负责喊

`sections` 先于 `contexts` 求值（`assemble()` 里两个 map 分别 map，再拼），三块里 `persona` 是 section、`hooks` 与 `memory` 是 context。要让"哪块失败"汇总成一句话，只能挑一个每轮必定被求值、且最后求值的位置——`memory` 块（`memoryOrder` 最大）。于是：

- 三块的失败计数都写进同一份 per-session 注册表 `promptHealth`；
- 只有 `memory` 块输出状态行，内容是**所有**连续失败 ≥3 的块；
- `memory` 自己失败时返回状态行本身；`memory` 正常但别的块失败时，状态行**追加**在正常记忆之后（不吞掉记忆内容）；
- 任一 label 成功即 `delete state[label]`，计数清零，恢复后状态行自动消失。

前两次失败刻意静默：单次抖动（一次锁等待、一次瞬时 IO 错）不该在 prompt 里留痕。

### 16.3 状态行的代价

降级期间每轮多约 90 token（中文），并且**追加在预算之外**——`recallFor()` 已经按 `retrieval.budgetTokens` 裁过，状态行是后贴上去的。硬上限 3000 的会话在降级期间会轻微越界。这是有意的取舍：宁可多 90 token，也不要模型在失忆时照常编。

### 16.4 memory_doctor 的设计约束

| 约束 | 原因 |
| --- | --- |
| 每个探测独立 try/catch | 库彻底打不开时，报告本身必须还能产出；否则工具层再抛一次，用户拿到的是错误而不是原因 |
| 不用 `actorOf()` | 它内部调 `engine.identityOf()`，会读库——正是坏掉的那条路径。改用 `sessionOf(exec)` 只取 id |
| 只读 | 诊断工具不该改动状态。修库是人的决定（备份、重建、清进程） |
| 时间格式有兜底 | `engine.timezoneOf()` 在引擎关闭后也抛，`when()` 退回本机时区格式化 |
| 报告分 ✓ / ✗ / · 三档 | `·` 是信息（WAL 不存在、暂无召回记录），不参与"发现 N 处问题"计数，避免把正常状态报成故障 |

### 16.5 固定的行为

`loom-e2e/probe-degrade-notice.mjs`：

```
✓ 健康时不出状态行
✓ memory_doctor 已注册（第 10 个工具）
✓ 健康时自检报「未发现故障」
✓ 前两次失败保持静默
✓ 第三次失败插入状态行
✓ 状态行要求别硬编 + 指向自检
✓ 状态行只出现一次（persona/hooks 仍为空）
✓ 坏库时自检不抛错且定位到连接
```

未覆盖：库恢复后的计数清零（`notePromptSuccess()`）只做了代码核对，没有构造"失败 3 次后恢复"的故障注入——fake ctx 一旦 dispose 引擎就不可逆。

### 16.6 会话销毁时的清理（终检补）

`promptHealth` 是 per-session 的，必须跟会话同寿命。`agent/disposed` 原本清了 `agentDisposers` 与 `turns`，新加的这张表漏了，补 `promptHealth.delete(sessionId)`。凡是 per-session 的 Map，都要在同一个 disposed 钩子里成对出现——这是本插件新增 per-session 状态时的检查项。

## 17. v0.2.15：三处「以为有、其实没有」

这一版是对照一篇外部记忆架构文章自查后做的，外加写探针时撞见的两个真缺陷。共同点是：文档里写着有，代码里也在跑，但**产物是空的，且不报错**。

### 17.1 偏好为什么召回不到（最严重）

`compileMatch()` 生成的是 `tokensOf(query)` 用空格连起来的 FTS5 表达式。分词是 **bigram**（相邻两字），空格分隔的多个 phrase 在 FTS5 里是**隐式 AND**。

实测（`probe-preference-resident.mjs` 的原始形态）：

```
偏好：我不吃香菜，点外卖一定要备注
查询 "香菜"            → 命中（1 个 bigram）
查询 "我不吃香菜"      → 命中（3 个 bigram 全中）
查询 "记得我不吃香菜吗" → 不命中（7 个 bigram，只中 4 个）
查询 "今天天气不错"    → 不命中
```

不命中时 `subjective` 里没有偏好，`blocks` 为空，`renderMemoryBlock` 返回 `copy.cold`（空串）。结果是：**那一轮模型看到的记忆块是空的**，不是「记忆少一点」，是整块消失。

这不是偏好独有的问题，facts / events 走同一套 match。它们之所以还能出来，是因为另有兜底：`pinnedFacts()` 无条件加入、`recentFacts(8)` / `recentEvents(3)` 在 FTS 无命中时补位。**偏好没有任何兜底路径**，所以只有它彻底消失。

修法两条，都保留可关闭的开关：

1. `recentPreferences(identityId, limit)` + `retrieval.residentPreferences`（默认 3）：最近 N 条偏好每轮都进 `subjective`，不依赖 query。语义上这本来就是「长期偏好区」该有的行为。
2. `compileLooseMatch()`：偏好命中的 match 改用 `OR` 连接，单个 bigram 重叠即算候选，bm25 负责把命中多的排前面。风险是常用二字组（`我不`、`今天`）带来弱命中，由 `minScore` 与排序兜底。

`residentPreferences = 0` 可回到旧行为，探针里固定了这一分支。

### 17.2 主观层的 cap 语义是错的

`appendSection(title, lines, cap)` 内部的判断是：

```js
if (used + blockUsed + cost > cap) break;   // used 是全局累加
```

但渲染主体传进去的是 `Math.floor(target * subjectiveShare)` —— 这是**块内配额**，不是绝对位置。事实区一多，`used` 就超过这个数值，于是：

- `chosen` 为空 → 该块整段不输出；
- 不打日志、不置 `degraded`、不报错；
- 配置里 `subjectiveShare = 0.25` 依然写着「主观层占四分之一」。

实测（`probe-diary-budget.mjs`，20 条长事实）：

```
修复前  事实区 8 条 → 印象 ✗  日记 ✗  偏好 ✓
修复后  事实区 8 条 → 印象 ✓  日记 ✓  偏好 ✓
```

偏好之所以「幸存」，是因为它不走 `appendSection`，走的是 `pushWhole(..., hard)`，用的是绝对上限。

修法：把起点补上（`subjectiveBase + share`），并给日记留 `retrieval.diaryShare`（默认 0.4）的保底，防止一条长印象把日记挤空——文章里把这类现象叫「共用预算导致另一块归零」，这里是它的变体。

### 17.3 快照：把「用户责任」变成「默认行为」

此前 README 把备份写成用户责任，实际上没人会做，而 `loom.db` 是单文件明文无副本。v0.2.15 起：

| 决策 | 原因 |
| --- | --- |
| 用 `VACUUM INTO` 而不是拷文件 | 拷贝 `loom.db` 会漏掉 WAL 里的写入；`VACUUM INTO` 通过活动连接生成一致副本，产物自包含 |
| 按 `everyHours` 而不是「每日首份」 | 每日首份会拍到刚开机那一刻的空数据；按间隔拍能覆盖当天的实际内容 |
| 内容为空时不拍 | 新装第一天会连拍 7 份空库，把名额占满 |
| 放在库同级 `backups/` | 同一个隐私边界内，不额外暴露路径；但**同盘**，所以挡不住硬盘故障——文档写明 |
| 失败只 warn | 快照失败不该影响对话，与 `guardPrompt` 的取舍一致 |

### 17.4 溯源标注

`facts` 表一直有 `source` 与 `confidence`，`factLine()` 却只用了 pinned / possiblyStale / 日期 / 类型。结果两种来源完全不同的事实渲染得一模一样。

现在 `scoreFact()` 把 `source` / `confidence` / `unconfirmed` 放进 `meta`，`factLine()` 对 `source !== "manual" && confidence < 0.6` 的条目加后缀，协议块里解释这个标记的含义。

**只标低置信度**是有意的：每条都挂标签会让整个记忆块变成噪音，而 `memory_write` 写入的条目本来就是用户说的，不需要提示。

### 17.5 交接卡为什么只读

`memory_handoff` 不写库，也不生成新的摘要。理由是文章里那条：「身份这一步不要自动化」。任何由模型自己概括的「我是谁」，都会随着模型换代和摘要压缩而漂移；而人设区与长期偏好是原文，漂移不了。

所以卡片是**引用**：身份 / 语气 / 价值观 / 边界 / 偏好逐条原文贴出，「下一步」明确留空。它能被复制到新会话，但不会自己改写记忆。

### 17.6 固定的行为

新增 6 个探针，共 52 项断言：

| 探针 | 项数 | 固定什么 |
| --- | --- | --- |
| `probe-compaction` | 12 | 压缩前后三块 prompt 不减少、WAL 被 checkpoint、压缩后自检仍正常 |
| `probe-preference-resident` | 7 | 偏好常驻、开关可关、OR 匹配、超上限时关键词仍可召回 |
| `probe-diary-budget` | 5 | 事实撑满预算时印象与日记仍在 |
| `probe-backup` | 8 | 快照生成、内容完整、按份数清理、无 `-wal` 依赖 |
| `probe-fact-source` | 6 | 「待确认」只打在低置信推断上、协议有解释 |
| `probe-handoff` | 14 | 五格齐全、规矩原文、下一步留空、调用不改记忆 |

未覆盖：快照在真实 DSH 里的首次触发时机（探针用 10 秒间隔模拟）；偏好常驻对长会话 token 预算的实际影响（每条约 15–40 token，默认 3 条）。

## 18. v0.2.16：事件块的可辨识与可枚举

### 18.1 一个被问出来的问题

起点是个具体场景：同一个人在两段对话里推进同一个项目，插件把它们记成两块互不相干的事件，换个会话之后模型接不上。看起来像缺一个 `project_id`。

不这么做的理由有三条：

1. **插件拿不到可靠的项目标识。** 它绑定的是 `agent.id`，从头到尾没有读过工作目录。即使宿主暴露路径，路径也不是稳定标识：同一仓库在不同机器上路径不同，改个目录名就断，换台机器就全丢。
2. **项目是主题轴上的聚合，而 `domain` 是粗分类。** 十个固定域，实测还会判错——一段讲插件与上下文预算的对话被判成 `财务`。拿它当项目键，等于把两个不相干的项目合并。
3. **真正缺的不是维度，是块能不能被认出来、能不能被列出来。** 这两件都在自然语言层解决，不需要新表。

所以 v0.2.16 不建项目维度，只补块的**可辨识度**与**可枚举**。

### 18.2 实测：四块里三块认不出

这是本机真实库（`~/.dsh/memory/loom.db`，4 块 / 1 会话 / 4 条事实）：

| 标题（改前） | 摘要长度 | 来源 |
| --- | --- | --- |
| `财务·那么，装了这个插件，需不需要考虑上下文崩…` | 30 字 | 规则兜底 |
| `用户想让AI主动追问` | 114 字 | 模型生成 |
| `技术·插件我更新了，你去更新一下` | 13 字 | 规则兜底 |
| `技术·也就是说，已经撞上了？` | 30 字 | 规则兜底 |

模型路径唯一的那块，标题和摘要都能用；规则兜底的三块是「领域·原句」，摘要就是原句。这种块当项目节点用不了：标题里没有对象名，同一批块的领域前缀完全一样。

兜底标题的旧写法是 `${DOMAIN_LABELS[domain]}·${第一句}`。前缀没有信息量（`domain` 有自己的列），第一句常常以语气词开头，而 `clip(…, 24)` 又把仅剩的内容截掉一半。

### 18.3 标题取第一句，不取最长句

第一版实现取「最长句」，理由是信息量最大。跑 `scenario-merged` 立刻失败：它搜「辞职」，期望命中 E1，结果只命中 `D1`。查下来 E1 的第一句含「辞职」，最长句却是「她问我在怕什么，我说怕的不是没钱，是怕自己没本事」——标题换成这句之后，「辞职」这个词从钩子索引上消失了。

结论：第一句通常承载主题词（用户先说要做什么，再解释为什么），**长度不是信息量的代理**。规则改为「第一个 ≥6 字、去掉语气词开头的句子」，语气词表是 `那么 / 但是 / 不过 / 所以 / 然后 / 对了 / 其实 / 也就是说 / 嗯 / 啊 / 诶 / 哎 / 哦`，同时剥掉残留的 `用户：` 前缀。上限从 24 字符放宽到 32，够放一个项目名。

模型路径同步：提示词从「标题 ≤12 字」改成「≤16 字」，并加一条——写清在做什么、涉及哪个具体对象（项目名 / 工具名 / 作品名 / 人名 / 地点），不要只写领域词，也不要照抄第一句。模型返回空标题时不再退化成领域名，而是走同一套句子规则。

### 18.4 摘要兜底与渲染去重

摘要兜底此前取「最长两句」，一段题外话就能把主题句挤出去。现在取「首句 + 最长句」。

规则路径下标题就是摘要的第一句，`标题 —— 摘要` 会把同一句说两遍（实测输出：`Blender 导出 glTF 时材质丢了，先记一下 —— Blender 导出 glTF 时材质丢了，先记一下`）。清单渲染时比较两者的公共前缀，超过 12 字就只印标题。

### 18.5 为什么是清单工具，不是聚合工具

`memory_episodes` 只做列举，不做归并。理由是「这两块是不是同一个项目」需要判断，而判断该由模型做——插件做只会做错且无法解释。插件给的是原料。

也不指望 `memory_search` 兼任：它走 FTS5，而 match 是把每个二字组用空格连起来（隐式 AND），「这个项目我都干过什么」这种问题没有关键词可用。列举不需要关键词，只需要时间轴。

输出每行带 `E` 编号，可以直接交给 `memory_expand` 取正文；跨会话可见——同一个身份换个会话，上个会话的块还在同一份清单里。

### 18.6 固定的行为

新增探针 `probe-episodes`，18 项断言：

| 断言 | 固定什么 |
| --- | --- |
| 空库不抛错并说明原因 | 新装时调它不会炸 |
| 列出事件块 / 有汇总行 / 按时间倒序 | 清单的形状 |
| 无「领域·」标题前缀 | 标题不再带零信息前缀 |
| 标题带项目名 `loom` / `Blender` | 两块各自认得出自己的对象 |
| 每块带 `E` 编号 | 能接 `memory_expand` |
| 至少一块带关联事实数 | `event_facts` 计数出得来 |
| 标题不被摘要重复 | 去重生效 |
| `query` 命中相关块 / 排除无关块 | 关键词过滤 |
| `days` 过滤更早的块 | 时间过滤 |
| `limit` 生效 | 条数上限 |
| 跨会话块合并列出 / 上个会话的块仍在 | 换会话不丢 |
| 调用不改记忆块 / 自检仍报库连接正常 | 只读 |

### 18.7 模型路径的一行都没跑过

上面那 18 项全部跑在规则模式（`harness` 不提供 `llm`）。改的却是模型提示词——「提示词写好了」和「模型照做」之间隔着 `extractWithModel → bridge.complete → host.stream → 解析 JSON → 落库` 一整条链，一行都没被执行过。

补的办法是给 harness 一个可选的假 `llm`：实现 `listProviders` / `listModels` / `stream` 三个成员即可，`createLlmBridge` 只用这三个。假服务把插件真正发出的请求记下来，再按提示词里的格式回一份 JSON，于是整条链都走了真代码，只有模型那一步是桩。

`probe-model-title` 16 项，固定四件事：

1. **请求发对了**：抽取调用确实发生（不是静默退回规则），提示词里含「具体对象」与「≤16 字」。
2. **回包用对了**：标题、摘要、事实三项都按模型给的落库，标题经过 32 字硬上限。
3. **空标题不退化**：模型回空字符串时走 `episodeTitle()`，标题是对话里的句子，不是裸领域名。
4. **坏回包不扩散**：非 JSON 与 `stream` 抛错两种情形都退回规则，对话不中断，模型编的那条事实不会落库。

这仍然不等于真模型：它证明的是管线，不是模型的服从度。真模型会不会照提示词写标题，只能看真机会话里的块。

### 18.8 块粒度：先分清是配置还是行为

本版初稿在 §18.6 末尾留过一条「块可能偏碎」，当时没实测。第一次测，6 轮对话得到 6 块，看起来印证了担心。查下来是探针自己的问题：`consolidation.triggerTokens` 设成 1，而 `completeTurn()` 的判定是 `tokenCount >= triggerTokens`——设 1 等于每轮整合一次，每次整合只看得到 1 轮，必然一块一轮。默认是 20000。

按真实节奏重测（每轮约 17 token，`triggerTokens=80` 让五轮凑成一次整合），五轮同一项目得到 3 块：前 3 轮合并，第 4 轮「缓存键用文件路径加修改时间」、第 5 轮「先只缓存颜色贴图」各成一块。单条消息里混三个话题（缓存 / 配色 / 下雨）仍然是一块——段内切分只在轮与轮之间发生。

所以碎是真的，来源是段内 `drift`（`microTopicJaccard=0.3`），切点落在「同一件事的不同侧面」。不调，理由是：块变小对「按块认领项目」是加分项，而调大之后一块里会混进多个话题，标题又回到含糊——正是本版要修的问题。要调只有这一个旋钮。

## 19. v0.2.17：显式 AND 的漏召回

### 19.1 问题不是「不如向量检索」，是「AND 判死了一半重合」

外部一份记忆插件测评的结论是：没有一家打赢最朴素的 qwen 向量检索加重排。这个结论在检索这一项上成立，但成立的原因跟「词法 vs 语义」只对了一半。

`compileMatch` 把用户这句话切成中日韩二字组，用空格连起来，交给 `facts_fts` / `events_fts`。FTS5 里空格是**隐式 AND**，也就是要求每个二字组都出现在原文里。「你还记得我不吃香菜这件事吗」切出 11 个二字组，记忆原文命中 4 个就足够人读懂整句，但 11 个里缺 7 个，判定不命中，`recall()` 拿到的就是空——不报错，不降级，记忆块照常渲染，只是少了这一段。

0.2.15 修过同一类问题，修的是偏好层：加常驻 + `compileLooseMatch`（OR）。事实与事件没动，因为它们的量比偏好多，放宽的代价看起来更大。这次实测发现代价可控——只要三件事同时成立：只在第一遍太瘦时放宽、放宽命中按分数打折、共享过少的候选直接丢掉。

### 19.2 三个约束，缺一个就会污染记忆块

| 约束 | 配置 | 默认 | 不做会怎样 |
| --- | --- | --- | --- |
| 只在严格命中太少时跑 | `relaxBelow` | 3 | 长句用 OR 命中全库，事实区被噪声填满，把真正重要的挤出去——正是 0.2.15 修过的「预算被占满」那一类 |
| 放宽命中按分数打折 | `relaxPenalty` | 0.55 | 一条勉强沾边的记忆可能排在严格命中前面，模型先看到错的 |
| 与查询共享太少就丢 | `relaxMinOverlap` | 0.25 | 一个高频二字组（「的」「我们」）就能把整库拖进来 |

守卫用 `containment(query, text)`：查询的二字组里有多大比例出现在候选文本中。实测那个反例很典型：

```
查询：你还记得我不吃香菜这件事吗        （11 个二字组）
命中：我不吃香菜，闻到味道就反胃        → 4/11 = 36%  ✓ 保留
误中：买菜时香菜便宜，不吃也行          → 2/11 = 18%  ✗ 丢弃
```

36% 与 18% 之间就是守卫的位置。25% 是拍的，但这一拍的依据是「至少三个二字组（六个汉字）重合」——两个字的重合在中文里几乎不构成语义关系。

### 19.3 分数怎么保证不反超

严格命中与放宽命中走同一个 `normalize(raw, topRaw)`，`topRaw` 取两者中最大的 bm25 绝对值。所以严格命中的最高分恒为 1.0，放宽命中最高只有 1.0 × 0.55 = 0.55——**结构上不可能反超**，不依赖 bm25 数值的可比性（严格查询与 OR 查询的 bm25 本来就不是同一量纲，这点无法完全消除，所以只用它排序内部分数，跨层比较交给 `finalScore`）。

事件层更保守：`strictEvents === 0` 才放宽。每个事件块在 prompt 里占一整行（标题 + 90 字摘要），错一块比少一块贵。放宽排在「最近 3 条」兜底之前——兜底是「我完全不知道该给你什么」，放宽是「我知道大概是这个方向但字面对不上」，后者更有信息。

### 19.4 `memory_search` 走的是另一条路，必须一起改

模型自己检索时用的是 `Engine.searchFor()`，不是 `recall()`。它此前同样是严格 AND，于是出现了一个很怪的状态：用户问「你还记得我不吃香菜这件事吗」，模型主动去查，查回「没有找到相关记忆」。现在两处共用一个 `collect(expr, factor, guard)` 收集器，规则一致。

### 19.5 这不是向量召回，别自我安慰

修掉的是「字面有一半重合但被 AND 判死」——日常对话里最常见的一类失败。字面完全不重合的近义表达（「香菜」对「芫荽」、换语言、口语改写）仍然找不回来，那需要 embedding。这一版没有引入模型依赖、网络请求或额外进程，索引仍是本地 SQLite；代价是这类残留在，好处是零依赖离线这条卖点也还在。

### 19.6 探针固定了什么

`probe-recall-relax`，12 项，其中三对是 A/B 对照（同一份数据、只改一个开关），因为「放宽生效」和「本来就通」在结果上长得一样：

| 对照 | 打开 | 关闭 |
| --- | --- | --- |
| 用自己的话问能否找回 | 命中 | 找不到 |
| 守卫调高到 0.9 后 | 找不到 | — |
| prompt 路径的记忆块 | 出现该事实 | 不出现 |

最后那一对最关键，也是最容易写成假绿的一条：记忆块对最近 8 条事实本来就有兜底，只要目标事实还在最近 8 条里，开不开放宽都会出现。所以那一组单独起两个实例、**关掉整合**（整合会从用户那句话里抽出新事实，新事实必然排在最前），并在目标事实之后写九条填充把它挤出最近 8 条。第一版没做这两件事，断言通过了但是假的——这是本次唯一一次「测试骗了自己」。

## 20. v0.2.18：让模型在写的时候想关键词

### 20.1 位置是死的：想词不能发生在查的那一刻

0.2.17 松开了 AND，救回的是「字面有一半重合」那一类。剩下的漏是零重合：

```
存下  用户辞职后一直没跟家里说，怕父母担心
用户  我没敢告诉爸妈
```

两句共享 0 个二字组。放宽那一步也救不了——`containment(query, text)` 是 0，守卫直接丢掉。

最直觉的修法是「查的时候让模型自己想关键词」。这条路的问题不在效果，在**时序**：

```
组装 prompt（同步：persona / hooks / memory 三块求值）
   └─ recallFor() 是同步的，text: () => string
模型开始生成
   └─ 这里之后才可能有任何一次模型调用
```

任何一次模型调用都排在组装之后。所以「用模型想的词去查」最早也只能是「这一轮先查错，下一轮再查对」。四个能放模型的位置，只有三个能用：

| 位置 | 时机 | 能放模型吗 | 代价 |
| --- | --- | --- | --- |
| 整合时 | 本轮结束，异步 | 能，模型本来就在跑 | 几乎为零 |
| 注入路径里 | 组装 prompt，同步 | 不能：要嵌套一次模型调用 | 首字延迟，每 step 都跑 |
| 工具调用内 | 模型已开口 | 已经是这样（`memory_search`） | 一次往返，且已经晚了 |
| `turn-stopping` 之后 | 异步 | 能，但只能猜下一轮 | 会过期 |

结论：把想词这件事挪到**写**的时候。整合那一步模型本来就在读这段对话、产出标题和摘要，多要一个字段不多一次调用。

### 20.2 别名不进新列，混进 `tokens`

`facts_fts` 是 external-content 表（`content='facts'`），加一列要 DROP 重建、重刷全库，还要给新列定 bm25 权重。而 `tokens` 本来就是「把原文切成二字组、空格连起来」的索引列，`indexText()` 做的事就是切词。于是：

```js
tokens = indexText(`${text} ${tags.join(" ")} ${aliases}`)
```

查询端**一个字都没改**：`compileMatch` 还是把用户那句话切成二字组 AND 过去，只是现在这些二字组有机会落在别名上。触发器不用动（它照抄 `new.tokens`），bm25 权重不用动（别名和正文同权，这恰好是想要的：一个别名命中就是一次正文级别的命中）。

`aliases` 列本身只为两件事存在：`memory_doctor` 报覆盖率、合并时取回旧别名。旧库靠 `ensureColumn` 补列，不重建表。

### 20.3 只加别名没用，守卫必须把别名算进去

这是整件事唯一容易做错的地方。第一版只做了 20.2，实测**换说法 0/6**：严格匹配要求这句话的**每个**二字组都出现，三个短别名盖不住一句人话；而放宽那一步的守卫看的是 `containment(query, text)`，纯别名命中在守卫眼里是 0% 重合，被丢掉。

守卫改成 `containment(query, rowText(fact))`（`rowText` = 正文 + 别名）之后，同一批题变成 6/6。三臂对照（`probe-aliases`，同一份语料）：

| 问法 | A 无别名 | B 别名+放宽 | C 别名+仅严格 |
| --- | --- | --- | --- |
| 别名原文（短问） | 1/6 | 6/6 | 6/6 |
| 换说法（别名覆盖） | 0/6 | 6/6 | 0/6 |
| 第四种说法（没覆盖） | 0/6 | 0/6 | 0/6 |

C 臂是必须的。没有它，B 的胜利会被记成「别名让 AND 变容易」，而归因错一处，下次就会照着错的理由继续加别名、继续失望。真实结论是：**别名只在两种情形下起作用——短问（别名本身就是 query）和放宽那一遍（守卫认别名）**。中间那句人话，严格匹配永远过不去。

### 20.4 清洗：泛词是唯一的真风险

模型被要求给 2–3 个说法时，产出三类垃圾：整句、话语词（其实 / 有点）、原文本身。前两类让索引变胖，第三类纯浪费。所以 `cleanAliases()` 只收：长度为 2–6 个汉字（拉丁 12）、不在泛词表里、不是纯数字、不含密钥、不与已有重复、最多 N 个。

泛词表（`GENERIC_ALIASES`）很短，只放**不带任何对象**的词：工作、生活、心情、事情、问题、东西、状态、时候、今天、最近、聊天、话题……以及（见 §20.8）光秃秃的问句壳。「项目」「朋友」「公司」**不在**表里——它们是具体对象，只是常见。这个取舍写在代码注释里，因为它是可以争的：一个「项目」别名确实会把不相关的项目拉近一点，但把「项目」也禁掉，等于要求模型给出的别名必须比用户的实际用词更具体，那反而更容易落空。

### 20.5 换话题会怎样

这是最容易被误判的一条。别名只**增加**一个条目能被哪些词找到，不改变查询本身；而严格 AND 要求整句覆盖，所以一个换了话题的句子要误中，得把它的每个二字组都塞进某条记忆的别名里——那基本不可能。

实测 8 个无关问题（含两个刻意带泛词的：「最近有点累」「这个项目什么时候能结束」），三条臂都是 **0 条旧记忆漏进块里**，块大小一致（8 条）。那 8 条是 `recentFacts(8)` 冷启动兜底：**没有命中时，块里塞的就是最近 8 条事实**，与话题无关。这件事在 0.2.18 之前就是如此，不是别名引入的；它值得单独记一笔，因为它意味着「换话题」时记忆块的真实状态是「一段无关的近期流水」，而不是「空」。

真正会被别名放大的是**短查询**：用户只说「项目」两个字时，任何带「项目」别名的记忆都会严格命中。这是别名机制的性质（别名就是用来被命中的），不是 bug；它换来的是「我没敢告诉爸妈」能被找到。

### 20.6 天花板，以及一个不会自我修复的缺口

- **模型想不出第四种说法。** 探针里「没人教过的问法」6 条全漏。别名把「零重合」变成「有重合」，没有变成语义检索，这个边界和 0.2.17 一样硬。
- **老库不会自动回填。** 别名产生于写入那一刻。旧记忆要重新整合一次才有，`memory_doctor` 会报 `检索别名 12/30 条带别名（旧记忆要重新整合一次才会有）`。宁可把这个缺口印在体检报告上，也不要让它看起来已经生效。
- **常驻 token 不变。** 别名只进索引，不进 prompt；记忆块那 2300 token 一分没涨。

### 20.7 一个白名单 bug，和一次差点假绿

`toEngineConfig()` 是一份**显式字段白名单**，`aliasCount` 忘了写进去。传到引擎是 `undefined`，`extractPrompt(…, aliasCount = 0)` 的默认参数把 0 补上——提示词里悄悄没有这个字段，而配置项看起来「已经生效」。

探针第一版没抓到，因为假 `llm` 不看提示词，照样返回了别名：数据是绿的，链路是断的。现在 `probe-alias-prompt` 先断言提示词里出现 `aliases`，再断言 `aliasCount: 0` 时提示词干净且别名不生效——两侧都钉住，白名单漏字段就一定会红。

这类错误的共性是：**开关失效不会报错，只会让功能静默地回到默认值**。

### 20.8 「换个叫法」与「他会怎么问」，不是一回事

0.2.18 的提示词写的是「用户下次可能拿来检索它的说法」。这句话模型理解成了**同义替换**，而它本意是**问法**。两者差得很远：

- 同义替换：「体检」→「健康检查」。用户检索时本来就会想到「体检」这两个字，所以这条别名救不了任何一次真实检索。
- 问法：「体检」→「身体怎么样」「什么时候去查」。这才是用户想不起原词时会打出来的字。

这不是推测。在真实库（`~/.dsh/memory/loom.db`）里数了当时全部的 11 条别名，**含疑问词的 0 条**，长度全在 2–6 字之间、清一色是名词短语。也就是说别名机制本身是通的，但喂给它的东西正好是没用的那一半。

改法只动提示词（检索端一个字没改）：点名要「他会用什么话问起这件事」，并给出正反例——`身体怎么样` 对，`健康检查` 错，错的原因写清楚是「他不会那样问」。

**顺带补一个反向的洞。** 一旦开始要问法，模型很容易给只剩疑问词的壳：「什么时候」「怎么样」。这种别名比同义词更糟——它挂在一条事实上，等于让这条记忆对每个问题都算命中，正是 §20.4 说的磁铁。所以 `GENERIC_ALIASES` 里补了一组问句壳（怎么样 / 什么时候 / 为什么 / 有没有 / 是不是 / 哪些……），只挡光秃秃的壳；带对象的「身体怎么样」必须留下，`probe-alias-prompt` 对这两侧都有断言。

**这次改动没法自证。** 提示词改了，别名质量是否变好只能等真实使用后再数一次疑问词占比。探针能证明的只有三件事：提示词确实点名要了问法、正反例在提示词里、壳被挡而带对象的留住了。这和 §20.7 是同一类诚实的边界——**探针证明链路通，不证明效果变好**。

## 21. v0.2.19：用相关性去管不该靠相关性的东西

### 21.1 三个格子，一个错误

上一轮那张对比表里，loom 在三个格子上都不够：计划与现实、基本信息与偏好、改口与矛盾。看着是三件事，其实是同一个错误——**把它们交给了相似度**。

- 偏好：用户不会重复说，所以 query 里永远没有它
- 计划：用户不会再去问自己说过要做的事
- 矛盾：两条事实打架，但当前这句话只涉及其中一条

相似度能回答的是「这段话和哪条记忆像」。上面三个问的都是「什么东西不需要像，也必须想起来」。这是两个问题。

### 21.2 计划：一条独立的通道

`kind = "plan"` 从 0.2.12 就在 `KIND_SET` 里，`parseKind` 也会把「明天 / 下周 / 打算」判成 plan。但它从来没被单独查过——它混在 facts 里按分数排队。

而计划的分数天生低。它拿不到 FTS 命中（当前这句话不会提到它），只能靠 `recentFacts(8)` 兜底进来，排在一堆真命中后面。用户说「下周三前把简历改完」，三天后聊别的，这句话就沉底了。

改法是加一条平行通道：

```js
openPlans(identityId, limit, now)     // 未到期，按 expires_at 升序
overduePlans(identityId, limit, now)  // 已到期，按 expires_at 降序
```

不进 `scoreFact`，不参与相似度竞争。`maxPlans` 默认 3，`0` 关掉。

**过期的处理是这次真正的设计判断。** 旧路径里 TTL 到期就是 `expired_at`，`scoreFact` 的 `expiryFactor` 把分数压下去，于是慢慢沉底——等于「忘了」。但一个计划过了日子，只说明那个日子过去了，我们并不知道结果。它可能是做完了，可能是放弃了，也可能只是没再提。

所以过期的计划不删、也不压到看不见，而是渲染成：

```
- [11-01 · 已到期，之后没再提] 用户约好下周和房东谈换热水器的事
```

措辞是刻意选的。不写「未完成」，因为那是替用户下结论；写「之后没再提」，是把事实（我们没再聊过）和推论（所以不知道结果）分开，让模型自己去问一句。

顺带修了 `maxPlans` 的语义。第一版让 overdue 取 `ceil(n/2)`、open 取 `n`，总数是 1.5n——配置写 3，实际出 4 到 5 条。一个读起来像上限的值，实际是它的 1.5 倍，这种错误在测试里表现为 `shown <= 2` 失败，而不是崩溃。

### 21.3 计划不再降级成事实

第一版只在计划区渲染计划，事实区照旧——结果同一条计划会在块里出现两次（一次带截止日，一次不带）。加了 `planIds` 排除之后，又发现另一个方向的问题：被 `maxPlans` 挤掉的第四条计划，会以「事实」的身份出现在下面一行。

所以改成**所有 plan 都不进事实区**。理由是语义的：`用户打算换工作` 渲染成一行事实，读起来是关于用户的描述；渲染在「你说过要做的事」下面，读起来是待办。同一个句子，位置决定它被怎么用。

代价是第四条计划不在块里。它还在库里，还能用 `memory_search` 取。这个取舍是有意的——块负责「必须想起来」，工具负责「要查全部」。

### 21.4 偏好区的丢失，根因不在渲染

这一节记录一次判断错误。我最初以为问题是 `renderMemoryBlock` 里的顺序：`pushWhole(copy.preferences, ..., hard)` 排在最后，facts 吃满 target 之后偏好就塞不进了。

改完顺序和保底预算，探针还是红的——**偏好区是空的**。

真因在上一层：

```js
const selected = [
  ...facts.slice(0, maxItems),
  ...events.slice(0, 4),
  ...subjective        // 印象、日记、偏好
].sort((a, b) => b.score - a.score).slice(0, maxItems);   // maxItems = 20
```

一屋子 20 条高分事实，subjective 全部出局。不是渲染时被截掉，是根本没到渲染那一步。而偏好的分数结构注定它排不高——`similarity(.55) × strength(.85) − penalty ≈ 0.45`，事实一旦 `normalize` 到 1.0 就永远压过它。

两层都得改：

1. `recall()` 里主观项不再参与排序，facts/events 单独切 `maxItems`
2. `renderMemoryBlock()` 里偏好区和计划区前置，各给保底预算

只改第 2 层没用，行早就没了；只改第 1 层，偏好还是排在 20 条事实后面。探针 `probe-block-zones` 钉的是这个组合：budget 400 / hard 450，24 条事实 + 3 条偏好，断言 19 条事实进块的同时 3 条偏好也在。

### 21.5 矛盾：标记，不裁决

整合时模型判 `contradicts`，是唯一能抓住「换个说法」的路径。它有一个不报错的失效模式：模型没看出来，两条都是 `active`，块里并列呈现，模型挑先读到的那条。

补一个机械兜底，跑在维护里：

```
同 identity、同 kind
且 0.45 ≤ jaccard(text_a, text_b) < 1.0
且 数字集合不同 或 否定极性不同
→ 旧的那条标 disputed
```

三个限制都是刻意的：

- **只标不删，也不判谁对。** `disputed` 的分数乘 `conflictPenalty`（0.85），块里标「可能已过时」。判断哪条为真是模型的事，代码只负责让「这两条打架」这件事变得可见。
- **同 kind 才比。** 一条偏好和一条事实本来就可以说不同的话。
- **每次最多 3 对。** 一次维护把半个库标脏，比漏标更糟。

`memory_doctor` 报「N 条计划（M 条已到期） · X/Y 条待确认」。把这个数字印出来是为了让扫描器保持诚实：如果哪天它标了库里一大半，阈值就是错的，而那应该被看见，不是从「块里什么都标了已过时」反推出来。

### 21.6 称谓：别名唯一能做、向量也做不好的事

提示词加一条：事实里提到人时，把用户对这个人的所有称呼都写进 aliases。

「我妈」「母亲」「李慧」是同一个人。embedding 对专名和称谓的关联一样含糊——`母亲` 和 `李慧` 在向量空间里不近，除非模型知道她们是同一个人。而别名是显式枚举，写一次就一直在。这一格 loom 反而占优。

### 21.7 一次测试顺序的教训

`probe-block-zones` 第一版全绿。但它跑的是「没有事实竞争」的场景：query 是「今天外面风挺大的」，FTS 不命中任何事实，只有 `recentFacts(8)` 兜底，8 条根本填不满预算。

把 query 换成 `用户`（所有事实都以这两个字开头，一个二字组命中全部 24 条）之后，偏好区立刻红了。

同一份代码，两个结论。差别只在测试有没有真的把预算占满。这件事值得写进文档，因为「测试通过」和「被测路径真的被执行了」是两件事，而后者不会自己报错。

### 21.8 没做的

- **`hypothesis` 没单独建类型。** 假设没有到期日，生命周期和事实一样；它的不确定性已经由 `unconfirmed` 标记覆盖（低置信度且非手写的事实，块里带「待确认」）。多一个枚举，多一堆分支，换不来判对「这是假设还是事实」的能力。
- **矛盾检测不覆盖改写。** 数字和否定都是机械信号。用户说「我不喝酒」和「我滴酒不沾」共享零个二字组，这个扫描看不见——那是整合时模型该抓的，不是这段代码能抓的。
- **计划没有「已完成」状态。** 现在只能靠后续事实 supersede 它，或者等它过期。一个显式的 `done_at` 需要一次新的工具调用设计（用户得能说「那个做完了」），留到下一版。

## 22. v0.2.20：时间是一个区间

### 22.1 一个点存不下一个范围

`expires_at` 一直是单个时间点。这个形状能回答「什么时候到期」，回答不了「他说的是哪一段」——而后者才是模型回话时真正要用的。

```
用户  下周我要搬家
存下  expires_at = 11-15 23:59   ← 信息丢了：这到底是「这一周」还是「周五之前」？
```

压成一个点有个具体后果：第二天 `overduePlans` 就把它捞出来标「已到期，之后没再提」。用户说的是一周，系统记的是一天，然后主动报告一个没发生过的失约。

所以期限改成区间：`due_from` 到 `expires_at`。一天也是一个区间，只是长度为一天。这样只有一种形状，渲染和查询都不用分支：

```
[11-09~11-15 · 截止]  下周
[11-09 · 截止]        下周一
```

`precision` 单独存（`day` / `week` / `month` / `fuzzy`），因为它的唯一用途是**决定要不要加「约」**。`fuzzy` 是猜的，写出来要让人知道该怀疑；`day` 不是。

### 22.2 换算是代码做的，不是模型做的

`ttl` 从一开始就是模型抽出来的**原始短语**。这次没有让它改成分数更高的「结构化日期」，反而在提示词里加了硬约束：

> 把时间短语原样抄进 ttl，一个字都不要改，也不要自己换算成日期——换算由代码做，你换算会错。

理由是算术可靠性。让模型把「下周三」换算成日期，等于让它在脑子里做日历减法；它答得又快又自信，错了也不会犹豫。而错的代价是一个具体日期，事后没有任何东西能提示它错过——块里那行读起来和正确的一模一样。

代码只有一个入口 `parseDue(text, base, tz)`，纯函数，可以拿固定日历测。这是整个设计里最值钱的一点：**唯一需要做日期算术的地方，是一个能被断言的地方**。

### 22.3 模糊的存成范围，语焉不详的不存

「过几天」怎么写？三个选项：

| 写法 | 问题 |
| --- | --- |
| 某个具体日期（比如 +5 天） | 编造。它会以「事实」的形态留在库里，再也没人知道那是猜的 |
| `null` | 丢掉了用户确实说过的东西 |
| 一个区间 + `fuzzy` | 保留了「他说过，但没说准」这件事本身 |

选了第三种：2–10 天，渲染成 `约 11-04~11-12`。这个范围是照着用户的原话定的（他们把「过几天」理解成 2–10 天），不是从语料里统计出来的——写在这里是为了让人知道它是可以争的。

「过段时间」「以后」「改天」「早晚」不记。它们的共同点是**没有信息**：既没有量，也没有锚点，任何区间都是我们编的。判据写在代码里：这些词一旦命中，`parseDue` 返回 `undefined`，条目按「未定期限」渲染。

顺序很重要：具体说法先判，模糊词后判。否则「三天以后」会被「以后」吃掉。

### 22.4 换时间为什么要问

用户先说「下周去看房子」，后来说「下周一去」。这一次改的是**日期**，不是内容。

以前这种情况会经由 `update` / `duplicate` 合并路径直接覆写；`update` 甚至根本不碰 `expiresAt`，所以更常见的结局是：日期悄悄留在旧值上，而文本已经变成新的。两种结局都错，且都没有痕迹。

现在 `reconcileDue` 把新期限和已存期限比一次，四种结果：

| 结果 | 含义 | 处理 |
| --- | --- | --- |
| `fill` | 库里没有期限 | 直接落 |
| `same` | 同一个区间 | 不动 |
| `refine` | 新区间在旧区间里 | 记成待确认，措辞「说细到」 |
| `shift` | 新区间在旧区间外 | 记成待确认，措辞「改到」 |

`refine` 也要问，这一条是想清楚之后才定的。直觉上「下周一」比「下周」更精确，接受它似乎是安全的；但旧区间有可能才是他真正说的那个（「下周之内」），而新的一句可能来自另一件事（比如另一个下周一）。**只要覆盖的是用户给过的日期，就值得问一句**；问一次的成本是一个来回，记错的成本是他在错误的那天被提醒。

`accept: false` 必须是正经结果：把提案丢掉、保留原期限、**以后不再问**。第一版把它写成 no-op，结果是同一个问题每轮再问一次，直到用户投降——那不是询问，那是磨。

### 22.5 一个藏了很久的时区错位

加入区间之后，单日渲染成了两天。追下去发现日期被算了两遍，用的还是两个时区：

```js
// 写入（memory_write）
const due = parseDue(text, now, this.config.timezone);      // 默认 "" → 回落 UTC

// 渲染
renderMemoryBlock(result, config, this.timezoneOf(sessionId)) // 会话已记录本机时区 → 上海
```

过去 `expires_at` 只显示一个日期，8 小时偏移落在「日界」里，看不出来。区间一来，起点按 UTC 日界算、终点按上海日界算，一个点变成两天，错误立刻可见。

修法不是加一次 `?? zone`，而是让两条路走同一个函数：`timezoneOf()` 在会话没记录时回落到部署时区，写入侧也改成 `timezoneOf(sessionId)`。

这个 bug 从有 `expires_at` 那天就存在。它能活这么久，是因为没有任何断言同时看「写入时的日界」和「渲染时的日界」。加维度的时候，旧的错位会成批现形——这一条值得记住。

### 22.6 「又说一遍」不等于「确认」

用户被问「是下周一吗」，回答「对，下周一」。这句话会走整合路径，抽出一条与旧事实重复的候选，`reconcileDue` 看到同样的 `refine`，于是**再生成一次相同的待确认**，而不是落实。

不是没想过自动确认：新候选的区间和待确认的区间完全相同时，就当作同意。但这个判据在另一条真实路径上会静默出错——跨轮再抽一次同一句原话，区间也完全相同。文本上区分不了「重申」和「确认」，而猜错的代价是记错日期。

所以确认只有一个入口：`memory_settle(id, accept)`，由模型在听到用户表态后显式调用。多一次工具调用，换掉一整类静默错误。

### 22.7 天花板

- **不解析钟点。**「今晚八点」落在当天，时间部分是 23:59。带时刻的期限需要另一个字段，而现在没有东西会用它。
- **不处理「以后」的表格。** 「下周三以后」会命中「下周三」，丢掉「以后」。这是一个已知的窄缝，写在这里而不是假装没有。
- **跨时区不切日界。** 会话时区在建立时记录，人在别的时区继续聊，日期仍按原时区算。要修得先有「当前时区」这个信号，宿主没给。
- **老库不回溯。** `due_from` 为空的旧行按「expires_at 所在那一天」渲染，就是它们本来的意思；不会凭空长出一个起点。

## 23. v0.2.21：认得的说法就是这条通道的宽度

### 23.1 解析器认得多少，等于这个功能有多少

v0.2.20 把期限做成了区间，形状是对的，覆盖是窄的。窄在哪，值得先看清楚：

```
用户  下下周五交初稿
解析  11-13          ← 早了一周
```

不是没解析，是解析成了另一个日子。这类错比「不认」贵得多：`undefined` 的后果是「未定期限」，看得见；错日期的后果是块里有一行 `[11-13 · 截止]`，通顺、合理、无法从界面上分辨。

所以这一版的重点不是加功能，是把「认成了别的东西」这三处修掉，再把常用说法补齐。

### 23.2 三个看着有答案的错

**`下下周五` 早一周。** 双写前缀里包含单写前缀，`下(?:个)?(?:周|星期|礼拜)([一二三四五六日天])` 在 `下下周五` 的第二个字符处就匹配上了，于是返回 `下周五`。

改的时候还踩了一次同样的坑：`下下周五` 的偏移写成 `14 - weekdayOf + target - 1`，结果还是 11-19。原因是「下一个周一」的偏移本身是 `8 - weekday`，那个 `-1` 已经在里面了；照抄单写的公式等于减了两次。单写是 `8 - wd + target - 1`，双写必须是 `14 - wd + target`。

**`下个月五号` 塌成整月。** `12月5号` 有 `11月9日` 那条绝对日期规则接，`下个月五号` 没有——`月` 前面是个 `个`，不是数字。于是落到 `下个月` 那条，整月窗口返回，`五号` 被丢掉。用户说的是「12 月 5 日」，系统记的是「12 月之内」，提醒会提前四周。

现在有一条专门的规则：`(下下个月|下个月|这个月|本月) + 数字 + 日/号`。它会验算落地日期——`2月30号` 转出来是 3 月 2 日，日期不符就整个不作数，而不是顺手给一个 3 月的日子。

**`周天` / `周日` / `星期天` 不认。** 只认带 `这` / `下` 前缀的写法。口语里最常说的恰好是不带前缀的那个。

裸星期几的含义取「最近的那个，含今天」——人说「周天去爬山」指的就是即将到来的周日。`上周五` 用负向前瞻排除，理由见下一节。

### 23.3 过去的日子不是期限，而且不能是「过去的期限」

`昨天` `前天` `上周五` `上周末` 一直没被解析。加上它们看起来很自然，直到问一句「记成什么」：

```
expires_at 落在过去  →  块里写「截止 11-01 · 已到期」
                     →  kind=plan 的从出生就进 overduePlans
```

「前天我把车卖了」没有期限这回事。给它一个已经关上的窗口，等于让系统主动报告一次不存在的失约。

所以这类句子必须返回 `undefined`，而且这个判断放在 `parseDue` 的出口，不放在各个分支里——任意一条规则解析出一个已经过去的窗口，都由同一个守卫丢掉：

```js
if (hit.to < startOfLocalDay(baseTs, timeZone)) return void 0;
```

守卫一加，顺带暴露了一个更坏的旧行为。绝对日期落在过去时，代码会**把它推到明年**，为的是让「12 月说 1 月 5 号」成立。但「11 月说 10 月 15 号」也被推，凭空造出一个 11 个月后的期限——这比丢掉更糟，因为它是未来，会真的到期、真的提醒。

现在只有「往回差大半年」才推（就是年终那一种情形），近处的过去留在过去，交给守卫丢掉。

### 23.4 习惯不是期限

`每周一` `每天七点` `每月5号` 会被裸星期几和月内指定日接住，变成某一个具体日子。结果是一条永久的、每周都会重新逾期的「期限」。

判据简单到可以写在正则里：出现 `每 + 天/日/周/星期/礼拜/月/年` 就不按一次性期限处理。这里**没有**区分「每天吃药」和「每周一交周报」——两者都不该变成一个固定日期，而区分它们需要模型，这条路径恰恰是没有模型时的兜底。

### 23.5 第二份手写清单迟早会漂

无模型兜底路径里有个 `hasTemporal()`，判断一句话里有没有时间短语：

```js
/明天|后天|下周|下个月|月底|三天|一周|之后|以后|tomorrow|next week|.../
```

这是第二份关键词表。`parseDue` 学会 `下个月五号` 的时候，它不知道；`parseDue` 开始认 `周天` 的时候，它也不知道。**一份清单负责「认不认」，另一份负责「认成什么」，两者没有任何机制保证一致。**

现在「认不认」也问 `parseDue`，只留一条例外在外面：习惯不算期限（23.4）。这条例外之所以留在外面，是因为它是**策略**，不是识别能力——`parseDue` 认得 `每周一` 指的是哪个周一，只是我们决定不把它当期限。

### 23.6 时区不承担

时区在会话建立时记录一次，之后不改、不推断、不随系统漂移。用户真的换了地方，让他自己跟模型说一声去改配置。

理由是错的代价不对称：悄悄跟随系统时区，改对的时候用户察觉不到，改错的时候（VPN、容器、笔记本时区被同步成 UTC）是一个静默移位的日期，和 23.1 里那类错一样无法从界面分辨。而「我不改」是一个能被说清楚的行为。

### 23.7 天花板（更新）

- **不解析钟点。** 没变。「今晚八点」落在当天 23:59。
- **「下周三以后」丢掉「以后」。** 没变，仍是已知窄缝。
- **跨时区不切日界。** 没变，见 23.6。
- **不认纯粹的时刻词。** 「下午」「早上」不带日期时不构成期限。
- **两个日期并列时只取一个。** 「周一到周五」取周五（`到` 前面的那个被负向前瞻挡掉，剩下后面的匹配上），「周一、周五」取周一（先命中的胜出）。都没法表达范围，因为区间只有一条。

## 24. v0.2.22：期限属于没做的事

### 24.1 一个字段挂在了两类记忆上

v0.2.20 的期限窗口做对了形状，v0.2.21 把说法认全了，但都建立在同一个未曾追问的假设上：**凡是句子里有时间，那条记忆就有期限**。

「今天我把车卖了」和「昨天我把车卖了」是同一件事。可前者会拿到一个当天到期的窗口，后者什么都不拿——不是设计上有区别，纯粹是因为 `parseDue` 认得 `今天` 而不认 `昨天`。同一类记忆有了两种形状，而形状是模型读到的唯一区别。

后果有三层，一层比一层不显眼：

```
- [11-02 · 事实] 用户今天把车卖了 (期限 11-02)     ← 读起来像这车有个保质期
第二天维护把 expired_at 打上                          ← 一条已完成的事被判「过期」
再说一次类似的话 → reconcileDue 判「时间待确认」         ← 模型跑来问「日期改了吗」
```

第三层最糟：事实没有日期可改，问出来的是一个不存在的问题。

现在窗口只挂在 `kind=plan`。判据不在渲染层，在写入口：`applyCandidate` 和 `writeFact` 都先看 `candidate.kind === "plan"`，不是计划就不产生窗口。时间原话照旧写进 `evidence.ttlPhrase`——它是诊断信息，丢掉可惜，但它不再变成可比较、可逾期、可追问的东西。

### 24.2 过期不是结果，是一个问题

计划过期以前只有两种结局：被后续事实取代，或者永远挂在块里标「已到期，之后没再提」。第二种文案其实已经承认了问题——**「没再提」是我们不知道，不是他忘了**。

用户说「下周去看房」，下周过去了。三种可能：办成了、没办成、改主意了。库里只有一条过期的计划，三者不可区分。

所以过期的计划现在是一个待问的问题：

```
- [11-05 · 已到期，之后没再提] 用户打算去看房
  （过了期限还没有下文——这轮问一句「后来成了吗」，按他的回答调 memory_resolve(id=12, done=true/false)）
```

### 24.3 只问一次，而且问句的来源只有一个

「只问一次」写起来有三种做法，选了最土的那种：

| 做法 | 问题 |
| --- | --- |
| 每轮都问 | 一条被无视的计划会变成每天一次的提醒，用户会开始无视整个块 |
| 问过就删 | 删掉的是用户亲口说过的事，而「他不知道」正是最有用的状态 |
| 标记问过、留在块里 | 采纳：`nudged_at` 记一次，之后这行恢复成没有问句的样子 |

`nudged_at` 在 `recall()` 里花掉，不在渲染里。原因很实际：prompt 块是懒求值的，同一轮里可能被求值不止一次（`recallFor` 有按会话和 query 的缓存，第二次直接返回缓存字符串）。在渲染里打标记，等于让「这轮问了」取决于渲染被调用几次。

代价也写在这里：如果那一轮被中断，标记已经花掉了，这句话没有真的问出去。选择接受它，而不是引入「已送达」这种需要宿主确认的状态——插件拿不到「这句话用户看到了」的信号，伪造一个只会更糟。

### 24.4 两种回答都写一条新事实，原文不动

```
用户打算去看房            ← 计划，保留原文，outcome=done
用户打算去看房 —— 已办成（11-06 确认）   ← 新事实，kind=fact
```

不覆盖原文，是因为两句话在各自的时间点上都是真的。用结果覆盖承诺会删掉承诺唯一的记录，而下一次要问的正是它。

「没办成」同样要写。只记成功的记忆会心安理得地把同一个失败的计划再提一次——它没有材料判断那次为什么没成。

日期写的是**确认日**，不是完成日。我们只知道他什么时候说的，不知道他什么时候做的；写成完成日就是编。

### 24.5 收尾要有守卫

`memory_resolve` 拒绝三种输入：

| 输入 | 回答 | 为什么 |
| --- | --- | --- |
| 不是 `kind=plan` | 「不是计划，不用这样收尾」 | 否则任何事实都能被贴上结论 |
| `resolved_at` 已有值 | 「之前已经收过尾了（办成/没办成）」 | 重复调用会写出两条互相矛盾的结论 |
| id 不存在 / 无权 | 明说 | 静默成功是最难查的一类 bug |

它也不修改计划行本身：`resolved_at`、`outcome` 只让这条计划退出计划区（`openPlans` / `overduePlans` 都加了 `resolved_at IS NULL`），原文留在库里，`memory_search` 仍然找得到。

### 24.6 天花板

- **不自动判断「办成了」。** 只能靠用户说。计划文本里出现「交完了」不算证据——那是另一条对话事实，`resolved_at` 该由模型在听到回答后调工具。
- **计划没有「进行中」状态。** 只有未到期、已到期、已收尾三种。改期走 `memory_settle` 那条线，不新增第四种。
- **一次问不到就没有第二次。** 不重复问是刻意的；`memory_doctor` 会显示「N 条已问过」，看得见这个欠账。
- **`maxPlans` 会挡住问句。** 逾期计划超过上限时，排在后面那几条不会拿到问句，也没有其它通道提醒。
- **老库不回溯。** 之前的计划 `nudged_at` 为空，会被当成没问过——一批历史的逾期计划会在升级后集中冒出来问一次。这是有意的：那些问题本来就没问过。

## 25. v0.2.23：问一次就把嘴闭上，等于交给运气

### 25.1 「只问一次」其实是一次机会

v0.2.22 的写法是：计划过期，块里出现一句问话；问过就记 `nudged_at`，之后再不出现在任何一轮里。

它的前提是「那一轮一定会被看见」。这个前提不成立。问话写在 prompt 块里，模型可能那一轮在答别的事、可能被打断、可能只回一句「等会儿说」。任何一种情况发生，这条计划就再也不会被问——它在系统里的状态从「待确认」变成「无需确认」，而变化的唯一依据是我们自己发过一次问句。

这不是产品偏好问题，是把一次投递当成了一次确认。**一条承诺不会因为我们问过一次就变得不需要回答。**

### 25.2 两个时间戳，两种语义

原来只有一个坑位，`nudged_at` 同时承担了两件事：

```
状态位   问过了，就不要再问
时间锚   上次问是什么时候
```

v0.2.23 只保留第二个含义，第一个交给 `resolved_at`：

| 字段 | 回答的问题 | 谁写 |
| --- | --- | --- |
| `resolved_at` | 有没有结果 | 模型听到回答后调 `memory_resolve` |
| `nudged_at` | 上次问是什么时候 | `recall()` |

判断一条计划该不该问，于是只有一条式子：

```js
overdue && (nudgedAt === null || now - nudgedAt >= planNudgeDays * DAY)
```

`resolved_at` 不在式子里，因为 `overduePlans()` 的 `WHERE` 已经把它排除了。**有结果的计划根本进不了这个函数**——这比在判断里多加一个条件更可靠：一个条件可能被忘掉，一个查询条件不会。

第一次问的时机也没变：`nudgedAt === null` 就是「从没问过」，而能走到这里的计划都已经过期，所以是「过期即问」。之后才是间隔。

### 25.3 间隔是拍的，2 天不是算出来的

2 天没有推导过程。取它的理由是它同时满足两个约束：

- 比「一轮对话的长度」长得多——同一天里不会重复问同一件事；
- 比「用户忘记这件事的周期」短得多——下次提到类似事情之前，大概率已经问过一轮。

真正决定这个数的不是理论，是这个功能能不能被容忍。`retrieval.planNudgeDays` 可以改，`0` 恢复成 v0.2.22 的行为（只问一次）；这一点是刻意留的：如果某天发现重问让人烦，关掉它不该需要改代码。

### 25.4 排序：加了重问之后，原来的顺序会饿死人

逾期区原来按 `expires_at DESC` 排，最近过期的排最前。只有一次询问时这没问题——反正每条都会被问一次，顺序只影响观感。

有了重问，顺序就决定谁被问到：

```
limit = ceil(maxPlans / 2) = 2
计划 A  过期 11-01
计划 B  过期 11-02
计划 C  过期 11-03     ← 每次都排第一、第二
```

B 和 C 刚被问过（不满两天，`nudge=false`），但它们仍然占着两个名额，A 永远进不来。**问题不在排序键，在于「占了名额却不问」**。

改成按上次问的时间升序（从没问过的算 0）：

```sql
ORDER BY COALESCE(nudged_at, 0) ASC, expires_at ASC
```

从没问过的一律排最前，问过的按上次问的时间排队。刚问过的虽然还在列表里，但已经沉到后面，名额先给真正轮到的。这是一条很朴素的公平性：**每轮问的是最久没被问过的，而不是最新的。**

`COALESCE` 那个 `0` 是关键：`NULL` 在 SQLite 的 `ORDER BY ... ASC` 里排最前，行为上等价，但显式写出来才能让读的人不必去查 NULL 的排序规则——这个表达式是这条查询里唯一有语义的地方。

### 25.5 还剩一次「白问」

`nudged_at` 仍然在 `recall()` 里盖，不在渲染里。理由和 v0.2.22 一样（块是懒求值 + 按 `session+query` 缓存，渲染里盖会让「问没问」取决于求值次数）。所以那一轮如果被中断，这次询问白花了，要等下一个间隔。

v0.2.22 里这个代价是致命的（白问 = 永久不问）；现在它只是晚两天。这也是为什么先加重问、别的都可以慢慢来：**重问把「一次投递」的失败从终局降级成了延迟。**

### 25.6 块里的字

```
- [11-05 · 已到期，还没有下文] 用户打算去看房（……memory_resolve(id=12, done=true/false)）
```

`之后没再提` → `还没有下文`。差别在于主语：前者说的是用户（他没提），后者说的是这件事（它没结果）。而这个功能要表达的正是后者——我们不知道结果，所以问。

### 25.7 天花板

- **间隔固定，不递增。** 一条被无视半年的计划每两天被问一次，不会因为问过很多次而拉长间隔。递增退避在这里是错的：它假设「问不到就是不想答」，而真实原因更可能是每次都撞上别的事。
- **问的次数没有上限。** 唯一的出口是 `resolved_at`。用户永远不答，它就永远在计划区——这是设计意图，但意味着 `memory_doctor` 的「问过没结果」计数会一直涨，需要有心理准备。
- **`maxPlans` 仍然会挡住一些计划。** 轮转保证不被饿死，不保证同一轮全被问到：逾期计划多于 `ceil(maxPlans/2)` 时，每轮只露出这么多，其余等下一轮。
- **沉默不等于没办成。** 没有任何「N 次没回答就判失败」的路径。判断只能来自用户说的那句话。
- **不判断「问过但用户转移了话题」。** 模型要不要坚持问，是提示词的事（协议里写的是「一轮最多问一次、别追着问」），不是数据层的事。

## 26. 一致性检查：每版自己的探针证明不了七版之间没互相踩

### 26.1 为什么还要再查一遍

七个版本各有自己的探针，全部绿。但探针只能证明「写探针时想到的那个场景能跑」。它们之间的缝隙不在任何一条断言的射程里，而缝隙恰好是最容易出问题的地方——两处代码各自正确，合起来不对。

所以发布前不看 diff，改成按一条数据的一生重走：写进来（字段、CHECK、索引）→ 存住（迁移、老库）→ 取出来（通道、渲染）→ 改它（改期、收尾）→ 数它（doctor）。

### 26.2 升级路径值得单独造一个假

`ensureColumn` 那五条 ALTER 是最少被跑到的代码：新库走 `CREATE TABLE`，永远不经过它；只有老用户升级时才知道它对不对。而如果某条 DDL 和 `CREATE TABLE` 里的定义不一致（少了 `NOT NULL DEFAULT`），新库和老库就会有两种行为，这个差异只有老用户遇得到，报上来时也很难复现。

造老库的办法有对有错。**错的是手写一份「v1 schema」**：那测的是写的人记忆里的 v1，而不是真的 v1，记忆错了测试也跟着错。**对的是反向降级**：先用当前代码建库、写入数据，再 `ALTER TABLE ... DROP COLUMN` 掉新增的列、把 `user_version` 改回去。表结构、FTS、触发器、数据都是真的，只有版本号是假的。

`probe-upgrade.mjs` 就是这么做的。它也顺带证明了另一件事：`user_version` 缺失（0）时同样能迁移——这是「用户从很老的版本直接跳过来」的情形。

### 26.3 查出的两个问题

**改期提案与「成了吗」同时出现。** 一条计划可以既有一份没确认的改期提案，又已经过了原定期限。渲染时两段说明会叠在一行：`memory_settle(id=1)` 和 `memory_resolve(id=1)` 指着同一条计划，没有先后。

这不是排版问题。用户上一轮刚说「改到下周了」，系统这一轮却问「后来成了吗」——**问的是他已经回答过的问题**。所以判据不是「一行里别放两个问句」，是「有更新的日期提案时，这件事还没到下结论的时候」。

**已收尾的计划还能被改期。** `settle()` 只看有没有提案，没看有没有结果。于是 `resolve` 之后仍然可以 `settle`，把 `expires_at` 推到未来并把 `expired_at` 清空，而 `resolved_at` 还在——这一行同时满足「不进计划区」（已答）和「不进事实区」（是计划），**在任何视图里都不存在**。

修法有两处，缺一不可：`settle()` 拒绝已收尾的计划；`resolve()` 顺手清掉 `pendingDue`，否则 `memory_doctor` 会把一条已有结果的计划永远算进「时间待确认」。

### 26.4 自己引入的那个静默失效

改第一处时写的第一版是 `pending === null`。缺省值是 `undefined`，而 `undefined === null` 是 false，于是**每一条没有提案的计划都被读成「有提案」**，`nudge` 恒为 false。

它不报错、不崩、不降级：行还在、日期还在、「已到期，还没有下文」还在，只是那句问话消失了。而当时探针里唯一的相关断言是「有提案时不问」——它对这个 bug 是绿的。

这类错误的共同形状是**判据和被判断的值不是同一个**：渲染字段用的是归一化后的值，判断用的是原始值。现在两者共用一个 `pending`，并且探针补了反向断言（没有提案的计划照常问）。

### 26.5 查了但决定不改的

**重复提到一件已收尾的事，会不会把它「复活」。** `applyCandidate` 的 duplicate 分支会更新文本与提案，但不动 `resolved_at`，于是「我下周还得再去交一次」可能被合并进那条已经办成的计划，然后既不显示也不再问。

改法是合并时清掉 `resolved_at` / `outcome` / `nudged_at`，让它重新变成待办。**没做**，因为反向的误判更贵：用户只是在复述「我上周交过了」，也被读成「又要做一次」，于是一件已经完成的事重新变成待办、过期、被问。而 `judgement.relation === "duplicate"` 这个信号里没有「还没做」的信息——用它来决定复活，等于让「说法相似」承担「事情状态」的判断。宁可留一个静默的窄缝，也不要一个会反复追问的错误。

### 26.6 这次检查的边界

没有真模型、没有长周期、没有并发、没有真实宿主的定时器。这四项里的任何一项都可能推翻上面的结论——尤其是「提示词被遵守」这一条，七版里所有靠模型写的东西（别名、时间短语原样抄、收尾调用）都还只是设计意图。

## 27. 升级不重启等于没升级（v0.2.24）

§14.2 的结论「装上就生效」是对的，但它的主语被误读成了「任何一次安装」，包括升级。2026-11-02 真机实测把这条推开：`dsh plugin add` 从 0.2.16 升到 0.2.23，13.9 秒跑完、磁盘上确实是新包，而进程里跑的还是启动那一刻的代码。

### 27.1 证据链

| 检查 | 结果 | 这个值只可能来自 |
| --- | --- | --- |
| 工具数 | 9 个 | 0.2.12（0.2.16 是 12，0.2.23 是 14） |
| `memory_doctor` | `unknown tool` | 该工具 0.2.16 才有 |
| `PRAGMA user_version` | 1 | 0.2.12 与 0.2.16 的 `SCHEMA_VERSION` 都是 1；0.2.23 是 4 |

三条互相独立，却指向同一个版本。注意「有 recall trace」不能当证据——recall 早在 0.2.12 就有了，把「有记忆在读」当成「新代码在跑」，是这次一开始误判的原因。

### 27.2 机制

§14.2 观察到的重组，触发条件是 **profile 的 `bundles` 列表发生变化**：新增一项 → 组合器多激活一层 → 调 `apply()`。升级时列表内容相同，只是 `node_modules` 里那个包的文件换了，**没有任何一项发生变化**，所以重组不触发——`apply()` 从头到尾没被再调一次，这才是「跑着旧代码」的直接原因。

「模块缓存」不是这次的原因，至少不能当结论：pnpm 把包放在内容寻址路径（`.pnpm/dsh-memory-loom@<版本>/…`），版本一变解析出的 realpath 就变了，Node 按 realpath 缓存，反而会拿到新模块。只有在宿主按固定 specifier 且 `preserveSymlinks` 生效时，缓存才会参与。这一点没有验证，**不作为解释写进结论**。

所以问题出在「谁会来调 `apply()`」，不是「调了之后拿到哪个模块」。插件侧无法解决它：`apply()` 里没有任何钩子能在「文件已换、模块未换」这个状态下被执行——那段代码本身就没在跑。

### 27.3 能做的只有两件事：说清楚、看得见

**说清楚**：README §2 与 §14.2 都改成「首次安装不用重启，升级必须重启」，并给出升级四步（备份库 → 装 → 完全退出重开 → 确认）。

**看得见**：`memory_doctor` 第一行恒为

```
· 版本  运行 0.2.24 · 库 schema v4 · 库上次由 0.2.12 打开
```

三个字段各有分工，缺一不可：

| 字段 | 来源 | 能证明什么 |
| --- | --- | --- |
| 运行版本 | `lib/index.js` 写死的 `BUILD_VERSION` | 此刻执行的是哪一版代码 |
| 库 schema | `PRAGMA user_version` | 迁移跑过没有 |
| 上次由谁打开 | `meta["runtime.previousVersion"]` | 这次升级真的发生过，不是原地不动 |

为什么 `BUILD_VERSION` 必须写死、不能读 `package.json`：`package.json` 回答的是「磁盘上装的是哪一版」，而这里要问的是「正在执行的是哪一版」。§27.2 那个情形恰恰是两者不一致——文件已经换了，跑的还是旧代码；此时读 `package.json` 会拿到新版本号，于是这一行**跑着旧代码却报新版本**，从诊断依据变成伪证。写死的常量永远描述「这段代码自己」，而这正是要问的问题。

代价是它会漂移，所以 `check-docs.mjs` 多了一条 CI 检查：`BUILD_VERSION` 必须等于 `package.json.version`。这是本项目第一次给「常量与包版本」加锁——之前只有 README 直链的版本号被盯着。

### 27.4 边界

- 只有三条证据、一次观测、一台机器。机制解释（bundle 列表没变 → 不重组 → `apply()` 没被再调）是从现象反推的，没有读宿主源码确认。
- 没有验证「先卸载再装」是否等价于首次安装（理论上会触发列表变化，因此会重组；没测）。
- `probe-version.mjs` 直接改库里 `meta` 来模拟升级，它验证的是「换版本之后能不能说出来」，**不是**「宿主在升级后会不会重组」——后者只能在真机上验，探针无能为力。

# dsh-memory-loom：架构、机制、读数与未解问题

> 版本 **0.2.71** ｜ 2026-11-13 ｜ 面向"没参与这个项目、但技术背景足够"的读者
>
> 这份文档不是使用说明（那在 `README.md`），也不是施工日志（那在 `docs/design.md`，93 节）。
> 它做三件事：**把系统的形状讲清楚**、**把读数的口径钉死**、**把还没解决的问题摊开**。
>
> 每个数字都带版本和脚本名。凡是"我们试过但失败"的地方，都给出当时的逐题读数——
> 因为这个项目里最贵的知识不是"做了什么"，是"哪些看起来显然该做的事其实是负的"。

## 0. 三个数字，和它们各自的意思

一句话版本：**它不追求"记住一切"，它追求"在 2,000 token 里放下最该被想起的东西，并且知道剩下的去哪拿"。**

| 读数 | 值 | 口径（这句话必须连口径一起说） |
|---|---|---|
| 检索面覆盖 | **690 / 714** | 714 题榜上"自动注入块 ∪ 搜索行"至少有一条含证据 10 字窗的题数。0.2.71，`bench-hmb/surface-coverage.mjs` |
| 端到端判分 | **689 / 714**，同尺子 **677** | 0.2.53 回放产物 + 一个强作答模型 + 官方 `grade.py`。689 是主 agent 单遍自判，677 是 28 个隔离子代理用更严的判分提示重判同一份答卷 |
| Benchmark 2.1 定位率 | **135 / 190 = 71.1%** | 证据轮原话是否落进"块 + 搜索 + 展开"任一通道。0.2.63 起，`bench-hmb/anchors-21.mjs`，产品档位 |
| Benchmark 2.1 端到端 | **A = 44.5** | 0.2.58，212 题（200 主 + 12 control），官方判分，与上一行**不是同一件事** |

**读这份文档前必须接受的三条口径纪律**（这三条每一条都是踩出来的）：

1. **"定位率"不是"通过率"。** 135/190 说的是"证据原文有没有被端到模型眼前"，它回答的是
   *材料到没到*；A=44.5 才是"答题判过没有"。两者之间隔着作答模型和判分尺子。把 71.1% 当成绩
   对外引用，是把天花板当成了地面。
2. **同一份答卷换判分员，会掉 12 题。** 714 上 689 → 677，12 题全单向、0 题反向，严的地方
   集中在"违反禁止 / 未知当事实 / 编造日期"这三类硬否决——旧判分基本没用过它们。所以
   **跨版本比较只能用同一把尺子的数**（677 对 673 这种）。
3. **所有"上界"都是代理量。** 锚点分层数的是"至少一个锚点命中"，而它和判对的关联只有
   69.4%（0.2.54 那批 200 题里，"至少命中一个锚点"的 111 道中判对 77 道）；"全部锚点命中"
   是 76.7%（23/30），但那个分母只有 30 题。**我们长期用一个宽松的代理指标指挥优化**，这是第 13 节 F 条要谈的问题之一。

**如果只有 20 分钟**：读 §5.2（为什么"给一半"比"不给"更危险）、§12.5（可判的 94 道失败里
92.6% 是召回问题，不是提示词问题）、§13（六条结构性缺陷）、§23（我想请教的八个问题）。
这四节加起来，就是这套系统的现状与我卡住的地方。

# 第一部分 · 架构与机制（Why & How）

## 1. 问题的形状：记忆是一个预算问题，不是一个容量问题

先把这件事说破：**如果上下文窗口无限，就不需要记忆系统。** 所以这个插件的存在理由不是
"帮模型记住"，而是"在固定预算下决定什么不进上下文"。整份代码里几乎所有取舍，都在回答同一个
反问句。

由此派生三个子问题，它们分别对应后面三节：

| 子问题 | 大白话 | 技术说法 | 对应机制 |
|---|---|---|---|
| 压缩什么 | 把一段对话压成几句话，压哪几句？ | 有损压缩的**保真度**与**聚合度**之取舍 | §2 分层 |
| 怎么找回来 | 压丢了的东西，还能不能拿到？ | 索引的**可达性**（reachability） | §5 Hook & Pull |
| 凭什么信 | 找到的这条是不是当时那句话？ | 证据链、时态、**可解释性** | §4 写入、§7 时间 |

一条贯穿全项目的经验：**这三件事不能用同一套判据解决。** 用相似度解决"压什么"会得到摘要，
用相似度解决"怎么找回来"会得到指针，用相似度解决"凭什么信"会得到幻觉——第三种必须靠
结构（谁说的、什么时候、什么条件下），不能靠分数。

## 2. 分层：压缩比就是产品定义

```
L0  原始对话        一字不改（写前脱敏），无长度上限，不进上下文
L1  原子事实        一句话 + 类型 + 域 + TTL + 显著度 + (主体,属性,值) 槽位   ~15–40 token/行
L2  事件摘要        标题 + 1–2 句摘要 + l0_from/l0_to 原文指针              ~50 token
L3  自我叙事        助手对自己的长期叙述（需 12 条证据才改写）
主观层              印象 / 日记 / 长期偏好（隔离，按人）
人设卡              五分区、可锁定、按来源分权（独立 section，不抢预算）
```

**为什么 L0 不裁剪。** v0.2.1 之前单条消息有长度上限，取消它的理由不是"存储便宜"，而是
**截断会让指针说谎**：钩子承诺"这段 2.7k 字"，取回来只有 800 字，用户无从知道尾巴去哪了。
宁可让库变大，也不让"取回的内容"与"承诺的内容"不符。这条后来成了整个 Hook & Pull 的地基。

**为什么 L1 是一句话，而不是原文。** 这是全项目最贵的一次取舍，也是最容易被误读的一次：

同一份 642 题语料，**索引原文的纯 BM25 拿 82.7%，索引一句话摘要拿 20.5%**。差距不在排序算法，
在**信息闸门**——命中一条，一边给你 382 字全文，一边给你 50 字摘要；取 6 条就是 2,300 字对
300 字，5–7 倍。

试过把摘要选句从"最长"改成"带具体值（数字/英文标识符）优先"：中间指标"关键句进摘要"
26.6% → 82.6%，**最终指标 20.3% → 8.7%**。原因是叙事文本里最长的往往是情节点，而那些数字是
"三天后""第十年"。

> **代价写在明面上：这套系统在"需要逐版本穷举"的任务上天然弱于全文检索。** 这是压缩的代价，
> 不是实现的缺陷。对抗它的办法不是把摘要换回原文（那等于取消产品），而是加一条**旁路**：
> 指针（§5）和原话通道。

**为什么事件摘要只留一到两句。** 一条经历的价值大部分在"发生过"，不在"每个细节"；细节由
`l0_from/l0_to` 保证可达。摘要的作用是**可辨识**（让我知道这条要不要展开），不是**可引用**。

## 3. 底层：为什么死磕 SQLite + FTS5 + CJK 二元组，不接向量库

### 3.1 问题的起点是一个没人管的细节

SQLite 的 `unicode61` 分词器把**一串连续汉字当成一个 token**。也就是说「我喜欢猫」是一个词，
只有原句完整出现才命中。任何中文检索的第一步，都是先解决"切不开"。

三条路：分词词典（要维护、有 OOV）、字符 n-gram（无词典、抗 OOV、有假匹配）、embedding
（要模型、要网络、要一致性）。

这里选了**二元组（bigram）**：`我喜欢猫 → 我喜 喜欢 欢猫`。写入与查询用同一个函数切，
FTS5 里用空格拼成短语序列。

### 3.2 文献早就把这条路的代价写清楚了，我们逐条对上

| 文献里的结论 | 出处 | 我们的对应 |
|---|---|---|
| 二元组是中文最稳的兜底表示（词 0.502 / 二元组 0.494 / 单字 0.449 平均精度） | Zobel & Dart, IRAL 1999 | 起点正确 |
| 最优是 unigram+bigram+word 混合，但代价大 | Nie et al. 2001；Kwok 1999 | 混合表示在**排序阶段**实测 −4.8pt，撤回 |
| 高召回、低精度，主要噪声是跨词边界假匹配（"京都"命中"東京都"） | Lucene SOLR-3653，30 万篇法律文书上二元组词表 180 万条 | 原话指针精度 **约 50%**（0.2.44 的 49%，修完跨天口径后 54.5%）——两条指针里有一条是废的，模型靠 60 字预览自己挑 |
| 碎片化：严格要求相邻，中间插一个字就整段失配 | — | 「渡口夜雾」对「夜雾从樟树渡口」只剩 2 个二元组；靠"片段扩展"补上下文，不补匹配 |

一个反直觉的量化结果（`docs/design.md` §46.3，0.2.42 口径：58/62，剩 4 道；现在 61/62 只剩
1 道）：那 4 道**没有一道是切分粒度问题**，全是**词汇失配**（vocabulary mismatch）：问「什么路子的歌」对「老粤语歌和
旧爵士」，问「那口味」对「美式加双份奶」，零个二元组共享。换任何分词器都救不了。

**所以二元组表示层的残余缺陷是 0 题；卡住的是表示层之上的两件事：选点策略和语义桥。**

### 3.3 为什么至今不接向量检索（离线实验做过，没合入）

bge-small / base / large，k=3 命中 41.0% / 49.0% / 52.4%，无条件并行接入可达 53.8%。
**没有合入**，四条理由按硬度排序：

1. **融合税。** 两路强弱悬殊时（词法整句 20.5% vs 向量 49.0%），RRF 会把强的一路拉平到弱的
   一路。合适的做法是**并集**而不是融合排序，但并集意味着候选集翻倍、预算不变——多出来的
   候选只会挤掉别的区（见 §6 的"加候选零和"定律）。
2. **它救不了这批题的主因**：一半是"这句话没成为一行"（写入侧），另一半是"一条只覆盖一个
   槽位"（粒度）。向量救的是"问法和原文用词不同"，占比最小。
3. **同构句上它更差**：`依赖名是 lmdb` / `依赖名是 badger` 余弦几乎一样，而这两句的区别
   **就是全部信息**。
4. **工程成本**：宿主 `LlmAdapter` 只有 `stream()` 没有 `embed`；FTS 靠 SQL trigger 同步，
   embedding 必须异步，于是多一条"索引落后于写入"的一致性问题；onnxruntime 体积超过整个插件。

结论：**值得做，但定位是"真实使用里的模糊召回"，不是基准提分手段，且只能做并集第四路。**

### 3.4 一次真实的性能事故：查询计划选错驱动表（0.2.64）

这是本文档里唯一一个"和算法无关、和数据库有关"的坑，值得记，因为它解释了一类系统性盲区。

**症状**：新接的官方 Benchmark 2.2 取面，单题 2,630 ms，一整卷 45 分钟里 96% 花在
`memory_search`（block 3 ms / search 2,538 ms / expand 2 ms）。

**定位**：`--cpu-prof` 只能到帧（`searchEvents` 里的 `stmt.all()`），再包一层 `DatabaseSync.prototype.prepare`
抓真实 SQL 与 `EXPLAIN QUERY PLAN`，才看见：

```
SEARCH e USING INDEX events_identity (identity_id=?)   ← 驱动表是 events
SCAN events_fts                                        ← 内表扫了 6686 次
```

写成 `FROM events_fts JOIN events` 时，SQLite 选了有索引的那张表当驱动表，然后用 FTS 表做
逐行 `SCAN`——**FTS 的 MATCH 只在驱动时才会走倒排索引**。改成 `FROM events_fts CROSS JOIN events`
（CROSS JOIN 在 SQLite 里禁止重排）后：

| 查询 | 改前 | 改后 |
|---|---:|---:|
| `searchEvents` | 1,209 ms | **3 ms** |
| `searchFacts` | 156 ms | **1 ms** |
| `searchL0` | 不变（本来就写对了） | 不变 |
| 单题取面 | 2,630 ms | **74 ms（35×）** |

**为什么三套基准都没发现**：714 每个身份只有几百行、2.1 也才几千行，那个规模下两条计划的
代价相当；**按行数增长的性能问题，在小基准上必然量不出来**。这不是"没想到优化"，是
"评测语料不在问题发生的规模上"——一个关于**测量环境**的教训，比 SQL 本身更值钱。

## 4. 写入：切段 → 抽取 → 判定，以及"换一个值不等于把话说准"

写入延迟是刻意的：**累计 2 万 token 或空闲 5 分钟**才触发一次整合（`maxRunSeconds: 180`，
单条 30 s 超时，重试 2 次，死信 20 条留 7 天）。理由很朴素——整合要调模型（可选），
而对话的响应不能等它。

### 4.1 切段：三条硬边界 + 一条动态上界

```
① 时间间隔 > 30 min
② 话题偏移（相邻轮的词汇重合度塌陷）
③ 情绪尖峰（valence/arousal 突变）
④ 段内再按"近期段长中位数"微切（样本 < 100 轮时用下限 minSecondary）
```

第 ④ 条是唯一"从数据里学"的参数，也是唯一带**样本不足降级路径**的参数：样本不够时它不猜，
退到下限，并在审计里写明原因（`样本不足（57/100 轮），使用下限`）。这是这个项目的通用风格：
**没有分布的地方不要造分布。**

### 4.2 抽取：双路径 + 一个"只记录不拦截"的校验位

| 路径 | 触发 | 产出 | 特征 |
|---|---|---|---|
| 模型路径 | 宿主提供 `llm` | 事实/事件/偏好/计划/指令 + 每条一句**原文摘抄** | 更准、更贵、有方差 |
| 规则路径 | 无模型 | 按标记词表 + 槽位规则抽原话 | 100% 可复现，抽取质量低但 L0 完整 |

模型路径的每条事实都要求附一句原文摘抄，写入前用 `quoteMatches` 在本地做字符级比对。三种
结局分开记（逐字命中 / 近似命中 / 找不到），但**不因为找不到就丢掉这条事实**——那会让抽取
质量差的模型直接失忆。校验位的作用是**事后能算出"这个模型在编造的比例"**，不是当场执法。

### 4.3 判定：当判据的维度与变化的维度正交时，加规则没用

这是 v0.2.32 修掉的核心 bug，也是全项目最值得讲的一处设计。

**现象**：「这个项目的依赖名改过哪几次」——库里明明有五次变更，检索最多返回一条。

**两层根因，第二层更隐蔽：**

- **抽取口径**：`FACT_MARKERS` 只认「调整为」「改名为」，而真实语料里 44% 的属性陈述用的是
  别的动词：`首次确立为`（115 条）、`转为`（171 条）、`被撤销`（48 条）、`移到了`（93 条）、
  `出现两种并存的取值`（39 条）。这些句子不是排在检索第 20 位，是**从来没成为一行**。
- **判定维度**：判定器比较**措辞相似度**，而一次取值变更前后恰好只差一个 token
  （`依赖名是 lmdb` / `依赖名是 badger`）。相似度极高 → 判成 `update` → `updateFactText`
  把旧行整行改写。库里只剩当前值，**"变过"这件事本身没被记下来。**

```
判定维度 ──► 措辞
变更维度 ──► 取值
       两者近乎正交，所以判定器在变更点上必然误判
```

修法不是加一条规则，是**换判定依据**：同一个 `(主体, 属性)` 下取值不同 → `contradicts`
（新行建出来，旧行 `superseded` 留在链上，`memory_edges` 记一条 `SUPERSEDES`）；取值相同
才交给判定器决定合并与否。判断收敛在 `judgeAgainst` **一处**，整合路径和 `memory_write` 共用——
因为"只有模型在场时才成立的链"不叫链。

**改名是唯一允许"两个名字等于一个主体"的地方。** 做法是把改名本身存成一条槽位
`(旧名, 名称, 新名)`，查询时按并查集求名字闭包。不新建 `aliases(subject, alias)` 侧表的理由：
侧表要重新回答"带不带版本、erase 清不清、导出里有没有"三个问题，每个答案都是一次迁移；
而"改名就是一行事实"免费继承了 `updated_at`、被 `purgeIdentityLayers` 扫到、出现在 `export` 里。
**能复用已有生命周期的东西，不要新开一张表。**

读数：变更题 0/38 → 31/38，材料齐备率 20.5% → 69.0%；事实行数 420 → 915（存储代价翻倍，
保留变更链的成本）。

## 5. 读取（一）：Hook & Pull

### 5.1 两个层次，两种失败

```
常驻层：钩子索引    上限 16 条 / 300 token 双约束（`maxHooks` + `hooksBudgetTokens`），
                    实测满员约 59 token/轮，只有指针：「- E37 要不要辞职的长谈 2.7k字」
常驻层：记忆块      软 2,000 / 硬 3,000 token，八区配额；714 全卷实测中位 567 token
按需层：memory_expand(ref)   按 E/F/D/P/L 编号取回正文，分页不截断
```

**为什么钩子要"稳定性优先于相关性"**：常驻集合落盘在 `loom_hooks.resident`，只在定时器
（5 分钟）、`memory_pack` 之后或显式 rebuild 时重算，渲染只读快照。这样同一段记忆在轮次之间
**逐字稳定**。这是刻意防**人格漂移**——漂移的根因不是上下文长，而是注入内容每轮都在变。

打分因此被刻意做得很朴素（事件 `0.75·salience + 0.25·recency`，事实 pinned 0.72 / 普通 0.24 +
`0.5·salience + 0.18·recency`）。它不需要准，只需要**排序稳定**；准是记忆块的工作。

淘汰策略也不是压缩：超预算的低分钩子进冷区（7 天，降权 10 分），正文一直在 L0 里，
冷区钩子仍可被 `memory_index search` 命中、直接 `expand`。**不花一次模型调用去做摘要压缩**，
因为那会引入不可预测性。

### 5.2 为什么说"传半截摘要比不传更危险"

这句话不是修辞，是量出来的。

2.1 的失败题按"证据可达性"分三层，再数"踩红线"（命中 `forbidden` 项）。口径：0.2.54 那批
98 道失败题（`judgments-21-v0254-report.json` × `lay-block/lay-refs.json`，逐题可复现）：

| 证据可达性 | 判挂题数 | 踩红线 | 踩线率 |
|---|---:|---:|---:|
| 只有检索摘要行 | 20 | 9 | **45.0%** |
| 块里只有 1 个锚点 | 13 | 5 | 38.5% |
| 三层都没有 | 65 | 10 | **15.4%** |

**半截信息比没有信息更容易踩线，接近 3 倍。** 机理不复杂：摘要行给了标题，模型照着标题补
细节，补出来的东西越过 `forbidden` 边界；而什么都没有的时候，模型倾向说"没记到"。

一个具体例子（`M02-G019/d000`，四个间隔全挂）：

```
原文 ：去晚了，黄铜的前天被人换走了，我换了只钢圈的，声音也还行。……我拿旧图纸换的
块里 ：事件标题「晨跑、画图、量现场、给薇薇带汤、换铃铛、看画室的猫」
        → 三个要点（黄铜被换走 / 换了钢圈 / 用旧图纸）压缩成一个词「换铃铛」
```

这道题考的就是被压掉的那部分。**这就是 Hook & Pull 必须存在的理由**：不是所有东西都该进块，
但进了块的那一条必须是"能指的"，而不是"看起来像答案的一个词"。

> **这条对产品的含义是反的：给一半不如不给。** 而当前实现做不到这个判断——它不知道
> "拿到的这条是不是完整"（第 13 节 B 条，第 23 节 Q2）。

## 6. 读取（二）：五路候选、三道闸门、七条旁路

### 6.1 五路

```
① pinned            常驻，不问查询
② FTS strict        所有二元组 AND（隐式 AND，见下）
③ FTS relax         任一命中，有前提
④ slot              问句同时点名了已知主体 + 已知属性 → 按 (subject, attr) 主键查
⑤ 原话 l0           派生层太瘦时才启动，返回 #L120-121 指针 + 60 字预览
```

四条设计判断值得单独说：

**(a) 为什么必须有第二遍。** `compileMatch` 把「你还记得我不吃香菜这件事吗」切成 11 个二元组，
用空格拼给 FTS5——**在 FTS5 里空格是隐式 AND**。原文命中 4 个就足够人读懂整句，11 个必须全中。
结果是那条记忆**整条消失，而且不报错**。这是全项目最典型的一类 bug：静默失效。

第二遍只在"太瘦"时跑（严格命中 < 3），三道守卫：放宽命中乘 0.55（结构上不可能反超严格命中）；
必须共享 ≥25% 的二元组；事件层更保守（严格命中为 **0** 才放宽，因为每个事件在 prompt 里占一整行）。

**(b) 第三条旁路：数实词，不除以问句长度。** 25% 那道闸门的分母是**整句问句**的二元组数——
短题 13 个、长题 30 个。同样共享 3 个实词，短题算 0.231，长题算 0.100，后者永远过不了。
可它共享的可能是「象棋」「送过去」「周一」这种一个词就够定位的实词。所以并列加一条：
**共享 ≥3 个内容词（`solidOverlap`）就放行**，不除分母。判据是"变坏的题必须为 0"，不是净值
为正：714 搜索 463 → 478（+15/−0，注入块一字未变）、62 题五个主读数逐位不动、2.1 开发集
111 → 120（+9/−0）。

**(c) 为什么槽位通道不做兜底。** 它只在词法结果为空时才查——这一条反直觉而重要：这类问题的
词法结果**不是空，是错**。它返回共享问句措辞的那几条，通常正好是最新那一条 + 几条无关的，
而链上更早的节点恰恰因为取值变了、措辞也跟着变了，不在里面。**等一个永远不为空的信号，
等于永远不等。**

**(d) 为什么融合不用 RRF。** RRF 在"两路都还不错且量纲不可比"时最优；这里两路强弱悬殊，
RRF 会把强的一路拉平到弱的一路。槽位通道因此用**锚定**：`slotSimilarity = 0.85`，略低于最好的
严格命中。`slotMax = 12` 只截块内，`memory_search` 尊重调用方的 limit（链题常要 50 条以上）。

### 6.2 七条旁路

这些通道的共同形状是：**不靠词面相似度进入结果**。多数命中后进 `tailRows`——排完序再填空位，
有空位才出现、不参与打分；钟点规矩更轻，它只给已有行加一段注记（"现在 17:25，已经过了
「下午三点后」这条线"）；界线那两条则相反，带着略高于当前最高分的分数插到最前。

| 通道 | 触发条件 | 为什么不能按词召回 |
|---|---|---|
| 稀有实词 | 与行共享一个 DF 极低的实词（专名） | 「周哥」全卷只出现 3 次，按问句比例永远过不了闸门 |
| 话题链 | 每次检索都跑（`topicTrigger: always`） | 问"这事走到哪了"时，答案那一句的词面最不像 |
| 计划 → 结局 | 问句在问进度/结果 | 「搬家后来办成了吗」的动词在原话里根本不出现 |
| 钟点规矩 | 解出钟点、与 `now` 比一次 | 「下午三点后就不喝了」与「这会儿喝咖啡合适吗」零共享 |
| 界线（情绪） | 问句是"对着助手的低落" | 「别主动提退稿邮件」与「今晚写得很卡」零共享；靠**情形**不靠词 |
| 界线（有听众） | 问句里有"公开/在场/当面" | `permission as runtime state`：敏感记忆的浮现由情形决定 |
| 承诺 → 履约 | 种子是承诺句、问句在问下文 | 「我欠你三件夜班见闻」与「先还一件」零共享 |

界线为什么可以插队、而别的不行：**代价不对称。** 答错一条普通事实可以再问一次，踩一次线撤不
回来。这个理由在代码里写成 `lead = 最高分 × 1.02` 加一行注释——它不是相关性判断，是**风险定价**。

### 6.3 三条定律（这是全项目最硬的经验）

1. **加候选零和**：62 题只有两条指针 + 每面 token 预算，多出来的候选只能顶掉有字面证据的那条。
   五次全负。
2. **换候选零和**：`baseRefs[0..1]` 已经是这类启发式能挑的最好的两条。拆臂优先、实体扇出、
   换第二条指针，三次全负（扇出窄表在 714 上 648 → 617，+5/−36）。
3. **只有"有空位时追加"不为零和**：界线指针、话题链、计划→结局都靠这条。**但"只追加不插队"
   只对顺序成立，对容量不成立**——结果列表是固定 10 条，追加进去就要顶掉第 10 条（0.2.58 唯一
   一条变差的题就是这么坏的）。

## 7. 时间：三种时间、一种意图、一次算术

### 7.1 三种时间不是一回事

| 时间 | 字段 | 回答的问题 |
|---|---|---|
| 事务时间（transaction time） | `l0.created_at`、`facts.created_at` | 他**哪天说的** |
| 有效时间（valid time） | `eventDayKey`（从"明天/昨天/今天"算出） | 那件事**哪天发生的** |
| 生命周期 | `ttl` / `expires_at` / `expired_at` / `status` | 这条**现在还算不算数** |

第二行是从 Zep / Graphiti 的双时间轴搬来的，但只搬了"能算出来的那一半"：`eventDayKey` 用
和 `anchorRelativeTime` 同一张表、同一套排除（「后天免疫」「明天出版社」不认），算不出返回
`null` 而不是"当天"。**覆盖率只有 9%**（证据对里能算出事件日的比例）——这是第 13 节 F 条。

用途是"并指针"：事件日相同 + 共享实词 ≥2 + 同一段对话 + 相隔 ≤8 轮 → 并成一个 `#L` 区间；
同一事件里更晚的那次陈述当**代表句**（同一个 valid time 上，最新的 transaction time 才是这件事
现在的说法）。渲染成 `[04-01 · 原话 · 事件 04-02] 「明天还得陪我爸…」`——引号内一个字不动。

### 7.2 衰减：为什么"想起"改变的是斜率，不是起点

```
strength = base · (1 + t/S)^(−d)        base ∈ [0.55, 1]（情绪显著度），d = 1，S₀ = 30 天
访问后   ：S ← S · (1 + boost·S^(−0.2))  boost = 0.25，S 上限 50·S₀
过期后   ：× 0.5^(天数/45)，地板 0.02
```

**为什么双曲而不是指数**：指数衰减早期跌得比人快、晚期跌得比人慢；双曲尾部更肥，符合
"很久以前的事还在，只是模糊了"。

**为什么访问提升 S 而不是重置 t**：重置 `t` 意味着"每次被想起，它就和刚写下时一样新"——
一条被反复问到的老事实会永远占前排，新记忆永远挤不进来。提升 `S` 是"这次想起让它以后忘得
更慢"，但**当前年龄照算**。前者是通货膨胀，后者是复利。

**地板 0.02 的意义**：`finalScore` 最后取 `max(floor, ...)`，保证任何存在的记忆都有非零分数。
这样"找不到"永远只由**召回**决定，不由**打分**决定——两个失败原因分开，才查得动。

**过期不是删除，是连续降权**：一条过期两年的偏好仍然找得到（0.02 而不是 0），只是排不到前面。
删除只有两种来源：用户明确要求，或路人到期。

### 7.3 LATER_INTENT：一个问句侧的意图，管两件事

名字容易误解，要说清它到底是什么：

```js
const LATER_INTENT = /(后来|之后|以后|最后|最终|结果|到底|交完|完后|成了|办完|弄完|送到|交齐|有没有|进展|还欠|还剩)/u
```

它是一个**问句正则**，不是时间字段，也不是"最后意图"这种记忆类型。它管两件事：

1. **两个时间端里取哪一端。** 当候选池里同时有"最初"和"后来"两句时，问句命中它就取**较晚**的
   那一端；问句命中「最初/最早/当初」时取**较早**的那一端（0.2.41 补的对称）。
2. **话题链的入口（0.2.56 起）**：答案端不在池里时也走话题链。触发面 10/212 → 56/212，
   但补进去的 13 条只命中 1 条（7.7%）——这个 7.7% 直接引出了 0.2.57 的重新设计（§7.4）。

它解决的是**"早期提及干扰"**，但这个干扰的根因不在时间，在**词面**：

```
79 道未命中题里，48 道（60.8%）检索到的条目全部早于答案轮
```

原因是人的说话方式：**第一次介绍一件事时会把细节说全，最终结果往往只有一句。**
所以"词面最像的那一条"系统性地是"第一次介绍"，不是"最后结果"。

### 7.4 topicAnchor 的重构：从"最稀有词"到"最像在谈这件事的轮"

**第一版（0.2.51）**：取问句里 DF 最小的内容二元组当锚（DF 本身就是"这个词有多专指"：灯箱
全卷 1 行，"上次"几十行），沿话题取**最晚**一次陈述。

**它错在哪（0.2.57 量出来的）**：M01 的 39 道话题链题里，**29 个锚点是跨词边界的碎片**——
「我之」（「我之前」切出来的）、「爸问」「式有」「底多」「有跟」。它们 DF 只有 1–3，靠"最稀有"
赢下比赛，带回一句与话题无关的话；真正"没有候选"的题只有 1 道。

**第二版**：判据换成**"哪一轮最像在谈这件事"**——与整句问句共享 ≥2 个**内容词**（就是事件
合并用的那条 `SAME_EVENT_OVERLAP`），取最新在先，最多三条。位置走旁路出口：排完序再追加、
有空位才出现、不参与打分，老锚点通道**并存不删**（第一版做成二选一，714 上 +22/−2，两条变差
全是"话题名唯一"的编故事题）。

读数：714 搜索 479 → 501、工具面 663 → 667、**+22/−0**；2.1 上界 121 → 126/190、**+5/−0**；
62 题五个主读数逐位不动（指针 104 → 120，全是追加）。

0.2.58 把入口也放开（`topicTrigger: always`）：714 搜索 501 → 535、**+34/−0**；2.1 上界
126 → 129/190。代价是每题平均多 66（714）/ 100（2.1）个字符。

> **M02 上收益只有 3 个时点**，原因不是判据不好：那副库里"与问句重叠 ≥2 的轮"中位 **43 行**、
> 最多 465 行（M01 是 2 行）。**同一个判据在闲聊密度高的语料上区分力弱，这不是调参能解决的。**

### 7.5 "另一天"是日历上的次日，不是满 24 小时（0.2.45）

原话通道给第二个指针时优先"跨天"那句（"后来呢"的答案常在另一天），而"跨天"原来按
`abs(Δt) ≥ 24h` 算。04-08 18:10 说「我把那盆迷迭香挪到阳台里侧」，04-09 11:17 说「浇水壶先放
在阳台门旁边」——**这是次日，也是答案**，只隔 17 小时却被判成同一天，名额让给了一条隔三周的
无关句。改成按本地日历日比较（`dayKey`，不是 `floor(ts/864e5)`，否则跨零点会话会在 UTC 整日
边界上切错）。

一行语义错误的修复：62 题 **6 好 0 差**（要点 77/99 → 83/99，全中 42/62 → 48/62），
714 工具面 84.3 → 86.0，`相似事件` 80 → 90%。

### 7.6 跨天窗口的日期是产品的责任（0.2.59）

一条原话指针的窗口常有 8–16 行、**经常跨天**，而搜索行上只标了**被匹配那一句**的日期。于是
窗口里前一天说的「明天」被当成标签那天说的——`P17-CASE-025` 四个时点全错一天。

修法是纯渲染：换天处行首打 `[04-01 周三]`，同一天后面的行沿用上一个标记。周几一起给，
因为「周一」「上周三」是同一个算术、只多两个字。

**这是"产品该负责的算术"，不能外包给模型。** 相对日期是模型最容易算错、也最容易"自信地算错"
的一类，而我们要的信息全在库里。

## 8. 装配：预算是分区制，不是排行榜；抗噪的结论是"别罚"

### 8.1 八区配额

```
【长期偏好】 floor 15% 或 140 token —— 常驻 3 条，不问查询
【计划】      floor 10% 或 100 token —— 常驻 3 条，过期的会问"后来成了吗"
【今天该做的事】 floor 8% 或 80 token —— 常驻 2 条原话，按提前量排序（0.2.65 起默认开，0.2.66 起认节日与农历）
【事实】      目标份额 75%（1 − subjectiveShare），保底 300 token，用尽后可从硬上限回填
【共同经历】  至少 25%，且不低于事实区已到的位置
【印象】【日记】 合计 25%（下限 120 token），其中日记保底 40%，防止长印象吃光份额
【自我叙事】  单独一段，不占那 25%——只要还有空间就追加到硬上限
```

**为什么偏好和计划必须常驻、不能靠 similarity**：它们回答的是同一个问题——**什么必须在不被
问的情况下想起来**——而这恰恰是相似度答不了的那个问题。用户不会重复说「我不吃香菜」，
也不会重问一个已经说过的计划，所以查询里永远不会出现这两个区需要的词。

**一个真实事故的形状**：`preferences` 表在规则路径下**是空的**（偏好一直写在 `facts` 里，
`kind='preference'`），而偏好区读的是那张空表，于是它每一轮都渲染成空，
`residentPreferences` 这个配置项从来没接过线（调到 5，714 题逐项不变）。
**一个配置项读的表永远是空的，调它不会报错，也不会有效果。**

**【今天该做的事】为什么在块里，不在检索结果里**：它的问句是"到单位了，先去泡杯茶"这种情形
陈述，字面上总能撞满十条闲聊（"我先去洗漱""先去把窗帘拉上"）——**检索结果的名额永远是满的**，
而追加档只填空位，所以第一版（0.2.64，挂在 `memory_search` 后面）在 76 题上是 0 好 0 坏。不是
判据错，是没有位置。常驻块没有这个竞争：它回答的本来就是"没人问的时候该想起来什么"。

判据是**按日子找，不按词找**，日子本身也分三类：公历字面量与相对词（`resolveDue`，所有日期路径共用）、**节日与农历**（`festiveDue`，只服务这一区）。后者三路按具体程度排——农历日期字面量、`节日前 N 天`、节日当天（要有**未来指向词**或「那天 / 当天」，「中秋得加班」「中秋那天回不来」是将来，「中秋的月饼真难吃」是评价）；过去指向（去年 / 上次 / 那次）整句不认。**二十四节气另有一张表**（`SOLAR_TERMS`，2020–2060，同样是天文台公布值）：节气在公历上是浮动的，清明落 4 月 4–6 日、冬至落 12 月 21–23 日，这四十一年里清明有 26 年不在 4 月 5 日。**判据写成规则表与闸门表两张，闸门独立于规则**——加一条新规则时闸门自动生效，不会因为漏写一个判断而静默失效；歧义大的五个节气词（雨水 / 小满 / 白露 / 小雪 / 大雪）只认「那天 / 当天」，因为它们在口语里多数时候不是节气（「小满」在 2.2 语料里出现 1562 次，全是人名）。**2020–2060 的农历月首落成一张表**（`LUNAR_STARTS`，41 年 507 个初一，约 4 KB，由香港天文台的逐日对照表生成），查表同时拿到初一与月长；表外年份退回春节公布表与 `Intl`。为什么不信 `Intl`：ICU 算朔的时刻有中位 4.5 分钟误差，朔落在午夜前后就把初一判到隔壁那天，官方逐日比对里 1901–2100 有 0.6% 的日子对不上，2020–2060 这四十一年里错了三个月初一（2027 正月、2030 正月、2057 九月）。有月长还挡掉一类错：正月只有二十九天时，「正月三十」不该被算到二月初一（见 `docs/design.md` §101.5–§101.10）。两条实现上的坑写进 `docs/design.md` §101.4：SQL 模板串里的注释**不能带反引号**（会把模板串提前闭合，运行时是 `ReferenceError`，被 `catch` 吞成「到期区为空」）；**「取最晚」是分句之间的规则，不能跨解析器用**（泛的节日名不许覆盖具体的公历词）。

并且端原话（证据几乎都是原话，派生层对"打算月底那天下班去交
电费"这种句子有损）：单个日子、指的那天晚于说的那天、至少提前两天，然后按**提前量**降序。
提前量那一步是被实例打出来的——"明天弄完""我明天先打个电话"和"科目二下周二考"在日期判据上
完全一样，能分开它们的只有提前量：**说"明天弄完"的人不需要记忆。** 三套读数见
`docs/design.md` §100.10–§100.11（714 块 132→135、+3/−0；62 题逐位不变；自然榜 X4 1/13→9/13）。

**预算是个上限，不是目标**：`budgetTokens = 2000` 时块实际渲染 369–480 token（18%）；压到 400
才从 13 行掉到 11 行。也就是说 **2000→1000 之间几乎不产生差别**，决定"块里有什么"的是评分与
配额，不是 token。这件事重要，是因为它会让一个很自然的猜想落空——"块太大，模型觉得够了就不
调工具了"。**块并不大。**

### 8.2 四种行内标记

| 标记 | 触发 | 含义 |
|---|---|---|
| `（待确认）` | 模型抽取且自报 confidence < 0.6 | 这是推断的，不是他说的 |
| `（可能已过时）` | 与当前话共享 ≥45% 词汇且**命题**否定/数字不一致（「不错」「差不多」「忍不住」「不算」这族固定搭配先剥掉再判，它们含否定字、整词却是肯定或弱化） | 现在的说法优先 |
| `（语气偏冲）` 等 | 事件 valence/arousal 非中性 | 这话当时的口气 |
| `（旧值）` | 槽位链上被 superseded 的那节 | 这是历史版本，不是当前值 |

**第一行曾经是坏的（0.2.54 修）**：规则路径把 `confidence` 写死成 `.55`，而标记的线是 `.6`。
两条线一夹，抽出来的**每一条**都低于阈值，全被标成「待确认」——2.1 上量过：注入块的事实行
1009 行里 975 行带这个标记，**96.6%**。它一条也没筛掉，只是给每一行都加了一句"这是推断的"，
而那一行恰恰是用户原话的截断。

> **阈值不是判据，判据是"谁写的、写的时候有多确定"。一个写死的常数配一条阈值，等于没有阈值。**

### 8.3 抗噪：为什么最终结论是"别罚"

主流 RAG 的直觉是"去重 / 减冗余 / 多样性采样"，因为冗余直接等于成本。**这里量出来是负的，
而且是最伤的一条。**

四份外部材料里唯一标"极其重要"的就是冗余惩罚（"共享 >4 个词就丢低分那条"），第四份还把它
升级成边际信息增益。实测（`diag-21-anchor.mjs`，9 条规则逐条在同一池子上裁决，口径是
**真增量**——只在"旧版产物还没交付到答案轮"的题里数）：

| 规则 | 判据 | M01 命中 / 真增量 | M02 命中 / 真增量 |
|---|---|---:|---:|
| `q2tail3` | 最新 3 行（现产品） | 21 / **10** | 8 / **7** |
| `w3` | 分数（重叠词数）前 3 | 23 / **10** | 11 / **7** |
| `comp3` | **连通分量各取 1（拓扑学）** | 21 / **10** | 8 / **7** |
| `marg3` | **边际增益（减已选重叠）** | 23 / **10** | **4 / 2** |
| `dens3` | 密度分（重叠/字符） | 23 / 10 | 10 / 6 |
| `budget200` | 200 字符从最新往回装 | 22 / 10 | 8 / 7 |

两件事一次看清：

- **M01 上十条规则的"真增量"全是 10**，不是"差不多"，是同一批题。换判据在这一层是零和。
- **冗余惩罚 M02 7 → 2，掉 5 题**，所有规则里最差。原因：M02 的池子中位 53 行，正确答案
  **本来就在那一簇里**——同一个事件被说了十几遍，十几行互为冗余，多样性抽样把唯一的正确
  那一行当成"重复"丢掉。

> **池子大的时候，"和已选重复"不等于"没用"。** 这与 RAG 的直觉相反，但 53 行同话题的库就是
> 这么长出来的。更根本的区别：**在 RAG 里冗余是成本，在这里冗余是候选**——因为最终进上下文
> 的只有两三条指针，"同一件事被说成五遍"恰恰是"其中一遍带着你要的那个数字"。

另外，那个"200 字符预算"恰好等于 3 条钩子——**这是等重条目，带 Token 约束的 0-1 背包在这里
是退化的**，"按 `Score/L` 装包"就是"取前 k 条"。这是第三部分第 15 条的伏笔。

## 9. 横切：身份、删除、降级、备份、热加载

| 切面 | 做法 | 为什么这么定 |
|---|---|---|
| **身份** | `master` / `friend` / `visitor` 三级；所有表带 `identity_id` | 跨身份只给 L1/L2，不给 L0 逐字；主人也不能读别人的原话 |
| **路人** | 48 小时后删原始对话，事实保留但降权到 ≤0.4 | 「不记得你说过什么」和「不记得你是谁」是两件事 |
| **删除** | 访客立即、六层全清；朋友 7 天冷静期 | 承诺是"把这个人删掉"，就得按**承诺**实现，不是按表实现 |
| **降级** | 三类原因分开记（配额 / 调用失败 / 判断层），每天 200 次调用上限 | 一个布尔说不清"为什么今天没记住" |
| **备份** | `VACUUM INTO`，24 小时一次，留 7 份，同盘 | 挡误删和写坏，不挡硬盘坏；同盘不算备份 |
| **热加载** | 首次安装即生效；补挂已存在的 agent；**升级必须重启** | 宿主只在"bundle 列表长度变化"时重组，升级长度没变 |
| **版本哨兵** | `BUILD_VERSION` 写死 + `memory_doctor` 首行打印 + CI 校验 | 新代码没跑起来时这行根本打不出来——所以它不会撒谎 |

**"删除按层实现，不按表实现"**这条值得单独记：第一版 `erase` 只清 `l0` 和 `facts`，而
`events.summary` 里躺着的就是原话的压缩句，`memory_expand` 仍能按 E 编号读回；偏好、日记、
印象、人设覆写没有任何删除路径碰过。修法是 `purgeIdentityLayers()` 一次清六表。
**一个删除动作涉及几张表，应该在设计时就写下来，而不是等用户发现"它还记得"。**

### 11.4 结构化赢在哪、输在哪（0.2.42 的对照，以及它是怎么被补上的）

0.2.42 时按考点把覆盖面拆开，和题库公开的六家成绩并排，形状非常清楚：

| 考点 | loom（0.2.42） | Qwen RAG | OpenViking | 属于 |
|---|---:|---:|---:|---|
| 生日 / 相对日期 | **100 / 100** | 100 / 63.6 | 100 / 63.6 | 聚合 |
| 约定和欠账 | **89.4** | 81.8 | 58.2 | 聚合 |
| 纠错 | **93.8** | 91.7 | 87.5 | 聚合 |
| 用户的基本信息 | 68.8 | **85.7** | **83.9** | 保真 |
| 带条件或期限 | 43.5 | **76.3** | **79.7** | 保真 |
| 敏感的事 | 50.0 | **87.5** | **95.0** | 保真 |

**赢的是"聚合"**——答案不在任何一句原话里，要把两端接起来（约定→履约、生日、相对日期、纠错）。
**输的是"保真"**——答案就是那一句话，逐字，而那句话在压缩里被改写、丢了主语、被截断了。

到 0.2.53，三格保真全部补上来了（用户基本信息 100%、带条件或期限 98.3%、敏感的事 100%），
但补法值得注意：**每一格都是加一条规则**（`SELF_SLOT_RULES`、`KIN_SLOT_RULES`、
`BOUNDARY_MARKERS` + `BOUNDARY_SITUATION` / `BOUNDARY_WITNESS`、情景词表、钟点规矩）。
这就是第 23 节 Q6 的由来：**规则的维护成本在上升，而每条规则的覆盖面都很窄。**

一句话：**结构化的收益在聚合上兑现，代价在保真上支付。** 原文路线不做结构化，所以没有这笔支出——
代词和称谓都还在同一段上下文里；但它也永远得不到"约定→履约"这种跨轮聚合的分。

| 全部锚点命中 | 30 | 7 | 76.7% | **7.1%** |
| 无锚点（不可判，剔除） | 4 | 4 | — | 4.1% |

口径：最后一行是 `state: unjudgeable` 的特例题（`xu1` / `xd1` / `xc1`），锚点尺子量不了它们，
**不进归因分母**。所以可判的失败是 **94 道**。

**92.6% 的失败（87/94），答案原文从来没有完整地出现在模型眼前。**

再看那 34 道"有锚点命中却答错"（= 27 道部分命中 + 7 道全命中；**与 12.4 里 0.2.58 判分的
`over_hedged` 34 道不是同一批**，两者只是数字碰巧相同）：里面**没有一道是"全部锚点都进块"**。
13 道"块内有"的题，锚点数 2–4 个，**命中数全部是 1**——也就是说模型看到的是"答案的一个碎片"，
它说"不记得"是**正确的行为**，不是过度防御。

```
M01-G089/d000  问：咱俩编的汤团的武侠故事，汤团现在是什么身份？
   答案（1924 轮）：它不是刺客，它是威风的总镖头，带一帮猫小弟押镖
   块里（1948 轮）：镖头负责踩脸        ← 同一个话题、更晚一轮、另一个说法
```

模型看到"镖头"这个词，但没有"总镖头"这个身份。它弃权是合理的。

> **所以"过度防御"这个词在 2.1 上并不成立；准确的说法是"欠召回导致的合理弃权"。**
> 唯一的例外是 0.2.59 修掉的那一条：作答须知第 5 条原来写"两条冲突时以时间新的为准"，
> 这条对**改口**是对的，对**没解释的矛盾**是错的（用户一处说地板浅灰、一处说米色，谁也没解释
> 为什么），它让作答者替用户裁定。`没解释的矛盾` 47 题里 8 道失败（`design.md` §82 那次复跑；
> 0.2.53 的 689 口径下是 3 道），其中 **6 道**是这条规则直接造成的。这是真正的提示词问题，已修。

### 12.6 间隔梯度其实是召回梯度的投影

| 间隔 | 失败率 | 其中"三层都没有" | 零召回占失败 |
|---|---:|---:|---:|
| d0 | 34.1% | 4 | 28.6% |
| d3 | 43.6% | 11 | 64.7% |
| d15 | 56.8% | 16 | 76.2% |
| d45 | 51.4% | 12 | 66.7% |
| d90 | 57.6% | 12 | 63.2% |

d0 是唯一"零召回占不到三成"的格子：当天的事大部分被注入块捞到了，14 道失败里 10 道是**碎片**。
d3 之后零召回稳定在 63–76%。

表外还有 15 道特例题（后缀是 `xt1a` / `xu1` 这类，不进四个间隔档），98 道失败里有 9 道落在
它们身上——所以四档的题数是 41/39/37/35/33，加起来 185，不是 200。

**所以 d0→d90 掉的那 23 个点，掉的是召回，不是记忆的衰减。** 这条也解释了"为什么当天题反而
失败率高"——不是模型不擅长时间近的事，是注入块里塞了太多碎片（见 §5.2 那张 45.0% vs 15.4% 的表）。

## 13. 六条结构性缺陷（机制层面，不是调参层面）

以下六条是我认为**在当前架构内无法靠调参解决**的。每一条都给出可复现的证据。这一节是第三、
四部分的入口。

### A. 表示层：词汇失配（vocabulary mismatch）

问「什么路子的歌」对「老粤语歌和旧爵士」，问「那口味」对「美式加双份奶」，**零个二元组共享**。
2.1 的 N 桶 21 道（36%）全在这一类。文献里这叫 vocabulary mismatch，解法只有三条：查询扩展
（PRF，实测取不到词）、稠密检索（融合税，见 §3.3）、**写入时改写成自足句**（Mem0 那条路，
需要模型，且会覆盖历史）。**规则路径里没有素材。**

### B. 完整性：系统不知道"这条指针够不够"

一条搜索结果回来了 60 字预览，它可能是答案本身，也可能是答案的第一个词。当前实现**无法区分**，
于是只能全给——而 §5.2 量出"给一个碎片比什么都不给更容易踩线，接近 3 倍"。

这不是排序问题，是**信息完整性判定**问题：需要知道"问题问几个点、这条覆盖了几个"。当前连
"问题有几个提问点"都没有可靠标签（试过用"证据 fact 数 ≥ 2"当标签，逐题看发现标签本身是错的：
「《海边的钟》作者这一栏该怎么填」是一个提问点、两条证据）。

### C. 容量：两条指针 + 10 条窗口

`memory_expand` 只展开前两条指针（第三、四条对模型没有增量，实测过）；`memory_search` 的结果
列表固定 10 条。而 §6.3 那三条定律说明：**在固定容量下，任何"换人"的策略都是零和**——
加候选、换候选、拆臂、扇出、换判据，五次以上全负。

> 一句话：**这不是"排序还不够好"，是"这个容量下已经没有更好的排序"。** 想再往上，只能增加
> 容量（成本）或增加通道（§6.2 的追加档是唯一允许的形式）。

### D. 判据：同一候选池上换判据零和，说明"选择"这一层没有信息了

M01 上十条规则的真增量全是 10；M02 上三换三。这意味着池子里的行**在判据这一维度上是等价的**，
真正区分它们的信息不在"重叠多少 / 密度多少 / 是否冗余"，而在**"这一行讲的是谁的哪件事"**——
也就是实体与属性，抽取层还没解出来的东西。

**这是我认为最根本的一条**：检索层已经没有可挖的信息，剩下的增量必须从**写入层**（把每一行
写成自足的、带主语和属性的句子）来。而写入层要模型，模型要钱，钱在这个比赛里是负分项（§24）。

### E. 测量：代理指标与目标指标脱节，且作答方差比产品差大一个量级

- 代理指标（至少一个锚点命中）与判对关联 **69.4%**；目标指标（全部锚点命中）**76.7%**，
  但分母只有 30 题。
- 91 题配对实验：同一份记忆、换一批作答者，**13 题翻转（14.3%）**。而这几轮改动落在 1 个点
  以内。

> **后果：我们测不出 1 个点的改动。** 714 严判的配对翻转数是 58（8.1%），标准误 √58 ≈ 7.6，
> 所以"净 −4"和"净 −1"都在噪声里。任何"这次涨了 1 个点"的说法，如果没有 ≥10 题的单向差，
> 都应当存疑。

### F. 时间：有效时间只能从相对词算，覆盖率 9%

`eventDayKey` 依赖原话里的「明天/昨天/今天」；算不出来就返回 `null`。证据对里**只有 9%** 能算出
事件日。而 2.1 里 `相对日期`（25 个 missed 项）与 `时间题`（24 个）是最大的两个失分点，
2.2 的 dev 集里 `due_day` 是**全场 0%** 的一类（Qwen / BM25 / 全塞都是 0）。

**这一格特殊：它不是我做得不好，是所有人都 0%，而我们有现成零件没接上**（`clockRules`，§21）。

# 第三部分 · 被证伪的"伪需求"（What we killed）

这一部分是这份文档里我最看重的。开源项目通常只写"我用了什么"，而这里要写"我试过什么、
为什么它是错的"——因为下面每一条，在会议室里听起来都对。

裁决工具是同一套：**逐题比对 + 真增量 + 两套基准一起跑**。任何一个机制，只要出现"变坏的题不为 0"，
就撤回，不管净值多好看。

## 14. 手写概念映射表 / 同义词扩展

**这个想法长什么样**：`{单位: [公司, 合同工, 职员]}`、`{咖啡: [美式, 拿铁, 手冲]}`，检索时把
问句里的词按表展开成 OR 组。这是最自然也最古老的做法，我们试了**三次**，全负。

| 次数 | 做法 | 读数 | 结论 |
|---|---|---|---|
| 1 | 职业词表加进**查询侧**（往召回表达式里加词） | 62 题定位 59 → **56** | 同一属性试了三轮全负 |
| 2 | 六组同义词（天气/咖啡/上下位/对象词…） | 714 工具面 +6，但**变坏 3 行** | 撤回；变坏的全是"磁铁" |
| 3 | 把「雨夜」收进情景词表 | `whisky/d15` 全中，**同一人物 d45 从全中掉成 0** | 净 +1/−1，撤回 |

**为什么错**（三条机理，一条比一条硬）：

1. **同义是双向的，情景不是。** 天气可以互认（「下雨」≈「雨天」），但咖啡与美式是**上下位**，
   认了就会把「我喝什么」当成「别人该喝什么」——第 2 次变坏的三行全是这个形状：「只喝常温茶
   或者热美式」抢了「给我姐点咖啡」的第一条。
2. **对象词的 IDF 高，但不携带区分力。** `合同工` / `编制内` 这类词在库里出现在几十条不相关的
   事实上，展开它等于把它们全拉进来。**IDF 高不等于有意义。**
3. **补充短语在排序里是"领先一档"，不是"加一点分"。** 密度就是杀伤力——只有"记下来时一定
   长这样"的词才配进这张表（`我爸`、`别叫`），而"这个人可能这么说"的词不配。

**那正确的位置在哪？** 索引期，而且**不是按词，是按条目**：`ALIAS_SYSTEM` 在写入时给每一条
记忆生成"用户下次可能怎么问它"的别名，写进 `facts_fts.alias_tokens` 独立列（schema v7），
权重 5.0，`GENERIC_ALIASES` 挡掉 30 个无对象词（工作/心情/事情/时候…）防磁铁。
规则路径也在生成：M01 的 386 条事实里 14 条带别名，M02 的 2502 条里 405 条带。

Solr 文档里那句话是这一节的判词：**同义词展开只能选索引期或查询期之一，不能两边都做。**
我们索引期已经有一份别名列，查询期再展开一次本来就是冗余的——实测的零正是这个冗余。

**还有一条产品层面的**：那份 JSON 里的例子是 `镖头`/`刺客`/`军师`/`车铃`/`钢圈`——**全是测试集
里的人物与物件**。手写这份表就是对着题库做题，换成真实用户全废。而那套词"不在问句里，
也不在任何一张人能写出来的表里，**它在语料里**"。

## 15. 拓扑学连通分量、贪心背包、冗余惩罚

**这个想法长什么样**：把上下文组装写成一个带 Token 约束的 0-1 背包（率失真 / 贪心装包），
用图论找连通分量做多样性抽样，用贝蒂数查"矛盾环"，并对"共享 >4 个词"的条目做冗余惩罚。

### 15.1 背包在这里是退化的

材料的所有招式都建在一个前提上：**候选行长度 `L_i` 各不相同**，所以要按 `Score/L` 装包。
这个前提在本产品里不存在：

1. 进块的每一行都是钩子，`clip(60)` 之后统一 ≤60 字符；
2. 正文不进块，走 `memory_expand`。

所以等重条件下的最优解就是"取前 k 条"。材料那个"200 字符预算"**恰好等于 3 条**，也就是说
它算出来的解和现有实现逐位相同——中间多出来的所有复杂度，收益为 0。

### 15.2 连通分量等价于"最新 3 行"

`comp3`（每个连通分量各取 1）在 M01 上命中 21、真增量 **10**，与 `q2tail3`（最新 3 行）**逐位
相同**；M02 上 8 对 8，也相同。原因很朴素：这个"图"是"同话题邻接"，连通分量就是"最近这一段
在聊的那件事"，而最新 3 行本来就在那一段里。**拓扑结构在这个问题里没有信息量**——它不是
一个有洞的复形，是一串时间上相邻的句子。

（贝蒂数那条没测：它属于生成端的矛盾检测，要判分回路才能验；而"改口"已经由 `status` +
`superseded_by` 承担了。）

### 15.3 冗余惩罚是所有规则里最差的一条

| 规则 | M02 真增量 |
|---|---:|
| 最新 3 行（现产品） | **7** |
| 分数前 3 / 前 5 | 7 / 9 |
| 连通分量各取 1 | 7 |
| 密度分 | 6 |
| **边际增益（减已选重叠）** | **2** |

**掉 5 题。** 原因：M02 的池子中位 53 行，正确答案本来就在那一簇里——同一个事件被说了十几遍，
十几行互为冗余，多样性抽样把唯一的正确那一行当成"重复"丢掉。

> 这与 RAG 的直觉相反，但区别是结构性的：**RAG 里冗余是成本，这里冗余是候选。** 最终进上下文
> 的只有两三条指针，"同一件事被说五遍"恰恰意味着"其中一遍带着你要的那个数字"。

### 15.4 唯一动得了的变量是"条数"，但那笔账也不划算

`pool5`（池 ≥20 行才给 5 条）：M01 真增量 10 不变，M02 7 → 8，字符 173 → **254（+47%）**。
**+1 题换 +47% 字符**，与 714 上判 `tailBeyond` 是同一把尺子（那次是 +1 题），不值得，
何况还要多养一个"条数随池子变"的分支。

## 16. LLM 问句改写、拆臂、实体扇出、PRF、trigram、单字通道

这一族有同一个幻觉：**"只要把查询变得更聪明，就能解决表示不对齐的问题。"** 六条全否。

| 机制 | 想法 | 实测 | 判 |
|---|---|---|---|
| **LLM 问句改写** | 把「那个呢？」改写成完整问句 | **没有可改写的对象**：212 题问句最短 7 字（「高姐生日是几号？」），主体+槽位+问型齐备，**没有一题需要指代消解** | 不迁 |
| **查询拆臂** | 一个问句含两个侧面，拆成两条查询各取一条 | 251 题 223 → **216**（变好 5、变坏 12） | 不迁 |
| **实体扇出** | 把问句里的实体扩成同族实体再召回 | 宽表 223 → 212；窄表 714 **648 → 617**（+5/−36） | 不迁 |
| **PRF / 伪相关反馈** | 用首轮结果的词再查一次 | 机制天花板高，但**取不到词**：问句里 DF 最小的词八成是跨词碎片（「样的」「办这」「在干」），覆盖答案共享词只有 **3.4%** | 不迁 |
| **FTS5 trigram** | 用 3 字滑窗代替 2 字 | **严格劣化**：共享 3 字串必然共享 2 个 2 字串（召回是真子集），索引 3.4 倍，212 题里 16 道掉证据 | 不迁 |
| **单字独立通道** | 给单字也建一路索引 | 四种形态全量过，最好的一种只是打平（714 619 → 617，62 题定位 59 → 60） | 不迁 |

**关于问句改写，还有两笔账**：改写要花钱（每题多一次模型往返，而比赛里成本是负分项）；
改写只是把问句换成**另一套词**，不保证换到库里那套——真正能建桥的是**语义表示**（把「单位」
和「合同工」映射到相邻位置），不是把问句翻成另一种说法。

**关于"稀有词直查"**（这是最近一次，值得写得细一点，因为它证伪了一个"上界"）：
有人提"别用整句搜，挑问句里最稀有的那个词直接查"。做了三版（问句直挑 / 满额替换 / 从候选行
反馈学词），714 全部 132/550/681/690 逐位不变，2.1 全部 135/190 不变，62 题指针
143 → 188 → 147 而证据 71 → 71 → 70。

**为什么**：瓶颈从"排序"挪到了"挑词"，而挑词在问句侧没有素材——问句里 DF 最小的词八成是
跨词碎片（DF=1，比「奶茶」DF 6 还稀有）。这是同一个病的第二次发作：**把"看起来更聪明"的
判据塞进一个没有信息的层。**

## 17. 向量库（不是"不该做"，是"不该现在做、也不该这样做"）

已经写了完整的离线论证（§3.3），这里只补一条最容易被忽略的：

**向量救的是 2.1 里占比最小的那一类。** 58 道漏检里 N 桶 21 道是词汇失配（向量能救一部分），
但 I 桶 32 道是"稀有词共享却没召回"——向量对这个形状毫无帮助（它的分数和词面无关）。
而 714 那套的失败主因是"这句话没成为一行"（写入侧）和"一条只覆盖一个槽位"（粒度）。

工程成本那一条也值得再写一次：宿主 `LlmAdapter` **只有 `stream()` 没有 `embed`**；FTS 靠 SQL
trigger 同步，embedding 必须异步，于是多一条"索引落后于写入"的一致性问题；onnxruntime 体积
超过整个插件（当前插件 860 KB）。这三条任何一条都足以让"加一路向量"变成一个季度的工作。

## 18. 通信类比的四条（DPSK / 盲均衡 / 包络检波 / FEC）

这一族来自"把记忆当信道"的类比，很漂亮，但**前提在我们的数据上全部不成立**。

| 机制 | 声称解决的问题 | 实测 | 判 |
|---|---|---|---|
| DPSK 差分（低命中时拼上一轮关键词） | 问句太短、代词漂移导致检索失效 | 问句字数与命中率**无单调关系**（0–12 字 50.0%，26+ 字 60.7%）；79 道 miss 里"零共享"的 **0 道** | 不迁 |
| 盲均衡（TF-IDF × 实体密度乘法重排） | 分数没反映真实相关度 | 重排可救的天花板 **1.3%**（79 题里 1 道） | 不迁 |
| 包络检波（本地小向量 / sqlite-vec） | 同义不同词、共享词但错行 | 方向对，但**那是换检索范式，不是加旋钮** | 见 §17 |
| FEC（System Prompt 硬规则纠错） | 模型会编、会说错 | 编造 **0 道**、被诱导 **0 道**；而"整个没答到"47 道、"该说却说含糊"39 道 | 已在产品里，且方向相反 |

一句话：**这批材料假设我们的信号在衰减，实测是我们的对照表错了。** 通信里所有"用更便宜的方式
恢复同一个信号"的思路都在对付衰减；而这里量出来的断点是"问句和行之间没有共享词"，是
**表示不对齐**，不是幅度不够。对不齐的时候，任何解调方式都解不出来。

## 19. 数据库类比的四条（逐条对账）

| 主张 | 现状 | 判 |
|---|---|---|
| **双时态**（`valid_from/valid_to`，问"现在"加 `WHERE valid_to IS NULL`） | 已有，且是 Zep 那种**合边**而不是加列：`facts.status ∈ {active, superseded, disputed}` + `superseded_by`；`eventDayKey` 是有效时间，`created_at` 是事务时间；同一事件里更晚的陈述当代表句 | **已做** |
| **LSM**（最新覆盖最旧 + 聚成事件组） | 写侧 L2 就是这个形状：`status` 链 + 事件合并（事件日相同 + 共享实词 ≥2 + 同段 + ≤8 轮） | **已做** |
| **物化视图** | 钩子索引（`loom_hooks.resident` 快照）+ `memory_expand` 按 `#L` 取整段 | **已做** |
| **CBO / 查询优化器** | 一半已做：`topicAnchor` 就是"按 DF 挑最稀的词"；另一半"放开表达式截断"**三测三负**（§71.4 +1、§75.4、§90.5 并 690 → 689） | **不做** |

**四条都不需要新表。** 这条结论本身有价值：外部类比最容易带来的不是机制，是"你缺一张表"的
错觉；而这里每一次"加表"的冲动，最后都发现已有结构能表达（改名 vs `aliases` 侧表、双时态 vs
状态机、物化视图 vs 钩子快照）。

## 20. 方法论：怎么判断一条建议是不是"伪需求"

这一节是给下一个人（或者三个月后的我）的操作手册。

1. **只认"真增量"，不认"命中数"。** 命中数会虚高：很多题旧版本早就交付过答案轮，新规则再
   命中一次对模型没有新增信息。`diag-21-anchor.mjs` 的每一行都有两列：命中 / 真增量。
2. **判据是"变坏的题必须为 0"，不是净值为正。** 714 上 +10/−1 也不接受——因为那条变坏的题
   往往是一个考点的唯一一道（`P17-CASE-017/d00`）。
3. **看到"上界"先问它用了什么信息。** `probe-21-rare-direct` 曾给出 +15 的漂亮上界，追问后
   发现它挑的是"与承载行共享"的词——**等于先看了答案**。凡探针拿"答案侧"的量当输入，读数
   就不能当产品上界。给上界之前先写明"产品侧能不能拿到这个量"。
4. **比例规则只往上放，不往下压。** `dfCeiling` 从 `max(3, ...)` 撤掉下限后，714 **0 好 3 坏**
   （搜索 550 → 547、工具面 681 → 679、并 690 → 688）。714 的 d15/d45 切点只有 460–608 行，
   纯比例算出 2/4，比标定值更严，于是丢行。**标定值本身就是下限。**
5. **中间指标和最终指标可能反向。** 摘要选句那个改动：中间指标 26.6% → 82.6%，最终 20.3% → 8.7%。
   只量前者会得到一个漂亮而错误的改动。
6. **探针红了先问"它依赖什么外部量"。** `probe-block-zones` 曾断言"无关话题下偏好区为空"，
   而样本偏好里有「不接受晚上十点后收到消息」——`clockRules` 22 点后把它追进偏好区，于是这条
   断言白天绿、深夜红。上次同类问题是"事实写在 L1 所以 DF=0"。**两个都不是产品的错。**

## 21. 先捡那几笔"零风险"的分

### 21.1 `clockRules` 接进检索：`due_day` 是全场 0%，而我们有零件

2.2 的 dev 集（809 题，离线取面）按题型拆开，短板极其集中：

| 类型 | M01 全中 / 沾到 | M02 全中 / 沾到 |
|---|---|---|
| `premise_twin`（前提成对） | 64.3% / 85.7% | 32.1% / 92.9% |
| `regular` | 39.7% / 63.8% | 12.5% / 77.1% |
| `legacy`（2.1 老题） | 15.5% / 68.0% | 3.2% / 75.8% |
| `implicit`（暗考） | 11.5% / 49.2% | 6.3% / 62.6% |
| **`due_day`（到点该提）** | **0% / 29.6%** | **0% / 16.7%** |
| `no_due_control`（不该提） | 7.7% / 15.4% | 0% / 5.9% |

`no_due_control` 低是**对的**（那类题的正确行为就是不提）。而 `due_day` 是官方表里**全场 0%**
的一类（Qwen / BM25 / 全塞都是 0）——**这是唯一一处"别人做不到、我们有现成零件"的格子**：
`clockRules`（0.2.60）已经能解出"下午三点后不喝咖啡"并用 `now` 比一次，只是它现在作用在
**注入块的注记**上，还没接进 `retrieve` 的取面通道。

这一笔的性价比是全项目最高的：**不需要新机制，只需要把已有判断接到另一个出口**，
且 0.2.60 那四条通道整体读数是 +11/−0（714 逐题）。

### 21.2 把目标指标换成"全锚点命中"

现在的指挥指标是"至少一个锚点命中"，它与判对的关联 69.4%；"全部锚点命中"是 76.7%，但只有
30/200 题落在那格里。**指标不改，我们会继续优化一个和答对关系很弱的量。**

代价要说清：换成"全锚点命中"后，分母从 200 掉到 33，方差变大，单次改动的读数会抖。
折中方案是**双指标并行**：主指标仍用"至少一个"（稳、可比），但每个改动的验收标准加一条
"全锚点命中不许降"。这条不花钱，只改验收习惯。

### 21.3 比赛里成本项已经封顶，别用钱换分

`S = A − 3 × log2(C / C_ref)`，`C` 有下限 `C_ref/4`，所以成本项最多 **+6**。dev 集实测：

| 榜 | 权重 | `C_ref`（qwen-base） | 我们的 C | 比值 | 成本项 |
|---|---:|---:|---:|---:|---:|
| 短对话 | 0.25 | ¥1.121 | ¥0.883 | 0.787 | **+1.0** |
| 长对话 | 0.25 | ¥4.755 | ¥1.159 | 0.244 | **+6.0（封顶）** |
| 自然用记忆 | 0.50 | ¥11.481 | 待测 | — | 预期封顶 |

规则路径零模型调用，所以我们的 C 几乎就是"进提示词的记忆文本"。两件事由此确定：

1. **长榜已经吃到上限的 +6，再省没有意义**；短榜只值 +1.0（qwen-base 自己就很便宜），
   **A 就是全部**。
2. **任何"加一次模型调用"的改动，都是在用 A 换 −3 分的方向**。写入侧自足句（§22 的语义桥）
   因此必须算清账：如果它把 C 从 0.24 提到 0.5，成本项从 +6 掉到 +3，那它必须换来 **A +3 分
   以上**才回本——而 A 的 3 分在这个榜上是很贵的。

## 22. 三个方向，按"能不能量化收益"排序

### 22.1 检索层：还有两处，但都不便宜

| 位置 | 现状 | 可做的 | 风险 |
|---|---|---|---|
| **N 桶（21 道，零共享）** | 字面通道按构造够不着 | 写入时把记忆改写成**自足句**（主语用实体名、条件写全） | 要模型（成本），且会覆盖历史（Mem0 在九道矛盾题上 0–1/9） |
| **I 桶（32 道，稀有词共享却没召回）** | 承载行不在候选池里 | "只用那个稀有词直查"能救 15 道上界，但**三版产品化全零** | 瓶颈在挑词：问句侧没有素材（覆盖答案共享词 3.4%） |
| **due_day** | 0% | §21.1 | 无 |

**I 桶那 15 道的上界是假的**（§20 第 3 条）：探针挑的是"与承载行共享"的词，等于先看了答案。
产品侧拿不到这个量，所以它不能当上界。**这是我认为"检索层已经基本挖空"的最强证据。**

### 22.2 上下文组装：有一处真问题（完整性），但没有好解法

`memory_search` 返回 60 字预览，模型不知道这是答案本身还是答案的第一个词。当前的补偿是
"给两条指针 + 允许 `expand`"，但 §5.2 量出**碎片比空白危险 3 倍**。

可做的方向（按代价排序）：

1. **保守化**：只返回"能确认是完整句"的行（以句号/问号结尾、长度 ≥ N）。代价是召回下降，
   需要用 714 的 690 当护栏——这一条可以离线先仿真，不花钱。
2. **提示层**：在搜索行上标注"这是片段 / 这是整段"（信息来自 `l0` 区间长度与句子边界）。
   这是纯渲染，零风险，但收益未测。
3. **展开前移**：对"只回来一条指针"的题直接自动 `expand`（不花模型调用，只多几轮 SQL）。
   风险是 token 成本（`C` 会涨，长榜有 +6 的余量）。

### 22.3 提示词：**别把召回问题当提示问题**

这是我最想强调的一条判断，因为它能省掉一整轮无效劳动。

- 2.1 的 111 道判挂里 34 道标了 `over_hedged`（"该说却说没记得"）。按 0.2.54 的分层，其中
  13 道"块内有"，而块内命中数**全是 1**——模型看到的是碎片，弃权是对的。用 0.2.61 的锚点
  复算这 34 道：18 道零命中、10 道部分命中、6 道三条通道全在（这 6 道是定位改善之后才出现的，
  作答那一版未必在）。
- 真正属于提示词的失败只有一处，已修（§12.5：作答须知第 5 条让作答者替用户裁定矛盾）。
- 714 那边同理：13 道"说没记到"集中在少数题号上（25 道失败只压 18 个题号，`P17-CASE-017` 与
  `P17-CASE-012` 各挂两次），而这两个题号的病是"问句与库里零 bigram"（「搬家」全卷 0 次、
  「办成」0 次）——这不是提示词能让它答出来的。

> **如果只能记住一句话：这套系统的失败有 92.6% 在"材料没到"，不在"材料到了不用"。**
> 所有以"教模型怎么用记忆"为目标的改动，天花板是那 7.4%（7/94）。

## 23. 我需要被指导的八个问题（基础框架层面）

每一条写成：**现象 → 已经排除的路 → 我卡在哪 → 我需要什么判断**。

### Q1 表示层：不引入 embedding，还有没有"第三种表示"？

**现象**：词汇失配（「什么路子的歌」对「老粤语歌和旧爵士」）占 2.1 漏检的 36%，零二元组共享。

**已排除**：trigram（严格劣化）、单字通道（打平）、同义词/上下位表（磁铁，三次全负）、
查询改写（无对象、且换的是另一套词）、PRF（取不到词，覆盖 3.4%）。

**卡点**：二元组表示层的残余缺陷在 62 题上是 0 题——**它不是"没调好"，是"到顶了"**。

**想请教**：在"无模型、无网络、单文件 SQLite"的约束下，除了 bigram，还有没有一种**不依赖
预训练**的中间表示，能部分桥接词汇失配？（我怀疑答案是没有，因为词汇失配本质上是"词表之外
的知识"，而任何不依赖外部知识的表示都无法凭空获得它。但如果有一条我没想到的路——比如利用
**同一语料内的分布相似性**做 latent 表示——那会是这个项目最大的一次跃迁。）

### Q2 完整性：怎么在不问模型的情况下判断"这一条够不够答"？

**现象**：碎片比空白更容易踩线（45.0% vs 15.6%）。

**已排除**：用"证据 fact 数 ≥ 2"当"两个提问点"的标签——逐题看发现标签本身是错的
（「《海边的钟》作者这一栏该怎么填」是一个提问点、两条证据）。

**卡点**：要判"够不够"，需要知道"问题有几个提问点、这条覆盖了几个"。前者是语义，后者需要
覆盖计算——两个都在模型侧。

**想请教**：有没有一种"结构化但不需要模型"的完整性代理量？我目前的想法是用**槽位密度**
（这条记忆的 `(主体,属性)` 覆盖了几个不同属性）+ **句子完整性**（是否含谓语、是否以句末标点
结束）当特征，但不确定它能不能区分"答案"和"答案的第一个词"。

### Q3 容量：固定 2–3 条指针下，是否该改成"少给一条、多往返一次"？

**现象**：三条定律（加候选零和、换候选零和、只有有空位时追加不为零和）说明容量是硬约束。

**已排除**：拆臂、扇出、换第二条指针、加第三条指针（第三、四条对模型没有增量）。

**卡点**：现在的策略是"一次给 2 条指针 + 10 条摘要行"，本质是**单轮 top-k**。

**想请教**：如果改成**交互式检索**（先给 1 条，模型判断不够再要第 2 条），精度会上升，但多一次
往返（延迟 + 成本 + 轮数）。在"记忆系统"这个场景里，这个取舍应该怎么算？我的直觉是：**用户
不会等，所以不能加往返；但如果往返发生在 `memory_search` 内部（工具自己迭代），成本只是 SQL**——
后者是不是一条被低估的路？（注：`memory_expand` 已经是这个思路，只是它只作用于"指针"，
不作用于"选择"。）

### Q4 判据：同池换判据零和，是否说明"选择层"的信息已经耗尽？

**现象**：M01 上十条规则的真增量全是 10，同一批题。

**推论**：池子里的行在"重叠 / 密度 / 冗余 / 拓扑位置"这些维度上**等价**，真正的区分信息是
"这一行讲的是谁的哪件事"——实体与属性，抽取层的东西。

**想请教**：这个推论如果成立，是不是意味着**规则路径的检索天花板就是 72%**，再往上必须走
"写入时生成结构"（要模型）？还是说"选择层"还有一种我没试过的信息源（比如**对话行为的元数据**：
谁先开口、回复长度、是否提问——这些不需要语义理解）？

### Q5 时间：有效时间覆盖率 9%，有没有不依赖模型的时间归一？

**现象**：`eventDayKey` 只能从「明天/昨天/今天」算，证据对里只有 9% 能算出；2.1 的 `相对日期`
（25 个 missed 项）与 `时间题`（24 个）是最大失分点。

**已排除**：不解析（那会让"明天"永远跟着当前时间漂移——这是 §7.1 那条不变量的反面）。

**卡点**：绝大多数句子里没有相对时间词，只有"那天""上次""后来"。

**想请教**：能不能用**会话内绝对时间锚 + 序数传播**（"这一段里最近一个绝对时间是 04-08 18:10，
之后的句子按轮次间隔推"）来补？我的顾虑是：轮次间隔不是真实时间间隔（人可能隔一天才回），
推出来的日期会系统性偏。这个问题在文献里有没有标准解法？

### Q6 产品边界：哪些考点应该"放弃结构化，直接给原文"？

**现象**：结构化赢在聚合（生日、约定、纠错），输在保真（第三方画像、带条件的偏好、敏感话题）。
0.2.42 量过一组对照：`用户的基本信息` 68.8%（Qwen RAG 85.7）、`敏感的事` 50%（Qwen 87.5 / OpenViking 95）。

**卡点**：这些格子后来靠"补通道"补到了 100% / 96.4%，但每一次都是加一条规则（`SELF_SLOT_RULES`、
`KIN_SLOT_RULES`、`BOUNDARY_MARKERS`…），**规则的维护成本在上升，而每条规则的覆盖面都很窄**。

**想请教**：从架构上看，是继续"按考点加规则"，还是应该有一个**分流器**：判断这个问句属于
"聚合型"还是"保真型"，前者走结构化、后者直接走原话通道（`l0_fts`）？后者的风险是分流器本身
需要判断力（也就是需要模型）。

### Q7 测量：作答方差 14% 大于产品差 1 个点，怎么在有限预算下做可信 A/B？

**现象**：91 题配对实验，同一份记忆换一批作答者，13 题翻转（14.3%）。714 严判的配对翻转 58 题
（8.1%），标准误 ≈ 7.6，净 −4 在噪声里。

**已排除**：单臂跑两次取平均（方差不是零均值噪声，是"作答者的口径漂移"）；用旧判分（少用三条
硬否决，等于换尺子）。

**卡点**：一次端到端 714 要 21 包作答 + 判分，约 3 小时；2.1 也要 3 小时；比赛封存在 12-03。

**想请教**：在这个约束下，"可信"的最低标准是什么？我目前的方案是：**一题两臂同批、同一个
作答者一次答完、盲标、只认 ≥10 题单向差**（§82.6 的教训：把两臂打散到不同批次，等于没固定
作答）。这个标准是否过严/过松？

### Q8 工程：参赛前要不要重建 TS 工程？

**现状**：`lib/index.js` 14,604 行，是一次 TS 构建的产物，`//#region src/xxx.ts` 是当年的文件
边界；源码已不在仓库（提交 `584668d` 承认了这件事）。代价三条：改代码靠 region 注释导航、
无类型检查、`git diff` 只能看到"一个大文件变了多少行"。

**我的判断**：现在重建是**负期望**——重写会引入行为差异，而行为差异在这个项目里极难被测出来
（见 Q7）。但长期看它是债。

**想请教**：如果你是我，会在"比赛前 3 周"这个时间点动它吗？还是等比赛结束、用当时的读数当
回归基线再动？

## 24. 参赛约束下的决策（把上面的判断落到日期上）

| 约束 | 值 | 对决策的影響 |
|---|---|---|
| 计分 | `S = A − 3·log2(C/C_ref)`，成本项封顶 +6 | 长榜已封顶，**A 是唯一变量**；加模型调用是负向 |
| 封存跑 | 一次，系统调用自付 ≤ ¥50 | 不能靠"多跑几次挑好的"；必须一次性可复现 |
| 冻结 | 2026-12-03 | 距今 3 周，只够做 2–3 个改动 + 各一次验证 |
| 自然用记忆榜权重 | 0.50 | R 侧 X 类（该想起时必须想起）占 80%，正是"常驻块 + 指针"的主场 |
| 我们的 C（dev） | 短 ¥0.883 / 长 ¥1.159 | 距 `C_ref` 的 1/4 下限还有余量，但**没有理由花掉它** |

**因此这三周的动作排序**（按"收益 / 风险"）：

1. **`clockRules` 接进取面**（§21.1）——零新机制、零回退风险、`due_day` 从 0% 起步。
2. **完整性判据的离线仿真**（§22.2 第 1 条）——不花钱，只用已有产物复算；如果 714 不失分
   而 2.1 的"碎片题"减少，再上产品。
3. **验收指标加一条"全锚点命中不许降"**（§21.2）——零成本，防止继续优化代理量。
4. **不做**：语义桥（要模型、要吃成本项）、交互式检索（要改产品形状）、重建 TS 工程。

---

**最后一句总结**：这个系统的形状不是"我选了一个架构"，而是"我量出了一组约束，然后让架构
收敛到它们上面"——**预算 2,000 token、候选两条指针、判据在同一池子上零和、作答方差 14%**。
每一条约束都杀掉了看起来更聪明的一版设计。剩下能动的只有两处：**材料到不到**（写入层），
和**到的那一条够不够**（完整性）。这两处都不在检索算法里。

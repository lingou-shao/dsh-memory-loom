# dsh-memory-loom

给 DeepSeek Harness 的长期记忆插件：把对话沉淀成**四层记忆 + 主观层 + 人设卡**，全部存在一个本地 SQLite 文件里。**v0.2.0 起内置钩子索引层**：上下文里只放每条约 15 token 的"钩子"，完整正文留在库里按需取回。

- **L0** 原始对话（只追加，不按时间清理）
- **L1** 原子事实（带类型、主题域、TTL、情绪显著度）
- **L2** 事件摘要（按话题与情绪切分出的「一段经历」）
- **L3** 自我叙事（助手对自己的长期叙述）
- **主观层** 印象、日记、隔离的长期偏好
- **人设卡** 分区、可锁定、用户/助手按来源分权
- **钩子索引**（v0.2.0）记忆块的指针版：`- E37 要不要辞职的长谈 2.7k字`，背后是几千字完整叙事，`memory_expand` 按需取回
- **原文不裁剪**（v0.2.1）单条消息整条落库，贴多长的日志、代码、报错都不丢尾巴

不依赖任何在线服务：中文检索用 CJK 二元分词 + SQLite FTS5，衰减、切分、冲突判断都有确定性规则版本。**没有可用模型时插件照常工作**，只是抽取与判断走规则，L0 仍然完整积累。

---

## 1. 它解决什么问题

多数「记忆插件」只做两件事：把对话塞进向量库，检索时贴回来。后果是记忆越来越多、越来越像、越来越不可解释。

这个插件按「人会怎么记」来设计：

| 问题         | 做法                                            |
| ---------- | --------------------------------------------- |
| 什么值得记      | 只抽稳定信息（偏好、身份、关系、计划、经历、长期要求）；寒暄与工具输出不记         |
| 记多久        | 双曲衰减 `base·(1+t/S)^(−d)`；被检索到会提升稳定性 S，而不是重置时间 |
| 过期了怎么办     | 软失效：不删除，只连续降权（半衰期 45 天，地板 0.02）               |
| 旧事实与新说法冲突  | 写入时 supersede；检索时再标「可能已过时」并降权；当前对话永远优先        |
| 一段对话是什么    | 按时间间隔、话题偏移、情绪尖峰切段，段内再按微观话题细切                  |
| 该怎么读记忆     | 事实用表格行、主观层用自然语言；事实在前、主观在后，紧挨对话                |
| 不同人之间      | 主人 / 朋友 / 路人的权限梯度；记忆按人隔离；路人 48 小时后删原始对话       |
| 上下文装不下所有记忆 | **钩子索引**：常驻 prompt 只放快照化的钩子清单，正文顺指针取回（见 §6）   |

## 2. 安装

要求 Node `^22.19.0 || >=24`（使用内置 `node:sqlite`，无原生编译）。

### 装之前先看一眼：是不是已经装了别的记忆插件

**这是替代品，不是叠加品。** DSH 的工具名全局唯一，重名不是「后装的少一个工具」，而是**后装的整个插件加载失败**——16 个工具一个都不进表，三块提示词也一起撤销。宿主的行为是实测过的，不是推测。

这个生态里至少四个记忆插件用了同一套工具名：

| 插件 | 与我们重名的工具 |
| --- | --- |
| `dsh-memory`（SQLite + FTS5） | `memory_search` `memory_write` `memory_forget` |
| Memory Library（工作区卡片库） | `memory_search` `memory_write` `memory_forget` |
| Workspace Recollection | `memory_search` `memory_write` `memory_forget` `memory_index` |
| `@max-null/dsh-memory` | `memory_search` `memory_forget` |

`memory_search` / `memory_write` / `memory_forget` 是这个生态的事实标准名。**16 个名字里任意一个撞上就整体装不上**，所以装之前值得花十秒确认。

**如果你决定卸掉对方，它的记忆不会跟着走。** `dsh plugin remove` 只摘插件，`$DSH_HOME/memory/memory.db` 这类文件原地不动；装好本插件之后它会自己扫一遍，问你要不要把这些记忆搬进来（见下面「装完会问的一句」）。

装的时候如果撞了，你会看到这样一句（不是宿主的 `already registered`，那样看不出该怎么办）：

```
memory-loom: 工具名 memory_search 已被另一个插件占用（多半是另一个记忆插件）。
DSH 的工具名全局唯一，重名会让整个插件加载失败——所以这一版不会半残运行，也不会顶掉对方。
两种解法，任选一种：
  ① 二选一：dsh plugin --profile <你的 profile> remove <那个记忆插件>（它的记忆文件不会被删除，以后装回来还在）
  ② 共存：在 profile 的 cordis.patch.yml 给本插件设置 toolPrefix: loom_ …
```

**① 二选一（推荐）。** 卸载另一个插件**不会删掉它的记忆**：`dsh plugin remove` 只摘插件，`.dsh-memory/`、`$DSH_HOME/memory/memory.db` 这些文件原地不动，以后装回去还在。所以「换一个试试」是有退路的，代价只是重装一次。

**② 共享一个进程（`toolPrefix`）。** 愿意付代价的话可以两个都留：

```yaml
- id: memory-loom
  name: dsh-memory-loom
  config:
    path: !!js dshHomePath('memory', 'loom.db')
    toolPrefix: loom_
```

设了之后 16 个工具变成 `loom_search` / `loom_write` / …，提示词、工具描述、工具返回里出现的名字**一起跟着换**（不是只换注册名——那样模型会照着一个不存在的名字去调）。默认值是 `memory_`，所以**不设就是原来的行为**。

不设为默认，是因为共存不是「多一个备份」，是每轮多读一份「关于你的长期记忆」：

- 两边都往系统提示词里注入，加起来每轮多 3000–5000 字符（我们的块约 300 token，同类插件普遍 2000–4200 字符）；
- 两边都在会话结束时调模型做抽取，同一段对话付两次钱、等两次延迟；
- 模型看不到「这块是 loom 的、那块是别人的」，它会当成一段连续回忆来读——两份互相矛盾时，它不知道信哪个；如果对方还写人格（`SOUL.md` 之类），冲突会更明显。

**技术上也别指望「谁都能装」**：改名只能让**我们**避开别人的名字。如果本插件先加载、占住了 `memory_search`，后装的对方照样会整插件失败——那是它的重名，不是我们能修的。所以真要两个都装，先装对方、再装我们并设 `toolPrefix`。

### 装完会问的一句：以前那些记忆要不要搬过来

装好之后，本插件会先看一眼周围有没有别人留下的记忆文件（`$DSH_HOME/memory/*.db`、`$DSH_HOME/storages/memory*.json`、当前目录的 `.dsh/storages/`，一层深，不递归）。找到了，它**不会自己导**，而是在对话里问你一句：

> 发现你以前装的记忆插件里还有 42 条记忆，要搬到现在这个记忆里吗？搬过来就能一起检索到。

三种回答，对应三种做法：

| 你说 | 它做什么 | 记忆文件 |
| --- | --- | --- |
| 要 | 先给你看清单（会进多少条、哪些重复、补别名要调几次模型），你点头才真的写 | 原样留着 |
| 不要 | 记下来，以后不再提这件事 | 原样留着 |
| 想自己指定一个文件 | 直接把文件拖进聊天窗口，或给出路径 | 原样留着 |

**只读，不删也不改。** 导入只把句子读出来，源文件一个字节都不动——卸载别的插件不删它的数据，所以哪天你反悔，那两个文件都还在。

**导进来的东西和本插件自己记的一样用。** 不是塞进一张「外来记忆」表：类型（事实 / 偏好 / 要求）和领域重新判定，要求进常驻区、事实进召回层、原始日期保留，来源标成 `import:<插件名>` 便于追溯。唯一的例外是**旧计划**：「下周三去体检」里的日子是那个插件的时钟算出来的，拿今天重新解析等于编一个期限，所以按事实存放，不会到期来问你。

**补别名要花钱，所以先报价。** 老库和导入的行都没有检索别名——没有别名也能用，只是换个说法就搜不到。`memory_import(aliases=true)` 分批补（每批 12 条），预览里会写「要调模型 N 次」，并且**先看当天预算**（`consolidation.dailyLlmCalls`），用完了就停下报「还剩 N 条」，不偷偷超支。

这套东西的边界写在 §9 和 `docs/design.md` §31：格式靠嗅探不靠白名单（SQLite / JSON / JSONL / Markdown / 纯文本，JSON 里只有一个字符串数组也认），认不出的文件会在预览里说「读不出来」并给出原因，而不是当作空文件；一张表读不了不连坐整份文件。别人的记忆结构（事件、时间线、人格文件）读不进来，只搬句子；反过来，**对话记录和人格设定也不会被当成记忆搬进来**——有 `role` 列的表、名字像配置的表都跳过。

### 方式一：DSH 里一键安装（推荐）

打开 DSH → **插件** → **添加插件**，输入框里贴一个地址，回车。三种都实测可装：

| 贴什么 | 例子 | 特点 |
| --- | --- | --- |
| **Release 里的 tarball**（推荐） | `https://github.com/lingou-shao/dsh-memory-loom/releases/download/v0.2.30/dsh-memory-loom-0.2.30.tgz` | 版本钉死，装到的就是这一版 |
| **GitHub 仓库地址** | `https://github.com/lingou-shao/dsh-memory-loom` | 跟随 `main`，能拿到最新提交，但每次装到的内容会变 |
| **本地目录** | `D:\code\dsh-memory-loom` | 必须写**绝对路径**（相对路径会被 DSH 拒绝），先 clone 再填 |

> **贴本地 tarball 的要注意一件事**：DSH 会把你给的源**原样**记成 profile 里的依赖——贴本地文件就写成 `"dsh-memory-loom": "file:C:/Users/you/Desktop/dsh-memory-loom-0.2.24.tgz"`，贴 git 地址就写成 `git+https://...`。也就是说，本地 tarball 的**绝对路径变成了长期依赖**：这个 tgz 一旦被挪走/删掉，再遇到「重新解析依赖」的场合（profile 的 `pnpm-lock.yaml` 丢失或重生成、pnpm store 被 prune、换机器、`--force` 重装）就会报 `Could not install from ... as it does not exist`。
>
> 规避办法（任选一条）：
> - **tgz 别放桌面/下载目录**，放到固定位置再装，例如 `%USERPROFILE%\.dsh\vendor\`；
> - 或者贴 Release 里 tarball 的 **HTTPS 直链**（上表第一行），profile 里记的是 URL，跟着文件位置无关；
> - 或者贴 **git 地址**，最稳，也和后三种插件的记录方式一致。
>
> 已经钉在桌面了也不要紧：把 tgz 挪到新位置后，改 profile `package.json` 里那一行的路径、再 `pnpm install` 即可。这条是 DSH 插件管理器的记录方式决定的，不是本插件的配置。

DSH 用 pnpm 把包装进 profile（`~/.dsh/profiles/<profile>/node_modules`），并自动把 `dsh-memory-loom` 写进该 profile 的 bundle 列表。包内 `package.json` 声明了 `dsh.bundle.patch`，组合器据此读取 `cordis.patch.yml`，**不需要手改任何配置**；数据库默认落在 `$DSH_HOME/memory/loom.db`。

**首次安装：装上就生效，不用重启。升级：必须重启 DSH。**

这两件事走的不是同一条路。之前这一节把它们写成一条，是错的——2026-11-02 在真机上踩到了，见下。

**首次安装**走的是 DSH 的**即时重组（live reconcile）**：pnpm 一装完，它就把 `dsh-memory-loom` 追加进 profile 的 bundle 列表、读包里的 `cordis.patch.yml`、激活这一层并调用插件的 `apply()`，然后把新的工具 schema 推给**正在运行的那个会话**。实测时间线：

```
20:05:09  dsh plugin add 跑完，profile 的 package.json 被 pnpm 改写
20:05:11  loom.db 被创建            ← 就是它调用了 apply()
```

宿主主进程此前已经在跑（不需要新进程），当前会话的 id 也没变，只是收到一条 `### Updated Tool Schemas` 注入，16 个 `memory_*` 工具当场出现在工具列表里。

**升级不走这条。** 升级是「同一个 bundle 换内容」，不是「出现一个新的 bundle」，宿主不会为它重组一次。实测（0.2.16 → 0.2.23，`dsh plugin add` 13.9 秒跑完、磁盘上确实换了包）：

| 检查 | 结果 | 说明 |
|---|---|---|
| 工具数 | 还是 **9** 个 | 0.2.12 才有 9 个；0.2.16 是 12，0.2.23 是 14 |
| `memory_doctor` | `unknown tool` | 这个工具 0.2.16 才加 |
| 库 `user_version` | **1** | 0.2.23 是 4 |

三条同时指向同一件事：**磁盘上装的是新版，进程里跑的是启动那一刻的旧代码。** 所以升级之后不重启，看到的是「装上了」，实际是「没生效」——`git`、文件时间、`package.json` 版本号全都对，唯独跑的东西没变。

**升级的正确顺序**：

1. **先备份库**：把 `%USERPROFILE%\.dsh\memory\loom.db` 复制一份。第一次加载新代码会 `ALTER TABLE` 加列（0.2.23 加三列），备份是为了万一出问题有退路。
2. 装新版（粘新链接 / `dsh plugin add` / `pnpm install`，同平常）。
3. **把 DSH 完全退出再打开**（不是新开会话，是重启进程）。
4. 用 `memory_doctor` 第一行确认：应该显示 `运行 0.2.27 · 库 schema v4`。**这一行是唯一不会撒谎的证据**——它由代码自己打印，跑的是哪版就报哪版。

通常几秒内就能确认两件事：

1. 工具列表里出现 `memory_search` / `memory_expand` / `memory_profile` / `memory_index` 等 16 个 `memory_*` 工具。**首次安装**不必新开会话，当前会话会被刷新；**升级必须重启 DSH**，重启之前那 16 个不会变（见上）。若迟迟不出现，先排除下面「安装被拒绝」那种情况。
2. `%USERPROFILE%\.dsh\memory\loom.db`（Linux/macOS 是 `~/.dsh/memory/loom.db`）被创建。**`diary/` 目录不会跟着出现**——它是懒创建的，要等第一条日记落盘才建；刚装好看不到那个目录是正常的，不是没生效。

> 注意区分两件事：「装上了」只意味着**工具挂上了**。真正开始积累记忆（写事件、写日记）要等**整合**触发——单会话累计 2 万 token，或空闲 5 分钟。装完立刻问「你还记得什么」，答案当然是空的。

如果安装被拒绝并提示 `incompatible-version`，那是插件声明的 DSH 版本范围与当前 DSH 对不上。本包声明的是 `engines.dsh: ">=0.2.1-rc.2 <0.3.0"`，DSH 的预检优先读这个字段，读到就不再逐个比对 `peerDependencies`，所以报错只会有一项（`engines.dsh`），比一长串 peer 列表好定位。上限定在 `<0.3.0` 是**故意的**：插件用到 `defineTool`、`systemPrompt.section`、session 事件这些宿主内部面，0.3 改语义时它不会自动知道——装不上比装上了坏掉好。提 issue 时请附上你的 DSH 版本。

### 方式三：手动挂载

把包放进 profile 的 `node_modules`（或 `$DSH_HOME/profiles/node_modules`），并在 profile 的 bundle 列表里加入 `dsh-memory-loom`。`cordis.patch.yml`（包内自带）会被组合器读取：

- insert:
    - id: memory-loom

        path: !!js dshHomePath('memory', 'loom.db')

`path` 是必填项：对话的长期记录不应该落在「启动目录」里。临时试用可以设成 `:memory:`。

### 本地开发

```bash
git clone https://github.com/lingou-shao/dsh-memory-loom
cd dsh-memory-loom
npm install        # 安装 peer/dev 依赖
npm test           # 钩子索引自测，30 项（node test/selftest.mjs）
```

`test/` 虽然随包发布，但**在安装位置直接跑 `npm test` 是跑不起来的**——`lib/index.js` 要 import `@deepseek-ai/dsh-tools`，DSH 里由宿主解析，普通 `node` 进程里没有那份 `node_modules`。自测脚本会打印一句提示让你回仓库跑，不会甩一屏堆栈。

仓库直接以构建产物发布（`lib/index.js` 即完整插件），没有独立的源码目录和构建步骤；`npm run build` / `typecheck` 已随 v0.2.5 移除。改动后的验证方式是 `npm test` 加上仓库外脚手架里的端到端场景。

## 3. 配置

全部字段都有默认值，只有 `path` 必填。

| 字段                                                        | 默认                                             | 说明                            |
| --------------------------------------------------------- | ---------------------------------------------- | ----------------------------- |
| `path`                                                    | —                                              | SQLite 文件路径，或 `:memory:`      |
| `ownerName`                                               | `主人`                                           | master 身份的称呼，用在事件抽取提示与「关系印象」里 |
| `locale`                                                  | `zh`                                           | 记忆块语言（`zh` / `en`）            |
| `timezone`                                                | 空                                              | IANA 时区；空表示用宿主时区              |
| `capture`                                                 | `true`                                         | 是否把每轮对话写入 L0                  |
| `toolPrefix`                                              | `memory_`                                      | 16 个工具的名字前缀。装有别的记忆插件、又不想卸载时设成 `loom_`，提示词与工具描述里的名字会一起换（见 §2「装之前先看一眼」）。默认值不改成别的，因为共存有实际代价 |
| `l0.maxCharsPerMessage`                                   | `0`                                            | 单条消息存储上限。`0` = 全文落库，一个字不丢（v0.2.1 已修改：0.2.0 及以前硬编码 8000 字静默截断） |
| `maintenanceIntervalSeconds`                              | `60`                                           | 后台维护与整合检查间隔                   |
| `consolidation.enabled`                                   | `true`                                         | 关掉后**完全不整合**：不产生事件与事实，也不再调模型；原始对话照旧落 L0、`T` 尾巴照旧可见。省额度用这个（v0.2.7 已修复：此前该开关不生效，设 `false` 仍会整合） |
| `consolidation.provider` / `.model`                       | 空                                              | 整合调用的路由；空表示沿用会话最近一次请求的路由      |
| `consolidation.triggerTokens`                             | `20000`                                        | 单会话累计到多少 token 触发整合           |
| `consolidation.idleMinutes`                               | `5`                                            | 空闲多久视为可以整合                    |
| `consolidation.maxRunSeconds`                             | `180`                                          | 单次整合总时长上限                     |
| `consolidation.itemTimeoutSeconds`                        | `30`                                           | 单条模型调用超时                      |

## 5. 运行时行为

### 捕获

`session/event` 上的 `user/message` 与 `assistant/message` 同步写入 L0。只收 `source.kind === 'user'` 的真实用户输入，工具注入、系统提示、子智能体消息都不算。写入前脱敏（私钥、API key、Bearer、密码赋值、手机号、身份证、银行卡）。

**整条消息原样落库**，默认没有长度上限。要压体积就设 `l0.maxCharsPerMessage`：超限时会截断，并把截断原因和原文长度写进正文（`…[已截断：原消息 40000 字，仅保留前 32000 字]`），不会让模型把半截日志当成完整日志读。脱敏先于截断执行——密钥不会因为被截断而漏存。

> v0.2.1 已修改：0.1.x–0.2.0 在这里硬编码 `clip(..., 8000)`，超出部分静默丢弃，既不报错也不可配置。详见 `docs/design.md` §10。

`request/context` 用来记住会话的 provider/model，整合调用默认沿用这条路由。

### 整合

`agent/turn-stopping` 收尾本轮并计数；命中「累计 token 超阈值」时在后台启动整合，**不阻塞用户**。另有一个 60 秒的后台循环，处理空闲会话、访问回写、软失效、路人清理、冷静期到期删除与每月去重扫描。

一次整合最多两次模型调用：先抽取事实与摘要，再一次完成「去重 / 更新 / 矛盾 / 显著度 / TTL」四项判断。解析失败按规则兜底并记死信。没有模型时全程规则，`report.degraded` 保持 `false`——规则模式是受支持的部署形态。

### 注入位置（Q65）

```
系统提示
  ├─ …（宿主自己的 section）
  ├─ memory-loom:persona:<session>   人设卡（section，常量协议之外唯一的静态块）
  ├─ memory-loom:protocol            记忆使用约定（全局 section）
  └─ memory-loom:index-protocol      记忆索引使用约定（全局 section）
动态上下文
  ├─ memory-loom:hooks:<session>     钩子索引块（context，在记忆块之前）
  └─ memory-loom:memory:<session>    记忆块（context，落在对话之前）
对话历史
```

记忆块内部：事实 → 事件 → 印象 → 日记 → 自我叙事 → 长期偏好 → 原文下钻片段。软目标 2000 token，硬上限 3000，主观层独占约 25%。

人设卡独立成 section 这件事属于 Q65 的落地：它不跟事实抢预算，也不随召回结果变化。

> **Q64 在 v0.2.9 收口（原文写「语气分离注入」）**：当时的设想是给语气单开一条注入通道，再加一套离线评估。实际结论是——只要模型在读记忆时能看见「这话当时是什么口气」就够了，不需要独立通道。现在语气以 `（语气偏冲）` 这样的短标注跟在事件行后面，见下面的「语气」小节。

两个 prompt 贡献都设了 `interpolate: false`：用户写进人设或事实里的 `{{...}}` 是字面文本，不会被当成模板变量。

### 冲突（Q66，用户确认版）

协议里固定一条规则：**当前对话永远优先于记忆块**。此外做一次确定性检测——候选事实与当前这句话共享足够词汇（containment ≥ 0.45 且 ≥3 个共同 token），却在否定词或数字上不一致时，标「可能已过时」并乘 0.85。不额外调用模型。

### 语气（Q64，v0.2.9 定稿）

整合时每个事件已经存了 `valence`（正负）与 `arousal`（强度）。渲染时用一个纯函数把它们折成一句话，附在事件行尾部，**只在情绪不中性时才出现**：

```
【我们一起经历过】
- [10-30] 为辞职吵起来的那次：说到加班时声音变高，明显不高兴。（语气偏冲）
- [10-30] 她夸我那次：聊到最后心情不错。（语气愉快）
- [10-30] 问天气：问了明天的天气，语气平常。          ← 中性，不加标注
```

- **只影响“读到的语气”，不影响排序**：打分仍然只看相似度、衰减、salience。
- **不额外调模型**：用的是已经落库的两个数，`memory_search` 的结果里同样带。
- **成本**：每条被标注的事件约 +3 token；中性事件 0。实测两条情绪事件让记忆块从 59 → 65 token。
- **可以关**：`retrieval.toneHint: false`。
- **不声称准确**：语气标签是阈值映射，不是判断模型。离线评估没有做，也不打算做——这正是 Q64 被缩小掉的那一半。

### 日记：不给权重，给一个能看的文件（Q63，v0.2.9 定稿）

日记是唯一「写给助手自己」的层。原来的设计里它按 `weight`（情绪 salience）参与叙事触发，后来发现：**日记按权重加进去也不会让人更愿意看它，反而让「谁更重要」这件事被一个拍出来的系数绑住**。所以定稿是——

- **不加权**：日记不参与事实/事件的排序，也不计入叙事证据（`narrativeEvidence()` 只数事件）。
- **给入口**：每天一个 Markdown 文件，导出到数据库旁边的 `diary/` 目录，任何文件管理器点开就能读：

```
~/.dsh/memory/loom.db        ← 数据库（默认 path）
~/.dsh/memory/diary/
  2026-10-29.md
  2026-10-30.md
```

文件长这样（按人分组，只读镜像，写入以数据库为准）：

```markdown
# 日记 2026-10-29

## 主人

- 15:23 今天她把辞职的事说到底了，我怕的其实不是钱。

> 由 memory-loom 从 diary 表导出，只读镜像；以数据库为准。
```

导出时机：插件加载时回写最近 `diary.mirrorDays`（默认 14）天，之后每次维护 tick 检查最近两天，只在内容变了（条数或时间戳变了）才重写。**目录是懒创建的**：库里一条日记都没有时不建 `diary/`，第一次写日记才 mkdir。目录写不进去不会影响主流程——条照旧进数据库，每 tick 重试一次，日志里给一条 warn。`memory_profile` 会打印这个目录的绝对路径，那就是用户找日记的入口。

## 6. 钩子索引（v0.2.0 新增）

记忆块是"渲染出来的摘要"，钩子索引是"指向正文的指针清单"。两者并存：记忆块负责日常氛围与事实，索引负责**任何一段经历的完整叙事都可回溯**。

索引块的真实样子（约 60 token）：

```
【记忆索引】只有钩子，细节用 memory_expand(ref) 取；不要仅凭钩子断言具体内容。
- T 最近未整理 · 4轮 304字
- E1 技术·线上那个 Node 服务… 415字
- E2 其他·改完了，把 handle… 390字
- E3 其他·我用 pandas 读一… 329字
```

三条设计原则：

1. **驻留快照，不是每轮重排。** 常驻钩子集合是落盘快照（`loom_hooks.resident`），只在定时器（`index.rebuildMinutes`）、`memory_pack` 之后、显式 `rebuild` 时重算。渲染只读快照——同一段记忆在轮次之间逐字稳定，这是刻意防人格漂移：漂移的根因不是上下文长，而是注入内容每轮都在变。
2. **淘汰钩子，绝不压缩正文。** 超预算时低分钩子进冷区（`index.coldDays`，默认 7 天，不回抖），而不是花模型调用去摘要压缩。正文一直在 `l0` 里，冷区钩子仍可用 `memory_index search` 命中、直接 `memory_expand` 取回。
3. **软上限双保险。** token 预算 + 条数硬顶；低于 `index.minHookScore` 的候选直接不占位——空位比坏钩子便宜。同名近重复事件只留最高分。

实测（端到端，跑真实 bundle，79 项断言全过）：

| 场景                     | 记忆块                      | 索引块                              |
| ---------------------- | ------------------------ | -------------------------------- |
| 两条工作会话（写代码 + 表格）同时活跃   | 504 token                | **65 token**                     |
| 60 轮 + 41 条事实 + 40 段事件 | 407 token / 13 行（超限静默丢弃；索引块只是旁路兜底，没有改变记忆块自身行为） | **137 token / 10 条钩子，任意一条可展开全文** |

遗忘级联：`memory_forget` / `erase` 删除素材后，`memory_expand` 拒绝返回对应正文，`memory_index gc` 清理孤儿整理版；重建时会自动清掉已失效的驻留钩子。

从 0.1.x 升级：无需迁移。索引表（`loom_docs` / `loom_links` / `loom_hooks`）在启动时自动创建，已有 `loom.db` 直接可用；曾经单独安装 `dsh-memory-loom-index` 的，把两个插件换成这一个即可。

### v0.2.30：配额用完了，得说一声

`consolidation.dailyLlmCalls` 默认 200 次。用完之后 `canUseLlm` 返回 false，抽取退回规则路径——**这一步没有任何提示**。原话照样入库，只是抽不出压缩后的事实，于是「它好像不太记得了」这种印象要过几周才形成，而那时候已经没法归因了。

真正让这件事变糟的是另一面：代码里其实**算过**降级。`report.degraded` 在三个地方被赋值，然后没有人读它——`engine.consolidate()` 的返回值在维护循环里直接被丢掉，audit 只记了 `model: true/false`，医生一个字都不提。一个被计算、被传递、最后被丢弃的信号，比完全没有这个信号更危险：看代码的人会以为这件事已经被照顾到了。

所以这次不是「加一个告警」，是把这条链路接通，同时把那个布尔拆开——配额用尽、模型调用失败、判断层降级，这三件事的处置完全不同，一个是明天零点自己好，一个要换模型，一个根本不用管：

```
degradeReasons: { budget: 2, model: 0, judge: 1 }
  → audit 每次整合都写（即使 false 也写，「这天到底有没有走模型」需要否定面）
  → memory_doctor 报「今日已用 2/200」以及最近一次整合的降级原因
  → 日志每天第一次踩线时提醒一句，之后不再刷屏
```

医生那一行还顺带纠正了一个容易误报的地方：**判断层走规则不算「出问题」**。事实已经抽出来了，只是四条判断改由规则给出，用户什么都不用做。把它和「配额用尽」混在同一句里，一次完全正常的整合也会看起来像事故。

另外两个洞一起补了。

**规则路径只认「谁做了什么」，不认「什么是什么」。** `looksWorthKeeping` 的词表全是用户画像、经历、计划、要求，对「依赖名调整为 badger」「超时设成 30 秒」这类句子完全无感。在同一份 270 段的技术记录上量，整份语料只抽出 **2 条**事实——而这些记录里几乎每段都有一句带确切值的话。补上「属性、配置、命名」三类陈述之后是 **404 条**，其中 95% 落在带值的那句上，噪音只有 2 条。

刻意没收「数字 ＋ 单位」这个形状。「等了 3 分钟」「花了 200 块」在闲聊里太密，收进来就是把噪音写进记忆，而记忆里的噪音比没记更贵——它在此后每一次检索里都参与排序。

**还有一件试过又退回去的事，记在注释里了。** 事件摘要原本取「首句 ＋ 最长句」，我一度认为「最长＝信息最多」这个前提不成立，改成优先挑带数字或英文标识符的句子。中间指标很漂亮：关键句进摘要从 26.6% 升到 82.6%。但同一批题上的检索反而腰斩，20.3% 掉到 8.7%，叙事文本上最明显——故事里的数字是「三天后」「第十年」，而情节点恰恰是最长的那句。判据只在一类文本上成立就不是判据，所以退回按长度选，把测量结论写进了函数的注释，省得下一个人再试一遍。

**外部基准这件事结案了。** 在 [hive-memory-bench](https://github.com/FuRongJun-1999/hive-memory-bench) 的 chain 轨上跑完了 561 道主读数题：整句材料齐备 20.5%，变更链覆盖 73.3%，同口径全文字 BM25 是 82.7% 和 94.1%。差在索引粒度——一条摘要覆盖一个槽位，一段原文覆盖五到十个，而这个差距发生在**检索**这一步，`memory_expand` 补不回来。既然补不回来，为它把索引换回原文就等于换掉「省 token、按需展开」这个前提。详细读数、分离实验、以及为什么语义检索也救不了这张表，写在 [`docs/design.md`](docs/design.md) §35。

### v0.2.29：校验位，不是重传

模型抽一条「用户对芒果过敏」，此前没有任何东西能判断这句话是不是它编的。`evidence` 里只有 `ttlPhrase` 和 `duePrecision`——都是**关于时间**的，没有一个字段关于**这句话从哪来**。于是幻觉进库是无声的：行在、能搜到、读起来还通顺，而且会一直待在那里。

这个洞的形状是「缺校验位」，不是「缺重传」。所以补法是在抽取时多问一句「支撑这句话的原文是哪几个字」，然后在**本地**做一次子串比对：

```
quoteVerified: true    原文里找到了
quoteVerified: false   没找到——可能编的，也可能改写造成的
（键不存在）            没给摘抄，或短到没法判：不算失败
```

**为什么不是「让模型再校验一遍」。** 那是 ARQ，要多一次模型调用、多一份延迟、多一次可能出错的地方，而它能做到的事（这句和原文对不对得上）用 `String.includes` 就能做到。校验位不该是算出来的，应该是**读出来的**。

**为什么第一版只记录、不拦截。** 提取提示词要求把主语写成「用户」，模型很容易把这个改写顺手带进摘抄：「原文是我，我照抄成了用户」。这类误报和真编造在字符串层面长得一模一样。按 `false` 直接丢事实，会把一条真事扔掉——而在记忆系统里，**漏记比多记难发现得多**。所以先攒数据：`memory_doctor` 加一行 `· 引用核对  12 条带出处，全部对得上`，出现对不上的时候变成 `✗`、点名其中两条，并说清下一步怎么核对。等实测知道误报率，再决定拦不拦。

五个细节：

- **归一化去掉标点和空白**再比。模型给自己的引文换个标点，不能说明那些字不在原文里。
- **省略号切段，每段都要在**。「下周三去北京……挂的是上午的号」能过，因为它没有要求中间那些字也在。
- **短于 4 个字的不判**。「好」「嗯」这种摘抄作为证据没有意义，判成 false 只是噪声。
- **merge 不覆盖旧值**。同一条事实第二次被抽到时，`evidence` 是合并的，旧的 `quoteVerified` 留着——一次没给出摘抄，不能推翻上一次已经核对过的事实。
- **这行给的建议得真能把它自己消掉**。第一次写的时候医生那条查询漏了「只数活着的行」，于是你按建议 `memory_forget` 掉那条编造的事实之后，`✗` 还亮着、还点名它。补上之后，删完这一行就消失——一条照着做也没有用的建议，比没有建议更坏。

顺带把抽取的 `maxTokens` 从 900 提到 1200：每条事实多一个摘抄，8 条就多出三分之一输出。截断的 JSON 解析不出来，整段会掉到规则路径——那个失败是无声的，掉的是记忆而不是错误码。

`probe-extract-quote.mjs` 23 项，七组：提示词口径 6 项、逐字摘抄与标点差异各 1 项、编造与主语改写都标 `false` 且两条事实**都还在库里**、没给摘抄与太短的都不写这个键、省略号两段都在才过、医生三种状态（全对 / 有错 / 没数据）各一行、以及删掉那条之后 ✗ 整行消失。

**没覆盖到的地方**：规矩（`kind=instruction`）进的是 `preferences` 表，那张表没有 `evidence` 列，所以规矩没有校验位；v0.2.29 之前写进来的事实也没有。这两类在医生那一行的分母里都不出现——分母只数**带摘抄的行**，否则比例永远是假的。

### v0.2.28：规矩也得有门，可门牌号会撞

长期规矩（`kind=instruction`，用户说「以后都这样」的那些）一直待在两个地方：常驻区，和 `preferences` 表。常驻区每轮带最近 3 条，`preferences` 表则只有一条召回路径——记忆块里那次「OR 匹配」。`memory_search` 从来没接它。

于是第四条规矩开始就悬空了。实测（写四条 instruction，第四条是「我不吃香菜」）：

```
[我有什么忌口]      块里有香菜? false    search: 没有找到相关记忆。
[点外卖注意什么]    块里有香菜? false    search: 没有找到相关记忆。
[我有什么规矩]      块里有香菜? false    search: 没有找到相关记忆。
```

三条路全断，而那一行就在表里。**不是「只能靠块撞见」，是块也经常撞不见。**

### 只加一行调用会修出更坏的东西

`searchPreferences()` 早就写好了（块召回在用），所以直觉上是在 `searchFor()` 的 `collect()` 里补一个循环。但三张表的 `id` 各自从 1 开始：

```
已记入长期偏好 #1 … #4
已记住 #1                     ← 事实表的 #1，和偏好表的 #1 是两条不同的记忆
```

`memory_forget` 只收整数、只查 `facts`。结果里一旦出现一个裸数字，模型把它填进 `id`，删掉的就是一条毫不相干的事实，而且回话还说「已标记删除」——**成功、无声、错的是另一行。** 所以这次一起改了三处：

- 编号分类型：`#P3`。`parseRef` 认 `p`，`memory_expand("P3")` 取回原文，`refAlive` 也知道 `P` 不是 `F`；
- `memory_forget` 加 `ref`，`ref="P3"` 走偏好、`ref="F7"` 等同 `id=7`；回话带上被删那句的原文，删错会在对话里一眼看见；
- 跨身份查询整类跳过偏好。事实有 `isolated` 标记可供判断能不能外露，规矩没有这样的列；主人跨读的约定本来就是「查对方的事实」，顺手把对方私下让你遵守的要求也端出来，是把门开大了一格而没人要求过。

排序另给一个 `PREFERENCE_HIT_WEIGHT = 0.6`：两张 FTS 的列数不同，bm25 不在一个量纲上，不压一下，一条只共享一个词的规矩能排到命中三处的事件前面。规矩本来就已经常驻，搜索只需要让旧的那些**够得着**，不需要它们赢。

### 顺带补的那个出口

改这条时才发现：整个插件里没有任何代码写过 `active = 0`。也就是说规矩只有进没有出——用户说「以后不用管我那条了」，模型没有任何工具能落实，那一行会一直待常驻区继续生效。

所以 `memory_forget(ref="P3")` 现在的默认动作是把行**收回**（`active = 0`）：块、`memory_search`、导入去重三处本来都按这一列过滤，一次写三处同时生效；`permanent=true` 才真删行。收回的动作记进 `audit`（`preference.retire`），谁在什么时候收回的、收回的是哪句话，都留得下。

收回只限本人：规矩没有可见性列，别人那条连读都不给（跨身份搜索整类跳过），所以主人也收不回朋友的规矩——给一个例外，等于把上面那扇刚关上的门从后门再开一次。

### 收回过的规矩不许从导入那条路复活

补上 `active = 0` 之后，「导入」这条路就必须看这一列了：`memory_export` 的产物拖回来、或者从另一台机器找回旧文件时，同一个文件里会同时有还在生效的和已经作废的规矩。`normalizeIntakeRows` 现在会跳过自己写着 `active: 0` 的记录，并在预览里报「已收回的 N 条」；`exportData` 也补上了 `active` 列——原来只导 `id/text/created_at`，导出再导回时唯一真正的差别恰好被丢掉了。

还有一条更隐蔽的路：源文件根本不可能知道用户后来改主意了（没人会在别人的导出文件里标注「这条我撤回了」）。所以导入去重的那份名单也不再只算 `active = 1` 的规矩——本地已经收回的，任何文件都搬不回来。想让它重新生效只有一个动作：用户再说一次。

**还差什么：** 这次补的是「有门」，不是「懂意思」。问题是词法匹配，「我有什么忌口」和「我不吃香菜」一个字都不共享，仍然搜不到——这条限制和事实、事件完全一样（见 §9「向量 / embedding 检索」）。真正的补救是用户把话说得具体些，或者靠常驻区里那三条兜住最近说过的规矩。

### v0.2.27：行首的日期是「他哪天说的」，不是「哪天要去」

每条记忆前面都带一个日期，所以这里一直有个说得过去的错觉：时间有记，不用再管。但那个日期是**他说这句话的那天**——

```
- [08-05 · 事实] 用户明天要去医院复查心脏，挂的是上午的号
```

到了 11 月，这一行一个字没变，意思却变了。「明天」指的是 08-06，而读者看到的是一个还在说「明天」的人。这不是模糊，是错，而且是一个会让人真的跑一趟医院的错。同类里轻一些的是「用户前天把明信片寄出去了」：不会误事，但被问「什么时候寄的」时，最省力的答案就是照抄「前天」——那已经是三个月前了。

**所以这一版做的不是「补日期」，是把句子里的词锚到那个已有的日期上。** 换算基准就是 `created_at`，也就是说，用的是插件本来就知道的东西，没有引入任何新表、新字段。

```
- [08-05 · 事实] 用户明天（08-06）要去医院复查心脏，挂的是上午的号
- [08-05 · 事实] 用户上周三（07-29）跟房东谈过续租，租金涨了两百
```

四条约束，每一条都对应一种会把事情做坏的方式：

- **原文不改。** 库里存的、FTS 索引的、`memory_expand` 展开的，都还是原话。改了就分不清「他当时说错了」和「我们后来记错了」，而那两件事的处理方式相反。
- **只补说得准的词。** 今天/昨天/前天/大前天/明天/后天/大后天/上周三/下周五，这类词指向确定的某一天。「前几天」「上个月」「过段时间」不补——它们本就没有那一天，补一个出来就是编，和这个插件在别处拒绝编日期是同一条理由。
- **看着像时间的名词要放过。** 「先天和后天都重要，习惯是后天养成的」「后天免疫」「明天出版社」——中文里这三个词都还是普通名词。补错了比不补坏得多：不补只是少一个日期，补错是往记忆里写了一句假话，还带着一个看起来很权威的括号。
- **有期限的计划不重复补。** 计划行的行首本来就是 `[11-11 · 截止]`，正文再补一个「下周三（11-11）」是同一行印两个相同的日期。只有「未定期限」的计划才补——它没有 due 可显示，句子里的时间词就真的没人翻译了。

**为什么不在写入时改。** 那样只算一次、也只错一次；放在渲染层则每次都要算一遍。但写入时改的代价是不可逆的：一条被改写成「（08-06）」的事实，再也没法证明用户当时说的是「明天」。这里的取舍是**宁可多算一遍，也不动证据**。

`probe-relative.mjs` 17 项断言，全部走真实 `apply()` 与真实记忆块：五个该补的词各自补对（含「上周三」跨周），六个不该补的都不补，库里没有一条被改写，搜索命中也补，有期限的计划不重复补而没有期限的照补。全套 39 个脚本（33 个探针 + 6 个场景）与 `selftest` 全绿。

### v0.2.26：换插件不该等于从头开始

这是 v0.2.25 留下的账。那一版教用户「装之前先卸别的记忆插件」或「把本插件改名成 `loom_` 共存」，两种办法都保住了一个人的记忆**从今往后**，也都留下了同一堆文件：`memory.db` 里那 42 条还在盘上，但再没有东西会去读它。用户卸载时看到的是「记忆不会丢」，装完新插件后看到的是「它不记得我」——两句话都对，合起来就是个坑。

**这一版只做一件事：把那些文件读进来。** 三个动作，分别解决三个不同的问题：

| 动作 | 解决什么 | 具体做法 |
| --- | --- | --- |
| 装好就扫 | 用户不会主动去找 | `apply()` 里扫一遍，之后每 6 小时一次；结果落在 `meta` 里，提示词和医生都读它，每轮不碰磁盘 |
| 问一句，然后闭嘴 | 不问等于没做，一直问等于被卸载 | 记忆块里出现一行「可导入的记忆」，点名是哪个文件、多少条、怎么调；**每个会话最多问三次**，之后靠 `memory_doctor` 长期可查 |
| 分层落库 | 「导入」如果只是把句子塞进去，导了也用不上 | 走和整合完全相同的分类路径：`kind`/`domain`/`salience` 重新判定，`instruction` 进常驻区，其余进召回层，原始日期保留，来源标 `import:<插件名>` |

**为什么不做成自动导入。** 别人的记忆是他的东西。`memory_import` 的三段式（清单 → 预览 → `confirm`）不是流程洁癖：预览里必须出现三个数字，人才答得上「要不要」——**实际会进来多少条**（去掉重复之后）、**哪些被丢掉以及为什么**（太短、疑似密钥、太长）、**补别名要花多少次模型调用**。第三个是唯一花钱的部分，所以说调用次数，不说「有成本」。

**别名的欠账，这次有了还款入口。** v0.2.18 起每条事实在写入时由模型顺手给 2–3 个「用户下次会怎么问」的别名。这带来一个一直只报不修的缺口：老库里的记忆没有别名，`memory_doctor` 报 `12/30 条带别名`，然后没有然后。现在 `memory_import(aliases=true)` 按 salience 排序分批补，每批 12 条，**先看当天预算再动手**（`consolidation.dailyLlmCalls`），用完了就停并报「还剩 N 条」，不偷偷超支。

四个刻意的取舍，都写在 `docs/design.md` §31：

- **旧计划按事实存放。** 「下周三去体检」里的日子是**那个插件**的时钟算出来的，拿今天重新解析就是编一个期限。所以导入的计划不成其为计划，原文照留，`evidence.wasPlan` 留个痕迹。
- **稳定性按年龄补齐。** 强度是 `base × (1 + 年龄/S)^-d`，一条两年前的记忆按新事实的 S 进来，直接掉到七分之一、永远过不了相关性门槛。那两年没人访问它，不是它的错——导入的行按 `S = max(sInitial, 年龄)` 起步，落在半强度上，之后照常生长。
- **不删源文件。** 搬家没有「顺手清空旧房子」这一步。卸载别的插件也不删它的数据，所以导入之后那两个文件必须原样留着，用户随时可以反悔。
- **文本类文件也认。** 每个「导出你的记忆」按钮吐出来的都是 Markdown 或每个一行，所以 `.md`/`.txt` 按项目符号或行切；`path` 参数就是给「把文件拖进聊天窗口」用的，不依赖任何路径规律。

`probe-intake.mjs` 61 项断言，全部走真实 `apply()`：扫到别人的库且不把自己的算进去、提示词问三次后闭嘴、出现新的一份会重新问、预览前后事实数不变、`confirm` 之后 `kind`/`domain`/`created_at`/`source` 都对、同一个文件导两次第二次什么都没进来、说不要之后源文件一个字节没动、拖进来的 Markdown 也能导、指向**本插件自己的旧库**时只搬事实与要求（对话原话和人格设定一条都不搬）、`aliases=true` 在 `dailyLlmCalls=2` 时补完 24 条就停下并报「还剩 6 条」。全套 38 个脚本（32 个探针 + 6 个场景）与 `selftest` 全绿。

### v0.2.25：承诺是延迟兑现的，所以先把日子说出来

这个插件的旗舰功能**装上当天不会发生任何事**。用户说「下周五去体检」，插件记下来，然后什么都不做——要等到 11-13 过去、下一次对话，它才会问那句「后来去了吗」。从那句话到那天，中间是十几天，而这十几天里用户看到的只是一个「记住了一些事实」的工具，那也是所有记忆插件都会做的事。

这不是文案能补的洞：文案越强调「它会回来问你」，这十几天的空白就越像没兑现。

**改法不是加快触发，是把兑现时点提前贴现。** 两处，都是字符串加一次日期计算：

| 位置 | 之前 | 现在 |
| --- | --- | --- |
| 记忆块里的计划行 | `- [11-13 · 截止] 下周五去体检` | `- [11-13 · 截止] 下周五去体检（到期后我会问一句；他说已经做了或不做了，就现在调 memory_resolve(id=1, outcome=done\|cancelled)）` |
| `memory_doctor` | `· 计划与矛盾  1 条计划（0 条已到期） · 0/1 条待确认` | 同一行不变，下面多一行 `· 下一步  「下周五去体检」2026-11-13 23:59 到期，之后第一次对话就会问，没回答就每 2 天再问一次` |

第二处只报**最近一条还没收尾的计划**：已经办成或没办成的没什么要等，没有计划的库不该多出这一行。再问间隔从 `retrieval.planNudgeDays` 现读，不写死在文案里——配成 `0` 时那半句自己消失。

计划行里分号后面那半句不是同一件事，是补另一个口子（用户提前做完了、插件不知道），在下一节展开。

**顺带纠正一个容易读错的地方。** 第一次问不是「到期之后再过 2 天」，而是**到期之后第一次对话**就问了；`planNudgeDays` 只管「问了没回答，隔多久再问」。这两个数在代码里是两件事（`overduePlans` 用 `expires_at <= now`，`nudge` 用 `nudged_at` 的间隔），但在「2 天」这个数字上很容易混成一件。

**新增第 15 个工具 `memory_demo`。** 它在一个 `:memory:` 库里、用一根可以拨的假时钟，把整圈跑一遍给人看：

```
【第 1 天 · 2026-11-03 07:10】你说：下周五去体检
它记成计划 #1，期限 2026-11-13 23:59。
此刻记忆块里那一行是：
  - [11-13 · 截止] 下周五去体检（到期后我会问一句；他说已经做了或不做了，就现在调 memory_resolve(id=1, outcome=done|cancelled)）

【第 N 天 · 2026-11-14 00:59】期限过了，你照常聊天
记忆块里那一行变成：
  - [11-13 · 已到期，还没有下文] 下周五去体检（过了期限还没有下文——这轮问一句「后来成了吗」…）
```

演示里每一步调的都是生产代码——`writeFact` 解析「下周五」、`recall` 的计划通道挑行、`renderMemoryBlock` 拼行、`resolve` 收尾写新事实。**没有为演示另写一套渲染**，否则演的就是另一套东西，而演示的全部价值在于「你看到的这行字，就是以后真会出现在提示词里的那行」。跑完不留任何文件。

`probe-demo.mjs`（25 项）盯的是三件事：三幕都在且到期前后不重复写同一句话、演示前后真实库的 `facts` 计数不变（一个会写用户记忆的演示比没有演示更糟）、医生那行在计划收尾后消失。

### 提前做完的计划，不该留在计划区里等到期

上一节说的是「等」太长。这一节是同一件事的另一半：**用户没等，提前做完了，插件发现不了。**

真实库里就有一条：计划「11-13 在小黑盒发推广文」，而他 11-02 晚上就发了。计划区只在**过期之后**才给模型催问指令，在那之前用户说「发了」，模型手上没有任何理由去调收尾——于是这条计划会在 11-13 回头问一件十一天前就答过的事。计划待得越久，那一问越像没在听。

根因不在判定，在**模型拿不到 id**：未到期的计划行是 `- [11-13 · 截止] 下周五去体检（到期后我会问一句）`，里面没有编号，它就算想收尾也无从下手。所以收尾入口只能写在行上，和那句承诺时点放在一起。

| 行 | 之前 | 现在 |
| --- | --- | --- |
| 有日期、未到期 | `（到期后我会问一句）` | `（到期后我会问一句；他说已经做了或不做了，就现在调 memory_resolve(id=1, outcome=done\|cancelled)）` |
| 没日期（`未定期限`） | 什么都不写 | `（他说已经做了或不做了，就现在调 memory_resolve(id=2, outcome=done\|cancelled)）` |
| 已到期、正好轮到再问 | 有催问指令 | 不变，**不叠加**这一句 |
| 已到期、刚问过（间隔没到） | **只有标签，没有编号** | `（他说已经做了或不做了，就现在调 memory_resolve(id=3, outcome=done\|cancelled)）` |

判断条件是「**这一行没有催问句**」，不是「这一行还没到期」。这两者差在一格上，而那一格恰好是最常见的：计划刚过期、上一条已经问过、再问间隔（默认 2 天）还没到，那一行既没有催问句也没有编号——用户最可能正是在这时补一句「去了啊」。

四处边界都是刻意的：

- **没有日期的计划也要有入口。**「我打算戒烟」说过，用户后来说「戒了」——它一样会提前完成。只是不写「到期后」：没有日子，写「到期后」就是撒谎。
- **有催问句的行不叠加。** 那一行本来就有 `planAsk`，两条 `memory_resolve` 并排会读成两件事。
- **改期待确认的行也不给。**「时间待确认」那一行已经有 `memory_settle(id=…)`，再并一个 `memory_resolve` 就成了两个动作摆在同一行，模型不知道先答哪个——`planItem` 当初关掉 `ask` 就是为这个。改期落定之后，下一轮那半句自己回来。
- **只在用户说出结果时收。**「还没去」「再说吧」不是结果，模型不动它——宁可不收，不可错收。

顺带修掉一处一直自相矛盾的标签：没日期的计划原来渲染成 `[未定期限 · 截止]`。日期那一格已经说了它没有期限，再补「截止」既没有信息量，又把这个词用在了明确不成立的地方。现在整格省掉，读作 `[未定期限] 我打算戒烟`。

收尾之后它**真的离开计划区**：`openPlans` / `overduePlans` 都带 `resolved_at IS NULL`，写出来的新事实是 `kind=fact`，不会以计划身份回来。`probe-plans.mjs` 第 6、7 组（15 项）锁的就是这件事——从行上抓 id、收尾、断言那一行消失、断言另一条计划没被连坐、断言重复收尾被挡下、断言「刚问过还没到再问」的那一行仍然带着编号。

全套 38 个脚本（32 个探针 + 6 个场景）与 `selftest` 全绿。

### 取消不是失败：计划有第三种结局

提前收尾的第一版只给了「办成」这一个读法，因为怕错收。那个防线守住了，但漏掉了更常见的一半：**计划提前结束，多数时候不是做完了，而是不做了。**

「不去了」「算了」「那套没看上」——这些话在日期之前很常见。第一版行上写的是 `memory_resolve(id=3, done=true)`，模型面对用户这句话只有两条路：不调，或者调 `done=false`。前者让一条作废的计划在两周后回头问「后来成了吗」；后者把一次**主动放弃**记成一次**失败**。而这两件事在往后的对话里意味着完全不同的建议——一个是「上次没去成，要不要再约」，一个是「那套他已经不打算看了」。

所以布尔换成三选一：`outcome=done` / `missed` / `cancelled`。

| outcome | 用户的话 | 写下来的事实 |
| --- | --- | --- |
| `done` | 去了 / 交了 / 弄完了 | `用户打算去看房 —— 已办成（11-03 确认）` |
| `missed` | 没去 / 没弄完 | `用户打算去看房 —— 没办成（11-03 确认）` |
| `cancelled` | 不去了 / 算了 / 取消了 | `用户打算去看房 —— 已取消（11-03 确认）` |

三者共同的部分一点没变：计划原文不动、离开计划区、只写一条新事实。区别只有那一句话和 `outcome` 这一格。

三处是改的时候才想清楚的：

- **过期之后也还能取消。**「到日子了」不等于「必须给个成败」。催问句出现的那一行不叠加收尾入口（一行只放一个动作），但 `cancelled` 这个值本身不受时间限制——刚过期、已经问过、用户回一句「算了不去了」，照样记成取消。
- **取消的计划不该被打上「过期」。** 计划被取消之后，它当初那个日期还是会到。维护按 `expires_at <= now` 扫，第一版会把已收尾的计划一起打上 `expired_at`，而 `scoreFact` 里的 `expiryFactor` 会按天把它从检索里减半，最后 `factsDueForPurge` 会把这条唯一记录删掉——而 `resolve()` 刻意不改写计划，正是为了留下那句原话。现在 `expireDueFacts` 多一个 `resolved_at IS NULL`：已经收尾的不是待办，谈不上过期。
- **搜索结果也要说结局。** `memory_search` 里那条计划原来不带任何标记，搜「看房」会读到「用户打算周五去看房」，像还没去。现在带上：`用户打算周五去看房（已取消）`。记忆块靠「计划区不含已收尾」避免这个误读，搜索结果没有分区，只能靠这一句。

**代价**：布尔换枚举是一次不兼容改动。0.2.24 装出来模型看到的是 `done`，这一版看到的是 `outcome` —— 因为还没人装，现在换等于免费。**证明不了的仍然是同一件事**：探针能证明三种结局各写一条对的事实、计划离开计划区、搜索结果带标记、已收尾的不被标过期；证明不了模型在用户说「不去了」的那一刻会想起调它。

### 抽不出东西的那十段对话

用真实库量了一次：**13 个事件、9 条事实，其中 10 个事件一条事实也没挂上**，六个是技术类。而 `memory_doctor` 每一项都是绿的——库里确实有 13 段对话，只是其中十段没留下任何一句可以单独检索的话。

「没挂事实」不是检索 bug。检索只能捞库里有的东西；一段对话的内容根本没进事实层，问起来就只剩事件标题能命中，而标题是 16 个字的索引，不是答案。

两层各有一个洞。

**模型那条路**：提示词的收录口径是一句话——「只抽取稳定信息：偏好、身份背景、关系、计划与承诺、重要经历、明确的长期要求」。模型把「重要经历」读成人生大事，于是「今天把迁移脚本改完了，卡了三天的 WAL 锁终于弄明白」不入选。它不是没读懂，是这句话不在任何一格的名录里。

口径换成分两类，并且说清第二类的用途：

> ① 关于他这个人——偏好、身份背景、关系、明确的长期要求；
> ② 这段对话里他自己说的具体事——做了什么、遇到什么、卡在哪、做到哪一步、和谁、结论是什么。
>
> ②不是流水账，是「上次那件事」的落点。只抽①的代价很具体：他问「上次那个迁移怎么样了」，答案不在①里，而他想不起来把经过再讲一遍。

反例也写进去，因为光说「抽具体的事」模型会给回「用户在讨论代码」这种概括——没有对象也没有结论，等于没抽。同时保留逃生的权利：整段只有寒暄、只有让助手干活时 `facts` 给空数组，**交白卷比编一条强**。

**规则那条路**（没有模型时的兜底）：`PREFERENCE_MARKERS` 收了「不喜欢」，没收「不吃」——于是「我不吃香菜」这个所有人拿来测记忆的句子，恰好是它漏掉的那一句。而且词表里根本没有「做事」这一格，只有偏好、身份、指令和时间词。现在多两组：`EXPERIENCE_MARKERS`（做了什么、遇到什么、卡在哪）和否定式偏好。

这里真正的难点不是认出来，是**别无中生有**：

| 句子 | 结果 | 为什么 |
| --- | --- | --- |
| 我不吃香菜，闻着就难受。 | 记 | 口味 |
| 今天不吃早饭，赶时间。 | 不记 | 一顿饭。写进偏好区往后每顿都被否决一次，而用户没法解释那不是他的口味 |
| 我中午不吃，晚上再说。 | 不记 | 同上，只是主语还在 |
| 今天把迁移脚本改完了。 | 记 | 中文说话不带主语，而这正是这段里唯一值得记的一句 |

所以「不吃」之外还有一条时间判断：句子开头紧跟当天的时间词，就降级成一次性陈述。省主语的写法单独占两条规则，靠完成态动词站位（`把…改完了`、`今天…弄明白`），因为补了「经历」这一组却漏掉最常见的句式，等于没补。

最后让这件事**有数可看**。`memory_doctor` 多一行：

```
· 抽取  13 个事件 · 9 条事实 · 3 个事件挂着事实
```

只在一个都没挂上时才多说一句。挂了一半不是异常——一段纯寒暄、一段只是在让助手干活，本来就抽不出东西，把它们报成问题会让真正的问题沉在噪音里。

**这一版证明不了的事**：提示词改了，模型是否真的多抽了，探针证明不了。能证明的只有口径确实写在提示词里（`probe-extract.mjs` 比对那次请求的全文）、规则路径的九个正反例各归各位、医生那一行的格式与触发条件。**模型那半要等真实库的下一个数字**——这正是加那一行的原因：否则改完口径，没有任何地方能当场读出来它有没有生效。

### 和别人的记忆插件撞名

推广文发出去之后，最先要回答的问题不是「它比别的记忆插件好吗」，而是**「我已经装了别人的，这个能不能直接装」**。

**默认不能。** 宿主把工具放在一张按名字索引的表里，重名直接抛错；而 `apply()` 抛错会把**整个插件回滚**——不是丢一个工具，是 16 个工具一个都不进表、三块提示词一起撤掉。用户看到的只有「装上了，但它什么都不记得」。

这个生态里至少四个记忆插件用了同一套名字：

| 插件 | 与我们重名的工具 |
| --- | --- |
| `dsh-memory`（SQLite + FTS5） | `memory_search` `memory_write` `memory_forget` |
| Memory Library（工作区卡片库） | `memory_search` `memory_write` `memory_forget` |
| Workspace Recollection | `memory_search` `memory_write` `memory_forget` `memory_index` |
| `@max-null/dsh-memory` | `memory_search` `memory_forget` |

`memory_search` / `memory_write` / `memory_forget` 是这个生态的事实标准名——四家用的是同一套。**16 个名字里任意一个撞上，整体装不上。**

这一版加了三样东西。

**1. 装之前先说话。** `apply()` 一进门就把 16 个名字查一遍，撞了就在**打开数据库之前**停下，抛一句能照着做的话：谁占了、卸了会不会丢东西、共存的开关叫什么。宿主原来的报错是 `tool "memory_search" is already registered`——它说的是事实，但没告诉一个普通用户下一步该干什么，而且它是在我们注册到第 3 个工具时才抛的，前面两样已经挂上去了。

**2. 卸载不删记忆，这点要写进错误信息里。** 用户说「不想删以前的东西」时，怕的其实是数据。`dsh plugin remove` 只摘插件：`.dsh-memory/`、`$DSH_HOME/memory/memory.db` 这些文件原地不动，装回来还在。所以「换一个试试」是有退路的。

**3. `toolPrefix`：想共存的人可以共存，但默认关。** 设成 `loom_`，16 个工具变成 `loom_search` / `loom_write` / …，并且**提示词、工具描述、工具返回里的名字一起换**。

只换注册名是不够的——那样模型会在提示词里读到「用 `memory_search` 查更早的记忆」，然后去调一个叫 `memory_search` 的工具，而那个现在是别人的，参数完全不一样。所以改名落在三个出口上：工具定义（名字 + 描述 + 参数说明）、每个提示词 section 的 `text()`、每个工具的返回值。这三处覆盖了全部 **21 处**工具名引用，包括写死在文案里的那些；以后再新增文案也自动覆盖，不用回来补。

不设为默认，因为共存有真实代价：

- 两边都往系统提示词注入，每轮多 3000–5000 字符（我们约 300 token，同类插件普遍 2000–4200 字符）；
- 两边都在会话结束时调模型抽取，同一段对话付两次钱、等两次延迟；
- 模型看不到「这块是 loom 的、那块是别人的」，会当成一段连续回忆——两份矛盾时它不知道信哪个；对方若还写人格文件，冲突更明显。

**技术上还有一个不对称，值得说清楚。** 改名只解决「我们避开别人」。反过来不成立：如果本插件先加载、占住了 `memory_search`，后装的对方照样整插件失败——那是它的重名，我们修不了。所以真要两个都装，顺序是**先装对方，再装我们并设 `toolPrefix`**。

**证明不了的**：探针能证明撞名时抛的是人话而不是宿主原文、能证明改名之后 16 个工具都在且提示词跟着换、能证明同名调用不会串到对方身上；**证明不了**换成 `loom_search` 之后模型的调用率有没有下降。`memory_*` 是模型先验最强的名字，改名等于拿这一点去换共存——这也是它不该默认开的原因之一。

### v0.2.24：升级不重启等于没升级，医生自报版本

v0.2.23 发布当天，在真机上做了一次「从 0.2.16 升到 0.2.23」，暴露出一个比任何功能 bug 都更值得记的问题：**包换了，代码没换，而且从外面看不出来。**

| 检查 | 装完之后 | 应该是 |
| --- | --- | --- |
| 工具数 | **9 个** | 0.2.16 起 12 个，0.2.23 是 14 个 |
| `memory_doctor` | `unknown tool` | 0.2.16 就加了 |
| 库 `user_version` | **1** | 0.2.23 是 4 |

三条同时指向同一个结论：**实际跑的是 0.2.12**，0.2.16 和 0.2.23 都只是装到了磁盘上。之前之所以认定「装上就生效」，是因为那次实测是**首次安装**——宿主看到 bundle 列表多了一项，于是重组。升级是同一个 bundle 换内容，列表长短没变，不触发重组。

**这段诊断代码没赶上 v0.2.23 的 tag。** 它是在发布之后才想明白的，而版本号已经跟着 tag 走了；再把同一份代码塞回 `v0.2.23`，会让这个版本号同时指两份不同的代码。所以单独发 v0.2.24：功能与 v0.2.23 完全一样，多出来的只有「能说出自己在跑哪一版」和下面那条安装说明。

**代码上改了三处。**

1. **安装章节分成两种情形。** §2 现在写清「首次安装不用重启，升级必须重启」，并给出升级的四步（先备份库、装、完全退出重开、用 `memory_doctor` 确认）。
2. **`memory_doctor` 第一行报版本。** 之前没有任何一个地方能回答「你现在跑的是哪一版」，只能靠数工具反推。现在恒为输出第一行：

   ```
   · 版本  运行 0.2.24 · 库 schema v4 · 库上次由 0.2.12 打开
   ```

   三段分别是：`lib/index.js` 里写死的 `BUILD_VERSION`、库的 `PRAGMA user_version`、以及 `meta` 表里上一次启动时记下的版本。后两段能证明「这次升级是真的发生过」，第一段能证明「跑的是新代码」。升级后没重启时，新代码根本不会执行，也就打不出这一行——所以它不会撒谎。
3. **CI 盯住 `BUILD_VERSION`。** `check-docs.mjs` 多一条：这个常量必须等于 `package.json` 的 `version`。它是诊断依据，一旦过期就变成伪证，比没有更糟。

新增 `probe-version.mjs`（12 项）：医生首行是否同时给出运行版本与 schema、同版本重启不覆盖 `runtime.previousVersion`、以及「把库里版本改成 0.2.12 再启动」时能否说出「库上次由 0.2.12 打开」。全套 33 个脚本（27 个探针 + 6 个场景）与 `selftest` 全绿。

顺带把两处写死的工具数断言改掉：`probe-hotload` 的 `=== 13` 早就该变成 14（加工具时没人改），`probe-version` 初稿又写了个 `=== 14`。现在一处改成 `>= 14`，一处改成按名字查关键工具——加第 15 个工具时都不会再误红。

顺带修掉一处由此暴露的文档不一致：region 行号表全表重算（`apply()` 涨了 23 行，后面整段平移），并把 `probe-hotload` 的说明补清楚——**它证明的是「被组合进来就能挂上」，不证明「升级会触发组合」**。这个区别正是这次踩空的根因。

### v0.2.23：没有结果，就一直问下去

上一版（v0.2.22，没有单独发布）让计划过期时问一次，然后就再不问了。这个「一次」站不住：问的那一轮可能被打断、用户可能正在说别的事、可能回了一句「等会儿说」然后就没有下文——于是这条计划从此只是块里一行带日期的字，而它其实还没有答案。

**改的是 `nudged_at` 的语义，不是加一个字段。** 它从「问过了」变成「上次问是什么时候」：

| 状态 | v0.2.22 | v0.2.23 |
| --- | --- | --- |
| 从没问过、已经过期 | 问 | 问 |
| 问过、没回答、不满两天 | 不问 | 不问 |
| 问过、没回答、满两天 | **不问，永久** | 问 |
| 有结果（`resolved_at`） | 不问 | 不问，退出计划区 |

第一次仍然是「过期就问」，之后按 `retrieval.planNudgeDays`（默认 2 天）。`0` 恢复成只问一次。

**决定还问不问的只有 `resolved_at`，`nudged_at` 只负责节流。** 没有结果就一直留在计划区，有结果（办成或没办成）就退出——用户说的「把它当成一个问题，而不是一个结果」，落成代码就是这一行判据。块里的标记也从「之后没再提」改成「还没有下文」：没再提说的是用户，没有下文说的是这件事。

**顺带改了排序。** 逾期区原来按 `expires_at DESC` 排，最新过期的排前面。加了重问之后这个顺序会让排在后面的永远轮不到——每次都先问那几条新的。改成按上次问的时间升序（从没问过的算 0），最久没问的先问；名额不够时也不再有人被饿死。

`memory_doctor` 那行从「N 条已问过」改成「N 条问过没结果」，和「M 条已有结果」对起来看，欠账就是看得见的。

**顺手修掉两个一致性问题**，都是逐条检查时发现的，不是新功能：

| 现象 | 原因 | 现在 |
| --- | --- | --- |
| 同一行同时出现「时间待确认：改到 11-09」和「后来成了吗」，两个问句指着同一条计划 | 改期提案与过期判定各算各的 | 有改期提案时不问「成了吗」——用户刚说了新时间，这时问「成了吗」是问错了问题 |
| 已收尾的计划还能被 `memory_settle` 改期，改完 `resolved_at` 还在、日期却跑到未来，两头都看不见 | `settle()` 只看有没有提案，没看有没有结果 | 有结果的计划拒绝改期；要重做就记一条新计划。收尾时把那条例也清掉，`memory_doctor` 不再把它算成「时间待确认」的欠账 |

还有一个自己写出来的坑：`evidence["pendingDue"]` 不存在时是 `undefined`，不是 `null`。用 `=== null` 判断会把「没有提案」读成「有提案」，于是所有该问的计划都不问了——而且块看起来完全正常。归一化之后，`pending === null` 才是一个能用的判据。

`probe-plan-outcome.mjs` 28 → **52 项断言**，新增：不满两天不问、满两天再问、问的是同一条（id 不变、不多写一条）、`nudged_at` 被刷新、再下一轮又不问、`planNudgeDays=0` 只问一次、三条抢两个名额时最久没问的先问、改期提案与收尾互不打架。新增 `probe-upgrade.mjs`（42 项）专门跑老库升级。全套 32 个脚本（26 个探针 + 6 个场景）与 `selftest` 全绿。

### v0.2.22：期限是给没做的事的，计划过期了要问一句

v0.2.21 把说法认全了，但**认出来的日期挂到了不该挂的地方**：事实也拿到了期限。

「今天我把车卖了」和「昨天我把车卖了」是同一件事，都是已经发生的事。可前者会拿到一个当天到期的窗口，后者什么都不拿——于是同一类记忆有两种形状，第二天块里还多出一行 `(期限 11-02)`，读起来像这件事有个截止时间。更要紧的是，一条事实只要带了窗口，就可能被 `reconcileDue` 判成「时间待确认」，让模型跑来问用户「这个日期是改了吗」——而事实根本没有日期可改。

**现在：期限只属于 `kind=plan`。** 事实、偏好、关系一律不挂窗口，句子里的时间原话仍然存进 `evidence`（`ttlPhrase`），只是不再变成可比较、可逾期、可追问的东西。

**计划过了期限，不是一个结果，是一个问题。**

以前过期的计划就是一行 `[11-05 · 已到期，之后没再提]`，然后永远躺在那里。现在这行第一次出现时多一句：

```
- [11-05 · 已到期，还没有下文] 用户打算去看房（过了期限还没有下文——这轮问一句「后来成了吗」，按他的回答调 memory_resolve(id=12, outcome=done|missed|cancelled)）
```

**到期就问。** 提过就把 `nudged_at` 记下来，下一轮这行恢复成没有问句的样子（v0.2.23 起改成隔两天再问一次）。回答之后，计划和它的结果各自留一条：

| 用户回答 | 新写的事实 | 计划本身 |
| --- | --- | --- |
| 办成了 | `用户打算去看房 —— 已办成（11-06 确认）` | `outcome=done`，退出计划区 |
| 没办成 | `用户打算去看房 —— 没办成（11-06 确认）` | `outcome=missed`，退出计划区 |

**计划原文不动。** 「用户打算去看房」在说出口的时候是真的，「已办成（11-06 确认）」是现在真的。用后者覆盖前者会删掉这个承诺唯一的记录——而下一次要问的正是它。「没办成」也不是失败记录，它是两者里信息量更大的那个：只记成功的记忆会心安理得地把同一个失败的计划再提一次。

新增第 14 个工具 `memory_resolve(id, done, note?)`。它只对 `kind=plan` 有效，同一条不能收两次尾，对普通事实会直说「不是计划」。

schema 到 v4，新增 `nudged_at` / `resolved_at` / `outcome` 三列（老库走 `ensureColumn`，不需要重建）。`memory_doctor` 的计划行变成 `3 条计划（1 条已到期 · 1 条问过没结果 · 2 条已有结果）`，「时间」那一行只数计划——否则每一句带时间的普通事实都会被报成「只记了原话没算出日期」。

`probe-plan-outcome.mjs` 当时 28 项断言：事实不挂期限、到期问一句、办成与没办成各写一条事实、计划原文不改、收过尾的不重复写、非计划拒绝收尾（v0.2.23 扩到 52 项）。全套 32 个脚本（26 个探针 + 6 个场景）与 `selftest` 全绿。

### v0.2.21：把嘴上说的日子都认下来

v0.2.20 把期限做成了区间，但**认得的说法太少**：用户真正常用的几种，要么根本不认，要么认成了别的东西——后者更糟，因为界面上有个日期，看不出它错。

**三个真错，都是「看着有答案，其实答错了」。**

| 说法 | 之前 | 现在 |
| --- | --- | --- |
| `下下周五` | 11-13（**早了一周**，正则先匹配上里面的 `下周五`） | 11-20 |
| `下个月五号` | 12-01~12-31（**塌成整月**，`下个月` 那条先命中） | 12-05 |
| `周天` / `周日` / `星期天` | **不认**（只认带 `这`/`下` 前缀的） | 最近的那个周日 |

最后一行最典型：错的日子本身是个正常日子，模型拿它回话也通顺，只有用户自己知道不对。

**现在认得的说法**（`parseDue` 按「具体先说、模糊后判」的顺序试）：

| 类别 | 说法 | 精度 |
| --- | --- | --- |
| 绝对日期 | `2026-11-09` / `2026/11/9` / `2026年11月9日` / `11月9号` / `十二月二十号` | `day` |
| 明天类 | `明天` `明日` `明晚` `明早` `后天` `大后天` `今天` `今晚` | `day` |
| 周内 | `下周五` `这周五` `周五` `周天` `周日` `星期天` | `day` |
| 周末 | `这周末` `下周末` `下下周末` → 周六到周日 | `day`（两天） |
| 跨周 | `下周` `下下周` `这周` | `week` |
| 月内指定日 | `下个月五号` `下个月5号` `这个月20号` | `day` |
| 整月 | `下个月` `下下个月` `这个月` `月底` | `month` |
| 倒数 | `三天后` `两周后` `三个月后` `三天内` | `day` / `fuzzy` |
| 模糊 | `过几天`（2–10 天）`过几周`（7–28 天）`过几个月`（30–120 天） | `fuzzy`，渲染带「约」 |

**过去的日子不记，而且必须是「不记」，不能是「记成一个过去的期限」。** `昨天` `前天` `上周五` `上周末`，以及说出口时已经过去的绝对日期（`10月15号` 在 11 月说），一律不算期限。理由不是洁癖：`expires_at` 落在过去，那条事实写进去的瞬间就渲染成「已到期」，`kind=plan` 的还会从出生就被算进逾期——而「前天我把车卖了」本来就没有期限这回事。

这个改动顺带揪出一个更坏的旧行为：绝对日期落在过去时会被**自动推到明年**，好让「12 月说 1 月 5 号」成立。但 `10月15号` 在 11 月说也被推了，凭空造出一个 11 个月后的期限。现在只有「往回差大半年」才推（年终那一种），近处的过去就留在过去，由上面那条守卫丢掉。

**习惯也不记。** `每周一` `每天七点` `每月5号`——它们不是一次性的期限，记成某一天就等于让这个习惯从那天起天天逾期。

**换时区不管。** 时区只在写入时定一次（会话的 IANA 区），之后不改、不推断、不跟随系统漂移。用户真换了地方，让他自己跟模型说一声去改配置——悄悄替他改，改错的方向是不可知的，而错的日期没人看得出来。

**顺带把一份手写清单删掉。** 无模型时的兜底抽取靠 `hasTemporal()` 判断一句话里有没有时间，那是第二份手写的关键词表；`parseDue` 学会 `下个月五号`，它不知道。「能不能认」和「认成什么」现在问的是同一个函数，只有「习惯不算期限」这一条留在外面。

`probe-due.mjs` 从 50 项断言扩到 95 项，其中 20 项是过去时与习惯的「不该记」。

### v0.2.20：时间记成区间，改时间先问一句

以前期限是一个点：`expires_at`。这个形状能回答「什么时候到期」，回答不了「他到底说的是哪个范围」——而后者才是模型回话时真正要用的东西。

**「下周」和「下周一」不是同一件事。** 现在两者都存成区间：`due_from` 到 `expires_at`。消息里说「下周我要搬家」，存的是一整周（周一到周日）；说「下周一交材料」，存的是那一天。块里分别渲染成 `[11-09~11-15 · 截止]` 和 `[11-09 · 截止]`。把一周压成一天，后果是第二天就把它标成「已到期」。

**模糊的存成范围，语焉不详的不存。**

| 说法 | 存成 | 精度 |
| --- | --- | --- |
| 下周一 / 明天 / 三天后 / 11月9日 / 十二月二十号 | 那一天 | `day` |
| 下周 / 这周 | 周一到周日 | `week` |
| 下个月 / 月底 | 这个月余下的日子 | `month` |
| 过几天 | 2–10 天，渲染时带「约」 | `fuzzy` |
| 三天内 | 今天到这个期限 | `fuzzy` |
| 过段时间 / 以后 / 改天 / 早晚 | **不记** | — |

「过几天」写 2–10 天是刻意的：记成某一天是编造，记成 `null` 又丢掉了用户确实说过的东西。带上「约」，读的人知道该怀疑。

**换算是代码做的，不是模型做的。** 提示词只要求模型把时间短语**原样抄下来**（`ttl`），一个字都不许改。让模型把「下周三」换算成日期，等于让它在脑子里做日历减法，静默算错是默认结果，而错的是一个日期，事后没有任何东西能提示它错过。

**改时间先问。** 如果一句话给出的新期限和库里已有的不同，不直接覆盖，而是记成「待确认」，块里那行变成：

```
- [11-09~11-15 · 截止] 用户打算下周去看房子（时间待确认：说细到 11-02，原记 11-09~11-15；memory_settle(id=12)）
```

模型看到就开口问，用户答完再调 `memory_settle(id, accept)`。`accept=false` 是正经结果——把提案丢掉、保留原期限，下次不再问。做成 no-op 的话，同一个问题会一直问到用户投降。

「说细到」和「改到」是两种措辞，因为新时间落在旧范围里边和外边不是一回事，虽然都要问。

**顺带修掉一个一直存在的时区错位。** 日期在写入时算一次、渲染时又算一次，两次用的时区不同（写入走 UTC，渲染走本机时区）。过去这只让日期偏移 8 小时，看不出来；区间一来，单日就渲染成两天，立刻现形。现在两条路走同一个 `timezoneOf(sessionId)`。

新增第 13 个工具 `memory_settle`。`memory_doctor` 多一行「时间」：几条有期限、几条是区间、几条待确认、几条只记了原话没算出日期。

### v0.2.19：计划、偏好、矛盾，各自回到该在的位置

三件事看着无关，其实是同一个错误：**用相关性去管本来不该靠相关性的东西**。

- **偏好**：用户不会重复说，所以 query 里永远没有它
- **计划**：用户不会再去问自己说过要做的事
- **矛盾**：两条事实打架，但当前这句话只涉及其中一条

**计划有了独立通道。** `kind=plan` 一直在，但从没被单独捞出来过——它混在事实里按分数排队，而计划天生分数低（没有 query 会命中它）。现在 `recall()` 里单开一条：`openPlans` 取未到期的按截止日排，`overduePlans` 取过了截止日还没被取代的。

**过期的计划不等于作废。** 老代码里 TTL 到期就是 `expired_at`，分数往下掉，等于「忘了」。但一个计划过了日子，只说明那个日子过去了，我们并不知道结果。所以过期的计划不删也不藏，标一行「已到期，之后没再提」——不是「你没做到」，是「我们没再聊过」，让模型自己去问。

**偏好区的丢失，根因不在渲染。** `recall()` 里 `selected` 把事实、事件和主观项一起按分数切片到 `maxItems`（默认 20）。一屋子 20 条高分事实，偏好全部出局——不是渲染时被截掉，是根本没到渲染那一步。而偏好的分数结构注定它排不高（`0.55 × 衰减 ≈ 0.45`），事实一旦归一到 1.0 就永远压过它。所以改了两层：主观项不参与排序，事实/事件单独切片；渲染层再把偏好和计划前置、各给保底预算。**两层缺一不可**——只改渲染，行早就没了；只改 recall，偏好仍排在 20 条事实后面。

**矛盾：标记，不裁决。** 整合时模型判 `contradicts` 是唯一能抓住「换个说法」的路径，但它有个不报错的失效模式：模型没看出来，两条都是 `active`，块里并列呈现，模型挑先读到的那条。补一个机械兜底——同 kind、二字组 Jaccard ≥ 0.45 且 < 1.0、数字不同或否定极性不同 → 旧的标 `disputed`，分数乘 `conflictPenalty`，块里标「可能已过时」。只标不删，每次最多 3 对。`memory_doctor` 会报「N 条计划（M 条已到期） · X/Y 条待确认」。

**称谓进别名。** 提示词加一条：事实提到人时，把这个人的所有称呼都写进别名。「我妈」「母亲」「李慧」是同一个人——embedding 对专名和称谓的关联也一样含糊，而别名是显式枚举，这一格反而占优。

新增配置 `retrieval.maxPlans`（默认 3，`0` 关掉计划区）。

### v0.2.18：让模型在**写**的时候，先把用户会用的说法写进去

0.2.17 松开了「每个二字组都得命中」，救回的是「字面有一半重合」的那一类。剩下的漏是字面**完全不重合**：

```
存下  用户辞职后一直没跟家里说，怕父母担心
用户  我没敢告诉爸妈                      ← 零个共同二字组，0.2.17 也救不了
```

直觉的修法是「查的时候让模型自己想关键词」。这条路走不通，原因不在效果而在时序：记忆块是在组装 prompt 时算出来的（`text: () => string`，同步），而**任何一次模型调用都排在组装之后**。让模型想词去查，最早也只能是「这一轮先查错，下一轮再查对」。

所以方向反过来：**查的时候不做，写的时候做**。整合那一步模型本来就在读这段对话、产出标题和摘要，顺手多要一个字段——用户下次可能用哪几个说法来找它。

1. **整合提示词多要 `aliases`。** 每条事实 2–3 个口语说法，每段经历 2–3 个「这件事」的别的叫法。提示词里明确写：口语一点、允许换说法、带上具体对象名、每个 ≤6 字，**不要**写「工作」「心情」这类泛词，也不要照抄原句。
2. **别名混进已有的 `tokens` 列，不加 FTS 列。** `facts_fts` 是 external-content 表，加一列就要 DROP/重建并重刷全库；而 `tokens` 本来就是「把原文切成二字组」的索引列，把别名切进去即可，权重、触发器、查询表达式一个都不用动。查询端**一个字都没改**。
3. **放宽那一步的守卫，把别名算进「这一行能被哪些词找到」。** 这是整件事的关键。改动前（严格 AND 加别名）实测 0/6：严格匹配要求这句话的**每个**二字组都出现，三个短别名盖不住一句人话。守卫从 `containment(query, text)` 改成 `containment(query, text + aliases)` 之后，同一批题变成 6/6。
4. **别名要清洗，不能照收。** 只收 2–3 个、单个 ≤6 字（拉丁 ≤12）、去掉泛词与纯数字、去重、过一遍密钥检测。泛词是这里唯一的真风险：一个「工作」别名会把这条记忆变成所有无关对话的磁铁。光秃秃的问句壳（「什么时候」「怎么样」）和泛词同类，一起挡掉。
5. **`memory_write` 也能带 `aliases`。** 用户说「记住这个」的那条路，同样值得带上别的说法。
6. **`memory_doctor` 报别名覆盖率**（`检索别名 12/30 条带别名`）。旧库不会自动回填——别名是在写入那一刻产生的，这一点必须看得见，而不是假装功能已经生效。
7. **配置 `consolidation.aliasCount`**：默认 3，`0` 关掉（提示词不再出现该字段）。

**代价与边界，一并写清：**

- **词表还是模型写的，它想不出第四种说法。** 探针里「没人教过的问法」6 条全漏（0/6）。别名把「零重合」变成「有重合」，没有变成语义检索。
- **只对写的时候在场的信息有效。** 老库里的记忆要重新整合一次才会有别名，`memory_doctor` 会如实报出这个缺口。
- **prompt 的常驻开销不变。** 别名只进索引，不进记忆块；一轮 2300 token 的常驻预算没有变化。
- **换话题不渗漏。** 实测 8 个无关问题（含两个刻意带泛词的）在三条臂下都是 0 泄漏、块大小一致（8 条）。换话题时块里仍然是「最近 8 条事实」——那是冷启动兜底，与别名无关，也不是这一版引入的。

**后来补的一次：别名要的是「他会怎么问」，不是「换个叫法」。** 原提示词说「用户下次可能拿来检索它的说法」，模型照字面理解成了同义替换——在真实库里数了 11 条别名，**含疑问词的是 0 条**，全是「健康检查」式的另一个名字。而同义替换恰恰是最没用的那种：「体检」的另一半用户在检索时本来就会想到，他想不起的才是「身体怎么样」。提示词改成点名要问法，并给出正反例（`身体怎么样` 对，`健康检查` 错）；同时把「什么时候」「怎么样」这类只剩疑问词的壳加进泛词表——它们挂在一条事实上，会让这条记忆对每个问题都算命中。

新增两支探针。`probe-aliases`（6 条记忆 × 3 种问法 × 3 条臂 + 8 个换话题 + 清洗）：A 无别名 / B 别名+放宽 / C 别名+严格。C 是必须的——没有它，B 的胜利会被误记成「别名让 AND 变容易」，而真正起作用的是第 3 条的守卫改动。实测：

| 问法 | A 无别名 | B 别名+放宽 | C 别名+仅严格 |
| --- | --- | --- | --- |
| 别名原文（短问） | 1/6 | 6/6 | 6/6 |
| 换说法（别名覆盖） | 0/6 | 6/6 | 0/6 |
| 第四种说法（没覆盖） | 0/6 | 0/6 | 0/6 |

`probe-alias-prompt` 当时 13 项，走假 `llm` 服务，验证提示词确实要了 `aliases`、`aliasCount=0` 时提示词干净且别名不生效、脏别名被丢弃、`memory_doctor` 报覆盖率（改成问法后扩到 17 项，加了四项：提示词点名要问法、正反例对照、问句壳被挡、带对象的问法留得住）。

**顺带修掉一个真 bug。** `toEngineConfig` 是一份**显式字段白名单**，`aliasCount` 没写进去，于是传到引擎是 `undefined`，`extractPrompt` 的默认参数把 `0` 补上——提示词里悄悄没有这个字段，而配置项看起来「生效了」。探针第一版就是在这里假绿的：假模型照样返回了别名，因为假模型不看提示词。这类「白名单漏一个字段」的错不会报错，只会让开关失效。

### v0.2.17：把「每个二字组都得命中」这条松掉

起因是有人做了一份记忆插件测评，结论是**没有一家打赢最朴素的 qwen 向量检索加重排**。这个结论在「检索」这一项上成立，而且原因很具体：

`compileMatch` 把用户这句话切成中日韩二字组，用空格连起来喂给 FTS5——在 FTS5 里那是**隐式 AND**。「你还记得我不吃香菜这件事吗」切出 11 个二字组（`你还 还记 记得 得我 我不 不吃 吃香 香菜 菜这 这件 件事`），记忆原文里命中 4 个就足够人读懂整句，但 FTS 要求 11 个全部出现，于是判定不命中，**那条记忆整条消失，而且不报错**。0.2.15 抓到过一次同类问题（偏好整块变空），当时的修法是给偏好加常驻 + OR，事实和事件没动。

这一版补上第二遍：

1. **严格匹配太瘦时，用 OR 再查一次。** 门槛是 `retrieval.relaxBelow`（默认 3）：严格命中少于 3 条才跑第二遍。长句子用 OR 会把库里大部分条目拖进来，只在第一遍明显不够时才用。
2. **放宽命中永远排在严格命中后面。** bm25 归一后乘 `retrieval.relaxPenalty`（默认 0.55），结构上不可能反超。
3. **共享太少的不算记忆。** 候选必须与查询共享至少 `retrieval.relaxMinOverlap`（默认 25%）的二字组。没有这道守卫，一个「的」就能匹配全库。实测反例：`买菜时香菜便宜，不吃也行` 与那句问话只共享 2/11 个二字组（18%），被挡掉；同一句里的主记忆共享 4/11（36%），保留。
4. **`memory_search` 走同一条路。** 模型自己检索时用的是 `searchFor`，它此前也是严格 AND——用户问「你还记得…吗」，模型查出来是「没有找到相关记忆」。两处现在共用同一套放宽规则与守卫。
5. **事件层更保守：严格命中为 0 才放宽。** 每个事件块在 prompt 里占一整行，错一块比少一块更贵。放宽在「最近 3 条兜底」之前跑，兜底只在放宽也没结果时才用。
6. **配置四个开关**：`relaxMatch`（总闸）、`relaxBelow`、`relaxPenalty`、`relaxMinOverlap`。`relaxMatch: false` 完全回到旧行为。

**说清边界：这不是向量召回。** 它修的是「字面上有一半重合，但被 AND 判死」这一类失败——这是日常对话里最常见的一类。字面完全不重合的近义表达（「香菜」对「芫荽」、换语言、口语改写）仍然找不回来，那需要的确实是 embedding。这一版没有引入任何模型依赖、网络请求或额外进程，索引仍然是本地 SQLite。

新增探针 `probe-recall-relax`（12 项）：严格命中照常、严格命中排在放宽命中之前、用自己的话问能找回、共享过少的候选被挡住、无关问题不凑数、关掉开关后重新找不到（对照）、调高守卫后找不到、事件层放宽命中、事件层无关不命中、**prompt 路径里该事实出现**、**关掉之后同一轮记忆块里没有它**（这一对是关键：证明差异来自改动，不是「最近 8 条」兜底碰巧捞到）。

### v0.2.16：让每段经历自己认得出来

这一版只回答一个问题：插件要不要建「项目」维度。答案是不要——它从不读工作目录，也无从知道两段对话属于同一个仓库。但它本来就有「一段一块」的事件块，块上带标题和摘要；缺的不是维度，是块的**可辨识度**和**可枚举**。

1. **标题不再写「领域·原句」。** 实测库里四块有三块长这样：`技术·插件我更新了，你去更新一下`、`财务·那么，装了这个插件，需不需要考虑上下文崩…`。领域前缀在同一批块上完全一样（而且 `domain` 本身会判错：一段讲插件和上下文的对话被判成 `财务`），第一句又常以语气词开头。现在去掉前缀、去掉「那么 / 但是 / 也就是说」这类开头，保留**第一句**而不是最长句——按长度取会丢主题词，实测把含「辞职」的标题换成了不含「辞职」的长句，`scenario-merged` 立刻抓到搜索退化。
2. **摘要兜底改成「首句 + 最长句」。** 此前降级路径只取最长两句，一段题外话就能把主题句挤出去。
3. **提示词要求标题带对象名。** 「≤12 字」改成「≤16 字」，并写明：写清在做什么、涉及哪个具体对象（项目名 / 工具名 / 作品名 / 人名 / 地点），不要只写领域词，也不要照抄第一句。标题上限从 24 字符放宽到 32，够放一个项目名。
4. **新增第 12 个工具 `memory_episodes`。** 「项目树让 AI 或用户自己搭」的前提是块能**被枚举**；`memory_search` 只有在你已经说出关键词时才找得到，而那正是你已经不需要索引的时候。这个工具按时间倒序列出块（时间 / 类型 / `E` 编号 / 关联事实数 / 标题 / 摘要），可按关键词和天数过滤，每行的 `E` 编号能直接交给 `memory_expand`。跨会话可见——换个会话，上个会话的块还在同一份清单里。
5. **清单不把同一句说两遍。** 规则路径下标题就是摘要的第一句，直接渲染成 `标题 —— 摘要` 会重复。现在两者公共前缀超过 12 字时只印标题。

**这一版仍然不建项目维度，也不替谁生成项目树**：它只保证每块看得出讲的是哪件事、并且列得出来。归拢这件事留给模型和用户。

新增探针 `probe-episodes`（18 项）：空库不抛错、时间倒序、无领域前缀、两块各自带自己的对象名、标题不被摘要重复、`query` 只命中相关块、`days` 过滤、`limit`、跨会话合并、只读不改记忆块。

另一支 `probe-model-title`（16 项）补的是上一段没覆盖的部分：前面所有探针都不带 `llm`，改的却是模型提示词，那条链一行都没跑过。它给 harness 一个假 `llm` 服务，走完 `extractWithModel → bridge → 解析 → 落库`，验证标题/摘要/事实确实按模型回包写入、空标题退化成句子、非 JSON 与流抛错都退回规则且对话不中断。

块粒度也实测了：五轮同一项目、一次整合，得到 3 块（前 3 轮合并，后两轮各一块），单条消息内部不切。碎是真的，来源是段内 `drift`（`microTopicJaccard=0.3`）；这一版**不调**——块小对「按块认领项目」是加分，调大反而让一块混进多个话题、标题重回含糊。

### v0.2.15：修好三个「以为有、其实没有」

这一版全部来自对照外部记忆架构文章的自查，以及写探针时撞见的真实缺陷。核心是三条：**偏好会消失、日记会被挤掉、快照靠自觉**。

1. **长期偏好改为常驻（最重要）。** 此前一条偏好只有一种召回路径：`preferences_fts MATCH`，而 match 是把用户这句话的每个中日韩二字组用空格连起来——在 FTS5 里是隐式 AND。「记得我不吃香菜吗」被拆成 `记得 得我 我不 不吃 吃香 香菜 菜吗`，要求七个词全部出现在偏好文本里，实际一个都命中不了，**整块记忆变成空串**。现在最近 `retrieval.residentPreferences`（默认 3）条偏好每轮都带，另外用 OR 匹配补命中（`compileLooseMatch`），bm25 仍把命中更多的排前面。设为 0 即回到旧行为。
2. **主观层预算修正。** `appendSection` 比较的是全局 `used`，但调用方传进去的是「块内配额」的数值（`target × subjectiveShare`）。事实区一旦超过这个绝对值，印象和日记就整块消失，配置里还写着启用，且没有任何报错。改为传绝对位置，并给日记留 `retrieval.diaryShare`（默认 40%）的保底，避免长印象把日记挤空。
3. **每日滚动快照。** 用 `VACUUM INTO` 生成自包含副本（不需要另拷 `-wal`），默认每 24 小时一次、滚动保留 7 份、放在库同级 `backups/`；库还空的时候不拍。给出配置 `backup.enabled` / `everyHours` / `keep` / `dir`。**它挡「误删和写坏」，不挡「硬盘坏了」**，异地备份仍是用户责任。
4. **事实标注来源。** `facts` 表一直有 `source` 与 `confidence`，渲染时却没用上，于是用户亲口说的和整合时推断的看起来一样权威。现在低置信度（`retrieval.unconfirmedBelow`，默认 0.6）且非手动写入的条目后缀 `（待确认）`，协议里也解释了它的含义。
5. **新增第 11 个工具 `memory_handoff`。** 五格交接卡：我是谁（身份 / 语气 / 价值观）、我们的关系、不能破的规矩、未完成、下一步。全部**原文引用**，不改人设也不写记忆；「下一步」刻意留空——自动生成的下一步会和自动摘要一起被压掉，那正是要防的事。
6. **补压缩豁免探针。** `compaction/start` 一直只做 WAL checkpoint，文档也一直声称「压缩不影响记忆」，但从没有断言。`probe-compaction.mjs` 在压缩前后各取一次三块 prompt，逐条比对。

新增探针：`probe-preference-resident`（7 项）、`probe-diary-budget`（5 项）、`probe-backup`（8 项）、`probe-fact-source`（6 项）、`probe-handoff`（14 项）、`probe-compaction`（12 项）。

### v0.2.14：失忆不再无声，并给模型一个自检工具

v0.2.13 把 prompt 求值失败降级成空块，对话能继续了，但**没人知道它在失忆**——模型照常回答，用户看不出差别。这一版补两件事：

1. **连续失败 3 次后，记忆块吐一句状态行。** 三块里只有记忆块每轮必被求值，所以由它带这句话：`【记忆状态】记忆读取已连续失败 3 次（memory），本轮的记忆内容缺失或不完整（…）。请如实说明记忆暂时读不出来，不要凭印象编造；需要排查时可调用 memory_doctor，不必每轮都调。` 任一 label 成功即清零，库恢复后这句自动消失；前两次失败仍保持静默，避免偶发重试刷屏。代价是降级期间每轮多约 90 token——只在坏掉时才有。
2. **新增第 10 个工具 `memory_doctor`。** 只读、逐项体检：库连接、库文件大小与修改时间、WAL、`journal_mode`/`synchronous`、`quick_check`、六张表行数、最近一次 `recall` 的时间、prompt 三块的连续失败。每项独立 try/catch——库彻底打不开时它报的是「✗ 库连接」加下一步建议，而不是再抛一次异常。它**只诊断不修**。

另外补一处终检发现的疏漏：`agent/disposed` 里现在也会清掉这张 per-session 的健康登记表，避免会话越开越多时它只增不减。

实测（`loom-e2e/probe-degrade-notice.mjs`）：健康时不出状态行；断库后第 1、2 次为空块，第 3 次出现状态行且只出现一次（人设与索引块仍为空）；同一状态下 `memory_doctor` 不抛错，报出 `✗ 库连接 database is not open`，并给出「先确认有没有第二个 DSH 实例占着它」。

### v0.2.13：prompt 块求值失败不再打断整轮对话

来源是装了这个插件的 DSH 自己做的代码审查：它指出 `recallFor()` 外面没有 try/catch，而宿主可能不兜底。顺着这条查下去，比它说的更糟一点——宿主确实不兜底，而且会抛的不止一块。

**宿主侧的事实**（读的是本机 `D:\dsh\resources\app.asar` 里的实际实现）：

| 位置 | 事实 |
| --- | --- |
| `@deepseek-ai/dsh-system-prompt` `assemble()` | 直接调 `section.text(context)` 与 `resolveContext(entry, context)`，**全文件没有 try/catch** |
| 同文件 `required: true` | 只用于「运行期上下文被抑制时不要丢」，**与异常无关** |
| `@deepseek-ai/dsh-agent-loop` `preStep()` | `await this.loopCtx.systemPrompt.assemble(...)` 直接调用 |
| 同文件 `turn()` | 外层 catch 把异常折成 `turn/end: { reason: { kind: "error" } }` 后 rethrow |

所以库被删、损坏、磁盘满、连接被占时：本轮以 error 结束，**下一轮组装再抛一次**——不是崩溃，是每一轮都失败，直到库恢复。会抛的有三块（persona / hooks / memory），前面两块此前没人注意。

**修法**：`guardPrompt(label, fn)` 统一包住三块，失败返回 `""`，同一 label 60 秒内只告警一次。空块会被宿主过滤（`renderPrompt` 与 `renderContextSections` 都是 `filter(text.length > 0)`），不会留下空标题或空段落——这一轮没有记忆，但对话继续。

新增 `loom-e2e/probe-prompt-guard.mjs` 固定这条：关闭引擎（等效于库不可用）后三块都必须返回空串。修复前 3/3 抛错，修复后 3/3 降级为空块。

### v0.2.12：更正「必须重启」，并补上热加载漏挂的三块

**文档部分**：更正一个流传了几版的错误说法。

前面几版一直写着「装完重启 DSH，不重启不会出现」。这句话是**照着旧版宿主的行为写的，没有实测**。在真机上装一次就把这个说法证伪了：

| 事实 | 时间戳 |
| --- | --- |
| 宿主主进程启动 | 19:58:15 |
| `dsh plugin add` 跑完（profile 的 `package.json` 被 pnpm 改写） | 20:05:09 |
| `loom.db` 被创建（= 插件的 `apply()` 执行） | 20:05:11 |

宿主进程从头到尾没重启过（所有 `DeepSeek Harness` 主进程的 `StartTime` 都是 19:58:15），会话 id 也没变。所以建库的是那个 6 分钟前就启动的老进程。

1. **§2 安装章节更正为「装上就生效，通常不用重启」。** 写清 DSH 的机制叫即时重组（live reconcile）：装完 → 追进 bundle 列表 → 读 `cordis.patch.yml` → 调 `apply()` → 把新工具 schema 推给正在运行的会话（表现为一条 `### Updated Tool Schemas` 注入）。重启只作为「迟迟不出现」时的兜底手段。原来的写法把门槛写高了。
2. **「新开一个会话才看得到工具」也一并改掉。** 实测当前会话当场就被刷新了，不必新开。
3. **补一句区分**：热加载只管挂载工具，记忆要等**整合**（2 万 token 或空闲 5 分钟）才开始积累。否则刚装完问「你记得什么」得到空答案，会被误当成没装上。

> **补充（v0.2.23 发布后，2026-11-02）：上面这条结论只对「首次安装」成立，当时把它推广到「升级」是错的。**
>
> 那次实测是往一个**还没有这个插件**的 profile 里装，宿主看到 bundle 列表多了一项，于是重组。升级是「同一个 bundle 换内容」，列表长短没变，不会触发重组——装到 0.2.23，实际跑的还是 0.2.12（工具 9 个、`memory_doctor` unknown、`user_version` 1），三条证据齐全。
>
> 所以正确的说法是：**首次安装不用重启，升级必须重启。** 现在 `memory_doctor` 第一行会打印 `运行 <版本> · 库 schema v<版本>`，让「装的是哪版 / 跑的是哪版」不再需要靠数工具反推。
4. **`incompatible-version` 那段改准。** 之前还写着「声明已放宽到 `>=0.2.1-rc.2 <2`」，那是 v0.2.10 的说法；v0.2.11 已经改成 `engines.dsh: ">=0.2.1-rc.2 <0.3.0"` 并收窄了 peer。现在按实际声明写，并说明预检读到 `engines.dsh` 就会短路，所以报错只有一项。

**代码部分**：顺着「装完即生效」这个事实往下查，发现热加载漏了一半。

`apply()` 把三块按会话注册的内容（人设卡、钩子索引块、记忆块）挂在 `agent/created` 事件上。但热加载时**那个会话的 agent 早就创建好了**——事件不会再触发，于是这三块一块都挂不上。而当时实测确认「9 个工具」和「两个 prompt 块」都在，恰恰因为那两样是**全局**的：工具走 `ctx.tools.register`，两个协议块走 `ctx.systemPrompt.section`（不按会话）。

结果就是：装完插件，工具能调，但当前会话的系统提示里没有记忆块——模型得先想到去搜，才知道有记忆。用探针固定了这个差异（`loom-e2e/probe-hotload.mjs`，模拟「agent 先存在、插件后组合」）：

```
修复前：protocol ✓  index-protocol ✓  persona ✗  hooks ✗  memory ✗  工具 ✓
修复后：protocol ✓  index-protocol ✓  persona ✓  hooks ✓  memory ✓  工具 ✓
```

5. **`apply()` 时补挂已存在的会话**：从宿主的 `agents` 服务（`ctx.get("agents", false)`，`AgentRegistry.list()`）取当前所有 live agent，逐个 `attachAgent`。`attachAgent` 本身有幂等保护（`agentDisposers.has(sessionId)` 直接返回），不会重复挂。
6. **`turn-stopping` 兜底**：万一宿主不暴露 `agents` 服务（或 `list()` 不可用），就在每轮结束时补一次——下一轮生效，总比永远不生效好。
7. **卸载时清理按会话的 section**：新增 `ctx.effect("memory-loom:agents")`，插件被卸载（含热重组）时把 `agentDisposers` 里的全部撤掉。否则反复重组会在同一个 agent 上叠同名 section。

这三条都只在「插件中途装载」这个场景下起作用，正常启动路径的行为一个字节没变。

### v0.2.7：逐行审计修掉的四个真 bug

不带新功能，只修「文档说做到、代码其实没做」的地方：

1. **`consolidation.enabled: false` 之前完全无效。** schema 里有这个开关、README 也在宣传，但全文件没有任何地方读取它——关掉之后照样整合、照样调模型。现在 `tick()` 会整个跳过整合阶段（`maintain`、`T` 尾巴、钩子索引都不受影响），并且把 `enabled` 转发进引擎配置。要省 API 额度，这是正确的开关。
2. **分页会把 emoji 劈成两半。** `sliceByTokens` 按 UTF-16 码元切，正好落在代理对中间时，模型收到的是半个字符（渲染成 `�`），下一页开头又是一个孤立的低代理。现在 `safeCut()` 会把切点退到代理对边界外。实测 9 页里 0 页出现孤立代理。
3. **`memory_pack` 能挂到不存在的编号上。** 传 `ref="E9999"` 时，回执说「已挂到 E9999」，但这个编号根本不存在——之后 `memory_expand` 只会告诉你"已被删除"，这份正文永远取不回来。现在先校验编号是否真的存在，不存在就不建链接、并如实说明；正文仍然作为独立 `D` 条目可取。

4. **路径里有空格或中文时 `npm test` 直接崩。** `test/selftest.mjs` 用 `new URL(...).pathname` 取路径，这个值在 Windows 上带前导斜杠、而且是**百分号编码**的——目录名一旦有空格或汉字，读到的是 `tmp%20%E5%88%AB...`，`readFileSync` 直接 ENOENT。这是"别人的电脑"上最常见的失败：很多人的用户名或项目目录就是中文。现已全部换成 `fileURLToPath`（`test/selftest.mjs` 与两个探针各一处）。

另外三处小修：`sliceByTokens` 传负 offset 时 `done` 算错（返回 `done:false` 却已经给了全文，导出的 API，工具层自己夹紧了所以没暴露）；`memory_expand` 的工具描述把「4000 token」写死，改了 `expandBudgetTokens` 后文案会失真，现在按实际配置生成；`migrate()` 的两个分支代码完全相同（死代码），合并成一条并且只向前打版本号。

还有一处**为别人的电脑**加的容错：`PRAGMA journal_mode = WAL` 在网络盘、部分 FUSE 挂载和部分企业漫游家目录上会抛错，原来这一抛就整个 profile 起不来。现在降级到 `DELETE` 日志模式继续跑——慢一点，但能活。

### v0.2.4：`memory_search` 返回可直接使用的编号

旧版返回 `(#1234)`，但 `memory_expand` 要的是 `E1234` / `F1234`。而 `events.id` 与 `facts.id` 是两张表各自自增，**同一个数字可能既是 E12 又是 F12**——模型得先看行里的 `· event ·` 再映射前缀，撞号时会取错表。

现在直接返回 `#E12` / `#F7`，可原样喂给 `memory_expand`。这是「钩子看不见、靠检索找回」那条通道的最后一公里：FTS5 命中的老事件不必再猜编号前缀。

顺带实测了上限这一层（`docs/design.md` §9.6 已更新）：

| 项 | 数字 | 结论 |
|---|---|---|
| 取回成本 vs 钩子数 | 0.040 ms（16 条）/ 0.037 ms（64 条） | 解耦，扩上限不会让每次回看变贵 |
| 索引块每轮 | 16 条 124 token；64 条 422 token | 只有这项随上限线性涨 |
| rebuild（封顶 300） | 恒定 ~118 ms | 保护有效 |
| rebuild（不封顶，3000 事件） | 1248 ms 同步阻塞 | 扩候选池的真实代价 |

**结论：不扩 `maxHooks`、不扩候选池。** 前者的成本落在每一轮，后者会阻塞事件循环，而收益都被「只有 16 条能进 prompt」这条上限吃掉。

### v0.2.3：单页预算 2600 → 4000

5 万字正文在四档预算下的实测（累积输入 = 分页重发后的总 token 消耗）：

| 正文 | 2600 | 4000（默认） | 8000 | 12000 |
|---|---|---|---|---|
| 中文叙事 5 万字 | 12 页 / 24s / 189.6k | **8 页 / 16s / 128.3k** | 4 页 / 8s / 71.8k | 3 页 / 6s / 53.8k |
| 英文日志 5 万字 | 5 页 / 10s / 37.3k | **4 页 / 8s / 26.5k** | 2 页 / 4s / 17.1k | 2 页 / 4s / 13.1k |

从 2600 提到 4000，往返次数少三分之一，总消耗降到 68%；再往上收益递减，但单页把上下文占得更满、也更容易挤掉正在用的东西。4000 是拐点。

同版补了 §7 的备份提醒（要备哪些文件、在哪、怎么恢复），并把「48 小时兜底被空闲触发替代」的理由写清（`docs/design.md` §7.2）。

### v0.2.2：分页切片不再浪费预算

`sliceByTokens` 原先用固定 `budget / 0.65` 推算每页字符数（0.65 是中文的 token/字 比率，最坏情况），而收缩循环只能往下调、不能往上补。于是英文日志和代码（约 0.26 token/字）每页只用到预算的 **38%**，页数凭空翻倍。

现在先采样正文前 2000 字，用这段文本自己的比率推算。5 万字英文日志从 **14 页降到 5 页**，中文叙事从 14 页降到 12 页（中文本来就在 0.65 附近，只吃掉了浪费）。

分页成本是平方级的——第 k 页要把前 k−1 页重发一遍，所以「少一页」比「小一页」值钱。本地开销（SQL + 切片）实测 4–18 ms，可以忽略；时间全在往返次数上。

### v0.2.1：取消单条消息长度限制

0.1.x–0.2.0 在捕获层硬编码 `clip(..., 8000)`，超过就静默丢尾巴——贴长日志、贴大段代码时，被截掉的部分连自己都不知道。现在改为：

- **默认整条落库**，没有隐式上限。
- 想要体积可控就设 `l0.maxCharsPerMessage`；截断时会写明原文长度并提示调大配置，不让模型误读半截内容。
- 超长行不再写 `l0.tokens`（该列从无读取方，只是正文的 1.6 倍副本），所以放开上限后库体积只增长约 1.14 倍于正文本身。

实测：单条 5.2 万字写入耗时 79 ms，`memory_expand` 5 页读完。旧库无需迁移。

## 8. 隐私与数据权利

- **按人隔离**：事实、事件、印象、日记、偏好都带 `identity_id`；路人默认不可被跨用户查询，只有 `evidence.public === true` 才放行。
- **主人跨用户查询只有 L1/L2**：拿不到 L0 逐字内容。
- **删除**：`memory_forget` 软删除 → 冷静期 → 硬删；`memory_identity erase` 按角色处理；路人原始对话到期自动清除，事实保留但降权。
- **导出**：`memory_identity export` 给出 JSON；`engine.exportData` 是同一份数据。
- **审计**：每次写入、修改、删除、整合都进 `audit` 表；`traces` 只保留 14 天。
- **插件自己留本地快照**（v0.2.15 起）：默认每 24 小时一次，滚动保留 7 份，落在库文件同级的 `backups/` 下。它解决「误删/写坏」，不解决「硬盘坏了」——同一个盘上的快照跟着一起没。异地备份仍然是用户的责任（Q59），插件不做对象存储，也不上传任何东西。

### 安全事实（可自行复核）

这一节不是承诺，是可以一条命令验证的事实：

| 问题 | 事实 | 怎么自己查 |
| --- | --- | --- |
| 插件是否持有 API Key / Token？ | **没有。** 源码里不存在任何凭据常量 | `grep -nE "api[_-]?key\|secret\|password\|bearer" lib/index.js` → 只命中**脱敏正则**与情绪词表，无凭据值 |
| 是否会外联？ | **不会。** 没有任何 `fetch` / `node:http` / `node:https` / `WebSocket` / 原生 socket 调用 | `grep -nE "fetch\(\|node:http\|node:https\|WebSocket" lib/index.js` → 无输出 |
| 是否有遥测 / 上报？ | **没有。** 不加载任何统计 SDK，全文不含 `http` 字样 | `grep -n "http" lib/index.js` → 无输出 |
| 会写磁盘的哪些位置？ | **只有你配置的那一个 SQLite 文件**（以及 SQLite 自己生成的 `-wal` / `-shm`） | `grep -n "writeFileSync\|mkdirSync" lib/index.js` → 只有建目录那行 |
| LLM 调用走哪里？ | **走 DSH 宿主**（`ctx.get("llm", false)`，宿主没提供就降级为纯规则模式），插件不接触凭据、不代理请求 | `grep -n 'ctx.get("llm"' lib/index.js` |
| 库文件是否加密？ | **不加密。** 是明文 SQLite，任何能读该文件的人都能读全部对话 | 用任意 SQLite 客户端打开 `loom.db` 即可 |
| 落盘前会过滤敏感信息吗？ | **会。** `redactSecrets()` 在写入前把访问密钥、`Bearer xxx`、`password=`/`token:` 这类赋值串、手机号、身份证号、银行卡号替换成 `[redacted ...]` | `grep -n "SECRET_PATTERNS" -A 30 lib/index.js` |

关于脱敏要说清边界：它是**保守的正则匹配**，防的是「你不小心把密钥粘进对话」，不是 DLP 系统。自由叙述格式的敏感信息（比如身份证号中间夹了空格以外的写法、自定义格式的内部编号）不一定拦得住。

两条由此推出的操作建议：

1. **别把 `loom.db` 放进网盘/公开同步目录**，也别提交进任何 git 仓库（`.gitignore` 已拦截 `*.db`）。
2. **威胁模型是「本机文件权限」**，不是「服务端泄露」——因为没有服务端。你要防的是别人拿到这台机器或这个文件。

如果你在别人的分支/PR 里看到 `loom.db`、`.env`、带真实对话的 `.jsonl`，那一定是误提交，不要 merge。

### 备份：插件会自己留 7 份，但只留在同一个盘上

这个插件的全部记忆只有**一个 SQLite 文件**，没有云端副本。v0.2.15 起插件会自己滚动留快照，但那只挡住「手滑删了」「写到一半断电」，挡不住「硬盘坏了」「这台机器没了」。

**插件自己做的部分**（v0.2.15）

| 项 | 默认 | 配置 |
| --- | --- | --- |
| 是否快照 | 开 | `backup.enabled` |
| 间隔 | 24 小时 | `backup.everyHours`（1–720） |
| 保留份数 | 7 | `backup.keep`（1–60） |
| 位置 | 库文件同级的 `backups/` | `backup.dir`（相对库目录，或绝对路径） |

快照用 SQLite 的 `VACUUM INTO` 生成，所以**单个文件就是完整副本**，不需要再拷 `-wal`；文件名形如 `loom-2026-11-01-1045.db`，按时间排序自动清理旧的。库还是空的时候不拍（省得占满名额）。

**你自己要做的部分**：把某一份拷到**另一块盘或另一台机器**。这一步插件替不了你。

**要备份什么**

| 文件 | 是否必需 | 说明 |
| --- | --- | --- |
| `loom.db` | ✅ 必需 | 全部记忆：原始对话、事实、事件、自我叙事、索引与整理版正文 |
| `loom.db-wal` | ⚠️ 存在就必须一起拷 | 最近尚未合并回主库的写入。只拷 `loom.db` 会丢掉最近这段对话 |
| `loom.db-shm` | 可忽略 | 只是共享内存索引，会自动重建 |
| `diary/` | 可选 | v0.2.9 起的日记 Markdown 镜像。**它是只读导出，不是真相来源**：插件装载时会把最近 14 天重写一遍，更早的日子不会自动回来（库里的条目本身还在）。所以不必单独备份；只有当你把它当成唯一阅读副本时才需要一起拷 |

**在哪**

配置项 `path`，默认由 bundle patch 设为 `dshHomePath('memory', 'loom.db')`，也就是 DSH 主目录下的 `memory/loom.db`：

- Linux / macOS：`~/.dsh/memory/loom.db`
- Windows：`%USERPROFILE%\.dsh\memory\loom.db`
- 若设置了环境变量 `DSH_HOME`，则在其下面同样位置
- 你自定义过 `path`，就按你配置的路径

不确定的话，直接在 DSH 里问：*「memory 插件的 path 配置是什么？」* 或让它调 `memory_identity export` 导出一份 JSON 作旁证。

**怎么备（手动，用于异地）**

最稳的是停掉 DSH 再拷，三个文件一起拷：

```bash
# 停掉 DSH 之后
cp "$DSH_HOME/memory/loom.db"* ~/backup/loom-$(date +%F).db   # 连同 -wal/-shm
```

不停 DSH 也能拷，但要一次拷齐三个文件；或者用 SQLite 的一致性备份，避免拷到半写入状态：

```bash
sqlite3 "$DSH_HOME/memory/loom.db" ".backup '$HOME/backup/loom-$(date +%F).db'"
```

**多久备一次**

看你对「丢最近几天」的容忍度：记忆是持续累积的，越晚备丢得越多。日常每天一次、大改配置或换机器前手动备一次即可。库很小（纯文本，一万轮对话量级在几十 MB），不需要增量方案。

**怎么恢复**

停掉 DSH，把备份文件放回 `path` 指向的位置并命名为 `loom.db`，删掉同目录残留的 `-wal` / `-shm`，再启动。

**注意**

- 备份文件里是**未脱敏的完整对话**（脱敏只作用于写入前的敏感字段替换，不是加密）。别放到公开的同步目录或仓库里。
- `memory_identity erase` 后来删掉的人，其数据在旧备份里仍然存在。备份是时间点快照，删除不会回溯。

## 9. 已知边界

这些是刻意没做、或明知差距但暂时不动的，不是遗漏。逐条的原因、代价与切入点见 [`docs/design.md`](docs/design.md) §13。


| 项                   | 现状                                    | 原因                                   |
| ------------------- | ------------------------------------- | ------------------------------------ |
| 向量 / embedding 检索   | 用 CJK 二元分词 + FTS5 BM25                | 离线、无密钥、中文子串可召回；语义相近但用词不同的情况会漏。**不打算长在主包里**：它会带来模型依赖、网络请求和第二个存储，而这三样都是「装了就生效」的反面。规划是一个可选的子包插件，按需装、关掉后主包行为不变 |
| 相册（Q22）             | 未实现                                   | 图片记忆需要单独的相似度通道与存储，留作扩展点              |
| 对话历史去重（Q45）         | 未做 `in_conversation` 标记               | 记忆块与对话历史由宿主分别管理，重复内容靠模型读上下文消解        |
| 主观层配额的动态下调（Q30/Q31） | 固定 25%                                | 需要跨轮统计命中率；当前每轮独立计算                   |
| 备份                    | 本地滚动快照（v0.2.15）                 | 每 `backup.everyHours` 一次、保留 `backup.keep` 份；异地备份仍是用户责任（Q59） |
| 48 小时整合兜底（Q2）       | 用 5 分钟空闲触发替代                          | 到期判定是「有未整合轮次 + 空闲满 5 分钟」，比 48h 严格更早；两者本来跑在同一个 tick 上，替换不引入新漏点 |
| 单条消息上限              | 默认不限制（`0`），可设 `l0.maxCharsPerMessage` | 0.1.x–0.2.0 曾硬编码 8000 字截断且无提示，现在整条落库 |
| 正文无语义检索             | 只能顺钩子/编号取回；入口是模型自己调 `memory_expand`，找不到时先用 `memory_search` 按关键词定位 | 设计而非缺陷：想起来的是钩子，细节主动去捞。`memory_search` 走 FTS5，不受 16 条钩子限制，所以「不在索引里」不等于「找不回来」 |
| 钩子密度受整合质量约束         | 事件标题仍可能近似重复               | 规则路径自 v0.2.30 起认得出属性/配置句（270 段技术记录实测 2 → 404 条事实），但标题仍取首句，同话题的多段会重名；根治需提升整合层 |

| 别人的记忆（v0.2.26）       | 只搬句子：类型与领域按本插件重判，事件、时间线、人格文件读不进来 | 对方的结构没有可迁移的语义（它的 `category` 不是我们的 `domain`，它的时间线没有 `l0` 证据），硬映射会把「读不懂」变成「记错了」；旧计划也不成其为计划，见 §31 |
| 相对时间词（v0.2.27）       | 补到日期，但只补说得准的 | 「前几天」「上个月」「过段时间」没有确定的那一天，补出来就是编；「后天免疫」「先天与后天」「明天出版社」里的词是名词，不碰。补注只活在渲染层，库里仍是原话，见 §32 |
| 规矩的可检索性（v0.2.28）    | `memory_search` 能搜 `preferences` 了，但仍是词法匹配 | 「我有什么忌口」与「我不吃香菜」不共享任何二字组，照样搜不到；补上的是「有门」，不是「懂意思」。常驻区仍然只带最近 `retrieval.residentPreferences`（默认 3）条，更早的靠搜索或关键词召回，见 §33 |
| 删除不覆盖偏好（v0.2.28 发现） | `memory_identity erase` 清的是对话与事实，`preferences` 的行留着；能逐条收回，不能批量清 | `requestDeletion` 从来没碰过这张表——规矩在实现里一直是只写不删。这次补了单条出口（`memory_forget(ref="P…")`），批量清理要连带改 `erase` 的两条分支和它的回话，留到下一个版本，见 §33.8 |
| 抽取的引用校验（v0.2.29）   | 只记录，不拦截；规矩那一类没有校验位 | 模型如果把「我」改写成「用户」再抄进摘抄，会和真编造一样被判 false，两者在字符串层面分不开。按 false 丢事实会把真事扔掉，而漏记比多记难发现，所以先攒数据；`preferences` 没有 `evidence` 列，v0.2.29 之前写的事实也没有，都不进分母，见 §34 |
| 外部基准上的相对位置（v0.2.30） | 纯词法检索加摘要索引，在「逐版本穷举」类任务上明显弱于全文字 BM25：整句材料齐备 20.5% 对 82.7%，变更链覆盖 73.3% 对 94.1% | 索引粒度是设计选择，不是实现缺陷——一条摘要覆盖一个槽位，一段原文覆盖五到十个。取 6 条时一边拿到 300 字、一边拿到 2,300 字，而这个差距在检索这一步，`memory_expand` 补不回来。为追平把索引换回原文，等于换掉「省 token、按需展开」这个前提，所以不做。接入方式、读数、试过又回退的方案见 §35 |
| 摘要就是「首句 + 最长句」（v0.2.30 查证） | 不是语义摘要，没有主题聚类，也不会挑"最重要"的那句 | 试过改成「优先带具体值」：关键句进摘要 26.6% → 82.6%，检索却从 20.3% 掉到 8.7%。查了抽取式摘要这一支的文献才确认这不是没调好——位置是唯一稳定的信号，长度、TF-IDF、专有名词这类特征会把选择引向长而实体密集的句子，且偏法与语料类型强相关。真正该改的是「摘要不该替代原文」（§36.2 的 RAPTOR collapsed tree），不是把摘要写得更聪明。见 §36.1 |
| 事件层的宽松重跑是二值开关（v0.2.30 发现） | 严格检索命中 1 条就完全不放宽（事实层是 `< 3`），两层刻度还不一致 | 变更类问题恰好是「主体名到处都在、只有版本值不同」，strict 总能蒙对 1–7 条，剩下的版本就永远进不了候选。工业界的做法是 `mm`（minimum should match）这种滑动刻度，不是开关。改它会动排序、牵动几十个探针，留作独立版本，见 §36.3 |

## 10. 目录

本仓库**以构建产物发布**：没有 `src/`，`lib/index.js` 就是完整可运行的插件本体（10835 行，保留可读格式与注释，不是压缩代码）。原 TypeScript 源工程没有随仓库放出，所以这里**没有构建步骤**——改 `lib/index.js` 就是改源码，改完直接跑测试即生效。代价是没有类型检查、也没法用 `tsc` 做重构；收益是任何人 clone 下来就能改、能跑，不需要理解构建链。

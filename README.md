# dsh-memory-loom

给 DeepSeek Harness 的长期记忆插件：把对话沉淀成**四层记忆 + 主观层 + 人设卡**，全部存在一个本地 SQLite 文件里。上下文里只放每条约 15 token 的"钩子"，完整正文留在库里按需取回。

- **L0** 原始对话（只追加、不裁剪、写前脱敏）
- **L1** 原子事实（类型、主题域、TTL、情绪显著度，以及 `(主体, 属性, 值)` 槽位）
- **L2** 事件摘要（按话题与情绪切出来的「一段经历」，带 `l0_from/l0_to` 原文指针）
- **L3** 自我叙事（助手对自己的长期叙述）
- **主观层** 印象、日记、隔离的长期偏好
- **人设卡** 分区、可锁定、用户/助手按来源分权
- **钩子索引** 记忆块的指针版：`- E37 要不要辞职的长谈 2.7k字`，背后是几千字完整叙事，`memory_expand` 按需取回
- **16 个工具** `memory_search` / `memory_write` / `memory_expand` / `memory_index` / `memory_doctor` …

不依赖任何在线服务：中文检索用 CJK 二元分词 + SQLite FTS5，衰减、切分、冲突判断都有确定性规则版本。**没有可用模型时插件照常工作**，只是抽取与判断走规则，L0 仍然完整积累。

## 0. 一页速览

一句话：**它不追求"记住一切"，它追求"在 2,000 token 里放下最该被想起的东西，并且知道剩下的去哪拿"。**

```
                    ┌──────────────────────────── 写入 ────────────────────────────┐
  user/assistant ──► l0（原文，只追加、不裁剪、写前脱敏）
                       │  触发：累计 2 万 token 或空闲 5 分钟
                       ▼
                    切段（时间间隔 30min / 话题偏移 / 情绪尖峰；段内再微切）
                       │
                       ▼
                    抽取（有模型走模型，无模型走规则；两者都带"原文摘抄"校验位）
                       │
                       ▼
              ┌── facts（原子事实，带槽位 subject/attr/value、衰减参数、TTL）
              ├── events（一段经历：标题 + 摘要 + l0_from/l0_to 指针 + 情绪）
              ├── preferences（长期规矩，独立表，独立编号 P）
              └── 主观层（印象 / 日记 / 自我叙事）+ 人设卡

                    ┌──────────────────────────── 读取（每轮） ────────────────────┐
  每轮 prompt ◄── 【记忆索引】钩子清单（快照，约 65 token，正文不进上下文）
              ◄── 【记忆块】偏好 → 计划 → 事实 → 事件 → 印象 → 日记 → 叙事（软 2000 / 硬 3000 token）
                       ▲
                       │ 四路候选：pinned / FTS strict / FTS relax / 槽位(slot)
                       │ 打分：similarity × 双曲衰减 + 情绪 − 层罚，× 时效 × 冲突，下限 0.02
                       │
  模型需要细节 ──► memory_expand(ref) 按 E/F/D/P 编号取回正文，分页不截断
```

**决定这套设计形状的六个数字**

| 数字 | 值 | 它约束了什么 |
|---|---|---|
| 记忆块预算 | 2,000 软 / 3,000 硬 token | 一切"要不要现在给"的取舍都在这个天花板下做 |
| 钩子预算 | 300 token / 16 条 | 索引层能常驻多少指针 |
| 衰减参数 | `d=1`，`S₀=30天`，`S` 上限 50 倍，地板 0.02 | 一条事实多久沉底 |
| 整合触发 | 2 万 token 或 5 分钟空闲 | 记忆的"写入延迟" |
| 检索放宽门槛 | 严格命中 < 3 条才放宽，重叠 ≥ 25% | 召回率与噪音的闸门位置 |
| 事实行数（642 题语料） | 420 → 915（v0.2.32） | 保留变更链的存储代价 |

## 1. 核心定位与总体架构演进

### 1.1 初版原貌：把"记忆"当成一个压缩问题

需要先说明一个考古学事实：**git 仓库始于 v0.2.9**（首个提交 `be02ade` 只有 README、`package.json`、patch 和 LICENSE，没有 `lib/`），更早的 v0.1.x–v0.2.8 没有版本留痕。所以"初版"只能从两处反推：一是 changelog 里被反复提到的旧常量，二是代码里至今还在的休眠结构。

可以确认的早期形态：

- **四层记忆（L0–L3）+ 主观层 + 人设卡**从第一天就是这个骨架，没有被推翻过。这是罕见的稳定性——后面 30 多个版本改的全是**每一层怎么进出**，不是层本身。
- 记忆的消费方式是**"渲染"**：每轮把事实、事件、印象、日记拼成一段文字塞进系统提示（软 2,000 / 硬 3,000 token，这个量级至今没变）。
- L0 曾**有单条长度上限**（v0.2.1 取消）——贴长日志会丢尾巴，那是个明确的失败。同一时期 `memory_expand` 的单页预算从 2,600 提到 4,000（v0.2.3），依据是 5 万字正文的分页实测：往返次数少三分之一、总消耗降到 68%，再往上收益递减。
- 检索从一开始就是 **CJK 二元组 + SQLite FTS5**，没有向量库。这是最初的取舍，不是后来才做的决定。

初版的隐含假设是：**记忆的价值与"被放进上下文的信息量"成正比**。这个假设在 0.2.0 被自己推翻。

### 1.2 三次形态变化

| # | 转折 | 版本 | 触发事件 | 换来的 | 付出的 |
|---|---|---|---|---|---|
| A | **渲染 → 指针** | v0.2.0 钩子索引 | 上下文里塞不下 60 轮之后的经历，且塞进去的都是摘要、细节全丢了 | 常驻成本从"正文"降到"每条约 15 token 的钩子"，任何一段经历都可 `expand` 回溯 | 多一层表、多一个重建定时器、多一组"指针失效"的边界 |
| B | **单遍 AND → 两遍 + 守卫** | v0.2.15 / v0.2.17 | 外部测评指出"没有一家打赢最朴素的向量检索"；自查发现偏好整块会变空 | 整句话提问从"零召回"变成"能召回"，且放宽结果结构上不可能反超严格结果 | 多四个配置项、候选集变大、需要 overlap 闸门防噪音 |
| C | **措辞匹配 → 坐标匹配** | v0.2.32 属性槽位 | 「这个项目的依赖名改过几次」这类问题，前几版最多答出一条 | 变更题 0/38 → 31/38，材料齐备率 20.5% → 69.0% | facts 加三列、schema 升到 v5、事实行数翻倍、多一条 SQL 通道 |

三次转折有同一个方向：**从"猜哪段文字相关"退到"先确定这是哪个东西的哪个属性"**。A 把正文换成指针，B 把布尔判断换成带刻度的闸门，C 把相似度换成主键。每一次都在减少"用统计量代替结构"的地方。

### 1.3 演进的驱动力（按重要性排序）

**第一驱动力：token 成本。** 这是产品存在的理由，不是优化项。整个插件可以理解为一句反问："如果上下文无限，为什么要记忆系统？" 因为无限，所以一切设计都在回答"哪些不进上下文"。钩子索引、摘要而非原文、软 2,000 硬 3,000、`slotMax` 12 条上限，全是同一个约束的不同切面。

**第二驱动力：静默失效。** 这个项目里最贵的一类 bug 不是报错，是**没有报错**：偏好整块消失、记忆块少了一个分区、钩子指不到正文、删除只清了一半、升级了但跑的还是旧代码。它们共同的形状是"配置写着启用，行为却是关的"。所以后来的改动里有一半不是功能，是**哨兵**：`memory_doctor` 报版本、降级原因分三类、`BUILD_VERSION` 被 CI 盯着、探针必须包含"关掉开关后确实找不到"的对照组。

**第三驱动力：写入正确性。** 到 v0.2.32 才被真正正视：检索做得再好，也救不了"这句话从来没成为一行"。853 条属性陈述里 44% 因为动词不在词表里而根本没进库——那一段时间里所有检索调优都是无效劳动。

### 1.4 今天的形态

```
插件入口 apply()  src/index.ts
  ├─ 全局 section：memory-loom:protocol（记忆使用约定）
  │                memory-loom:index-protocol（索引使用约定）
  ├─ 每会话 section：persona（人设卡，常量块，不参与预算竞争）
  ├─ 每会话 context：hooks（钩子索引，order 895）
  │                  memory（记忆块，order 900，紧挨对话）
  ├─ 16 个工具 memory_*
  └─ 事件绑定：turn 捕获 / turn-stopping 兜底 / 定时维护（60s）

引擎 MemoryEngine  src/engine/index.ts
  ├─ recallFor()  每轮：四路召回 → 打分 → 分区渲染
  ├─ tick()       每轮：衰减、去重、trace 清理、路人到期、朋友删除期限清扫
  └─ consolidate() 触发式：切段 → 抽取 → 判定 → 落库

存储 MemoryStore  src/engine/store.ts      一个 SQLite 文件，WAL
  └─ 23 张表 = 20 张业务表 + 3 张索引层自建表（loom_*），另有 3 张 FTS5 虚拟表
```

**一次 turn 的生命周期**：用户消息 → `redactSecrets` → 写 `l0` → （若到阈值）整合 → 下一轮开始时 `recallFor` 渲染。读在写之前，所以**当轮说的内容不会出现在当轮记忆块里**——它已经在对话里了。这是刻意的，避免同一句话在上下文里出现两遍。

**关于"单文件"**：`lib/index.js` 不是手写的单文件，是一次 TS 构建的产物，`//#region src/xxx.ts` 就是当年的文件边界。源码已经不在仓库里（提交 `584668d` 明确承认了这件事），`index.js` 成为唯一真相。代价有三条：改代码靠 region 注释导航而不是靠文件树；无法用类型检查器约束内部；`git diff` 永远只能看到"一个大文件变了多少行"。**这不是值得模仿的架构，是一个被接受的历史成本。**

## 2. 核心模块设计（Why & How）

### 2.1 分层：压缩比就是产品定义

| 层 | 存什么 | 谁写 | 谁读 | 单条成本 |
|---|---|---|---|---|
| **L0** | 原文，一字不改（写前脱敏），无长度上限 | 捕获钩子 | `memory_expand`、取回正文 | 0 token（不进上下文） |
| **L1** | 原子事实：一句话 + 类型 + 域 + TTL + 显著度 + 槽位 | 整合 / `memory_write` | 记忆块、`memory_search` | 约 15–40 token/行 |
| **L2** | 事件：标题 + 摘要 + `l0_from/l0_to` | 整合 | 记忆块、钩子索引、`memory_episodes` | 摘要约 50 token |
| **L3** | 自我叙事：助手对自己的长期叙述 | 整合（需 12 条证据） | 记忆块尾部 | 一段 |
| 主观层 | 印象 / 日记 / 长期偏好 | 整合 / 用户 | 记忆块（偏好常驻、日记有保底份额） | 一行 |
| 人设卡 | 五分区，可锁定，按来源分权 | 主人 / 助手 | 独立 section，不抢预算 | 一块 |

**为什么 L0 不裁剪。** v0.2.1 之前单条消息有上限。取消它的理由不是"存储便宜"，而是**截断会让 `expand` 说谎**：钩子说"这段有 2.7k 字"，取回来只有 800 字，用户无从知道尾巴去哪了。宁可让库变大，也不让取回的内容与承诺不符。

**为什么 L1 是一句话而不是原文。** 这是整个项目最贵的一个取舍，在 §3-P1 详述。简短版：642 题基准上，索引原文的 BM25 拿到 82.7%，索引一句话摘要的 loom 拿到 20.5%。差距不是排序算法，是**信息闸门**——命中一条，一边给你 382 字，一边给你 50 字。选 50 字是因为真实会话里没人希望每次回答都从 2,300 字原文里挑重点。

**为什么事件摘要只留一到两句。** 摘要按"第一句 + 最长的第二句"选，而不是"信息密度最高的句子"。试过后者（带数字/英文标识符优先），中间指标"关键句进摘要"从 26.6% 涨到 82.6%，**最终检索指标从 20.3% 腰斩到 8.7%**，原因是叙事文本里最长的往往是情节点，而数字是"三天后""第十年"。判据只在一类文本上成立，就不是判据。

### 2.2 遗忘：双曲衰减，以及"想起"改变的是斜率不是起点

```
strength = base · (1 + t/S)^(−d)

t  距上次更新/访问的天数
S  稳定性（天），初始 30，上限 50 倍（即 1500 天）
d  形状参数，默认 1
base  由情绪显著度决定，0.55（中性）～1.0（极强）

访问后：S ← S · (1 + boost · S^(−0.2))，boost 默认 0.25，且不超过 50·S₀
```

**为什么是双曲而不是指数。** 指数衰减有个不符合直觉的性质：它在早期跌得比人快、晚期跌得比人慢。双曲 `(1+t/S)^(-d)` 的尾部更肥，符合"很久以前的事还在，只是模糊了"。`d` 可调，`d` 大则近事权重更高。

**为什么访问提升 S 而不是重置 t。** 这是最早一版就定下、且从未被推翻的一条，也是最该被解释的一条。重置 `t` 意味着"每次被想起，它就和刚写下时一样新"——一条被反复问到的老事实会永远占据前排，新记忆永远挤不进来。提升 `S` 则是"这次想起让它以后忘得更慢"，但**当前年龄照算**。前者是通货膨胀，后者是复利。

**过期不是删除，是连续降权。** TTL 到期后 `expired_at` 被写下，之后每天乘 `0.5^(天数/45)`，地板 0.02。所以一条过期两年的偏好仍然找得到（`0.02` 而不是 `0`），只是排不到前面。删除只有两种来源：用户明确要求，或者路人到期。

**地板 0.02 的意义**：`finalScore` 最后取 `max(floor, ...)`，保证任何一条存在的记忆都有一个非零分数。这样"找不到"永远只由**召回**决定，不由**打分**决定——两个失败原因分开，才查得动。

### 2.3 写入正确性：换一个值，不等于把话说得更准

这是 v0.2.32 修的核心问题，也是全项目最值得讲的一处设计。

**现象**：「这个项目的依赖名改过哪几次」——库里明明有五次变更，检索最多返回一条。

**根因有两层，第二层更隐蔽。**

第一层是抽取口径。`FACT_MARKERS` 只认「调整为」「改名为」，而真实语料里 44% 的属性陈述用的是别的动词：`首次确立为`（115 条）、`转为`（171 条）、`被撤销`（48 条）、`移到了`（93 条，属性名根本不写）、`出现两种并存的取值`（39 条）。这些句子不是排在检索第 20 位，是**从来没有成为一行**。

第二层是判定。判定器比较的是**措辞相似度**，而一次取值变更前后恰好只差一个 token：`依赖名是 lmdb` / `依赖名是 badger`。相似度极高，于是判成 `update`，`updateFactText` 把旧行整行改写。库里只剩当前值，**"变过"这件事本身没有被记下来**。

```
判定维度 ──► 措辞
变更维度 ──► 取值
       两者近乎正交，所以判定器在变更点上必然误判
```

修法因此不是加一条规则，而是换判定依据：**同一个 `(主体, 属性)` 下取值不同 → `contradicts`**（新行建出来，旧行 `superseded` 留在链上，`memory_edges` 记一条 SUPERSEDES）；取值相同才交给判定器决定合并与否。判断收敛在 `judgeAgainst` **一处**，整合路径和 `memory_write` 共用——因为"只有模型在场时链才成立"的链不叫链。

**改名：唯一允许"两个名字等于一个主体"的地方。** 变更题里有一批主体改过名，用新名字问，改名前写下的链节一条也取不到（那些行里没有新名字三个字）。做法是把改名本身存成一条槽位 `(旧名, 名称, 新名)`，查询时按并查集求名字闭包再枚举。

**为什么不用侧表（一张 `aliases(subject, alias)` 表）。** 侧表要重新回答三个问题：它带不带版本？`erase` 清不清它？导出 JSON 里有没有它？每一个答案都是一次迁移。而"改名就是一行事实"免费继承了这三点——它自己带 `updated_at`、自己被 `purgeIdentityLayers` 扫到、自己出现在 `export` 里。**能复用已有生命周期的东西，不要新开一张表。**

**嵌套主体按 `·` 单向隔离。** 问「猎户项目」不会连带「猎户项目·缓存模块」的值，因为父与子的同名属性通常不是一回事（项目有效期 600 秒，模块 60 秒），混起来就是把错误答案当答案。反方向也不做，对称不是美。

**摘抄校验位（v0.2.29）：只记录，不拦截。** 模型抽出的每条事实要求附一句原文摘抄，写入前在本地用字符级比对确认它真的在原文里。三种结局分开记（逐字命中 / 近似命中 / 找不到），但**不因为找不到就丢掉这条事实**——那会让抽取质量差的模型直接失忆。校验位的作用是**事后能算出这个模型在编造的比例**，不是当场执法。

### 2.4 召回：四路候选，两遍词法，一道闸门

```
候选来源（按优先级）
① pinned            常驻，不问查询      similarity 至少 0.45
② FTS strict        所有二元组 AND       bm25 归一
③ FTS relax         任一命中，有前提      ×0.55，且 overlap ≥ 0.25
④ slot              问句点名了主体+属性    0.85（结构匹配，非统计）

排序
score = (similarity × strength + emotion − layerPenalty)
        × expiryFactor × conflictFactor
        且 ≥ floor(0.02)，再 × weight × pinnedBoost(1.1)
```

**为什么必须有第二遍。** `compileMatch` 把「你还记得我不吃香菜这件事吗」切成 11 个二元组（`你还 还记 记得 得我 我不 不吃 吃香 香菜 菜这 这件 件事`），用空格拼给 FTS5——**在 FTS5 里空格是隐式 AND**。原文命中 4 个就足够人读懂整句，但 11 个必须全中。结果是那条记忆**整条消失，而且不报错**。

第二遍只在前一遍"太瘦"时才跑（严格命中 < `relaxBelow`，默认 3），因为长句用 OR 会把库里大半条目拖进来。三道守卫：

1. 放宽命中乘 `relaxPenalty`（0.55），结构上不可能反超严格命中；
2. 必须与查询共享 ≥ 25% 的二元组（`relaxMinOverlap`）——否则一个「的」就能匹配全库；
3. 事件层更保守：**严格命中为 0 才放宽**。每个事件在 prompt 里占一整行，错一块比少一块贵。

**为什么槽位不做兜底（只在词法为空时才查）。** 这是全项目最重要的一个判断，因为反直觉。这类问题的词法结果**不是空，是错**：它返回共享问句措辞的那几条，通常正好是最新那一条加几条无关的，而链上更早的节点恰恰因为取值变了、措辞也跟着变了，不在里面。**等一个永远不为空的信号，等于永远不等。**

代价是每次 recall 多一条带索引的 SELECT，所以入口条件卡得很死：问句里必须**同时**出现一个已知主体和一个已知属性名。「最近怎么样」什么也没点，就一次查询都不发。

**为什么融合不用 RRF。** RRF 在"两路都还不错且量纲不可比"时最优；这里两路强弱悬殊（词法整句 20.5% vs 向量 49.0%），RRF 会把强的一路拉平到弱的一路。槽位通道因此用**锚定**：`slotSimilarity = 0.85`，略低于最好的严格命中，且 `slotMax` 只截块内、`memory_search` 尊重调用方的 limit（链题常要 50 条以上）。

### 2.5 渲染：预算是分区制，不是排行榜

记忆块不是一个"top-N 列表"，是**七个各有配额的区**：

```
【长期偏好】  floor 15% 或 140 token —— 常驻 3 条，不问查询
【计划】      floor 10% 或 100 token —— 常驻 3 条，过期的会问"后来成了吗"
【事实】      目标份额 75%（`1 − subjectiveShare`），用尽后可从硬上限回填
【共同经历】  至少 25%，且不低于事实区已用的位置
【印象】【日记】【自我叙事】  合计 25%，其中日记保底 40%
```

**为什么偏好和计划必须常驻、不能靠 similarity。** 它们回答的是同一个问题——**什么必须在不被问的情况下想起来**——而这恰恰是相似度答不了的那个问题。用户不会重复说「我不吃香菜」，也不会重问一个他已经说过的计划，所以查询里永远不会出现这两个区需要的词。曾经它们排在最后、走硬上限，于是任何一轮事实塞满就静默丢掉偏好，没有报错。

**为什么计划要单独成区，而不是当事实渲染。** 两个原因：渲染成事实会丢期限（「用户打算换工作」读起来是背景，不是"该跟进的事"）；被 `maxPlans` 挤出计划区的计划会以事实身份在下一行重新出现，名额就白限了。代价是第四个计划不在块里——但它在库里，`memory_search` 找得到。"我需要完整清单"本来就该走工具，块是给"必须自己想起来"的东西。

**`appendSection` 的坑（v0.2.15）**：这个函数比较的是**全局已用**，而调用方一度传入的是"块内配额"的数值。事实区一旦超过那个绝对值，后面每个主观分区都被判超预算，印象和日记**整块消失**，配置里还写着启用。修法是传绝对位置。这类 bug 的形状值得记住：**单位不一致不会报错，只会让一段功能安静地不存在。**

**四种行内标记**，都是为了"别把不确定的说成确定的"：

| 标记 | 触发 | 含义 |
|---|---|---|
| `（待确认）` | 非手写且 confidence < 0.6 | 这是推断的，不是他说的 |
| `（可能已过时）` | 与当前话共享 ≥45% 词汇且否定/数字不一致 | 现在的说法优先 |
| `（语气偏冲）` 等 | 事件 valence/arousal 非中性 | 这话当时的口气 |
| `（旧值）` | 槽位链上被 superseded 的那节 | 这是历史版本，不是当前值 |

### 2.6 钩子索引：稳定性优先于相关性

```
【记忆索引】只有钩子，细节用 memory_expand(ref) 取；不要仅凭钩子断言具体内容。
- T 最近未整理 · 4轮 304字
- E1 技术·线上那个 Node 服务… 415字
- F12 ★ 不吃香菜
- D3 那次辞职长谈的整理 2.7k字
```

**三条设计原则，每条都在防止一种具体的坏结果。**

1. **驻留快照，不是每轮重排。** 常驻集合落盘在 `loom_hooks.resident`，只在定时器（`rebuildMinutes=5`）、`memory_pack` 之后、或显式 rebuild 时重算。渲染只读快照，所以同一段记忆在轮次之间**逐字稳定**。这是刻意防人格漂移——漂移的根因不是上下文长，而是注入内容每轮都在变。
2. **淘汰钩子，绝不压缩正文。** 超预算时低分钩子进冷区（`coldDays=7`，期间降权 10 分、不回抖），而不是花一次模型调用去摘要压缩。正文一直在 `l0` 里，冷区钩子仍可被 `memory_index search` 命中、直接 `expand`。
3. **软上限双保险。** token 预算（300）+ 条数硬顶（16）+ 分数下限（0.3）。低于下限的候选不占位——**空位比坏钩子便宜**。同名近重复只留最高分。

打分是刻意朴素的（事件 `0.75·salience + 0.25·recency`，事实 pinned 0.72 / 普通 0.24 + `0.5·salience` + `0.18·recency`，文档固定 0.62，未整合尾巴 0.8）。它不需要准，只需要**排序稳定**；准是记忆块的工作。

实测：两条并行工作会话 → 索引块 65 token；60 轮 + 41 条事实 + 40 段事件 → 137 token / 10 条钩子，任意一条可展开全文。

### 2.7 跨切面：身份、删除、降级、备份、热加载

| 切面 | 做法 | 为什么这么定 |
|---|---|---|
| **身份** | `master` / `friend` / `visitor` 三级；记忆全表带 `identity_id` | 跨身份只给 L1/L2，不给 L0 逐字；主人也不能读别人的原话 |
| **路人** | 48 小时后删原始对话，事实保留但降权到 ≤0.4 | 「不记得你说过什么」和「不记得你是谁」是两件事 |
| **删除** | 访客立即、六层全清（`purgeIdentityLayers`）；朋友 7 天冷静期，到期由维护扫 | 承诺是"把这个人删掉"，就得按**承诺**实现，不是按表实现 |
| **降级** | 三类原因分开记：配额 / 调用失败 / 判断层；每天 200 次调用上限 | 一个布尔说不清"为什么今天没记住" |
| **备份** | `VACUUM INTO`，24 小时一次，留 7 份，同盘 | 挡误删和写坏，不挡硬盘坏；同盘不算备份，这条写在文档里 |
| **热加载** | 首次安装即生效；补挂已存在的 agent；**升级必须重启** | 宿主只在"bundle 列表长度变化"时重组，升级长度没变 |
| **版本哨兵** | `BUILD_VERSION` 写死 + `memory_doctor` 首行打印 + CI 校验 | 新代码没跑起来时，这行根本打不出来——所以它不会撒谎 |

## 3. 踩坑与优化档案

按"教给下一个人的价值"排序，不按严重程度。

### P1 · 压缩的代价：优化了 A，B 却腰斩

**现象**：同一份 642 题基准，索引原文的 BM25 拿 82.7%，loom 拿 20.5%。变更链覆盖 94.4% 对 12.0%。

**根因**：不是排序算法差 4 倍，是**信息闸门**在检索这一步。BM25 命中一段，模型拿到 382 字全文；loom 命中一条，拿到约 50 字摘要。取 6 条：一边 2,300 字，一边 300 字，5–7 倍差距。原文没丢，`expand` 也真能调回整段——但只有被摘要捞出来的那几条才有机会调回。

次要根因：`searchFor` 的 overlap 门槛让整句查询经常**空手而归**（70 字的摘要装不下整句十几个词），43% 对 83% 的差距里，主因不是排错序，是根本没返回。

**试过什么**：把摘要选句从"最长"改成"带具体值（数字/英文标识符）的句子"。中间指标"关键句进摘要" 26.6% → 82.6%，看起来大胜；**最终指标 20.3% → 8.7%**。分离实验确认不是事实层挤占，是摘要本身——叙事文本里最长的往往是情节点，而数字是"三天后"。

**结论**：回退，不为基准改索引粒度。正确的说法是"**它在需要逐版本穷举的任务上天然弱于全文字检索，这是压缩的代价，不是实现缺陷**"。

**教训**：**中间指标和最终目标可能反向。** 只量了前者就下结论，会得到一个漂亮而错误的改动。这条写进了 `episodeSummary` 的注释，省得下一个人再试一遍。

### P2 · 隐式 AND：一条记忆整条消失，且不报错

**现象**：问「你还记得我不吃香菜这件事吗」，记忆块里没有香菜，而且没有任何错误。

**根因**：CJK 二元组用空格拼给 FTS5，空格是隐式 AND。11 个二元组必须全中，命中 4 个就足够人读懂，但 FTS 判不命中。

**修法**（v0.2.15 + v0.2.17，分两次才修完整）：偏好改常驻；事实层加第二遍 OR + 三道守卫；`searchFor` 走同一套规则（此前模型自己搜也是严格 AND，于是答"没有找到相关记忆"）。

**教训**：**不报错的失败，必须从结构上消除，不能靠"下次注意"。** 前一次（v0.2.15）只修了偏好，事实和事件没动，同一个 bug 在两周后以"整句零召回"的形式又出现一次。

### P3 · 热加载只挂了一半，升级不等于生效

**现象**：装完 0.2.23，工具 9 个、`memory_doctor` unknown、`user_version` 1——三条证据同时指向"实际跑的是 0.2.12"。

**根因有两层，第二层是致命的**：

1. `apply()` 把三个按会话的块挂在 `agent/created` 上，但热加载时那个 agent 早就创建好了，事件不会再触发。工具能调（全局注册），记忆块挂不上（按会话）——于是模型得先想到去搜，才知道有记忆。
2. 更根本的：**宿主只在"bundle 列表长度变化"时重组**。首次安装列表多了一项，触发；升级是同一个 bundle 换内容，长度没变，不触发。所以"首次安装不用重启"这个结论被错误地推广到了"升级"。

**修法**：补挂已存在的 agent（`ctx.get("agents")` + 幂等保护）+ `turn-stopping` 兜底 + 卸载时清理按会话 section；`BUILD_VERSION` 写死并在 `memory_doctor` 首行打印；CI 盯住它与 `package.json` 一致。

**教训**：**可观测性必须能自证。** 那行版本号的价值不在信息量，在于"新代码没跑起来时它打不出来"——所以它不会被伪造。任何"验证升级成功"的方案，都得满足这个性质。

### P4 · 换值被判成"说得更准"

见 §2.3。这里只补一条判断原则：**当判定器的比较维度与变化的维度正交时，加规则没用，得换依据。** 判定器比措辞，而变更恰恰是措辞差异最小的那一维；再怎么调阈值，`lmdb`/`badger` 都"很像"。换成 `(主体, 属性)` 的等值比较，问题消失，而不是被缓解。

### P5 · 删除只兑现一半，认领把主人降级

**现象一**：`memory_identity erase` 承诺"把这个人删掉"，实际只清 `l0` 和 `facts`。而 `events.summary` 里躺着的就是原话的压缩句，`memory_expand` 仍能按 E 编号读回。偏好、日记、印象、人设覆写也没有任何删除路径碰过。

**根因**：删除是按**表**实现的，不是按**承诺**实现的。写代码时想的是"对话和事实是记忆"，而用户想的是"关于我的一切"。

**修法**：`purgeIdentityLayers()` 一次清六表；访客立即调，朋友到期由维护调（`deletionDeadline` 此前只写不读）；删事实改走逐条 `purgeFact()`，不再在 `memory_edges` 留孤儿边。

**现象二**：主人走一遍认领 + 批准，把自己降成 `friend`，且没有回程。

**根因**：`claim` 排在 `requireMaster` 之后，claimant 取当前 actor。于是"只有主人能用"和"主人用它就降级"同时成立。

**修法**：`claim` 移到权限检查之前，并明确拒绝主人发起。

**教训**：**承诺要用"层"来数，不是用"我记得改过"。** 一个删除动作涉及几张表，应该在设计时就写下来（这里是六张），而不是等用户发现"它还记得"。

### P6 · 同一形状的其他实例（速查表）

这些不值得各写一节，但形状完全一样，读代码时会反复遇到：

| 实例 | 形状 |
|---|---|
| `toEngineConfig` 是显式白名单，`aliasCount` 漏写 → 传进引擎是 `undefined`，默认值补上"看起来生效了" | 白名单漏字段，开关静默失效 |
| `appendSection` 传入块内配额，函数按绝对位置比较 | 单位不一致，一段功能安静消失 |
| `memory_doctor` 读全局最近一次 consolidate audit | 查询缺 join，数字报到别人头上 |
| `probe-relative` 用 `days:-7` 表示"上周三" | 测试假设写入日就是周三，当天即红 |
| 探针里写死"工具数 === 13"，加工具后没人改 | 断言绑定了易变常量 |
| `preferences.source_l0` 写了但 `expand` 不读 | 只写不读，字段变装饰 |
| `roles.promotionVisits` 从未被消费，README 却宣称"路人转朋友" | 保留字段被当成功能宣传 |
| `searchFor` 用 `min(limit, slotMax)` 截断链 | 上限套错对象，链题永远取不全 |

**统一教训**：这个项目里绝大多数"难查的 bug"都不是逻辑错，是**两个地方对同一个量的理解不一致**（单位、范围、维度、谁负责写、谁负责读）。所以探针的写法也统一了：每个改动都必须有"关掉开关后行为确实回去"的对照组，否则测不出"差异是不是来自这次改动"。

## 4. 边界条件与 Trade-offs

### 4.1 明确做不到的

| 做不到 | 具体表现 | 原因 |
|---|---|---|
| **跨语言 / 近义换词** | 「香菜」搜不到「芫荽」，口语改写搜不到书面表述 | 词法检索，没有 embedding |
| **依赖编码的模糊指代** | 「那个项目现在是什么版本」里的"那个项目"不会被当成主体 | 没做指代消解；槽位通道只认显式主体名 |
| **序数引用** | 「截至第 16 次提交，依赖名是什么」答不全（状态归属 113/176） | 库里没有"第几次提交"这个坐标；真实对话里没人这样问 |
| **长链全量** | 60 节的链装不进 12 行块 / 50 条 search 上限 | 预算问题，不是通道问题 |
| **多模态** | 图片、语音、附件内容不进记忆 | 只处理文本 |
| **语义去重** | 两句话意思一样但用词不同，会存成两条 | 去重靠词汇相似 + 模型判定 |
| **多设备同步** | 一个 SQLite 文件，没有同步协议 | 本地优先是产品前提 |
| **加密存储** | 明文 SQLite，能读文件的人能读全部对话 | 威胁模型是"本机文件权限" |
| **服务端检索** | 无服务端 | 同上 |
| **别名自动发现** | 靠模型写"他会怎么问"，写不出就没有 | 规则路径生成不出有意义的别名 |

### 4.2 为了轻量化，牺牲了什么

| 牺牲 | 换来 | 是否可逆 |
|---|---|---|
| 索引摘要而非原文 | 每次回答不用从 2,300 字里挑重点；上下文成本降一个数量级 | 可逆（改索引粒度），但会推翻产品取舍 |
| 不做向量检索 | 零依赖、零网络、零额外进程、860KB 就能装下全库向量之外的一切 | 可逆，但见 §4.3 |
| 单文件无源码 | 无构建步骤，"改完即是生效版本" | 可逆（重建 TS 工程），成本高 |
| 规则路径兜底 | 没有模型也能工作，只是抽取质量下降 | 已是双路径，不必逆 |
| 不做项目/仓库维度 | 插件从不读工作目录，不假装知道两段对话属于同一个仓库 | 可逆，但会引入"猜" |
| 冷区淘汰而非压缩 | 不花模型调用做摘要压缩，行为可预测 | 可逆 |

### 4.3 为什么至今不接向量检索（v0.2.32 的当前位置）

离线实验做过（bge-small/base/large，k=3 命中 41.0% / 49.0% / 52.4%，无条件并行接入可达 53.8%），**没有合入**。四条理由，按硬度排序：

1. **融合税。** 两路强弱悬殊时 RRF 会把强的一路拉平。合适的做法是**并集**而不是融合排序，但并集意味着候选集翻倍，而预算没变——多出来的候选只会挤掉别的区。文献（2610.30612）对"两路均衡时 RRF 才赢"的结论与实测一致。
2. **它救不了这批题的主因。** 这批失败里，一半是"这句话没成为一行"（写入侧，已在 v0.2.32 修掉），另一半是"一条只覆盖一个槽位"（粒度问题）。向量救的是"问法和原文用词不同"那一类，占比最小。
3. **同构句上它更差。** `依赖名是 lmdb` / `依赖名是 badger` 余弦几乎一样，而这两句的区别恰恰是全部信息。
4. **工程成本是真的。** 宿主 `LlmAdapter` 只有 `stream()` 没有 `embed`；FTS 靠 SQL trigger 同步，embedding 必须异步，于是多一条"索引落后于写入"的一致性问题；onnxruntime 体积远超整个插件。

**结论**：值得做，但定位是**真实使用里的模糊召回**，不是基准提分手段。而且它只能追加成第三/第四路，不能替换词法——人名、编号、错误码是词法的强项。

### 4.4 口径警告：这些数字不能直接外推

- **561 题**是 642 题剔除 40 道可推、41 道歧义后的主读数。引用时要说清是哪一档。
- **20.5% → 69.0%** 是"材料齐备率"——答案那一版在不在取回的材料里。它是**天花板**，不是答题正确率；后面接多强的模型都突破不了，但也绝不等于模型会答对。
- **题库模板句都带实体全名和属性词**，所以槽位通道的数字偏乐观；真实问法需要指代消解，那部分没做。
- **LongMemEval 的 96% 不可类比**：它只要求落点新值，我们的 `all_needed` 要求整条链。0/38 和 96% 不是同一个尺子。

### 4.5 给测试员的"这不是 bug"对照表

有人提 issue 说"为什么搜不到"，先对这张表：

| 报告 | 判定 | 该去哪看 |
|---|---|---|
| 「我问了一句很长的话，什么都没搜到」 | 可能是 bug（v0.2.17 已修）；先确认 `relaxMatch` 没被关 | `probe-recall-relax` |
| 「换了个说法（香菜→芫荽）就搜不到」 | **不是 bug**，已知边界 | §4.1 第一行 |
| 「我记得说过，但它说没印象」 | 先看是否 < 2 万 token 且未空闲 5 分钟——**还没整合** | `memory_doctor` 的待整合轮数 |
| 「同一个项目改过五次，只返回一条」 | v0.2.32 之前是 bug，之后应返回链；若仍失败看在不在 §4.1「长链」 | `probe-slot` |
| 「记忆块里少了一个分区」 | 可能是预算挤占（有保底，但极端情况仍会）；查 `appendSection` 的绝对位置 | §2.5 |
| 「升级了但行为没变」 | **先重启**，然后用 `memory_doctor` 首行核对运行版本 | §2.7 版本哨兵 |
| 「它把我说的记成了别人的」 | 查 `identity` 绑定与 `claim` 流程 | `probe-claim` |
| 「删了还在」 | 访客立即、朋友 7 天冷静期；六层都清才算清完 | `probe-erase-layers` |
| 「钩子指向的内容取不回来」 | 可能是遗忘级联（素材被删后 `expand` 应拒绝返回） | `probe-index-gc` |
| 「一条普通记忆后面跟着一个早就过去的日期」 | v0.2.22 之前写进去的存量行；块里会印、库里还在按半衰期减分 | `memory_doctor` 的「时间」行（v0.2.33 起会报） |

## 5. 未来演进路线

### 5.1 判断标准：什么样的改动值得做

按这个项目自己踩过的坑，一个改动要同时满足三条才动手：

1. **它修的是"没有行"，不是"排得不好"。** v0.2.32 的收益全部来自把没进库的句子弄进库；v0.2.30 的检索调优收益接近零。
2. **它能用一个"关掉就回去"的对照组验证。** 验证不了差异来源的改动，不做。
3. **它不改变产品核心取舍。** "把摘要换回原文"能提分，但那是换产品。

### 5.2 三条安全切入（按风险从低到高）

**① 观测与运维（最低风险，最高性价比）**
现在最缺的不是能力，是**能回答"为什么这次没记住"**。已有三类降级原因，但缺一条从"用户报障"到"这一次 recall 用了哪几路、各返回几条、谁被预算挤掉"的完整链路。加一个可选的 recall trace（默认关、只记计数不记内容），比任何检索算法都更能减少后续误判。

**② 检索预算的显式化（中等风险）**
当前预算是"软 2000 / 硬 3000 + 七区配额"的硬编码策略。下一步可以让"这一轮需要多厚的记忆"由查询类型决定（问事实 vs 闲聊 vs 追问计划），而不是每轮同一套配额。风险在于：动态预算会让块大小在轮次间变化——**这与钩子索引"稳定性优先"的原则冲突**，所以只能调分区配额，不能调总量。

**③ 语义通道作为第四路并集（较高风险）**
前提条件全部满足才做：宿主的 embed 接口可用、embedding 异步一致性有方案（写入先落 FTS、向量后补，查询时允许 miss）、并且**只做并集不做融合排序**。定位写死为"真实使用的模糊召回"，不进基准评测的结论。

### 5.3 明确不建议做的

| 提议 | 为什么不做 |
|---|---|
| 为基准把索引换回原文 | 推翻产品存在理由。分数会涨，产品会没 |
| 按题库口径补"第 N 次提交"序号 | 拟合合成措辞；真实对话里没人这样问 |
| 用侧表存别名 | 重新回答版本/删除/导出三个问题，每个都是一次迁移 |
| 每轮重排钩子 | 人格漂移的根因就是注入内容每轮在变 |
| 把 `memory_write` 改成必须模型在场 | 链只在模型在场时成立的链，不叫链 |
| 加一个"重要性打分"模型 | 现有显著度是确定性规则，可解释、可复现；换模型只换来不可解释的抖动 |

### 5.4 什么时候才该动

不要按"版本号该涨了"驱动，按信号：

- **同一个 issue 出现三次**（同一形状，不同表象）→ 值得结构性修，而不是再打一个补丁。
- **某个通道的命中率连续两版没有变化** → 它已经不是瓶颈，别在上面调参。
- **某个"只写不读"的字段被用户当成功能提到** → 要么实现它，要么从文档里删掉，不能留着。
- **探针需要靠写死常量才过得去** → 说明断言绑定了易变的东西，先修断言。

## 6. 安装

要求 Node `^22.19.0 || >=24`（使用内置 `node:sqlite`，无原生编译）。

### 6.1 装之前：先确认没有别的记忆插件

**这是替代品，不是叠加品。** DSH 的工具名全局唯一，重名不是「后装的少一个工具」，而是**后装的整个插件加载失败**——16 个工具一个都不进表，三块提示词一起撤销。这个生态里至少四个记忆插件用了同一套名字：

| 插件 | 与我们重名的工具 |
|---|---|
| `dsh-memory`（SQLite + FTS5） | `memory_search` `memory_write` `memory_forget` |
| Memory Library（工作区卡片库） | `memory_search` `memory_write` `memory_forget` |
| Workspace Recollection | `memory_search` `memory_write` `memory_forget` `memory_index` |
| `@max-null/dsh-memory` | `memory_search` `memory_forget` |

`memory_search` / `memory_write` / `memory_forget` 是这个生态的事实标准名。**16 个名字里任意一个撞上就整体装不上**，所以装之前值得花十秒确认。

撞了会看到一句能照着做的话，而不是宿主的 `already registered`：

```
memory-loom: 工具名 memory_search 已被另一个插件占用（多半是另一个记忆插件）。
DSH 的工具名全局唯一，重名会让整个插件加载失败——所以这一版不会半残运行，也不会顶掉对方。
两种解法，任选一种：
  ① 二选一：dsh plugin --profile <你的 profile> remove <那个记忆插件>（它的记忆文件不会被删除，以后装回来还在）
  ② 共存：在 profile 的 cordis.patch.yml 给本插件设置 toolPrefix: loom_ …
```

**① 二选一（推荐）。** 卸载对方**不会删掉它的记忆**：`dsh plugin remove` 只摘插件，`.dsh-memory/`、`$DSH_HOME/memory/memory.db` 这些文件原地不动。换一个试试是有退路的，代价只是重装一次。

**② 共存（`toolPrefix`）。** 两个都留的写法：

```yaml
- id: memory-loom
  name: dsh-memory-loom
  config:
    path: !!js dshHomePath('memory', 'loom.db')
    toolPrefix: loom_
```

设了之后 16 个工具变成 `loom_search` / `loom_write` / …，提示词、工具描述、工具返回里出现的名字**一起跟着换**（只换注册名的话，模型会照着一个不存在的名字去调）。默认值是 `memory_`，不设就是原来的行为。

不默认开启共存，是因为共存不是「多一个备份」，而是每轮多读一份「关于你的长期记忆」：两边都往系统提示词注入（每轮多 3000–5000 字符）、两边都在会话结束时调模型抽取（同一段对话付两次钱）、而模型看不到「这块是 loom 的、那块是别人的」，两份矛盾时它不知道该信哪个。

技术上也别指望「谁都能装」：改名只能让**我们**避开别人的名字。如果本插件先加载、占住了 `memory_search`，后装的对方照样整插件失败。真要两个都装，先装对方、再装我们并设 `toolPrefix`。

### 6.2 三种装法

| 贴什么 | 例子 | 特点 |
|---|---|---|
| **Release 里的 tarball**（推荐） | `https://github.com/lingou-shao/dsh-memory-loom/releases/download/v0.2.33/dsh-memory-loom-0.2.33.tgz` | 版本钉死，装到的就是这一版 |
| **GitHub 仓库地址** | `https://github.com/lingou-shao/dsh-memory-loom` | 跟随 `main`，每次装到的内容会变 |
| **本地目录** | `D:\code\dsh-memory-loom` | 必须写**绝对路径**（相对路径会被 DSH 拒绝），先 clone 再填 |

离线 / 内网用 `npm install ./dsh-memory-loom-0.2.33.tgz`；手动挂载则把包放进 profile 的 `node_modules`，并在 bundle 列表里加 `dsh-memory-loom`（包内 `cordis.patch.yml` 会被组合器读取，`path` 必填——对话的长期记录不该落在启动目录里，临时试用可以设 `:memory:`）。

> **贴本地 tarball 的要注意**：DSH 会把你给的源**原样**记成 profile 的依赖。贴本地文件就写成 `"dsh-memory-loom": "file:C:/Users/you/Desktop/xxx.tgz"`——这个绝对路径变成了长期依赖，tgz 一旦被挪走，再遇到「重新解析依赖」（lockfile 丢失或重生成、pnpm store 被 prune、换机器）就会报 `Could not install from ... as it does not exist`。规避办法：tgz 别放桌面/下载目录，或贴 Release 的 HTTPS 直链，或贴 git 地址。

### 6.3 装完它会问一句：以前那些记忆要不要搬过来

装好后它会先看周围有没有别人留下的记忆文件（`$DSH_HOME/memory/*.db`、`$DSH_HOME/storages/memory*.json`、当前目录的 `.dsh/storages/`，一层深、不递归）。找到了**不会自己导**，而是在对话里问一句，然后按你的回答给清单、记账、或让你指定文件。

**只读，不删也不改**——源文件一个字节都不动。导进来的东西和本插件自己记的一样用（类型与领域重判，来源标成 `import:<插件名>`），唯一例外是**旧计划**：「下周三去体检」里的日子是那个插件的时钟算出来的，拿今天重新解析等于编一个期限，所以按事实存放，不会到期来问你。补别名要调模型，所以先报价、先看当天预算。

### 6.4 首次安装不用重启，升级必须重启

这两件事走的不是同一条路，把它们写成一条是错的（2026-11-02 真机踩到）。

**首次安装**走 DSH 的**即时重组（live reconcile）**：pnpm 一装完，宿主就把 bundle 追加进列表、读 patch、调 `apply()`，然后把新工具 schema 推给**正在运行的那个会话**。实测：`dsh plugin add` 20:05:09 跑完，20:05:11 `loom.db` 被创建，宿主主进程从头到尾没重启。

**升级不走这条。** 升级是「同一个 bundle 换内容」，不是「出现一个新 bundle」，宿主不会为它重组。实测 0.2.16 → 0.2.23：装完磁盘上确实换了包，但工具数还是 9、`memory_doctor` 是 unknown、库 `user_version` 还是 1——**磁盘上装的是新版，进程里跑的是启动那一刻的旧代码**。

升级的正确顺序：

1. **先备份库**（`%USERPROFILE%\.dsh\memory\loom.db`）。新代码第一次加载会 `ALTER TABLE` 加列，备份是为了有退路。
2. 装新版。
3. **把 DSH 完全退出再打开**（不是新开会话，是重启进程）。
4. 用 `memory_doctor` 第一行确认：`运行 0.2.33 · 库 schema v5`。**这一行是唯一不会撒谎的证据**——它由代码自己打印，跑的是哪版就报哪版；新代码没跑起来时它根本打不出来。

### 6.5 装完怎么确认

- 工具列表里出现 16 个 `memory_*`。首次安装当前会话就会被刷新，升级则要重启。
- `%USERPROFILE%\.dsh\memory\loom.db` 被创建。**`diary/` 不会跟着出现**——它懒创建，第一篇日记落盘才建，刚装好看不到是正常的。
- 注意区分两件事：「装上了」只意味着**工具挂上了**。真正开始积累记忆要等**整合**触发（单会话累计 2 万 token，或空闲 5 分钟）。装完立刻问「你还记得什么」，答案当然是空的。

若安装被拒绝并提示 `incompatible-version`，那是 `engines.dsh` 与当前 DSH 对不上（本包声明 `>=0.2.1-rc.2 <0.3.0`，上限定在 0.3 是故意的：插件用到 `defineTool`、`systemPrompt.section`、session 事件这些宿主内部面，0.3 改语义时它不会自动知道——装不上比装上了坏掉好）。提 issue 时请附 DSH 版本。

### 6.6 本地开发

```bash
git clone https://github.com/lingou-shao/dsh-memory-loom
cd dsh-memory-loom
npm install
npm test        # 单元自测
```

`test/` 虽然随包发布，但**在安装位置直接跑 `npm test` 跑不起来**——`lib/index.js` 要 import `@deepseek-ai/dsh-tools`，DSH 里由宿主解析，普通 `node` 进程没有那份 `node_modules`。自测脚本会打印提示让你回仓库跑，不会甩一屏堆栈。改动后的完整验证见 §10.2。

## 9. 运行时行为、隐私与数据

### 9.1 一轮里发生了什么

```
用户消息 ──► redactSecrets（密钥/手机号/身份证/银行卡替换成 [redacted ...]）
         ──► 写 l0（整条落库，不截断）
         ──► 阈值检查：累计 2 万 token 或空闲 5 分钟 → 整合（切段 → 抽取 → 判定 → 落库）
下一轮开始 ──► recallFor()：四路召回 → 打分 → 分区渲染 → 注入
```

**读在写之前**：当轮说的内容不会出现在当轮记忆块里——它已经在对话里了。这是刻意的，避免同一句话在上下文里出现两遍。

### 9.2 注入位置

```
系统提示
  ├─ …（宿主自己的 section）
  ├─ memory-loom:persona:<session>   人设卡（section，常量协议之外唯一的静态块）
  ├─ memory-loom:protocol            记忆使用约定（全局 section）
  └─ memory-loom:index-protocol      记忆索引使用约定（全局 section）
动态上下文
  ├─ memory-loom:hooks:<session>     钩子索引块（context，在记忆块之前）
  └─ memory-loom:memory:<session>    记忆块（context，落在对话之前）
对话历史
```

记忆块内部：事实 → 事件 → 印象 → 日记 → 自我叙事 → 长期偏好 → 原文下钻片段。软目标 2000 token，硬上限 3000，主观层独占约 25%。

人设卡独立成 section 这件事属于 Q65 的落地：它不跟事实抢预算，也不随召回结果变化。

> **Q64 在 v0.2.9 收口（原文写「语气分离注入」）**：当时的设想是给语气单开一条注入通道，再加一套离线评估。实际结论是——只要模型在读记忆时能看见「这话当时是什么口气」就够了，不需要独立通道。现在语气以 `（语气偏冲）` 这样的短标注跟在事件行后面，见下面的「语气」小节。

两个 prompt 贡献都设了 `interpolate: false`：用户写进人设或事实里的 `{{...}}` 是字面文本，不会被当成模板变量。

### 9.3 冲突：当前对话永远优先

协议里固定一条规则：**当前对话永远优先于记忆块**。此外做一次确定性检测——候选事实与当前这句话共享足够词汇（containment ≥ 0.45 且 ≥3 个共同 token），却在否定词或数字上不一致时，标「可能已过时」并乘 0.85。不额外调用模型。

### 9.4 语气：只标注，不单独注入

整合时每个事件已经存了 `valence`（正负）与 `arousal`（强度）。渲染时用一个纯函数把它们折成一句话，附在事件行尾部，**只在情绪不中性时才出现**：

```
【我们一起经历过】
- [10-30] 为辞职吵起来的那次：说到加班时声音变高，明显不高兴。（语气偏冲）
- [10-30] 她夸我那次：聊到最后心情不错。（语气愉快）
- [10-30] 问天气：问了明天的天气，语气平常。          ← 中性，不加标注
```

- **只影响“读到的语气”，不影响排序**：打分仍然只看相似度、衰减、salience。
- **不额外调模型**：用的是已经落库的两个数，`memory_search` 的结果里同样带。
- **成本**：每条被标注的事件约 +3 token；中性事件 0。实测两条情绪事件让记忆块从 59 → 65 token。
- **可以关**：`retrieval.toneHint: false`。
- **不声称准确**：语气标签是阈值映射，不是判断模型。离线评估没有做，也不打算做——这正是 Q64 被缩小掉的那一半。

### 9.5 日记：不给权重，给一个能看的文件（Q63，v0.2.9 定稿）

日记是唯一「写给助手自己」的层。原来的设计里它按 `weight`（情绪 salience）参与叙事触发，后来发现：**日记按权重加进去也不会让人更愿意看它，反而让「谁更重要」这件事被一个拍出来的系数绑住**。所以定稿是——

- **不加权**：日记不参与事实/事件的排序，也不计入叙事证据（`narrativeEvidence()` 只数事件）。
- **给入口**：每天一个 Markdown 文件，导出到数据库旁边的 `diary/` 目录，任何文件管理器点开就能读：

```
~/.dsh/memory/loom.db        ← 数据库（默认 path）
~/.dsh/memory/diary/
  2026-10-29.md
  2026-10-30.md
```

文件长这样（按人分组，只读镜像，写入以数据库为准）：

```markdown
# 日记 2026-10-29

## 主人

- 15:23 今天她把辞职的事说到底了，我怕的其实不是钱。

> 由 memory-loom 从 diary 表导出，只读镜像；以数据库为准。
```

导出时机：插件加载时回写最近 `diary.mirrorDays`（默认 14）天，之后每次维护 tick 检查最近两天，只在内容变了（条数或时间戳变了）才重写。**目录是懒创建的**：库里一条日记都没有时不建 `diary/`，第一次写日记才 mkdir。目录写不进去不会影响主流程——条照旧进数据库，每 tick 重试一次，日志里给一条 warn。`memory_profile` 会打印这个目录的绝对路径，那就是用户找日记的入口。

### 9.6 隐私与数据权利

- **按人隔离**：事实、事件、印象、日记、偏好都带 `identity_id`；路人默认不可被跨用户查询，只有 `evidence.public === true` 才放行。
- **主人跨用户查询只有 L1/L2**：拿不到 L0 逐字内容。
- **删除**：`memory_forget` 软删除 → 冷静期 → 硬删；`memory_identity erase` 按角色处理；路人原始对话到期自动清除，事实保留但降权。
- **导出**：`memory_identity export` 给出 JSON；`engine.exportData` 是同一份数据。
- **审计**：每次写入、修改、删除、整合都进 `audit` 表；`traces` 只保留 14 天。
- **插件自己留本地快照**（v0.2.15 起）：默认每 24 小时一次，滚动保留 7 份，落在库文件同级的 `backups/` 下。它解决「误删/写坏」，不解决「硬盘坏了」——同一个盘上的快照跟着一起没。异地备份仍然是用户的责任（Q59），插件不做对象存储，也不上传任何东西。

### 9.7 安全事实（可自行复核）

这一节不是承诺，是可以一条命令验证的事实：

| 问题 | 事实 | 怎么自己查 |
| --- | --- | --- |
| 插件是否持有 API Key / Token？ | **没有。** 源码里不存在任何凭据常量 | `grep -nE "api[_-]?key\|secret\|password\|bearer" lib/index.js` → 只命中**脱敏正则**与情绪词表，无凭据值 |
| 是否会外联？ | **不会。** 没有任何 `fetch` / `node:http` / `node:https` / `WebSocket` / 原生 socket 调用 | `grep -nE "fetch\(\|node:http\|node:https\|WebSocket" lib/index.js` → 无输出 |
| 是否有遥测 / 上报？ | **没有。** 不加载任何统计 SDK，全文不含 `http` 字样 | `grep -n "http" lib/index.js` → 无输出 |
| 会写磁盘的哪些位置？ | **只有你配置的那一个 SQLite 文件**（以及 SQLite 自己生成的 `-wal` / `-shm`） | `grep -n "writeFileSync\|mkdirSync" lib/index.js` → 只有建目录那行 |
| LLM 调用走哪里？ | **走 DSH 宿主**（`ctx.get("llm", false)`，宿主没提供就降级为纯规则模式），插件不接触凭据、不代理请求 | `grep -n 'ctx.get("llm"' lib/index.js` |
| 库文件是否加密？ | **不加密。** 是明文 SQLite，任何能读该文件的人都能读全部对话 | 用任意 SQLite 客户端打开 `loom.db` 即可 |
| 落盘前会过滤敏感信息吗？ | **会。** `redactSecrets()` 在写入前把访问密钥、`Bearer xxx`、`password=`/`token:` 这类赋值串、手机号、身份证号、银行卡号替换成 `[redacted ...]` | `grep -n "SECRET_PATTERNS" -A 30 lib/index.js` |

关于脱敏要说清边界：它是**保守的正则匹配**，防的是「你不小心把密钥粘进对话」，不是 DLP 系统。自由叙述格式的敏感信息（比如身份证号中间夹了空格以外的写法、自定义格式的内部编号）不一定拦得住。

两条由此推出的操作建议：

1. **别把 `loom.db` 放进网盘/公开同步目录**，也别提交进任何 git 仓库（`.gitignore` 已拦截 `*.db`）。
2. **威胁模型是「本机文件权限」**，不是「服务端泄露」——因为没有服务端。你要防的是别人拿到这台机器或这个文件。

如果你在别人的分支/PR 里看到 `loom.db`、`.env`、带真实对话的 `.jsonl`，那一定是误提交，不要 merge。

### 9.8 备份：插件自己留 7 份，但只留在同一个盘上

这个插件的全部记忆只有**一个 SQLite 文件**，没有云端副本。v0.2.15 起插件会自己滚动留快照，但那只挡住「手滑删了」「写到一半断电」，挡不住「硬盘坏了」「这台机器没了」。

**插件自己做的部分**（v0.2.15）

| 项 | 默认 | 配置 |
| --- | --- | --- |
| 是否快照 | 开 | `backup.enabled` |
| 间隔 | 24 小时 | `backup.everyHours`（1–720） |
| 保留份数 | 7 | `backup.keep`（1–60） |
| 位置 | 库文件同级的 `backups/` | `backup.dir`（相对库目录，或绝对路径） |

快照用 SQLite 的 `VACUUM INTO` 生成，所以**单个文件就是完整副本**，不需要再拷 `-wal`；文件名形如 `loom-2026-11-01-1045.db`，按时间排序自动清理旧的。库还是空的时候不拍（省得占满名额）。

**你自己要做的部分**：把某一份拷到**另一块盘或另一台机器**。这一步插件替不了你。

**要备份什么**

| 文件 | 是否必需 | 说明 |
| --- | --- | --- |
| `loom.db` | ✅ 必需 | 全部记忆：原始对话、事实、事件、自我叙事、索引与整理版正文 |
| `loom.db-wal` | ⚠️ 存在就必须一起拷 | 最近尚未合并回主库的写入。只拷 `loom.db` 会丢掉最近这段对话 |
| `loom.db-shm` | 可忽略 | 只是共享内存索引，会自动重建 |
| `diary/` | 可选 | v0.2.9 起的日记 Markdown 镜像。**它是只读导出，不是真相来源**：插件装载时会把最近 14 天重写一遍，更早的日子不会自动回来（库里的条目本身还在）。所以不必单独备份；只有当你把它当成唯一阅读副本时才需要一起拷 |

**在哪**

配置项 `path`，默认由 bundle patch 设为 `dshHomePath('memory', 'loom.db')`，也就是 DSH 主目录下的 `memory/loom.db`：

- Linux / macOS：`~/.dsh/memory/loom.db`
- Windows：`%USERPROFILE%\.dsh\memory\loom.db`
- 若设置了环境变量 `DSH_HOME`，则在其下面同样位置
- 你自定义过 `path`，就按你配置的路径

不确定的话，直接在 DSH 里问：*「memory 插件的 path 配置是什么？」* 或让它调 `memory_identity export` 导出一份 JSON 作旁证。

**怎么备（手动，用于异地）**

最稳的是停掉 DSH 再拷，三个文件一起拷：

```bash
# 停掉 DSH 之后
cp "$DSH_HOME/memory/loom.db"* ~/backup/loom-$(date +%F).db   # 连同 -wal/-shm
```

不停 DSH 也能拷，但要一次拷齐三个文件；或者用 SQLite 的一致性备份，避免拷到半写入状态：

```bash
sqlite3 "$DSH_HOME/memory/loom.db" ".backup '$HOME/backup/loom-$(date +%F).db'"
```

**多久备一次**

看你对「丢最近几天」的容忍度：记忆是持续累积的，越晚备丢得越多。日常每天一次、大改配置或换机器前手动备一次即可。库很小（纯文本，一万轮对话量级在几十 MB），不需要增量方案。

**怎么恢复**

停掉 DSH，把备份文件放回 `path` 指向的位置并命名为 `loom.db`，删掉同目录残留的 `-wal` / `-shm`，再启动。

**注意**

- 备份文件里是**未脱敏的完整对话**（脱敏只作用于写入前的敏感字段替换，不是加密）。别放到公开的同步目录或仓库里。
- `memory_identity erase` 后来删掉的人，其数据在旧备份里仍然存在。备份是时间点快照，删除不会回溯。

## 10. 附录

### 10.1 代码地图（按 region 定位，不按行号）

行号会漂，region 名不会。改代码的第一步永远是 `grep -n "//#region src/engine/xxx.ts" lib/index.js`。

| region | 职责 | 改这里之前先看 |
|---|---|---|
| `src/config.ts` | schemastery 校验 + 默认值唯一来源 | 注意 `toEngineConfig` 是显式白名单，加字段必须两处都加 |
| `src/engine/db.ts` | 建表、迁移、FTS5、WAL 降级、`SCHEMA_VERSION` | 升版本必须同时改 `probe-upgrade` 的期望 |
| `src/engine/text.ts` | 分词、token 估算、相似度、摘抄比对、`FACT_MARKERS`、`slotOf` | 正则带 `$` 锚点会漏掉带原因从句的句子 |
| `src/engine/store.ts` | 全部 SQL | 删除类操作要数表，不是数函数 |
| `src/engine/decay.ts` | 衰减与时效 | 纯函数，改完直接可测 |
| `src/engine/segment.ts` | 切段（时间/话题/情绪 + 微切） | 块粒度调大会让标题重回含糊 |
| `src/engine/consolidate.ts` | 抽取 → 判定 → 落库；`judgeAgainst` | 判定与写入路径必须共用一处 |
| `src/engine/retrieval.ts` | 四路召回、打分、冲突检测、分页 | 通道入口条件要卡死，否则每轮都付代价 |
| `src/engine/render.ts` | 分区渲染与预算 | `appendSection` 的 cap 是绝对位置 |
| `src/index-layer.ts` | 钩子索引三张表、快照、正文取回 | 重建要清掉"素材已消失"的钩子 |
| `src/index.ts` | `apply()`、注入、工具注册、热加载补挂 | 按会话的东西必须能被补挂 |

### 10.2 验证地图

- `npm test` → `test/selftest.mjs`，纯单元，不依赖宿主。

### 10.3 读代码时会遇到的历史编号

注释里有大量 `Q11` / `Q20` / `Q23` / `Q43` / `Q56` / `Q61` / `Q62` / `Q63` / `Q64` / `Q65` / `Q66` 这样的引用。它们是早期设计问答的编号（问题 11、20……），指向"这个参数为什么是这个值"的原始决策记录。**编号本身没有索引了**，但每处引用旁边的注释都写清了理由，按注释读即可。

逐版的施工记录也在那里：[`docs/design.md`](docs/design.md)。它按版本顺序记录了 v0.2.9 到 v0.2.33 每一版修了什么、踩到什么——**读它之前先读本文的 §3**，否则容易把"某一版的补丁"误当成"架构的一部分"。本文的 §1.1、§3 的绝大多数事实都是从那份记录里核对出来的。

### 10.4 这份文档自身的边界

- **它不解释每一个参数为什么恰好是这个数。** 有些是实测调的（`relaxBelow=3`、`relaxMinOverlap=0.25`），有些是拍的（`diaryShare=0.4`），文档没有逐个区分。
- **v0.2.9 之前的演进是推断。** git 仓库始于 v0.2.9，更早的形态靠 changelog 与残留结构反推，凡属推断已在 §1.1 标明。
- **它不含安装与配置教程。** 那些在 §6–§7，随宿主版本变化，这里不重复。
- **它会滞后。** 任何"行号""表数量""工具数量"都是 2026-11-04 的快照。判断是否滞后最快的办法：跑 `memory_doctor`，比首行的 `BUILD_VERSION` 与这份文档的版本号。

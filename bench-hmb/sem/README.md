# 离线语义检索实验（v0.2.31 冻结后，不碰产品代码）

回答一个问题：**把 loom 的检索补一条向量通道，能拿回多少「找不到」的缺口，代价是什么。**
这里只读 loom 自己写下的库，在库外重算一遍检索，不改 `lib/index.js` 一个字。

两轮：第一轮只量了 small 模型能不能补缺口；第二轮量了**模型容量、重排、接入形态**三件事。

## 复跑

```bash
# 1. 从一臂的库里导出单元与题目（纯 stdlib，无需额外依赖）
python bench-hmb/export-sem-units.py --arm loom-epB

# 2. 首次拉模型，走 hf-mirror（huggingface.co 直连超时）
node bench-hmb/sem/fetch-model.mjs                                          # small  24MB
node bench-hmb/sem/fetch-model.mjs --repo Xenova/bge-base-zh-v1.5          # base  103MB
node bench-hmb/sem/fetch-model.mjs --repo Xenova/bge-large-zh-v1.5         # large 328MB
node bench-hmb/sem/fetch-model.mjs --repo Xenova/bge-reranker-base         # 重排  279MB

# 3. 向量检索（--k 取 top-k 写盘，之后可在产物里截断算更小的 k）
node bench-hmb/sem/eval-vector.mjs --k 20 --tag base20  --model Xenova/bge-base-zh-v1.5
node bench-hmb/sem/eval-vector.mjs --k 20 --tag large20 --model Xenova/bge-large-zh-v1.5
node bench-hmb/sem/eval-vector.mjs --k 20 --tag baseins --model Xenova/bge-base-zh-v1.5 --prefix "为这个句子生成表示以用于检索相关文章："

# 4. 重排（embedder 召回 top-N，cross-encoder 重排）
node bench-hmb/sem/eval-rerank.mjs --n 20 --k 6 --tag small
node bench-hmb/sem/eval-rerank.mjs --n 10 --k 6 --model Xenova/bge-base-zh-v1.5 --tag base

# 5. 延迟与体积
node bench-hmb/sem/timing.mjs --model Xenova/bge-large-zh-v1.5
```

依赖：`npm i --no-save @huggingface/transformers`（含 onnxruntime-node，约 45 个包）。
模型全部是 q8 量化 ONNX，下在 `bench-hmb/sem/models/`（已 gitignore，718MB）。

## 单元口径

与 loom 索引时用的是同一段文本，不是另起一套：

- 事实：`text + aliases`（404 条）
- 事件：`title：summary + aliases`（270 条）
- 每条单元按 `source_ids` / `l0_from` 挂回它的 cid，判分与 `eval-compare.py` 同口径

问句用 `keys.json` 里的 `question` 原文，也就是 `raw` 臂用的那个。

## 读数（561 道可答题，题面整句问法）

### 模型容量

| 模型 | 体积 | 查询延迟 | k=1 | **k=3** | k=6 | k=10 | k=20 |
|---|---|---|---|---|---|---|---|
| bge-small-zh | 24MB | 6.3ms | 23.0% | **41.0%** | 49.9% | 57.8% | 66.7% |
| bge-base-zh | 103MB | 50.5ms | 34.4% | **49.0%** | 55.4% | 63.3% | 77.5% |
| bge-large-zh | 328MB | 78.0ms | 39.6% | **52.4%** | 59.2% | 66.7% | 79.9% |
| bge-base-zh + 检索指令 | 103MB | 50.5ms | 34.8% | **49.4%** | 57.8% | 63.6% | 77.9% |
| 词法 raw（现状） | — | — | — | **20.5%** | — | — | — |
| 词法 kw（对照） | — | — | — | **38.7%** | — | — | — |

「检索指令」＝ query 侧加 bge 官方中文前缀「为这个句子生成表示以用于检索相关文章：」，passage 侧不加。

参考：loom 真路径的 retrieve 是 **273.5ms/题**（642 题 175.6s，含桥接 IPC）。base 的 50.5ms 是它的 18%。

边际收益：small→base 是 **+8.0**（k=3），base→large 只有 **+3.4**。体积从 24MB 涨 4 倍换来 8 个点，再涨 3 倍只换 3.4 个点。**base 是拐点。**

### 重排

| 方案 | 候选 | k=1 | **k=3** | k=6 | 每题延迟 |
|---|---|---|---|---|---|
| small 向量 | — | 23.0% | **41.0%** | 49.9% | 6ms |
| small + rerank | 20 | 40.5% | **50.3%** | 56.9% | 1,926ms |
| base 向量 | — | 34.4% | **49.0%** | 55.4% | 50ms |
| base + rerank | 10 | 42.8% | **52.2%** | 58.3% | 1,104ms |

**同一条 k=3 的线上，base 无重排 49.0% / 50ms，rerank 52.2% / 1,104ms——多 3.2 个点，慢 22 倍。**
large 无重排是 52.4% / 78ms，比 base+rerank 还高 0.2 个点，快 14 倍。

重排只在**预算只有 1 条**时才划算（34.4% → 42.8%，+8.4；k=20 时收益归零，因为只是在同一批候选里换序）。

### 接入形态（base，k=3）

| 触发条件 | 命中 | 覆盖率 | 题均字数 | 触发题数 |
|---|---|---|---|---|
| 现状：只有词法 | 115 | 20.5% | 1,001 | — |
| 兜底：词法为空才查向量 | 208 | 37.1% | 1,429 | 207 |
| 无条件并行：每次都查，取并集 | 302 | **53.8%** | 2,161 | 561 |
| 无条件并行（large） | 314 | **56.0%** | 2,130 | 561 |

**兜底只拿得到一半的收益。** 增量 187 道题里，93 道来自「词法一条都没返回」的 207 道题，另外 94 道来自「词法返回了但材料不对」的 239 道题——后者兜底条件根本不触发。

## 四条结论

**1. 缺口在召回，不在排序，但「召回」得真的每次都跑。** 兜底式触发（词法为空才查向量）只覆盖 207 道，收益减半；只有无条件并行才拿得到 53.8%。代价是题均材料从 1,001 字涨到 2,161 字——真机记忆块约 2,000 token（≈3,000 字），k=3 装得下，k=6（3,319 字）就挤了。

**2. 扩模型比加重排划算一个数量级。** 3.2 个点 vs 22 倍延迟。重排的适用区间很窄：预算只够 1 条时（+8.4 点）。一旦预算有 3 条以上，向量的 top-k 已经把正确答案带进候选，cross-encoder 只能在里面换序。

**3. 向量不是延迟负担，重排才是。** loom 现在真路径的 retrieve 是 **273.5ms/题**（642 题 175.6s，含桥接 IPC），base 向量只要 50.5ms——**+18%**。而 rerank 是 1,054ms，**+385%**。把延迟当反对向量通道的理由站不住，它只反对重排。

**4. 变更题不是检索能解的，证据 100% 在库里但拿不出来。** 38 道变更题的 409 个 need cid **全部**存在于 loom 的单元里，是「没检索到」而不是「没记录」。但同一槽位的六十个版本文字几乎同构，embedding 把它们压成一团：large 的 top-20 也只中 7 道，和词法 kw 的 7 道持平。按主体名把它所有版本全取（13,602 字/题）也只有 7/38。要解它得按「主体＋属性」做结构化槽位，不是相似度问题。

**5. 相似度阈值切不开这批语料。** 扫 0.40–0.70：0.55 以下全部顶到候选上限（8 条），0.65 时覆盖率掉到 44.9%。同一槽位的版本相似度分布太密，用阈值做自适应截断没有空间，固定 k 更可控。

**6. bge 的检索指令前缀几乎免费，收益也几乎为零。** query 侧加「为这个句子生成表示以用于检索相关文章：」后，k=3 从 49.0% → 49.4%（+2 题），k=6 从 55.4% → 57.8%（+13 题）。加着不亏，但别指望它。产物 `vector_baseins.json`。


## 三个必须写下来的局限

**语料是模板句。** 整个 chain 轨的语料是「X 的 Y 首次确立为 Z」这类同构句，语义检索在这种文本上占便宜（结构全同，只差槽位名）。上面的百分数应读作上限，不能直接外推到真实对话。

**样本是单库。** 674 条单元、270 段落，暴力余弦 1ms 内跑完。真实用户记忆量级更大，但按这个增长速度，几千条仍在暴力枚举范围内，不需要向量扩展。

**重排延迟是 CPU 单线程实测。** 1926ms/题（20 对 × 96ms）与 1104ms/题（10 对 × 96ms）都在本机 M 系列之外的普通环境下测得，换机器会变，但量级差（vs 向量的 6–78ms）不会消失。

## 这个实验没回答的

- 接入后 `recall()` 的 `minScore` / `layerPenalty` / `maxItems` 会怎样重新切分候选（本实验是纯 top-k，没走打分链）
- 写时同步：embedding 是异步的，而现有三张 FTS 靠 SQL trigger 同步，换成向量要重新设计这个不变式
- 真实对话语料上的表现（模板句占便宜，真实语料可能低不少）
- 长链变更题（链长 27/42/57）需要的是结构化槽位，不是本文讨论的任何一条通道
